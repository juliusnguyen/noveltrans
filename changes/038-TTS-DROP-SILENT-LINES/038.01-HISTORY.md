# 038 — TTS: punctuation-only lines become silence — history

## [PLAN] 038.01-INITIAL-PLAN — 2026-07-29

Generated plan: `038.01-INITIAL-PLAN.md`.

Diagnosis of the reported `“…”` noise — the line reached the engine because every step
was individually correct:

1. `clean_for_tts` keeps `…` and quotes deliberately (they carry prosody *inside* a
   sentence), so the line passed through untouched.
2. `split_sentences` made it its own chunk — it is its own paragraph. 3 characters.
3. `merge_short_chunks` (028, `min_chunk_chars = 30`) glued that chunk onto the
   neighbouring sentence, since 3 is far below the floor.
4. The engine was handed `“Tên bây giờ khó nghe quá.” “…”` and pronounced the ellipsis.

## [IMPLEMENTATION] — 2026-07-29

938 tests pass (927 before, +11), ruff clean.

### `tts/clean.py`

`_has_speech(line)` — true if a line contains a letter or a digit. In `clean_for_tts`,
after `extra_remove` and before the whitespace tidy, lines without speech are blanked while
keeping their newlines, so the existing `_BLANK_RUN_RE` collapse turns the hole into an
ordinary paragraph break.

Three things that placement buys:

- **Whole lines only**, so an ellipsis *inside* a sentence is structurally untouchable —
  `Anh ta ngập ngừng… rồi im lặng.` still reads as written. Breaking that would have been
  a worse bug than the one being fixed.
- **After `extra_remove`**, which can itself empty a line (stripping `()` turns a `(…)`
  line into punctuation-only).
- **In `clean_for_tts`**, the one place both consumers already go through — the render
  (`base.py:129`) and the Audio tab's preview (`tab_audio.py:442`) — so the preview never
  shows text different from what gets spoken.

Digits count as speech, so a bare chapter-number line is still read.

### Verified against the reported text

The ellipsis no longer reaches the engine, and `clean_for_tts("Anh ta ngập ngừng… rồi im
lặng.")` is unchanged.

### Honest limitation — the beat's pause

The plan claimed the dropped beat always survives as paragraph silence. Measured, that is
only true when the neighbouring paragraphs clear 028's 30-char merge floor:

| case | chunks | gaps |
| --- | --- | --- |
| reported excerpt (27-char dialogue line) | 1 | **0** |
| same shape, realistic paragraph lengths | 2 | 1 |

In the short case the two paragraphs now merge into one chunk, so the beat becomes a word
gap rather than a pause — and, being precise, that *is* one pause fewer than before, since
the old chunking split after the ellipsis. Net it is still an improvement (a pause preceded
by a noise → no noise), and the cause is 028's paragraph-blind merge rule, which this
change's prompt puts out of scope. Worth a follow-up if the lost beat is audible in
practice: the fix would be teaching `merge_short_chunks` not to merge across a paragraph
boundary, which is a change to 028's own trade-off and deserves its own measurement.

### Known trade-off

A line of pure emphasis punctuation the author meant as sound (`“!!!”` as a shout) is now
silence. It was previously an engine noise, so this is still better, and text alone cannot
distinguish the two.
