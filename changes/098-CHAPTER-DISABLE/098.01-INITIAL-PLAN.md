# Implementation Plan: Feature 098 — Disable/Enable Chapters

## Design decisions (locked in before this plan was written)

1. **One shared per-chapter boolean flag** (`enabled`, default `True`), not three
   independent per-tab settings — a chapter disabled in any of the three tabs (Tải
   truyện, Dịch, Nghe audio) is disabled everywhere, since it's stored on the one
   `chapters` row all three tabs read.
2. **UI mechanism: a checkbox column**, appended as the LAST column in each of the
   three chapter tables (`ChapterTableModel` for Tải truyện + Dịch,
   `AudioChapterTableModel` for Nghe audio) — same architectural slot as the existing
   `RETRANSLATE_COLUMN`/`REGENERATE_COLUMN` per-row button columns, so it doesn't shift
   any existing hard-coded column index. One click toggles a single chapter. Disabled
   rows also get a dimmed visual treatment so a disabled chapter reads as such at a
   glance, not just via the checkbox.
3. **Skip is unconditional**: a disabled chapter is skipped by every pipeline
   (download, translate, audio, video), including when explicitly targeted (right-click
   "dịch lại riêng chương này", force re-download/re-QC in a range, etc.) — not just the
   "process all pending" bulk paths. To act on a disabled chapter, the user must
   re-enable it first.
4. Re-enabling a chapter makes it eligible again everywhere, subject to the normal
   resume rules that already exist (e.g. an already-translated chapter isn't
   re-translated unless forced).
5. A TOC re-scan (`replace_toc`) must NOT reset/clobber `enabled` on existing chapters.

## 4. Video batching rewrite (the crux)

### 4a. Core semantic decision

Two categories of "no usable audio right now" must stay distinct:
1. **Enabled but not yet voiced** — today this leaves a gap *inside* a fixed `[lo,
   hi]` number window without pulling chapters forward. This existing "partial batch,
   fills in later" behavior must be preserved exactly.
2. **Disabled** — must be treated as if the chapter's number doesn't exist on the grid
   at all, so the window reaches past it to still collect `batch` enabled chapters.

So a fresh (non-frozen) batch's `[lo, hi]` must come from the chapter's **position
among all ENABLED chapters** (regardless of whether they have audio yet), not from raw
chapter-number multiples of `batch`. Availability (has audio, right voice) still only
creates gaps *within* that span, exactly as today.

Concretely: `enabled = sorted(c for c in chapters if c.enabled, key=index)`. Batch `k`
(0-based) = `enabled[k*size : (k+1)*size]`; its `[lo, hi]` = that slice's first/last
`index+1`.

**Worked example (chapter 9 disabled, batch=10)**: `enabled` = chapters 1-8, 10, 11,
12, … Batch 0 = `enabled[0:10]` = {1..8, 10, 11} → `lo=1, hi=11`. Matches the request
exactly: "chương 1 đến chương 8, và chương 10 đến chương 11".

### 4c. `src/noveltrans/tts/video.py` — `plan_locked_video_windows` (lines 725-764)

**Design principle (stated explicitly, not left open): a frozen span (from
`discover_committed_video_windows` or `read_manual_windows`) freezes its own
membership by CHAPTER NUMBER, exactly as today, and is never recomputed, resized, or
filtered by `enabled` — it represents a fact about the past (a real render on disk, or
an explicit user split/merge decision) that a later enable/disable toggle must not be
able to alter. Only the NOT-yet-frozen portions of the sequence are computed fresh from
the current enabled set.**

Consequence: fresh-window accumulation consumes ENABLED chapters in order, skipping any
chapter number already claimed by a frozen span (regardless of that chapter's own
enabled state), and flushes whatever partial fresh window was accumulating the moment a
frozen span is reached (a frozen span always starts its own part).

```python
def plan_locked_video_windows(
    chapters: list, voice: str, batch: int, committed: dict[int, int]
) -> list[tuple[int, MergeWindow]]:
    enabled = sorted((c for c in chapters if c.enabled), key=lambda c: c.index)
    if not enabled:
        return []
    size = int(batch or 0)
    if size < 1:
        raise ValueError("batch size must be >= 1")
    avail_by_number = {
        c.index + 1: c for c in chapters
        if c.enabled and c.audio_path and c.audio_voice == voice
    }
    frozen = sorted(committed.items())  # [(first_num, last_num), ...] non-overlapping

    result: list[tuple[int, MergeWindow]] = []
    part_num = 0
    pending: list = []
    frozen_idx = 0
    claimed_through = 0

    def flush(pending_list):
        nonlocal part_num
        if not pending_list:
            return
        part_num += 1
        sel = [c for c in pending_list if (c.index + 1) in avail_by_number]
        if sel:
            result.append((part_num, MergeWindow(sel[0].index + 1, sel[-1].index + 1, sel)))

    def emit_frozen(lo, hi):
        nonlocal part_num
        part_num += 1
        sel = [avail_by_number[n] for n in range(lo, hi + 1) if n in avail_by_number]
        if sel:
            result.append((part_num, MergeWindow(lo, hi, sel)))

    for chapter in enabled:
        num = chapter.index + 1
        if num <= claimed_through:
            continue
        while frozen_idx < len(frozen) and frozen[frozen_idx][0] <= num:
            lo, hi = frozen[frozen_idx]
            frozen_idx += 1
            if hi < claimed_through:
                continue
            flush(pending)
            pending = []
            emit_frozen(lo, hi)
            claimed_through = hi
        if num <= claimed_through:
            continue
        pending.append(chapter)
        if len(pending) == size:
            flush(pending)
            pending = []

    flush(pending)
    return result
```

Notes:
- The `while` condition uses `<=`, not `==`, so a frozen span whose *own start
  chapter* is itself disabled (never appears in `enabled`) still triggers correctly on
  the first enabled chapter whose number reaches or passes it.
- A fresh window's `first_num`/`last_num` are the actual selected chapters' span
  (matching today's `window()` helper convention in merge.py) — e.g. still
  `0001-0011` for the worked example, not `0001-0010`.
- `part_num` increments unconditionally on every fresh-window flush AND every frozen
  emission, exactly like today's `part_num += 1` — callers (`tab_video.py`'s
  `_locked_part_numbers`, `workers.py`'s `locked_part_numbers`) need **no change**,
  since they already just key off the returned `(part_num, window)` tuples.
- **Known, accepted limitation**: if a chapter *inside* an already-rendered frozen
  span is disabled after the fact, that span's audio still physically exists in the
  already-published video (nothing can undo that) — a hypothetical re-render of that
  OLD span would now silently omit it. This is out of scope: disabling a chapter that's
  part of an already-uploaded video cannot retroactively edit that video.
- `discover_committed_video_windows` and `video_windows.read_manual_windows`/
  `split_window`/`merge_windows` need **no changes** — they only ever produce/consume
  `{first_num: last_num}` maps; this feature only changes how the fresh portions
  between/after them are computed. Verify `merge_windows`'s adjacency check and
  `split_window`'s non-empty-halves check still hold (they do — both are keyed purely
  by number and never look at `enabled`).
