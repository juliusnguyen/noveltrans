## [IMPLEMENT] 058.01-INITIAL-PLAN — 2026-08-23
Implemented per plan, with two deviations discovered during implementation:

- **New `src/noveltrans/video_state.py`**: `<stem>.created.json` sidecar, mirroring
  `youtube_upload.py`'s atomic-write style. `created_override()`/`set_created_override()`/
  `effective_created()`. An override only persists when it disagrees with disk; toggling
  back into agreement clears it. Tested in `tests/test_video_state.py` (18 tests).

- **`tab_video.py` — column 4 ("Trạng thái") is now checkable**: new `_created_item`
  builder replaces the plain-text cell; new `_on_created_toggled` handler confirms via
  dialog (Vietnamese, matching the upload column's tone) for any tick that disagrees with
  disk, and silently clears the override with no dialog when reverting to agreement.
  `_build_row_actions`'s "Tạo"/"Tạo lại" button gets a tooltip when a manual override is
  active, and still gates on the *real* file, not the override (rendering/uploading must
  operate on the actual `.mp4`).

- **Deviation 1 — single dispatching `itemChanged` slot, not two independent ones.**
  The plan called for a second, independent `itemChanged.connect(self._on_created_toggled)`
  alongside the existing upload-column connection. That crashed intermittently (Windows
  access violation): when one slot's handler calls `_refresh_video_list()` (which rebuilds
  the table and deletes every `QTableWidgetItem`), Qt still invokes the second connected
  slot with the now-dangling `item` argument — a use-after-free. Fixed by renaming the
  suppress-flag to `_suppress_status_toggle` (shared) and adding a single
  `_on_status_toggled(item)` dispatcher, connected once, that branches on `item.column()`
  and calls `_on_created_toggled`/`_on_upload_toggled` directly (not as separate slots).

- **Deviation 2 — stale-override clearing is event-driven, not passive.** The plan assumed
  a stale `created=False` override (from unticking a rendered part) would "self-clear the
  next time `_created_item` recomputes." That's wrong: it would also wipe the override on
  any innocent `_refresh_video_list()` call (e.g. switching batch size), defeating the
  point of a sticky manual override. Instead, `_on_video_file_done` (fired once per part
  the render worker actually finishes) now explicitly clears any override for that exact
  path via `set_created_override(path, True, file_exists=True)` — only a genuine new
  render clears a stale override, not a passive table refresh.

- Added `TestCreatedStatusToggle` to `tests/test_tab_video.py` (9 tests): checkable column,
  tick/untick with confirmation, decline reverts the tick, toggling into agreement clears
  silently (no dialog) and survives an unrelated refresh, a real render (via
  `_on_video_file_done`) clears a stale override, a `created=True` override survives a
  refresh while the file is still missing, and the rebuild-suppression guard still holds.

- `tests/test_tab_video.py` + `tests/test_video_state.py`: 181 tests, run 4× — all pass
  consistently. Full-suite `pytest -q` intermittently hits a Windows access-violation crash
  in unrelated GUI tests (e.g. `test_regen_all_thumbnails_covers_every_part`); confirmed via
  a stashed baseline run that this crash reproduces identically on the pre-existing,
  unmodified code — it is pre-existing flakiness in the offscreen-Qt test harness, not
  something introduced by this feature.

## [IMPLEMENT] locked batch windows — 2026-08-23
User question surfaced a real gotcha: with batch=10, if part 10 gets rendered early with
only 8/10 chapters (translation hadn't caught up), the old grid-based `plan_merge_windows`
would silently *grow* part 10 to (chương 91-100) once 2 more chapters arrived — a
different filename (`-0091-0098.mp4` → `-0091-0100.mp4`) than what was already uploaded,
orphaning the old file and offering to re-render+re-upload "part 10" as if new. User chose
(via AskUserQuestion): (1) fix scoped to the Video tab only, not the Audio tab's "Ghép
audio" batching (both use the same shared `merge.plan_merge_windows`/`part_number`, left
untouched); (2) "Tạo lại tất cả video" (redo-all) should ignore any lock and always use the
current full grid, since it's an explicit full rebuild.

- **New `noveltrans.tts.video.discover_committed_video_windows(video_dir, slug)`**: scans
  `video_dir` for per-part-subfolders matching `{slug}-{first:04d}-{last:04d}` whose `.mp4`
  is `effective_created()` (rendered OR manually ticked "đã tạo") — returns
  `{first_num: last_num}`. Only the modern per-folder layout is scanned; legacy flat
  renders predate this feature and aren't reconsidered as commit points.
- **New `noveltrans.tts.video.plan_locked_video_windows(chapters, voice, batch, committed)`**:
  like `merge.plan_merge_windows(..., mode="batch")` but a window whose start chapter is a
  key in `committed` is frozen to that already-committed span instead of pulling in more
  chapters — new chapters start the *next* part instead. Identical output to the plain grid
  when `committed={}`. Part numbers are the window's 1-based position in the *entire*
  novel's sequence (computed from chapter 1, regardless of what the caller wants rendered)
  rather than `(first-1)//batch+1`, since that formula assumes a fixed grid this function
  deliberately deviates from once a window is locked — a gap window (zero chapters
  currently available) still consumes a part number, preserving `merge.part_number`'s
  existing "a hole doesn't renumber everything after it" guarantee.
- **`tab_video.py`**: `_windows_for_current_selection()` now routes batch mode through new
  `_locked_batch_windows()`, which calls the two functions above and caches the part-number
  map (`_locked_part_numbers`) and raw commit map (`_locked_committed`) on `self` so
  `_part_number()` and the new `_chapter_range_item()` don't each re-scan the video
  directory. `_start_video()` now calls `_windows_for_current_selection()` directly instead
  of its own `plan_merge_windows` call, so the render matches exactly what the table/dialog
  promised. New `_chapter_range_item()` (column 1, "Chương") flags a locked-and-short window
  with "⚠️" + amber text + a tooltip ("đã tạo với N/M chương — bị khoá... chương mới sẽ vào
  phần kế tiếp") — only when it's both in `_locked_committed` and short, so a normal
  not-yet-committed tail window (still waiting for more chapters) isn't flagged.
- **Discovered and fixed a related pre-existing bug**: the per-row "Tạo"/"Tạo lại" button
  (`_render_one`) launches the worker with `mode="range"` and no `batch`, so
  `merge.part_number(first_num, None)` always fell back to `1` — re-rendering any single
  part (batch mode or not) wrote `.title.txt`/thumbnail text as "Phần 1" regardless of
  which row was actually clicked. Fixed by threading an explicit `part_num` through
  `_render_one` → `_launch_video` → `VideoWorker(part_num=...)`; the worker now prefers
  `self.part_num` when set, else the locked-plan's number (batch + skip_existing), else
  the old grid arithmetic (redo-all / true custom ranges) — this is also what makes a
  *locked* window's single-row re-render keep its correct (non-grid) number.
- **`workers.py` (`VideoWorker.run()`)**: for `mode == "batch" and skip_existing` (i.e.
  "Tạo video", never "Tạo lại tất cả") computes windows via the locked plan instead of the
  plain grid, matching the tab exactly; any other run (redo-all, single-part range render)
  uses the unchanged plain grid.
- Tests: `tests/test_video.py` — `TestPlanLockedVideoWindows` (5), `TestDiscoverCommittedVideoWindows`
  (5), plus 2 new `TestVideoWorker` end-to-end cases (locked commit skipped + new part
  titled correctly; redo-all ignores the lock and uses the fresh grid).
  `tests/test_tab_video.py` — new `TestLockedBatchWindows` (3: uncommitted tail not
  flagged, committed short part flagged, new chapters get their own part not absorbed),
  1 new case in `TestRedoAllVideos`, and `test_render_one_uses_range_mode_for_that_part`
  updated for the new `part_num` argument.
- Full related-suite (`test_tab_video.py` + `test_video.py` + `test_video_state.py`, 294
  tests) run 3× — all pass consistently. `tests/test_tab_audio_multiselect.py` +
  `test_merge.py` + `test_tab_audio_preview.py` (44 tests) re-run to confirm the shared
  `merge.py` functions and the Audio tab are untouched, per the scope decision.

## [IMPLEMENT] manual split/merge — 2026-08-23
User request: a part over YouTube's 12h cap needs to be splittable into two (choosing how
many trailing chapters move to the new part); two arbitrary — clarified via
AskUserQuestion to *adjacent* — parts need to be mergeable back into one. Confirmed
decisions: (1) the new boundary persists long-term, like the "đã tạo" lock; (2) allowed on
already-rendered/uploaded parts, with a stronger warning if uploaded; (3) merge limited to
adjacent parts only (chapters must stay in reading order); (4) the split UI asks for a
chapter *count* to cut off the tail, not a chapter picker.

- **New `noveltrans/video_windows.py`**: `video_manual_windows.json` at the *project root*
  (not per-part — a boundary is a property of the whole plan) holding `{first_num:
  last_num}`. `split_window()` turns one span into two (validates the tail count leaves
  both halves non-empty); `merge_windows()` turns two adjacent spans into one (validates
  adjacency — a non-adjacent "merge" would leave a chapter gap in the middle, silently
  skipping content). Merging a split's own two halves is how a split gets undone; no
  separate "clear" function exists. Tested in `tests/test_video_windows.py` (21 tests).
- **`tab_video.py` / `workers.py`**: `_locked_batch_windows()` (tab) and `VideoWorker.run()`
  now merge `{**committed, **manual}` before calling `plan_locked_video_windows` — manual
  entries win over an auto-discovered "đã tạo" commit at the same starting chapter, since
  the user's explicit choice is more authoritative than whatever's on disk.
- **Judgment call beyond the literal decisions above**: manual boundaries apply even during
  "Tạo lại tất cả video" (skip_existing=False), unlike the auto-discovered "đã tạo" commits
  redo-all was already told to ignore. Reasoning: redo-all exists to re-render with new
  visual settings, not to reset the chaptering plan — silently re-merging a 12h-cap split
  on redo-all would reintroduce the exact YouTube policy violation the split was for. Only
  `discover_committed_video_windows` is skipped for `skip_existing=False`; `manual` is
  always read and applied in batch mode. Flagged here in case this default is wrong —
  tested explicitly in `test_video.py::TestVideoWorker::test_redo_all_still_honors_a_manual_split_boundary`.
- **UI**: `video_list`'s selection mode changed from `NoSelection` to row-based
  `ExtendedSelection` (previously no row could be selected at all) + a custom context menu
  (`_on_video_list_context_menu`). Right-clicking an unselected row selects just that row
  first (standard behavior); 1 selected row offers "Tách phần…" (disabled if the part has
  only 1 chapter), 2 selected rows offer "Gộp 2 phần liền kề" (disabled unless the two are
  actually adjacent — chapter gaps aren't merge-able). Both gated to batch mode only (no
  fixed grid exists in range/whole-novel mode).
  - `_split_part`: `QInputDialog.getInt` asks how many trailing chapters to cut off
    (default `min(5, total-1)`), then one confirmation (`_confirm_restructure`) covering
    both the "old file gets deleted" case and (louder) the "already on YouTube — won't
    auto-update" case, then calls `video_windows.split_window` and deletes the old
    rendered folder.
  - `_merge_parts`: same confirmation shape, then `video_windows.merge_windows` and
    deletes both old rendered folders.
  - `_delete_rendered_part`: removes the whole per-part subfolder (video + every sidecar
    live there together, feature 026) — not a per-extension enumeration. A legacy flat
    render (no dedicated folder) only has its `.mp4` removed, matching how legacy layouts
    are already treated as read-only elsewhere.
- Tests: `tests/test_tab_video.py` — new `TestSplitMergeParts` (10): context-menu selection
  and action-enablement (via a fake `QMenu`/`QAction` double, since building/inspecting a
  real Qt menu headlessly isn't practical), split producing the right manual-window entries
  and table windows, decline/cancel are no-ops, old-file deletion + its warning text,
  upload-warning text, merge producing the right entry, and merge-undoes-split.
- Full related-suite (`test_tab_video.py` + `test_video.py` + `test_video_state.py` +
  `test_video_windows.py` + `test_settings_dialog.py`, 367 tests) run 3× — all pass
  consistently.

## [IMPLEMENT] multi-select "Tạo video" — 2026-08-23

of selected (possibly non-contiguous) rows can be rendered without waiting on everything
