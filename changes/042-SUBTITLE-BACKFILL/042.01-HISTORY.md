### The measurement that justified the approach

Before writing any of it: synthesised a chapter through the real `synthesize_chapter`,
**threw the cues away**, then recovered them from the audio alone.

```
true   0.000-  6.000 | got   0.000-  6.000 | err 0.0/0.0 ms
true   6.400- 10.900 | got   6.400- 10.900 | err 0.0/0.0 ms
true  11.300- 15.920 | got  11.300- 15.920 | err 0.0/0.0 ms
true  16.320- 20.700 | got  16.320- 20.700 | err 0.0/0.0 ms
worst boundary error: 0.0 ms      text identical: True
```

Exact, because the gaps are `np.zeros` — true digital silence of known length — not a
statistical property of speech. The test audio deliberately contained a quiet moment
*inside* a chunk, which the detector correctly ignored.

This is why the proportional-estimate idea floated earlier was dropped rather than built:
it would have drifted tens of seconds mid-chapter, and I had described it as merely
"approximate" when it was much worse than that.

### `tts/subtitles.py`

`detect_silences` (one audio-only ffmpeg pass), `expected_gap`, `chunks_for_text`,
`backfill_cues`.

`backfill_cues` returns `None` — never a best guess — unless the detected gap count is
exactly `len(chunks) - 1`. That equality is the whole safety argument: it says the silence
pattern in the file matches the text we believe produced it. Settings changed since
voicing, a chapter edited afterwards, or an unusually long pause inside a sentence all
break it, and skipping one chapter beats subtitles that are confidently wrong.

**The detail that would have broken it for this user specifically:** the detection
threshold comes from `gap / speed`. `apply_tempo` rescales silence along with speech, so
their 0.4 s gap at `tts_speed = 1.15` is 0.348 s on disk. A hardcoded 0.4 would have found
nothing in their entire library.

### `gui/workers.py` — `SubtitleWorker`

Plans the same windows as `VideoWorker`, backfills each chapter lacking cues, then writes
each part's `.srt` through `_with_real_durations` exactly as the render does — so a sidecar
written by this button and one written by a render are the same file at the same path.
Never overwrites cues captured during real synthesis: real timings beat recovered ones.

### `gui/tab_video.py`

"Tạo phụ đề (.srt)" beside "Mở thư mục video". Reports parts written, chapters recovered,
and — named rather than hidden — parts skipped because their gaps didn't match.

### The vacuous-fixture trap, third time

Three of the refusal tests used 29-character paragraphs. `merge_short_chunks` has a 30-char
floor, so they fused into a **single** chunk and the count assertions asserted nothing.
Fixed, with `test_the_fixture_really_makes_two_chunks` guarding the class.

That is the third time this session a fixture made tests pass for the wrong reason (039's
playlist fake, 040's cue fixture, now this). The tell is identical every time: **an
assertion that cannot fail given the fixture.** Worth checking for deliberately rather than
noticing by luck.

### Verified end to end

Legacy audio with no cue files → backfill → `.srt` with correct cross-chapter offsets
(chapter 2 starting at 10.360 s, chapter 1's exact duration).

### Known limits

- A genuine near-silent pause of gap length inside a sentence produces an extra detection
  and a refusal. Fails safe: skipped and reported, never mistimed.
- Very quiet speech could fall under the −50 dB threshold. Same failure mode.
- Recovery depends on the cleaning/chunking settings being unchanged since the audio was
  made — a change breaks the count equality, so it refuses rather than mistimes.
