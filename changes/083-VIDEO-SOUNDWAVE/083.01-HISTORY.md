## [BUG] Frozen bars on long videos — reproduced, root-caused, fixed — 2026-09-08
**Reproduced with real renders**, not reasoned about: a 4-hour chirp (frequency sweeping
with time, so a frozen frame is unmistakable) through the real filtergraph, then the bars'
rectangle sampled every 2 minutes of output and hashed.

| run | audio input | bars |
| --- | --- | --- |
| out4h | shared (as shipped) | frozen from ~41 min |
| r1 | shared (repeat) | frozen from ~47 min |
| r2 | separate input | alive to 4:00:00 |
| r3 | separate input (repeat) | alive to 4:00:00 |

The freeze point MOVED between the two shared-input runs, which is what identified it as a
race rather than an overflow: 20-minute and `-t 2600` renders never showed it, so an
earlier short-render check would have called the bug fixed.

**Cause.** One audio input fed both `-map 1:a -c:a copy` and `[1:a]showfreqs`. The copy
side drains packets as fast as the disk allows (ffmpeg's own progress showed the audio
muxed 1h32m ahead of a video that was at 57 min), and past ~40 minutes the visualiser
branch stopped receiving frames. `overlay` defaults to `eof_action=repeat`, so it repeated
its last bars frame for the remaining hours — bars alive at the start, frozen from the
middle on, audio and playhead unaffected. ffmpeg logged no warning at any level.

**Fix.** `render_video` opens `audio.m4a` TWICE: input 1 is copied to the output, new input
4 exists only to drive `showfreqs` (`_filtergraph` gained `viz_audio`). Two demuxers, so
the bars read the file at their own pace and cannot be starved by the copy side. Cost is
one extra AAC decode of a local file.

## [MEASURED] What turning the bars off actually saves — 2026-09-08
Asked before building the option. Real `render_video` runs, 3 minutes of audio, libx264
`veryfast`, Apple Silicon:

| preset | bars | no bars | saved |
| --- | --- | --- | --- |
| high 1080p25 spinning | 22.5 s | 20.1 s | ~10% |
| high_static 1080p25 | 20.0 s | 18.1 s | ~10% |
| fast 720p25 | 12.6 s | 11.1 s | ~12% |
| fastest 720p15 static | 8.7 s | 6.7 s | ~23% |

CPU time drops only ~5% (108 s → 103 s at 1080p) because x264 dominates; filters alone go
16.6 s → 13.5 s, i.e. `showfreqs` is ~19% of the FILTER work but ~5% of the total. On a GPU
encoder the filters become the bottleneck, so the saving there is nearer the filter share.
File size is where it really shows: 16.4 MB → 12.2 MB at 1080p (−26%), 4.5 → 2.7 MB at
`fastest` (−40%). Reported honestly that the quality preset is the far bigger lever
(1080p spinning 22.5 s vs 720p15 static 8.7 s = 2.6×) before adding the option.

## [FEATURE] "Cột sóng nhạc" checkbox — 2026-09-08
Independent of the quality preset (a preset picks resolution/fps/spin; this is a separate
axis), on by default because it is the look every published video has.
- `_filtergraph(show_bars=False)` drops the `showfreqs` branch and its overlay; the vinyl
  base feeds the playhead directly. `render_video` then does not open the audio a second
  time either — nothing would consume it.
- `AppConfig.video_show_bars` + `video_settings.WORKFLOW_KEYS` (per novel, seeded from the
  user's last-used value) + the tab checkbox + `VideoWorker`/`VideoPreviewWorker`, i.e. the
  exact path `burn_subtitles` already takes. The preview honours it too.
- `render_speed(preset, show_bars)` adjusts the three confirm-dialog time estimates by a
  deliberately conservative +12% (the smallest measured gain).

## [BUG] Long chapter titles ran over the bars — 2026-09-08
Two causes, both fixed; verified by rendering real preview frames at 1080p (short / long /
absurd titles × bars on / off) rather than by reading coordinates.

**No room.** The chapter title had ~7% of the frame height between it and the bars —
barely one line at its layout size — while a dead strip sat between the bars and the
progress track. `PlayerLayout` now starts the title block higher (novel 43.5% → 38.2%,
chapter 48.6% → 43.7%) and drops the bars to just above the track (55.5% → 59.3%, height
11.1% → 10.5%). The chapter band is ~16% of the height with the bars on, ~26% without.

**Nothing enforced the band.** New `fit_title` measures the real bundled TTF (`font_file_for`
maps the family libass resolves by to the file Pillow measures with) and lays the title out
to fit: greedy wrap — the same `_wrap_title` the cover art uses — at the column width with
explicit `\N` breaks so libass cannot re-wrap it downward, shrunk in 6% steps to a floor of
62% of the layout size, and ellipsised ONLY if even the floor overflows. `build_ass_subtitles`
gained `font_file` + `show_bars`; the novel title is held to one line because it sits
directly above the chapter title. Without `font_file` (the pure-builder tests) output is
unchanged, and a title that already fits is emitted byte-for-byte as before.
