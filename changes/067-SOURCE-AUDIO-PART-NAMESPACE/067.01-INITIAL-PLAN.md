# 067.01 — Initial plan: give the source audio edition its own part namespace

## Summary

Both audio editions render through `video_part_name()` (`src/noveltrans/tts/video.py:370`)
with the same novel slug, so a chapter part covering chương 1-10 and a source part covering
releases 1-10 resolve to the same folder, the same `.mp4` and the same six sidecars —
including `.upload.json`, which carries a live YouTube video id. The fix is one new concept
in the namer: an **edition slug**, `{slug}-nguon` for the source edition, applied inside
`video_part_name` / `video_part_dir_name` / `iter_rendered_part_dirs` /
`discover_committed_video_windows` behind a keyword-only `source_audio: bool = False`.
Chapter audio keeps its current name byte-for-byte, so there is **no migration for anything
that exists today** and no risk to any published chapter part. Callers change in exactly
three production places (`tab_video._part_output_path`, `tab_video._part_dir_name`,
`VideoWorker.run`) plus one guard in `cleanup.py`, which — this is a finding not in the
prompt — currently reads a source part folder's release ordinals as *chapter* numbers and
would offer the matching chapter MP3s for deletion.

---

## The collision, precisely

`video_part_name(slug, first, last, whole_novel=False)` (`src/noveltrans/tts/video.py:370-378`)
knows only a slug and two integers. Both planners feed it:

- chapter audio → `plan_merge_windows` (`src/noveltrans/tts/merge.py:47-59`), windows keyed
  by chapter number;
- the source edition → `plan_source_windows` (`src/noveltrans/tts/merge.py:62-86`), windows
  keyed by `SourceAudio.index` = `ord - 1` (`src/noveltrans/models.py:187-190`), i.e.
  release ordinals.

Both land in `project.video_dir` (`src/noveltrans/storage/project.py:267-269`). Resolution is
duplicated in two places that agree exactly: `tab_video._part_output_path`
(`src/noveltrans/gui/tab_video.py:765-789`) and `VideoWorker.run`
(`src/noveltrans/gui/workers.py:1699-1710`), both `video_dir/<stem>/<stem>.mp4` with a legacy
flat `video_dir/<name>` fallback.

The artifact family, all `<stem>.<ext>` beside the `.mp4`:

| artifact | written by |
|---|---|
| `<stem>.mp4` | `render_video` (`tts/video.py`) |
| `<stem>.srt`, `<stem>.txt` | `render_video` itself — `tts/video.py:859` and `:862` |
| `<stem>.title.txt`, `<stem>.txt`, `<stem>.tags.txt`, `<stem>.jpg` | `VideoWorker._write_metadata` — `workers.py:1778-1779` (the `sidecar()` closure), `:1783`, `:1798`, `:1805`, `:1811` |
| `<stem>.srt` (no render) | `SubtitleWorker.run` — `workers.py:2022` |
| `<stem>.created.json` | `video_state.state_path` (`src/noveltrans/video_state.py:24-28`), read by `effective_created` (`:83-88`) |
| `<stem>.upload.json` | `youtube_upload.upload_state_path` (`src/noveltrans/youtube_upload.py:660`), read by `is_published` (`:710`), `uploaded_video_id` (`:764`), `needs_attention` (`:715`) |

Consequences, each verified:

1. **Renders overwrite.** `out_path` is identical; `render_video` truncates and
   `_write_metadata` re-stamps every sidecar.
2. **"Đã tạo" reads across editions.** `effective_created(resolved)` at `workers.py:1710`
   and `tab_video.py:1254` is a pure path check → `skip_existing` skips an unrendered
   source part.
3. **"Đã tải lên" reads across editions.** `tab_video.py:1599` (`_part_uploaded`) and `:962`
   call `is_published(self._part_output_path(...))`. `_pending_upload_rows`
   (`tab_video.py:3352-3374`) and the thumbnail/subtitle pushes then resolve the *other*
   edition's `video_id`.
4. **`discover_committed_video_windows` freezes the wrong grid.** `tts/video.py:395-417`
   filters `iter_rendered_part_dirs` (`:420-439`), which matches on `f"{slug}-"` +
   `^(\d+)-(\d+)$` and nothing else. (066's `VideoWorker` source branch,
   `workers.py:1651-1667`, dodges this — but only for the worker.)
5. **Description resync.** `_resync_description_sidecars` (`tab_video.py:2702-2795`) walks
   `iter_rendered_part_dirs` and rebuilds each `.txt` from
   `[c for c in chapters if first_num <= c.index + 1 <= last_num]` (`:2765`) — for a source
   folder that selects *chapters* 1-10 for a part containing *releases* 1-10.
6. **NOT in the prompt, and the worst one: `cleanup.py` offers chapter audio for deletion.**
   `rendered_parts` (`src/noveltrans/cleanup.py:116-129`) takes any top-level `video_dir`
   folder containing a `*.mp4`; `part_range` (`:102-113`) reads `-(\d+)-(\d+)$` off its name;
   `covered_chapters` (`:132-140`) turns that into "these chapters are safely inside a
   video"; `plan_audio_cleanup` (`:150-195`) then offers those chapters' `.mp3`/`.cues.json`
   for deletion. A rendered source part `slug-0001-0010` therefore authorises deleting
   chapter audio 1-10 that no video contains. This module's whole doctrine is "refuse unless
   the replacement is present and checkable" (`cleanup.py:1-36`); this is a hole in it.

**One correction to the prompt's framing:** the second worker at `workers.py:1971/2019` is
`SubtitleWorker` (`workers.py:1886`), and it needs **nothing**. It plans only with
`plan_merge_windows(project.chapters(), self.voice, ...)` (`:1975-1978`) and has no
`source_audio` flag; with `voice == SOURCE_AUDIO_KEY` the voice filter (`merge.py:56`)
matches no chapter row (downloaded chapter audio stores a real adapter name —
`audio_voice="tieuthuyetmang"`, see `tab_video.py:2501-2503`), so it fails with "Không có
chương nào…" and writes nothing. It is structurally chapter-only today and stays
chapter-only after this change.

## Design decisions

### D1 — Namespace scheme: a distinct **edition slug**, `{slug}-nguon` (recommended)

Given the user's two constraints (only one edition per novel in practice; filenames are
app-internal), the choice is purely "cleanest and least error-prone in code".

**Recommended: (a) suffix the slug.** `video_dir/{slug}-nguon-0001-0010/{slug}-nguon-0001-0010.mp4`,
whole-novel `video_dir/{slug}-nguon/{slug}-nguon.mp4`. `nguon` is already this app's on-disk
marker for the source edition — `AudioDownloadWorker` writes
`exports/audio/nguon-{ord:04d}-{slug}.mp3` (`workers.py:1303`).

Why it wins:

- **The existing prefix+regex scan partitions the two editions for free, with no signature
  change to the scan.** `iter_rendered_part_dirs(video_dir, slug)` uses `prefix = f"{slug}-"`
  then `_COMMITTED_SUFFIX_RE = ^(\d+)-(\d+)$` on the remainder (`tts/video.py:431-439`). For
  `slug-nguon-0001-0010` the remainder is `nguon-0001-0010` → **no match** → chapter scans
  are clean today's code, unmodified. Passing the *source* edition slug as the `slug`
  argument makes the same function scan only source folders. Same for
  `discover_committed_video_windows`. Checked the pathological case (a novel whose own slug
  ends in `-nguon`): still safe, because the extra `nguon-` segment still fails the
  digits-only regex.
- **The folder NAME is used as a key elsewhere, so the name is the thing that must be
  unique.** `_stale_descriptions` is a `set[str]` of folder names (`tab_video.py:134-137`),
  written by `_resync_description_sidecars` as `part_dir.name` (`:2779`, `:2786`) and read
  via `_part_dir_name(window, whole)` (`:1069`, `:1802`, `:1886`). A scheme that keeps the
  name and changes only the parent directory (option b) leaves those keys colliding.
- **Zero layout change.** `exports/video/` stays one level deep, so `onedrive_upload`'s
  relpath→remote-folder mapping, `_delete_rendered_part`'s `out.parent.name == out.stem`
  check (`tab_video.py:1531-1533`) and every "open the part folder" affordance keep working
  with no thought.
- **The legacy flat fallback goes inert by itself.** `legacy = video_dir / name` for a source
  part is `video_dir/{slug}-nguon-0001-0010.mp4`, which can never pre-exist. No branch needed.

**Rejected: (b) a dedicated subfolder** `video_dir/nguon/{slug}-0001-0010/…`. It gets
`cleanup.py` right by accident (`rendered_parts` is non-recursive, so nested source parts are
simply invisible — safe direction, but by luck, not by intent) and it needs no naming change;
but it keeps the part folder *name* identical across editions, so `_stale_descriptions` still
cross-talks, it adds a directory level that `onedrive_upload` and `_delete_rendered_part` were
never asked about, and it means threading a different *base directory* through
`_part_output_path`, the worker, and every scan — a second axis of edition-awareness rather
than one.

**Rejected: (c) a prefix** (`nguon-{slug}-0001-0010`). Equivalent to (a) but breaks the
"everything for this novel sorts together" property and gains nothing.

**Cost of (a) that (b) doesn't have:** the trailing `-(\d+)-(\d+)$` in `cleanup.py:53` still
matches a source folder name, so consequence 6 needs an *explicit* one-line guard rather than
getting fixed implicitly. That is a feature, not a bug: it makes the exclusion visible and
testable (Step 5), and it keeps a *published* source part visible to
`video_cleanup_candidates` (`cleanup.py:198-236`), which is edition-agnostic and correct — an
`.mp4` that is on YouTube and verified on OneDrive is deletable whichever edition made it.
Option (b) would silently lose that.

**YouTube-facing artifacts are untouched.** The in-video title, the thumbnail text and the
upload title all come from `build_upload_title(novel_title, part_num)` with
`novel_title = project.meta.display_name()` (`workers.py:1616`, `:1783`); the description
comes from `fit_video_description`; the Studio upload fills the title box explicitly from
`<stem>.title.txt` (`_set_details`, `youtube_upload.py:1344`). Nothing user-visible on
YouTube reads the file name. The marker is app-internal, as the user confirmed it may be.

### D2 — Threading: one keyword, defaulted `False`, on four functions

Minimal signature change, all keyword-only with `source_audio: bool = False`, so **every
existing call site and every existing test compiles and behaves identically**:

```python
SOURCE_EDITION_MARKER = "nguon"

def edition_slug(slug: str, *, source_audio: bool = False) -> str: ...
def video_part_name(slug, first_num, last_num, *, whole_novel=False, source_audio=False) -> str
def video_part_dir_name(slug, first_num, last_num, *, whole_novel=False, source_audio=False) -> str
def iter_rendered_part_dirs(video_dir, slug, *, source_audio=False)
def discover_committed_video_windows(video_dir, slug, *, source_audio=False)
```

No caller ever concatenates the marker — `edition_slug` is the only place that knows it, and
`video_part_name` remains the single source of truth for naming.

**Are the ~25 `_part_output_path` call sites edition-agnostic?** Yes. All 25 checked
(`tab_video.py:845, 958, 962, 990, 1254, 1282, 1387, 1532, 1599, 1816, 1947, 2693, 3017,
3093, 3176, 3319, 3321, 3371, 3396, 3448, 3500, 3737, 3968, 4101, 4114`). Every one operates
on windows obtained from `_windows_for_current_selection()` (or `_selected_window()`) in the
same method, and that helper reads the same combo (`tab_video.py:669`). Nothing caches windows
across a voice change, and nothing reconstructs a window from a folder name and then
re-resolves it through `_part_output_path`. Three specifics worth naming:

- `_resync_description_sidecars` (`:2702`) is the only disk-driven enumerator. It must stay on
  the **base** slug — see D4 below.
- `_on_video_file_done` (`tab_video.py:3294-3302`) receives an absolute path from the worker
  signal and never re-derives it. Safe.
- The upload/thumbnail/subtitle-upload request builders snapshot absolute paths at click time.
  Safe.

So one private helper `_is_source_edition()` reading the combo, consumed by
`_part_output_path` and `_part_dir_name`, covers the whole tab.

**`VideoWorker`** already has `self.source_audio` (`workers.py:1542`) — one kwarg at `:1699`.
Its `discover_committed_video_windows` call at `:1660` sits in the `elif self.mode == "batch"`
branch that the 066 reorder made unreachable for source runs, so it needs nothing.

### D3 — Migration: none. Chapter audio keeps its current name.

**Recommendation: namespace only the source edition; no file moves, no read fallback.**

Alternatives considered:

| option | cost | failure mode |
|---|---|---|
| **chosen: source-only namespace, no migration** | zero | a *pre-067 source render* is now read as a chapter part (see below) |
| move files on open | a rename pass over `video_dir` on every project open, touching `.upload.json` | undecidable: nothing in a folder says which edition made it, so any automatic move is a guess with a published video id at stake |
| legacy read-fallback for the source edition (mirroring `_part_output_path`'s flat-file fallback) | ~5 lines | **actively reintroduces the bug**: a chapter part `slug-0001-0010` would be adopted as source part 1-10 on a novel that has both editions — exactly the cross-talk being fixed |
| namespace *both* editions | a real migration for every existing render, including published ones | all downside, no upside |

The ambiguity the prompt asks about is genuinely unresolvable *from a folder alone* — the
folder holds an `.mp4`, a title, a description and a thumbnail, none of which record the
planner that produced them. It is resolvable only from context, and the safe default is "an
existing folder is chapter audio", which is (i) what the user's actual library contains,
(ii) what the majority of installs contain, and (iii) the assumption that never touches a
published chapter part.

**What happens to a pre-067 source render** (possible: 066's history says *batch* was broken,
but per-row `mode="range"` and `mode="all"` source renders worked): its folder keeps the
chapter name and is now interpreted as a chapter part. Concretely —

- On the source edition the part shows **"chưa tạo"**, because nothing exists at
  `{slug}-nguon-…`. Visible and alarming, which is good.
- Its `.upload.json` is stranded. If the user re-renders and uploads, **the same episode is
  published to the channel twice** — the one thing `youtube_upload` is designed never to do
  (`youtube_upload.py:29-33`).
- It is recoverable by hand with zero data loss: rename the folder `slug-0001-0010` →
  `slug-nguon-0001-0010` and each `slug-0001-0010.*` inside it to `slug-nguon-0001-0010.*`.
  All state (upload record, created tick, thumbnail) follows.
- On a novel that has chapter audio too, the stale folder now blocks/pre-ticks the *chapter*
  part of the same span — but by the user's own account that combination does not exist.

Mitigation in scope (Step 7, cheap, non-destructive): a one-time status-line note when the
source edition is selected and chapter-namespace folders exist whose spans match planned
source windows. No renaming, no dialog, no guessing. An *assisted rename* is deferred (see Out
of scope): it would need the precondition "no chapter of this novel has an `audio_path`" to be
decidable, and that precondition is itself imperfect because `plan_audio_cleanup` deletes
chapter MP3s while leaving the DB column populated.

### D4 — The whole-novel name: in scope, and free

`{slug}.mp4` (no range suffix) collides identically, and `video_part_name`'s `whole_novel`
branch (`tts/video.py:376-377`) is *inside* the function that gets the edition slug — so it is
fixed by the same one-line change: the source whole-novel video becomes
`{slug}-nguon/{slug}-nguon.mp4`. Three follow-on checks, all clean:

- `iter_rendered_part_dirs(video_dir, slug)` sees `slug-nguon` (remainder `nguon`, not
  `\d+-\d+`) → skipped, as it already skips `slug` itself (pinned by
  `tests/test_video.py::test_ignores_names_that_are_not_a_span`).
- `_resync_description_sidecars`'s special case
  `whole_dir = video_dir / video_part_dir_name(slug, 0, 0, whole_novel=True)`
  (`tab_video.py:2750`) stays on the base slug → the chapter whole-novel folder only. Correct,
  and it is the reason `_novel_slug()` (`tab_video.py:795-805`) must **not** become
  edition-aware: that helper feeds the resync, and making it follow the combo would let a
  resync run while the source edition is selected rewrite source `.txt` files from chapter
  data — the very bug (consequence 5) being fixed. `_part_dir_name` applies the edition
  itself, via `video_part_dir_name(..., source_audio=…)`.
- `cleanup.part_range("slug-nguon")` → `None` already (no trailing range), so the whole-novel
  source folder contributes no chapter coverage even before Step 5.

### D5 — Revisiting 066's D4: keep the locks chapter-only, but for the honest reason

Once the namespaces are separate, D4's reason 2 ("`discover_committed_video_windows` scans by
filename, so chapter parts freeze source windows") **disappears** —
`discover_committed_video_windows(video_dir, slug, source_audio=True)` would legitimately
return only source commits.

D4's reason 3 ("the semantics don't exist for releases — a release is atomic, a batch of
releases never grows underneath a rendered part") is **overstated, and is retracted here**.
`plan_source_windows` → `_group_windows` (`merge.py:88-124`) builds a fixed ordinal grid and
includes whatever is *available*: if releases 9-10 are downloaded after part `1-8` was
rendered from an intended batch of 10, the window becomes `(1, 10)` on the next run — the
exact retroactive-growth problem commit-locking exists for. So the source edition *would*
benefit.

**Recommendation: still don't do it now**, for a different and concrete reason:
`plan_locked_video_windows` (`tts/video.py:441-484`) filters
`c.audio_path and c.audio_voice == voice` (`:459-462`). `SourceAudio` has no `audio_voice`
property (`models.py:187-206`) → `AttributeError`. Applying locks to the source plan requires
generalising that planner the way `_group_windows` generalised the grouping (split the filter
out from the locking), plus a per-edition commit map, plus a matching change to the tab's
`_locked_batch_windows`. That is a feature, not a namespace fix.

**`video_manual_windows.json` stays chapter-only.** It is a flat `{first_num: last_num}` map
at the project root (`src/noveltrans/video_windows.py:23-49`), with no room for two number
spaces. Per-edition support means a versioned schema (`{"chapters": {...}, "nguon": {...}}`)
with a back-compat read of the flat form, and per-edition `split_window`/`merge_windows`.
Deferred. 066's step 7 stands: the split/merge context-menu entries stay hidden for the source
edition (`tab_video.py:855`).

**Which 066 tests change, and why that is legitimate** (all in
`tests/test_video_downloaded_audio.py`):

| test | change | why it is not a regression |
|---|---|---|
| `test_batch_mode_renders_the_source_edition_instead_of_failing` (:239) | expected names get `source_audio=True` (:259) | it asserts "one part per release" *through the namer*; 067 changes the namer's source-edition output by design |
| `test_a_rendered_chapter_part_does_not_freeze_a_source_window` (:315) | `full` name gets `source_audio=True` (:336); **docstring must be rewritten** — its stated premise "Both editions render into the same `{slug}-NNNN-MMMM` namespace" is now false | the asserted *behaviour* is unchanged; it is now guaranteed twice over (the source planner still ignores commits, **and** the namespaces are disjoint) |
| `test_whole_novel_mode_is_unchanged` (:358) | `f"{slug}.mp4"` → `f"{slug}-nguon.mp4"`; rename to `test_whole_novel_mode_is_namespaced_too` | this is D4 landing — the whole-novel name collided identically and is fixed by the same lever |
| `test_a_manual_chapter_split_does_not_reshape_the_source_plan` (:307) | **unchanged, keep** | manual windows stay chapter-keyed; this still pins the surviving half of 066's D4 |

Nothing in `tests/test_tab_video.py` or `tests/test_video.py` changes: they are all
chapter-edition, and the new keywords default to `False`.

### D6 — Sizing

Realistically one edition per novel, so this is largely defensive — but the `.upload.json`
cross-talk (a subtitle or thumbnail push resolving the *other* edition's live `video_id` via
`uploaded_video_id`, `youtube_upload.py:764`) and the newly found `cleanup.py` audio-deletion
path are both correctness-of-user-data issues, so the core fix is worth doing regardless.
Sized accordingly: **~30 lines of production change across 4 files**, no migration, no schema
change, no UI change. Everything larger (per-edition manual windows, source commit-locking,
source subtitles, assisted rename) is deferred explicitly below.

## Step-by-step changes

### 1. `src/noveltrans/tts/video.py` — the edition slug (the whole scheme)

Insert above `video_part_name` (currently line 370):

```python
# The source edition's on-disk marker. The site's own audio releases already carry it
# (`exports/audio/nguon-0007-….mp3`, workers.AudioDownloadWorker); this is the same idea
# one level up. It exists because a chapter window and a source window are keyed by two
# different number spaces — chapter number vs `SourceAudio.index` — and rendering both
# under one name made "chương 1-10" and "phần 1-10 của bản nguồn" the same folder, the
# same .mp4, and the same `.upload.json` (which holds a live YouTube video id).
SOURCE_EDITION_MARKER = "nguon"


def edition_slug(slug: str, *, source_audio: bool = False) -> str:
    """The slug this EDITION's parts are named after. The only place the marker is spelled.

    Chapter audio keeps the plain slug, unchanged and forever: it names every part folder
    and `.upload.json` already on disk, so moving it would strand published videos.
    """
    return f"{slug}-{SOURCE_EDITION_MARKER}" if source_audio else slug
```

Then thread it, keyword-only and defaulted, through four functions:

```python
def video_part_name(slug, first_num, last_num, *, whole_novel=False, source_audio=False) -> str:
    slug = edition_slug(slug, source_audio=source_audio)
    if whole_novel:
        return f"{slug}.mp4"
    return f"{slug}-{first_num:04d}-{last_num:04d}.mp4"
```

`video_part_dir_name` (:381) just forwards `source_audio=` to `video_part_name`.

`iter_rendered_part_dirs` (:420) and `discover_committed_video_windows` (:395) take
`*, source_audio: bool = False` and start with `slug = edition_slug(slug, source_audio=source_audio)`.
**No other line in either changes** — `prefix = f"{slug}-"` plus `_COMMITTED_SUFFIX_RE` already
rejects the other edition's folders in both directions (a source folder's remainder
`nguon-0001-0010` is not `\d+-\d+`; a chapter folder does not start with `{slug}-nguon-`).
Extend both docstrings with a sentence on the partition and why it holds.

### 2. `src/noveltrans/gui/tab_video.py` — one helper, two resolvers

Add next to `_novel_slug` (:795):

```python
def _is_source_edition(self) -> bool:
    """Whether the parts on screen are the site's own audio edition, not chapter audio.

    The two are separate part namespaces (`noveltrans.tts.video.edition_slug`), and the
    combo is the single fact that decides which one every path in this tab resolves to —
    every caller of `_part_output_path` gets its windows from
    `_windows_for_current_selection`, which reads the same combo in the same call.
    """
    voice = self.voice_combo.currentData() or self.voice_combo.currentText().strip()
    return voice == SOURCE_AUDIO_KEY
```

`_part_output_path` (:765-789) — the only change is the namer call:

```python
name = video_part_name(
    slug, window.first_num, window.last_num,
    whole_novel=whole_novel, source_audio=self._is_source_edition(),
)
```

Leave the legacy flat fallback exactly as it is and note in the docstring that it is inert for
the source edition (a `{slug}-nguon-….mp4` can never predate this change).

`_part_dir_name` (:807-815) — same kwarg. Note in its docstring that `_novel_slug()` stays the
**base** slug and the edition is applied here, because `_novel_slug`'s other caller
(`_resync_description_sidecars`) must remain chapter-only.

`_resync_description_sidecars` (:2702) — **no code change**; add two sentences: the disk scan is
deliberately chapter-namespace-only (source folders no longer match
`iter_rendered_part_dirs(video_dir, slug)`), and that is correct rather than a gap, because its
window reconstruction at `:2765` selects *chapters* by number and a source part contains
releases. Same for `whole_dir` at `:2750`.

`_locked_batch_windows` (:657) — no change. It is only reached for chapter voices
(`_windows_for_current_selection` returns early for `SOURCE_AUDIO_KEY` at `:651`), so its
`discover_committed_video_windows(..., slug)` correctly stays on the base slug.

### 3. `src/noveltrans/gui/workers.py` — `VideoWorker`

## Migration

**What moves: nothing.** Chapter parts keep `{slug}-{first:04d}-{last:04d}` and `{slug}`
exactly as today — same folder, same `.mp4`, same `.title.txt` / `.txt` / `.tags.txt` / `.jpg`
/ `.srt` / `.created.json` / `.upload.json`. Every published chapter part keeps its `video_id`.
Every "đã tạo" tick, every manual override, every OneDrive manifest relpath, every
`video_manual_windows.json` entry keeps referring to the same thing. No code path, migration or
otherwise, rewrites anything on disk.

**What is new:** only source-edition renders made *after* this change, under `{slug}-nguon-…`.

**The ambiguity, and the safe default.** A folder on disk carries no record of which planner
made it — the `.mp4`, `.title.txt`, `.txt`, `.jpg` and `.upload.json` are byte-identical in
shape for both editions. So "which edition is this?" is undecidable from the folder alone and
stays that way. The default this plan takes is **"an existing folder is chapter audio"**: it is
true for the user's library, true for the overwhelming majority of installs, and it is the
choice that cannot damage a published chapter video. Any automatic rename would be a coin flip
with a live YouTube id on the table.

**The one hazard, stated plainly.** A source part rendered before this change (possible via
per-row "Tạo" or "Toàn bộ" — batch was broken until 066) reads as a chapter part. On the source
edition it shows "chưa tạo", so the user re-renders under the new name; its old `.upload.json`
no longer participates, so an already-published episode can be published a second time.
Detection is Step 7's status note; the fix is a manual rename (folder + every `<stem>.*` inside
it) that loses nothing. An assisted rename is deferred, because its only decidable precondition
("this novel has no chapter edition at all", i.e. no chapter row with a non-empty `audio_path`)
is itself imperfect — `plan_audio_cleanup` deletes chapter MP3s while leaving `audio_path`
populated, and `project.py:816` clears `audio_path` on an explicit "xoá audio".

## Risks / out of scope

**Risks**

- **A pre-067 source render is silently reclassified as a chapter part** — the accepted trade of
  "no migration". Detected by Step 7's note, fixed by a manual rename, and worst case causes a
  duplicate YouTube publish. Fully documented in the Migration section.
- **`_is_source_edition()` reads live UI state.** It is correct because every
  `_part_output_path` caller derives its windows from the same combo in the same call (verified
  across all 25 sites), but a future caller that *stores* windows across a voice change would
  resolve them under the wrong edition. Mitigated by the docstring and by
  `test_the_tab_and_the_worker_agree_on_the_source_stem`.
- **`cleanup.py` gains an import of `noveltrans.tts.video`.** Cycle-free today (`tts.video`
  imports only `errors`, `runtime_env`, `tts.*`), but it does drag a heavier module into the
  cleanup dialog's import path. Inlining the literal is the escape hatch.
- **Slug length.** `slugify` caps at 40 chars (`storage/project.py:90-96`); `-nguon` pushes
  source names to 46. Nothing downstream truncates or assumes a length; two titles that already
  truncate to the same 40 chars already collided before this change, identically.

**Out of scope / deferred (explicitly, not silently)**

- **Per-edition manual split/merge boundaries.** `video_manual_windows.json` stays a single
  chapter-keyed map; the source edition's split/merge menu entries stay hidden (066 step 7,
  `tab_video.py:855`). Needs a versioned schema plus per-edition `split_window`/`merge_windows`.
- **Commit-locking for the source edition.** Now technically unblocked and semantically
  justified (D5 retracts 066's "releases are atomic" argument), but blocked on generalising
  `plan_locked_video_windows` past its `audio_voice` filter.
- **Subtitles for the source edition.** `SubtitleWorker` cannot plan source windows and releases
  carry no cues or per-chapter text; `_subtitle_coverage` (`tab_video.py:3304-3322`) will
  therefore keep reporting `0/N` for source parts. Pre-existing, unchanged.
- **Description resync for the source edition.** Deliberately not implemented: a source part's
  "chapters" are releases, so the current window reconstruction cannot serve it. After this
  change it is skipped (correct) instead of being rewritten from chapter data (a bug).
- **Cleanup chapter-coverage credit for source parts.** A source video containing releases 1-10
  will not authorise deleting the chapter MP3s it does in fact contain. Correct-by-refusal;
  adding it would need a release→chapter mapping (`SourceAudio.number` is the site's chapter
  number, `models.py:175`) and belongs to a cleanup feature.
- **An assisted rename / adoption tool** for pre-067 source renders — see Migration for why its
  precondition is not reliably decidable.
