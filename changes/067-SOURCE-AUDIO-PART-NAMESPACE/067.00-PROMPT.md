# 067 — Video part folders collide between the two audio editions

## Ask (user)

> Fix the video part folder collision between both audio editions.

## The problem

A novel can have two independent audio editions:

- **chapter audio** — TTS-voiced (or downloaded onto a chapter row), planned by
  `plan_merge_windows`, windows keyed by **chapter number**;
- **the source edition** — the site's own audio releases, planned by
  `plan_source_windows`, windows keyed by **release ordinal** (`SourceAudio.index`).

Both render through the same namer. `video_part_name(slug, first, last)`
(`src/noveltrans/tts/video.py`) returns `{slug}-{first:04d}-{last:04d}.mp4` with no idea
which edition asked, and both land in the same `project.video_dir`. So "chương 1-10" and
"phần 1-10 của bản audio nguồn" are **the same folder and the same file**.

Feature 066 deliberately kept the chapter-keyed locks away from the source plan for
exactly this reason (see `066.01-INITIAL-PLAN.md`, decision D4 and its Risks section);
this feature is the underlying fix that D4 worked around.

## What actually breaks

Everything keyed off the `.mp4` path — the whole sidecar family lives beside it as
`<stem>.<ext>`:

| artifact | written by |
|---|---|
| `<stem>.mp4` | `render_video` |
| `<stem>.title.txt`, `<stem>.txt`, `<stem>.tags.txt`, `<stem>.jpg` | `VideoWorker._write_metadata` |
| `<stem>.srt` | subtitle burn-in / YouTube subtitle upload |
| `<stem>.created.json` | `video_state` ("Trạng thái" tick) |
| `<stem>.upload.json` | `youtube_upload` ("đã tải lên", incl. published video id) |

Concrete consequences:

1. **Renders overwrite each other.** Rendering the source edition over an already-rendered
   chapter part silently replaces the `.mp4`, its thumbnail and its description.
2. **"Đã tạo" reads across editions.** `effective_created` is a path check, so a rendered
   chapter part makes the source part show as already made — and `skip_existing` then
   skips a part that was never rendered.
3. **"Đã tải lên" reads across editions.** Worse than (2): `<stem>.upload.json` carries a
   real YouTube video id. The wrong edition can look published, and a subtitle or
   thumbnail push could target the *other* edition's video.
4. **`discover_committed_video_windows` freezes the wrong grid.** It scans
   `iter_rendered_part_dirs` by filename only, so chapter parts and source parts lock each
   other's batch windows. 066 dodged this by not consulting it for source audio.
5. **Description resync** (`_resync_description_sidecars`) walks the same folders and would
   rewrite one edition's `.txt` from the other's chapter data.

## Scope

- Give the source edition its own part namespace so nothing above can collide — a distinct
  slug, a subfolder, or another scheme (the plan should choose and justify).
- Keep `video_part_name` the single source of truth for naming; do not scatter
  edition-awareness across callers.
- **Migration matters.** Parts already rendered under the shared name must keep working —
  including any that carry a `.upload.json` with a live YouTube id. Do not orphan an
  uploaded part or lose its state. Decide (and state) whether existing renders are moved,
  or read from the legacy path as a fallback the way `_part_output_path` already falls back
  to a legacy flat file.
- Revisit 066's D4 afterwards: once the namespaces are separate, decide whether committed
  windows and manual split/merge boundaries can now legitimately apply to the source
  edition. (`video_manual_windows.json` is a single per-novel `{first_num: last_num}` map,
  so it needs the same per-edition treatment or an explicit decision to keep it
  chapter-only.)

## Open questions for the plan

- Do both editions ever get used on one novel in practice, or is this defensive? The fix
  should be sized accordingly — but the `.upload.json` cross-talk argues for correctness
  over minimalism either way.
- Does the whole-novel name (`{slug}.mp4`, no range suffix) need the same treatment? It
  collides identically.
