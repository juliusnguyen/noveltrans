# 089-CODEX-WINDOWS-MODEL-FIX — History

## [FIX] A model from one engine must not reach another — 2026-09-14

**Reported as:** "codex agent not working on windows machine (mac is fine)". Every chapter
failed with

> Không engine nào dịch được chương này: Lệnh CLI trả lỗi (mã 1): tài khoản ChatGPT không
> dùng được model này với Codex — đổi model trong ô Model (…)

### What it actually was

Not a Windows problem with Codex at all. Verified on the reporting machine (Windows 11,
codex-cli 0.154.0 installed at `%LOCALAPPDATA%\Programs\OpenAI\Codex\bin\codex.exe`):

- The exact command from `DEFAULT_CODEX_CLI_COMMAND`, and the full `CliAgentTranslator`
  code path, translate a real chapter (第275章：海洋之淚, 1998 chars) in ~50s with
  `-m gpt-5.6-luna`. `--sandbox read-only`, the `--output-last-message` temp file, stdin
  `-`, `CREATE_NO_WINDOW` and the npm/`.exe` resolution all work on Windows.
- With `-m sonnet` the same call reproduces the user's error in 6s. The backend returns
  `{"status":400,…"message":"The 'sonnet' model is not supported when using Codex with a
  ChatGPT account."}` — Codex never gets as far as translating.

`sonnet` came from Claude CLI: that machine had translated 278 chapters as
`CLI (claude, sonnet)` and `claude_cli_model = sonnet`. The Mac had no stale Claude model
to leak, which is the whole of "mac is fine".

**The leak:** `gui/qc_dialog.py` put a bare `QLineEdit(model)` in the chain table's Model
column and a bare `QLineEdit(config.qc_ai_model)` in the judge row, neither connected to
the engine combo beside it. Switching a row from Claude CLI to Codex CLI kept `sonnet`.
The Translate tab has always reloaded the model per engine (`cli_model_for`); these two
boxes did not — the one way the dialog could build a chain that cannot translate anything.

**Why it was undiagnosable:** `_friendly_codex_error` threw away the model the backend
named and said "đổi model trong ô Model". Someone whose Model box already reads
`gpt-5.6-luna` reads that as "the app is broken on Windows" — which is exactly what
happened, and the chain was never suspected.

### Changes

- `gui/qc_dialog.py`: `_remembered_model(engine)` — the model that engine was last used
  with (`cli_model_for` for CLI engines and LM Studio, `claude_model` for the API engine,
  else ""). Both the judge combo and every chain row's combo reset their Model box through
  it on `currentIndexChanged`. Connected *after* the widgets carry their saved values, so
  opening the dialog and `_move_chain_row` (which rebuilds every row) never rewrite a
  model. Both boxes gained the "model mặc định của engine" placeholder.
- `translators/cli_agent.py`: `_UNSUPPORTED_MODEL` pulls the rejected model out of the
  backend message; the advice now names it, says it is probably another engine's leftover,
  suggests real Codex model ids, and names *both* places a model comes from (the Translate
  tab's Model box and the QC chain's Model column).
- `tests/test_translators.py`: fixed a latent Windows-only failure introduced with 088 —
  `test_translate_runs_command_with_prompt` asserted `args[0] == "agy"`, but on a real
  Windows box with agy installed `_resolve_executable` has correctly rewritten it to
  `C:\Users\…\agy.EXE` by then. Compared by `binary_name` now, which is what the test means.

Tests: 5 new (chain-row and judge engine switches, a saved model surviving open/reorder,
the named model in the error, an unnamed one still getting advice). Affected modules: 153
passed. Full suite on Windows: **3542 passed**, 43 failures all pre-existing and
environmental (see below). Ruff: 26 findings before the change, 26 after — none added.

### Not done / noted

- The Windows venv carries runtime deps only. Installed `pytest`/`responses`/`ruff` into it
  to run the suite (what `make setup`'s dev extra would have done); `numpy` (tts extra) and
  `playwright` are still absent, which is all 43 failures except
  `test_storage.py::TestMigration::test_open_pre_translator_db_adds_column` — that one is
  this CPython's bundled SQLite ("error in table chapters after drop column").
- `runtime_env._candidate_dirs()` still does not list
  `%LOCALAPPDATA%\Programs\OpenAI\Codex\bin`, where the official Codex Windows installer
  puts `codex.exe`. It was on PATH on the reporting machine so nothing failed, but a GUI
  launched without that PATH entry would get "Không tìm thấy lệnh 'codex'". Left alone —
  unproven in the wild, and not this bug.
- `rewrite_ai_model` and `video_ai_model` are single global model strings shared across
  whatever engine those dialogs are set to — the same shape of leak as the QC judge box.
  Untouched here; neither was involved in the report.
- `uv.lock` stays uncommitted, as decided in 088: its diff is `uv run` lock/pyproject drift
  (cuda-bindings etc.), not this change.
