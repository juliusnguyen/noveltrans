# 078 — Audio: no pause between chapter title and body — History

## [IMPL] A terminator on the title — 2026-09-03

### The cause, reproduced rather than reasoned about

`synthesize_chapter` joins `f"{title}\n\n{body}"`. Running the real pipeline on
`title="Chương 127"`:

```
split_sentences    -> ['Chương 127', 'Tống Nam Thời trầm ngâm…', 'Hắn bước ra khỏi cửa.']
merge_short_chunks -> ['Chương 127 Tống Nam Thời trầm ngâm…', 'Hắn bước ra khỏi cửa.']
```

`split_sentences` **does** give the title its own chunk (it splits on `\n\n` first).
`merge_short_chunks` glues it back: the title is 10 characters against a 30-character
floor, and the join is a bare **space**. Two consequences — the 0.4s inter-chunk gap
disappears because they became one chunk, and there is no punctuation for the model to
break on.

### Why the obvious fix was not available

That merge is feature 028's measured fix for autoregressive drift: **80% of chunks under
10 characters babble, 0% at 40+**, and `028.01-HISTORY.md` states outright that the
absorbed fragment "loses its paragraph gap when absorbed — intended: that fragment was the
drift source." A bare `Chương 127` is exactly 10 characters, the worst band. Exempting it
would have traded this defect for that one.

Presented to the user as three options with that trade spelled out; they chose punctuation
only — consistent at every title length, zero drift risk.

### `src/noveltrans/tts/base.py`

New `ensure_sentence_end(title)`, applied in `synthesize_chapter` before the join. The
title is otherwise untouched: the audio **filename** (`slugify(title)` in the worker) and
feature 077's **fingerprint** both read the raw title, so neither moves.

Shape driven by a survey of all 4331 translated titles in the library:

| title ends with | count | handling |
|---|---|---|
| alphanumeric | 3552 | append `.` |
| `!` `?` `…` `.` | 489 | already finished, untouched |
| `)` `）` `】` `"` `“` `》` | 278 | peel the closer, then judge what is underneath |
| `:` `,` `-` `~` | 8 | replace the dangling separator with `.` |

Fullwidth enders (`。！？`) are in the terminal set because this runs **before**
`clean_for_tts` maps them to ASCII; without them a title ending in `。` would be judged
unterminated and come out as `。.`.

### Two bugs found by running it over the real library, not by unit tests

Both in `Chương 331: Chử đội, ngươi thật bẩn a! ~~~`:

1. After stripping the dangling `~~~` the first version never re-checked what was
   revealed, so it appended to a `!` and produced `…bẩn a!.`
2. It also dropped the `~~~` while doing so.

Fixed by peeling closers and separators to a `stem`, judging **that**, and only then
deciding. Now returns the title unchanged. Both are pinned as regression tests, along with
the real title that exposed them.

Final pass over all 4331 real titles: **3662 gain a period, 669 already terminated, 0 text
lost, 0 doubled terminators, 0 non-idempotent.**

### A test I got wrong

`test_a_title_that_is_only_punctuation_is_left_alone` asserted `ensure_sentence_end("《》")
== "《》"` without checking — it actually returns `"《》."`. Rather than bend the code for a
case that does not occur, the test now asserts the property that actually matters: a
punctuation-only title contributes nothing to the audio, because `clean_for_tts` drops
speechless lines outright. Verified for `《》`, `》》`, `……` and `---`.
