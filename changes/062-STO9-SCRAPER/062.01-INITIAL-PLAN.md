## 1. Summary of the approach

One new file `src/noveltrans/scrapers/sto9.py`, one line in `_import_adapters`, one test module, one fixture directory, one README row. No change to `SiteAdapter`, no model change, no schema change, no new dependency, no browser, no cookies, no encoding work.

**sto9 is a sibling of 69shuba.** Both run the same Chinese novel CMS: the chapter container is `div.txtnav`, the body is `<br>`-separated text nodes with no `<p>`, and the metadata is a full OpenGraph set. `shuba69.py:134-159` is therefore the closest template in the repo and roughly 70 % of `parse_chapter` transfers verbatim. The differences that matter are all in this feature's two hard parts:

1. **The TOC page lies.** `/book/{id}/index.html` ships 36 of 187 entries behind a `LoadMore()` button. The complete list lives at `/ajax_novels/chapterlist/{id}.html`. Naively scraping the page yields a *plausible-looking* 36-chapter TOC in which entry 16 is really chapter 167 — and because `replace_toc` upserts by `idx` (`project.py:273`), a later successful re-scan would leave chapter 167's downloaded text sitting under chapter 16's title. **That is silent corruption, and §2.3 is designed around refusing to produce it.**
2. **Three pages carry three different things.** Metadata is only on `/book/{id}.html` (14 og: tags vs. 0 on the TOC page); the truncation signal and the stated total are only on `/book/{id}/index.html`; the chapters are only in the ajax fragment. A scan costs three requests, and §2.6 argues that is correct rather than lazy.

Unlike 061 there is no paywall, no login, no JS payload, no obfuscation and no rate limit. The entire risk surface of this feature is the TOC.

## 2. Decisions

### 2.1 Identity, URL patterns, and what counts as an sto9 URL

**Recommendation:**

```python
name = "sto9"
display_name = "思兔閱讀 (sto9.com)"
url_patterns = [r"sto9\.com/book/\d+", r"sto9\.com/txt/\d+/\d+"]
```

**`name = "sto9"`** — it is written into `NovelMeta.site` and into `meta.json` forever, so it must be short, ASCII and stable. It is also the module name; unlike `69shuba` (`shuba69.py:161-166` records that the natural name is not a valid Python identifier) `sto9` starts with a letter and needs no such workaround.

**`display_name = "思兔閱讀 (sto9.com)"`** — the site's own `bookinfo.siteName` is `思兔閱讀` and the `<title>` suffix is `思兔sto9`. `思兔閱讀` is the branded form, and the `(domain)` suffix matches every existing adapter (`ixdzs.py:29`, `xbanxia.py:25`, `shuba69.py:168`, `bookqq.py:432`). Note this string is currently **decorative**: no GUI code reads `SiteAdapter.display_name` (verified in §0). Set it correctly anyway — it is the label a future "supported sites" list will use, and getting it right costs nothing.

**Both patterns are host-anchored, deliberately.** A pattern of `r"/txt/\d+/\d+"` without the host would steal 69shuba's chapter URLs (`https://www.69shuba.com/txt/<id>/<cid>`, `shuba69.py:5`), and `ADAPTERS` is ordered by import (`scrapers/__init__.py:8`, `:16-19`) — first match wins, so the theft would be silent and order-dependent. Include `sto9\.com` in every pattern and add a registry test that a 69shuba chapter URL does **not** match.

**Two patterns, not one**, because `sto9\.com/book/\d+` already covers *both* book forms (`re.search`, `base.py:118`): `/book/13908.html` and `/book/13908/index.html` both contain `/book/13908`. The second pattern exists only to accept chapter URLs.

**Should chapter URLs match at all? Yes.** Arguments:

* The user's realistic paste is the address bar, and after clicking into chapter 1 that is `/txt/13908/7671958.html`. `bookqq.py:433` accepts `book-read` for exactly this reason.
* The cost is one regex plus a book-id extractor that already has to handle two forms, so it is three lines.
* The risk normally attached to this — that a chapter URL becomes a second project for the same novel — is fully neutralised by §2.2 plus `workers.py:122`.
* `/txt/{id}/end.html` (the last chapter's 下一章 sentinel) does **not** match, because `end` is not `\d+`. That is deliberate and worth a test.

**Mirrors:** none are known. Do not speculatively widen the host pattern the way `xbanxia.py:26` and `ixdzs.py:30` do for domains that were actually observed. If a mirror appears, it is a one-character edit.

### 2.2 Canonical URL — store the read URL, `/book/{id}/index.html`

**Recommendation: `NovelMeta.url` is always `https://sto9.com/book/{id}/index.html`, regardless of which of the three forms the user pasted.**

Rationale, in order of weight:

1. `Library.find_by_url` is **exact string equality** (`library.py:46`). Echoing the pasted URL (the `xbanxia.py:54` / `shuba69.py:96-98` convention) would let `/book/13908.html`, `/book/13908/index.html` and `/txt/13908/7671958.html` become **three projects for one novel**, each with its own folder, its own `chapters.db` and its own translation progress. `shuba69`'s echo rule exists to avoid orphaning projects already on disk; sto9 has none, so the better rule is available for free — the same argument `061.01-INITIAL-PLAN.md` §2.6 made and `bookqq.py:83-90` implements.
2. `index.html` is the site's own `og:novel:read_url` — the site nominates it as the canonical reading address, and it is the target of the 開始閱讀 button on the detail page.
3. It is the URL in the feature prompt, i.e. the form the user actually pastes.

**Handing either form to any method must work.** Achieved with three tiny pure helpers, mirroring `shuba69.py:59-80` and `bookqq.py:75-102`:

```python
def book_id(url) -> str      # r"/(?:book|txt)/(\d+)"   → "13908", else ScrapeError
def read_url(url) -> str     # ORIGIN + f"/book/{bid}/index.html"   ← the canonical form
def detail_url(url) -> str   # ORIGIN + f"/book/{bid}.html"         ← where the og: tags live
def chapterlist_url(url)->str# ORIGIN + f"/ajax_novels/chapterlist/{bid}.html"
```

`fetch_metadata` and `fetch_chapter_list` **never fetch the URL they are handed**; they fetch the derived one. That is what makes all three paste forms behave identically and is directly testable without a network.

**`ORIGIN` is a module constant `"https://sto9.com"`, not derived from the pasted URL.** This diverges from `shuba69.py:67-70`, which preserves the pasted scheme+host so mirrors keep working. Diverging is correct here: there are no known mirrors, and a fixed origin guarantees that `http://sto9.com/...`, `https://www.sto9.com/...` and `https://sto9.com/...` all canonicalise to *one* string — which is the entire point of §2.2. Record the trade-off in a comment so a future mirror is an intentional edit rather than a surprise.

**No `ScanWorker` change is needed.** `workers.py:122` already does `library.find_by_url(self.url) or library.find_by_url(meta.url)` (commit `2652e4c`), which is precisely the canonicalising-adapter case. Walk the three re-scan paths:

| Re-scan pasted as | `find_by_url(pasted)` | `find_by_url(meta.url)` | Result |
|---|---|---|---|
| `/book/13908/index.html` | hit | — | reuses project ✅ |
| `/book/13908.html` | miss | hit | reuses project ✅ |
| `/txt/13908/7671958.html` | miss | hit | reuses project ✅ |

So sto9 gets the fix for free, and this feature must **add a regression test asserting that** rather than a code change. This is worth stating explicitly because the 061 history shows this exact hole shipped once already (in `giatocvuongtai`) and cost `translated_title`, `tags`, `thumbnail_prompt` and `video_settings` silently.

### 2.3 Chapter list — the ajax fragment is authoritative, and a known-truncated page is *never* an acceptable fallback

This is the load-bearing decision of the feature.

#### The shape

`fetch_chapter_list(url)`:

1. **GET `read_url(url)`** — the TOC page. Parse two things from it:
   * `page_refs` — `#allchapter ul li[data-num] a[href]`, in document order (36 entries on the reference novel);
   * `stated_total` — the true chapter count, from **two independent signals**:
     * `int` out of `#loadmore`'s text via `re.search(r"(\d+)\s*章", text)` — measured `點擊展開全部187章節目錄` → 187;
     * `max(int(li["data-num"]))` over the page — measured 187, because the page ships the *last* chapters as well as the first.
     Take `max()` of whatever is available. Two signals, because either alone is a single point of failure and they were both measured to agree.
2. **GET `chapterlist_url(url)`** — the ajax fragment. Parse `li[data-num] a[href]` into `ajax_refs`.
3. **Choose**, per the truth table below.
4. Emit a `_status` line whenever the outcome is anything but a clean complete list.

#### The truth table

Let `truncated = stated_total is not None and stated_total > len(page_refs)` — i.e. *the page itself told us it is incomplete*.

| Situation | Action | Why |
|---|---|---|
| `ajax_refs` complete (`len(ajax_refs) >= stated_total`, or `stated_total` unknown and `ajax_refs` non-empty) | **use `ajax_refs`** | the happy path, 187/187 |
| `ajax_refs` non-empty but **short** of `stated_total` | **use `ajax_refs`** + loud `_status` warning naming both numbers | the ajax list is still the only list that is *contiguous from chapter 1*; a short-but-ordered list is safe under `replace_toc`, a re-scan simply extends it. Never silently. |
| ajax fetch raised / returned nothing, **and `truncated` is true** | **raise `ScrapeError`** naming the fragment URL | ← **the decision.** See below. |
| ajax fetch failed, `truncated` is false, `page_refs` non-empty | **use `page_refs`** + `_status` note | a genuinely short novel (< ~35 chapters) has no `LoadMore` button and its page list really is complete. **Inferring** — not observed, but it is the only branch where a page fallback is provably safe. |
| both empty | **raise `ScrapeError("Chapter list not found — page layout may have changed")`** | family convention: `xbanxia.py:66`, `shuba69.py:123`, `bookqq.py:354` |

#### Why "raise" rather than "fall back to the 36 chapters we already have"

The instinct is that 36 chapters beat zero. It is wrong here, and the reason is structural rather than aesthetic:

`page_refs` is **not a prefix** of the real TOC. Its `data-num` sequence is `1…15, 167…187` (measured). `ChapterRef.index` is dense 0-based positional (`models.py:117`) and there is nowhere to record the site's own number — so `page_refs[15]` would be stored as `idx = 15` while actually being chapter 167. Then:

* `create_project` writes 36 rows with a plausible-looking Chinese title on each. Nothing about the library view says "incomplete".
* The user downloads and translates them, spending real API quota.
* A later re-scan succeeds against the ajax fragment. `replace_toc` (`project.py:273`) **upserts by `idx`, preserving `content`** — so row 15 keeps chapter 167's Chinese text and Vietnamese translation while its title and URL are rewritten to chapter 16's.
* The EPUB, the TTS audio and the video now all contain chapter 167's story under chapter 16's heading, and nothing is marked as an error.

That is unrecoverable without the user hand-deleting rows, and it is exactly the class of silent-persistence failure `061.01-INITIAL-PLAN.md` §4.1 was written about. A `ScrapeError` costs the user a retry; the fallback costs them their library. **When the page has told us it is truncated, an incomplete list is worse than no list.**

The error message must say what to do, in the app's Vietnamese voice — e.g. *"Không lấy được danh sách chương đầy đủ của sto9 (trang mục lục chỉ hiện 36/187 chương). Thử quét lại sau."* — naming both numbers so it reads as a diagnosis, not a mystery.

#### Building the refs

```python
ChapterRef(index=i, title=a.get_text(strip=True), url=urljoin(base, a["href"]))
for i, a in enumerate(anchors)
```

Four measured details:

* **`index` is `enumerate()`, never `data-num`.** `data-num` is the site's display number; recon flags it as potentially non-contiguous, and `ChapterRef.index` is a dense positional key that `replace_toc`, `pending_download` and every exporter depend on. Same rule as `giatocvuongtai.py:110` (`index=len(refs)`, decoupled from `order_number`) and `bookqq.py:330-334`.
* **`get_text(strip=True)` handles the trailing space** the site puts inside every anchor. Do **not** normalise further: no `_clean_title`-style prefix stripping (`shuba69.py:54-56` needs one; sto9 has no `N.` prefix), no colon normalisation, no full-width→ASCII. Titles are persisted, exported into the EPUB and read aloud by TTS; over-normalising is invisible data loss for a cosmetic gain.
* **`urljoin(base, href)`** even though the fragment's hrefs are absolute — costs nothing, and if the site ever switches to relative hrefs it keeps working. `xbanxia.py:68` and `shuba69.py:128` do the same.
* **Document order is reading order** — already ascending in both the fragment and the page. Do **not** sort by `data-num`: it is a display number, and sorting on it would reorder any novel where it repeats or skips. `giatocvuongtai.py:97` sorts defensively because its API is unordered; sto9's is not.

#### Parser choice: BeautifulSoup + lxml, and the unclosed `<li>`

The fragment's `<li>` elements are never closed. That is the one place where "just use a regex" is tempting and where it must be resisted: the dominant convention in this package is BeautifulSoup with the `lxml` tree builder (`xbanxia.py:35`, `ixdzs.py:52`, `shuba69.py:120`, `bookqq.py:299`; `lxml>=5.0` is a hard dependency in `pyproject.toml`), and **I measured that lxml recovers this markup correctly**: 187 anchors, zero nested `<li>`, no dropped entries. Selecting `li[data-num] a[href]` rather than a bare `a[href]` additionally immunises the parse against the `<div class="clear">` trailer and any wrapper the CMS adds. No regex, no `html.parser`, no special handling.

### 2.4 Metadata — OpenGraph on the detail page, with the placeholder cover treated as absent

**Recommendation: `fetch_metadata` always fetches `detail_url(url)`,** i.e. `/book/{id}.html`, whichever form it was handed. The TOC page has **zero** `og:` tags (measured) and its `<meta name="description">` is SEO boilerplate about "the chapter directory", not the blurb. Reading metadata off the pasted URL would therefore produce a title-only novel whenever the user pasted the (very common) `index.html` form.

Fields, via the `og()` closure from `ixdzs.py:54-56` / `shuba69.py:101-103`:

| Field | Source | Fallback |
|---|---|---|
| `title` | `og:novel:book_name` → `og:title` | `div.booknav2 h1` text; then `ScrapeError("Novel title not found — page layout may have changed")` |
| `author` | `og:novel:author` | the `作者：` row of `div.booknav2 p`, split on the colon (`xbanxia.py:44-48`'s shape, reusing its `_COLONS = ":："` idea); else `""` |
| `description` | `og:description` | `""` |
| `cover_url` | `og:image`, **unless placeholder** (below) | `""` |
| `url` | `read_url(url)` — §2.2 | — |
| `site` | `self.name` | — |
| `source_lang` | `"zh"`, **written explicitly** | — |

**Title is the only required field.** Everything else degrades to `""` — the family convention (`xbanxia.py:53-60`, `ixdzs.py:61-68`, `bookqq.py:306-316`), and the GUI renders blanks fine.

**The cover placeholder.** `og:image` on a coverless novel is `https://sto9.com/modules/article/images/nocover.jpg` — the reference novel has exactly this. Storing it would put a grey "no cover" JPEG into the EPUB and onto the video thumbnail, where it looks like a *broken* cover rather than an absent one, and the downstream code already has correct behaviour for `cover_url == ""`. Detect it by **path suffix**, not full-string equality:

```python
_PLACEHOLDER_COVER = "/images/nocover.jpg"
if cover.endswith(_PLACEHOLDER_COVER): cover = ""
```

Suffix matching survives a scheme change, a CDN host, or a `?v=2` cache-buster — and matching on the full URL would fail on any of those, which is exactly the kind of brittleness that ships unnoticed because *most* novels have real covers.

**`description` needs no unescaping.** `shuba69.py:83-90` has a `_clean_description` because 69shuba's `og:description` carries literal `<br />` *text* inside the attribute value. sto9's does not (measured: the reference blurb is plain prose with full-width brackets). Do **not** copy that helper speculatively; a `.strip()` is the whole job.

**`source_lang = "zh"` despite the content being Traditional.** There is no script field on `NovelMeta` and adding one is out of scope. The two places script actually matters are already handled: the translators pass `source=project.meta.source_lang` straight to the engine (`workers.py:270`), and every engine accepts Traditional under `zh`; and the name extractor converts to Simplified before its dictionary lookup (`translators/names.py:77-85`, `OpenCC("t2s")`). Write the `"zh"` explicitly rather than inheriting the dataclass default (`models.py:42`), for the reason `bookqq.py:313-315` gives: a future default change must not silently reclassify this adapter.

**Do not parse `var bookinfo = {...}`.** It is single-quoted JS, not JSON; it carries only `articlename`/`author`/`sortName`, all of which the og: tags already provide more reliably; and reading it would mean shipping a second, weaker parser for zero new fields. Mention it in the module docstring as a deliberately-unused alternative so nobody rediscovers it as a "fix".

### 2.5 Chapter text — the 69shuba shape, with a named strip list

**Recommendation: `parse_chapter(markup, title, url)`, pure, taking markup and never a URL** (the split `shuba69.py:16-18` documents and `bookqq.py:398` follows), with this exact algorithm:

```python
SEL_CONTENT = "div.txtnav"
SEL_CHROME  = "h1, div.txtright, div.txtad, div.txtcenter, script, style, ins"
```

1. `container = soup.select_one(SEL_CONTENT)`; `None` → `ScrapeError("Chapter content not found — page layout may have changed", url)`.
2. `for el in container.select(SEL_CHROME): el.decompose()`.
3. `lines = [l.strip() for l in container.get_text("\n").split("\n") if l.strip()]`.
4. Drop at most one leading line if it equals the chapter title after whitespace normalisation.
5. `if not lines: raise ScrapeError("Chapter content is empty", url)`.
6. `return "\n\n".join(lines)`.

**Measured end-to-end on the saved chapter sample: 105 paragraphs, 0 residual `&emsp;`, no nav or ad text, no recommended-books leakage.**

Each detail, and why:

* **`div.txtnav` is the container, and container-scoping is sufficient.** Everything after it — `div.page1` (上一章/書籤/目錄/下一章), `div#baocuo`, `div#tuijian`, `div.yuedutuijian` (a list of other novels) — is a **sibling**, not a child. Verified: none of it appears in the extracted lines. No page-level chrome removal is needed, unlike `bookqq.is_paywalled` which has to reason about the whole page.
* **The strip list is named, never blanket.** `xbanxia.py:79` decomposes `span, div, script, ins` wholesale; `shuba69.py:37-39` explicitly documents why that is a loaded gun — the day the CMS wraps a paragraph in a `<div>`, a blanket rule eats it silently. Name the four known containers. `script`/`style`/`ins` are the defensive tail every adapter in this family carries.
* **`div.txtcenter` is the interesting one: it appears 4–5× *mid-prose*, not just at the end.** Decompose (not `unwrap`, not `extract`-and-keep-text) — it contains only a `<script>loadAdv(...)</script>` ad slot. Measured, it always sits at the *end* of a paragraph run, immediately before a `<br />`, so removing it never joins two sentences. The residual risk if the CMS ever moves one mid-sentence is a spurious paragraph break — cosmetic, not data loss, and strictly better than leaking `loadAdv(10,0)` into the prose.
* **`h1` is decomposed rather than compared away.** Inside `div.txtnav` the `<h1>` *is* the chapter heading by construction (measured identical on ch. 1, 169, 187), so removing it structurally is more reliable than a string comparison. `shuba69.py:40` does the same for `h1.hide720`.
* **The tolerant title-drop in step 4 stays anyway**, as belt-and-braces for the day the CMS drops the `<h1>` and repeats the title as a plain text run. It must drop **at most one** line and **only** on a normalised match — `shuba69.py:147-153` states the reasoning and it applies unchanged: *a duplicated heading is cosmetic; an eaten opening line is invisible data loss, so bias hard to under-strip*. Normalisation is whitespace-only (collapse internal runs, strip ends), used **only** for the comparison and never for the stored title — the TOC title carries a trailing space and the `<h1>` does not.
* **`&emsp;&emsp;` needs no special handling at all.** `&emsp;` decodes to U+2003 EM SPACE, which is Unicode category Zs, so `str.isspace()` is `True` and plain `.strip()` removes the indents. Measured: zero residual em-spaces across 105 paragraphs. **Do not write a `replace(" ", "")`** — it would also strip legitimate em-spaces from *inside* a line, where the CMS occasionally uses them for alignment inside dialogue.
* **Whitespace normalisation is `.strip()` only.** No `re.sub(r"\s+", " ", line)` — CJK prose contains meaningful full-width spaces and stripping only the ends is what every sibling adapter does (`xbanxia.py:82`, `shuba69.py:145`).
* **The stray `<br /><br />  <br />` runs collapse for free**, because step 3 drops empty lines after stripping.
* **No pagination.** Recon checked chapters 1, 169 and 187: there is no `_2.html` and no next-page link inside `txtnav`. Do not build a pager. The 上一章/下一章 links in `div.page1` are *navigation between chapters*, and the last chapter's 下一章 points at the `/txt/{id}/end.html` sentinel — which `fetch_chapter` never follows because it only ever fetches `ref.url`.
* **One accepted artifact:** the reference chapter ends with a short site note in parentheses inside the prose flow, structurally indistinguishable from a paragraph. It is kept. Do **not** add a blocklist of Chinese phrases — a content-based filter is a rule that will eventually eat a real line of a novel, and the cost of keeping it is one extra sentence at the end of a chapter.

#### Which error, and why raising matters

| Case | Error | Why |
|---|---|---|
| `div.txtnav` missing | `ScrapeError("Chapter content not found — page layout may have changed", url)` | family wording (`xbanxia.py:76`, `ixdzs.py:100`, `shuba69.py:139`, `bookqq.py:414`); says "the site changed", which is the true diagnosis |
| container present, zero lines after stripping | `ScrapeError("Chapter content is empty", url)` | a **different** message on purpose — the two failures need different fixes, and a shared message would send whoever debugs it to the wrong place |
| — | **never** `ObfuscatedContentError` | `base.py:139-142` and `errors.py:16-17` reserve it for content that cannot be *decoded*. sto9 serves plain UTF-8 with a correct charset header; nothing here is obfuscated, and misusing it would mislead the next person |
| — | **never** `RateLimitedError` | `workers.py:2086-2093` would retry 8× at 60 s each — 8 minutes per chapter for a page that will never parse |
| — | **never** return `""` | ← the important one |

**Returning `""` is the silent failure.** `save_content(idx, "")` leaves `content = ''`, and `pending_download` keys **only** on empty content (`project.py:362`). So the chapter is re-queued forever: every "Tải các chương" refetches it, the progress bar never shrinks, and because `mark_error` was never called the row shows **no error at all**. The family-wide `if not lines: raise` (`ixdzs.py:106-107`, `xbanxia.py:86-87`, `shuba69.py:156-157`, `bookqq.py:421-422`) is a convention for this reason, not a formality.

### 2.6 Request budget — three per scan, one per chapter, and why that is right

| Call | Requests | Which |
|---|---|---|
| `fetch_metadata` | 1 | `/book/{id}.html` |
| `fetch_chapter_list` | 2 | `/book/{id}/index.html`, then `/ajax_novels/chapterlist/{id}.html` |
| `fetch_chapter` | 1 | `ref.url` |

A scan is 3 requests ≈ 4.5 s at the default 1.5 s delay (`config.py` `DEFAULT_REQUEST_DELAY`). `bookqq` manages 1 by caching one page that carries everything; sto9 physically cannot, and the alternatives are worse:

* **Drop the detail-page fetch** → lose author, blurb and cover entirely (0 og: tags on the TOC page, measured). Unacceptable.
* **Drop the TOC-page fetch** → lose `stated_total`, i.e. lose the ability to distinguish "the ajax list is complete" from "the ajax list is short", and lose the only safe fallback branch. That is trading the feature's one real safety property for 1.5 s once per novel.

**Cache the detail page per instance** anyway (`self._detail: tuple[str, str] | None`, keyed by book id — `bookqq.py:444-454` / `tieuthuyetmang`'s shape), so that a future field that could come from either page costs nothing. **Per-instance, never module-level:** the process is long-lived and the user switches novels in the GUI; a module cache would serve novel A's markup to novel B. `bookqq.py:441-445` makes the same point.

**No delay floor.** `AudioDownloadWorker` is the only place in the codebase that imposes one (`workers.py:1134`, `max(delay, 2.0)`), and nothing observed on sto9 suggests throttling: recon got 200s on every URL with a plain `curl`. If a live run ever shows throttling, the correct fix is to map the throttle signal to `RateLimitedError` — which `_fetch_with_backoff` already handles (`workers.py:2086-2093`) — not to slow everyone down globally.

**No cookies, no browser, no `close()` override.** Cloudflare is present but issues no challenge (recon; plain `curl` with a desktop UA, which `HttpClient` already sends, `base.py:35`). The invisible `/cdn-cgi/content?id=…` bait link is the first `<body>` child of every page — the adapter never follows links, so it is inert, but say so in the module docstring so nobody "helpfully" adds link-following later. `close()` stays the inherited no-op (`base.py:120-127`): there is nothing to release.

### 2.7 `content_is_translated` stays `False`

Inherited from `base.py:101`, with a comment saying why — this is a Chinese-source adapter in the `ixdzs`/`xbanxia`/`shuba69`/`bookqq` family. If it were flipped, `DownloadWorker` (`workers.py:2131`) would write the Chinese into `translated` and mark the chapter already-translated, so `pending_translation` would skip it and the user's Vietnamese output would be Chinese. A one-line test pins it (`test_scrapers_bookqq.py:276-279`).

### 2.8 GUI / registry / README touchpoints — exactly two, plus one test

* **`src/noveltrans/scrapers/__init__.py:25-33`** — add `sto9` to the `_import_adapters` tuple (alphabetically, after `shuba69`). **This is the one line whose omission ships silently:** without it the class never registers, `adapter_for_url` returns `None`, and every sto9 URL reports *"Chưa hỗ trợ trang web này"* (`workers.py:102-104`). `test_scrapers_bookqq.py:271-274` is the guard; mirror it verbatim.
* **`README.md:54-61`** — one row on the Chinese-source table (§6).
* **No GUI change.** Verified in §0: nothing in `src/noveltrans/gui/` enumerates `ADAPTERS` or reads `SiteAdapter.display_name`; site support is entirely expressed by `adapter_for_url` returning non-`None`. There is no supported-sites picker, no combo box, no settings entry (sto9 needs no cookie, so `config.SITE_COOKIES` is untouched).
* **No `ScanWorker` change** — §2.2 walks the three paste forms through the existing `workers.py:122` and all three reuse the project. Add the *test* (§5), not the code.

## 4. What breaks if this is done naively

### 4.1 Scraping the TOC page — the headline trap

Covered in §2.3. Restated as the one-line summary a reviewer needs: **`/book/{id}/index.html` returns 36 of 187 chapters and looks completely normal doing it.** An adapter written against that page passes every smoke test a developer would think to run (metadata correct, TOC non-empty, chapter 1 downloads, chapter 36 downloads) and loses 151 chapters silently. This is the reason the ajax fragment is primary and the reason a known-truncated page is a hard error rather than a fallback.

### 4.2 Using `data-num` as `ChapterRef.index`

It is a display number. On the truncated page it jumps 15 → 167, so using it directly would produce a TOC with a 151-row hole; recon also warns it can be non-contiguous in general. `enumerate()` is the only correct source for `index` (`models.py:117`, `giatocvuongtai.py:110`).

### 4.3 Regexing the ajax fragment because the `<li>`s are unclosed

Tempting and unnecessary — measured, lxml recovers it into 187 flat `<li>`s. A regex over `<li data-num="(\d+)"><a\s+target="_blank" href="([^"]+)">([^<]*)</a>` additionally hard-codes the double space after `<a`, the attribute order and the absence of any other attribute, all of which are CMS output details that will change without warning.

### 4.4 Blanket-decomposing `<div>` inside `div.txtnav`

`xbanxia.py:79` does this; `shuba69.py:37-39` documents why it must not be copied. Here it happens to work today, because the only `<div>`s inside `txtnav` are the four ad/share slots — which is precisely what makes it dangerous: it is a rule that is correct by luck and will eat a paragraph the day the CMS wraps one. Name the four.

### 4.5 Returning `""` from `fetch_chapter`

The permanent-requeue failure, spelled out in §2.5. Pinned by `test_an_empty_container_raises_rather_than_returning_empty`.

### 4.6 Echoing the pasted URL into `NovelMeta.url`

Three paste forms → three projects for one novel, each with its own translation progress and its own video settings. §2.2.

### 4.7 Reading metadata off whichever page the user pasted

Zero `og:` tags on the TOC page (measured) → a novel with a title and nothing else, for the *most common* paste form. §2.4.

### 4.8 Storing the placeholder cover

A grey "no cover" JPEG rendered into the EPUB and the video thumbnail reads as a broken cover, not an absent one. §2.4.

### 4.9 A module-level page cache

Long-lived process, user switches novels, novel A's markup answers novel B's questions. Instance attributes only (`bookqq.py:441-445`).

### 4.10 Assuming a mirror host

`ORIGIN` is fixed (§2.2). If someone later widens `url_patterns` to a mirror without also revisiting `read_url`, every mirror URL would canonicalise to `sto9.com` — which is arguably *right* (one project per novel) but must be a decision, not an accident. The comment on `ORIGIN` is what makes it one.

## 5. Testing strategy

Saved fixtures only. **No test in the default suite makes a network request** — the discipline every scraper test module in this repo keeps, using `responses` for adapter wiring and `load_fixture` (`conftest.py:79-80`) for the pure layer.

### `TestUrlDerivation`

* `book_id` reads all three forms: `/book/13908.html`, `/book/13908/index.html`, `/txt/13908/7671958.html`.
* `book_id` raises `ScrapeError` on a non-book URL (`https://sto9.com/novels/class/2_1.html`).
* `read_url` maps **all three** forms to the identical canonical string. *The §2.2 property.*
* `detail_url` and `chapterlist_url` likewise.
* `read_url("http://www.sto9.com/book/13908.html")` still yields the canonical `https://sto9.com/...` — pins the fixed-`ORIGIN` decision.

### `TestMetadata` (against `book.html`)

* title / author / description come off the og: tags; the Traditional-Chinese title round-trips unmangled (the encoding guard).
* `source_lang == "zh"`, `site == "sto9"`.
* **`meta.url` is the canonical read URL from all three paste forms.**
* **`cover_url == ""` for the placeholder** (`book.html`), and is the real URL for `book_cover.html`. *Both directions, because a one-directional test passes with the check deleted.*
* A cache-busted placeholder (`.../nocover.jpg?v=2`)… is **not** stripped by a suffix test — assert the known-limitation explicitly so the suffix rule is a documented choice rather than an assumed one.
* og: tags absent but `div.booknav2 h1` present → title still found (the DOM fallback).
* No title anywhere → `ScrapeError("Novel title not found")`.

### `TestChapterList` (pure, against the fixtures)

* `chapterlist.html` yields exactly 20 refs despite the unclosed `<li>`s. **The lxml-recovery property.**
* `index` is dense 0-based `0..19` and independent of `data-num`.
* Titles have the trailing space stripped and are otherwise **byte-identical** to the anchor text — no colon or width normalisation.
* Order is document order, ascending.
* `stated_total(index.html) == 20`, from `#loadmore`.
* `stated_total` still returns 20 when `#loadmore` is deleted, via `max(data-num)`. **The two-signal property; delete either signal and this fails.**
* `stated_total(index_full.html) is None` (no `#loadmore`) — and `max(data-num) == len(refs)`, so `truncated` is `False`.
* `parse_chapter_list("<html></html>", url)` → `ScrapeError("Chapter list not found")`.

### `TestChapterContent` (against `chapter.html`)

* Extracts the expected paragraph count, joined by `\n\n`.
* **No ad text.** Assert `"loadAdv" not in body` and that the mid-prose `div.txtcenter` content is gone — *and* assert the paragraphs on either side of a removed ad are both present, so decomposing did not eat prose.
* **No sibling chrome.** `"下一章"`, `"目錄"` and a recommended-novel title from `div.yuedutuijian` are all absent.
* **No ` `** anywhere in the output, without the code containing an em-space replace. *Pins that `.strip()` is doing the job.*
* The `<h1>` title is not the first line.
* Title de-dup drops **at most one** line: a fixture whose first prose line coincidentally repeats the title keeps exactly one copy of the following paragraph.
* The stray `<br /><br />  <br />` produces no empty paragraph.
* Missing `div.txtnav` → `ScrapeError("content not found")`.
* `chapter_empty.html` (container present, only chrome inside) → `ScrapeError("content is empty")` — **a different message from the previous case**, asserted as different.
* `ScrapeError` is raised, **not** `ObfuscatedContentError` and **not** `RateLimitedError` — subclass assertions in the shape of `test_scrapers_bookqq.py:234-239`, because `RateLimitedError` would cost 8 minutes of retries per unparseable chapter.

### `TestRegistry`

* `matches` accepts `/book/13908.html`, `/book/13908/index.html`, `/txt/13908/7671958.html`.
* `matches` rejects `https://sto9.com/`, `https://sto9.com/novels/class/2_1.html`, and **`https://sto9.com/txt/13908/end.html`** (the sentinel).
* **`matches` rejects `https://www.69shuba.com/txt/59024/12345`** — the host-anchoring property from §2.1. Without it this adapter silently steals 69shuba's chapter URLs.
* `adapter_for_url` resolves an sto9 URL to `Sto9Adapter`, and a 69shuba URL still resolves to `Shuba69Adapter`.
* `Sto9Adapter in ADAPTERS` — the forgotten-import guard (`test_scrapers_bookqq.py:271-274`).
* `content_is_translated is False` (§2.7).

### `TestAdapterWiring` (`@responses.activate`) — where the §2.3 truth table is proven

* **Happy path:** register the TOC page and the fragment; `fetch_chapter_list` returns 20 refs and issues exactly 2 requests, the second being the fragment URL.
* **Metadata from a chapter URL** fetches `/book/13908.html`, not the pasted URL.
* **Metadata + chapter list from a chapter URL** together issue 3 requests and no more (the detail-page cache holds).
* **★ The load-bearing test — a truncated page plus a dead fragment raises.** Register the TOC page; register the fragment as **404**. Assert `ScrapeError`, assert the message names both counts, and — the part that matters — **assert no `ChapterRef` was returned**. This is the test that fails if someone "improves" the adapter by falling back to the page.
* **Short fragment warns but is used.** Fragment with 12 entries against a stated 20 → 12 refs returned *and* a `_status` line containing both numbers.
* **The safe fallback works.** `index_full.html` (no `#loadmore`, 4 entries) plus a 404 fragment → 4 refs and a `_status` note. *The one branch where a page fallback is legitimate.*
* **Both empty raises** `ScrapeError("Chapter list not found")`.
* **A chapter fetches and extracts** end to end through `fetch_chapter`.

### `TestLive` (`@pytest.mark.live`, deselected by default)

The drift detector, modelled on `test_scrapers_bookqq.py:341-365`:

* Metadata for 13908: non-empty title, `source_lang == "zh"`, `meta.url` is the canonical read URL.

* The ref count equals the `#loadmore` stated total on the live page.
* Chapter 1 and the **last** chapter both fetch > 1000 chars, contain no `loadAdv`, and contain no `下一章`. Checking the last chapter matters: it is the one whose 下一章 points at the `end.html` sentinel.

## 7. Risks and genuinely open items

1. **The ajax fragment is an undocumented internal endpoint.** It is the only complete source of the TOC, so if the site removes or renames it, sto9 scanning stops working for long novels — by design, with a clear error, rather than by silently producing a 36-chapter novel. Mitigations: two independent truncation signals (§2.3), the `TestLive` count assertion as the drift detector, and a module docstring that names `LoadMore()` in `index.html` as where to re-derive the URL. **Accepted, deliberately, because the alternative is corruption.**
2. **The "safe fallback" branch is inferring.** Nobody has observed a short sto9 novel, so "a novel with fewer than ~35 chapters ships no `#loadmore` and a complete page list" is reasoning from the CMS's behaviour, not a measurement. The branch is written so that *being wrong about it is harmless*: it only fires when `stated_total` gives no evidence of truncation, and if the assumption is wrong the two signals disagree and the hard-error branch takes over instead. Worth confirming on a short novel during the first live run.
3. **`data-num` contiguity on the fragment.** Recon warns it "can be non-contiguous". We never rely on it for `index`, only for the `max()` truncation signal — where a non-contiguous sequence makes the signal *conservative* (over-estimates the total), which errs toward the hard-error branch. That is the right direction, but it means a novel with gappy numbering could produce a spurious "short list" warning. Cosmetic; noted.
4. **Cloudflare could start challenging.** Currently it does not (recon: plain `curl` 200s everywhere). If it ever does, the response is the `shuba69` route — `cf_browser.BrowserSession` behind a `_get_html` seam — which is why §2.5 keeps every parser pure and markup-taking: adopting a browser would be a change to `fetch_*` only, with the entire parsing surface and its tests untouched. Do **not** pre-build that seam now.
5. **Mid-prose `div.txtcenter`.** Removing them is measured safe on chapters 1, 169 and 187, where each sits at the end of a paragraph run. If the CMS ever places one mid-sentence, the result is a spurious paragraph break — cosmetic, visible, and strictly better than leaking ad script text. Not worth engineering against now.
6. **Traditional vs. Simplified.** `source_lang="zh"` with no script field. The translators pass it straight through and the name extractor already `t2s`-converts (`translators/names.py:77-85`), so nothing is broken — but if a user ever wants Simplified output, that is a whole-app feature (a script field on `NovelMeta` plus an OpenCC pass), not an adapter change. Out of scope; recorded.
7. **The site note at the end of chapters.** Kept as prose (§2.5). A content-based filter would eventually eat a real line; this is the honest trade.
8. **Nothing shared is edited.** No `SiteAdapter` change, no worker change, no model change, no config change. The blast radius of this feature is one new module, one import line, one README row and one new test module — so if sto9 turns out to be wrong about something, nothing else in the app is affected.
