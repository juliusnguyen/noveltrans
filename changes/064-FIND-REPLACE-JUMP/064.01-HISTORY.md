## [IMPL] Double-click a match to jump to it — 2026-08-26

Implemented `064.01-INITIAL-PLAN.md` in full. Nothing deferred.

### The decision that shaped everything: modal → modeless

`FindReplaceDialog`'s docstring named modality as a **load-bearing invariant**: being
modal is what stopped a replace-all racing the tab's save-on-blur handler. "Jump to the
match so I can fix it by hand" cannot coexist with that — a modal dialog blocks the very
editing the feature exists to enable.

The alternative was jump-*and-close*, which keeps modality. Rejected on the screenshot in
the request: 63 matches in 63 chapters, and jump-and-close means re-opening and
re-previewing for each one.

So the invariant had to be replaced rather than kept. `_is_stale()` re-reads every scanned
field before `_apply` writes and refuses on any drift ("Nội dung đã thay đổi kể từ lần xem
trước"). This is **strictly stronger** than what modality gave: modality only blocked the
*pane* from being edited, and never protected against a rewrite worker or another tab
writing the same rows.

### Three holes that only exist once the dialog is modeless

Each one is a bug that could not happen before, found by asking what `exec()` had been
hiding:

1. **`_preview_idx` was frozen at construction.** "Chương hiện tại" would keep meaning the
   chapter that was open when the dialog was launched. `set_current_chapter`, driven from
   `_on_row_selected`, keeps it honest.
2. **A batch run could start underneath it** — the button is disabled during a run, but a
   dialog already up stays up. Closed from both `_start_translate` and `_start_rewrite`.
3. **Switching novels closes the project handle** the dialog is holding; its next scan
   would hit a closed sqlite connection. Closed first thing in `_on_project_selected`.

### The subtle one: don't clear the list you're walking

`set_current_chapter` drops the cached preview when the scope is "Chương hiện tại", since
the preview then describes a different chapter. It must **not** do that under "Tất cả
chương" — and the jump changes the open chapter on *every* double-click, so an
unconditional invalidate would have the feature wipe its own result list on first use.
Pinned by `test_moving_chapters_keeps_an_all_scope_preview`.

### Re-find, don't seek an offset

The scan counts inside a raw field; the panes render `f"{title}\n\n{body}"`. Carrying a
character offset across that would land in the wrong place for a body match and in the
wrong *text* for a title match. `_jump_to_match` re-finds the search string in the pane
with `QPlainTextEdit.find` instead — which is also why the search text and case flag ride
along on the signal.

Repeat double-clicks on the same row search on from the cursor and wrap at the end, so a
chapter reading "2 khớp" has both hits reachable.

leave the button convinced a dialog is still up.
