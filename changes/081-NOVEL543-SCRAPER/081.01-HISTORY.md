# 081 — novel543.com scraper — history

## [PLAN] 081.01-INITIAL-PLAN — 2026-09-06

Generated plan: `081.01-INITIAL-PLAN.md`

Preceded by live reconnaissance of novel543.com through the repo's own
`cf_browser.BrowserSession` and `curl` — 9 real page fetches across the detail page,
`/dir` and six chapter pages. Everything in §1 of the plan is measured, not inferred.

Three findings shaped the whole plan:

1. **Cloudflare on every host and every UA** (`cf-mitigated: challenge`, 403), including
   the iPhone UA that unlocks bqg5, and there is no `m.` host. So this is the
   twkan/69shuba transport shape — `HttpClient` cannot read the site at all.
2. **novel543 runs the same CMS as timotxt** (`div.chaplist ul.all`, `#chapterWarp
   div.content`, `div.intro.is-hidden-mobile`, the unclassed trailing 溫馨提示 `<div>`,
   the `i<N>.<host>/thumb/120x160/` cover CDN). That was verified against
   `timotxt.py:112-116` after the plan was drafted. It makes the parsing layer largely a
   port rather than a new design, and it also means the two modules will sit next to each
   other looking alike — which is why the plan spells out the three places novel543 must
   NOT follow timotxt.
3. **Chapters are paginated, and only some of them.** The `(N/M)` suffix on the chapter
   `<h1>` is the authoritative page count; 下一章 chaining runs off the end of a chapter.
   This is the first adapter in the repo that fetches more than one page per chapter, so
   a full download of the reference novel is ~800 browser navigations.

Two traps that would have been inherited by copying a sibling module:

- `og:novel:latest_chapter_url` advertises `/<bid>/439.html`, which is a **404** — the
  real address is `/<bid>/8096_439.html`. `timotxt.stated_total` reads exactly that tag
  and `bqg5.fetch_chapter_list` fetches it as a cross-check.
- `/dir` carries a variable-length duplicate "newest chapters" block (12 entries on the
  probe) ahead of the real ascending list, distinguished only by the `all` class.

The plan's load-bearing guard is positional contiguity: chapter URLs embed the reading
position, so `positions == [1 … N]` is a proof that the list is a dense ascending prefix.
Every realistic degradation breaks it, and `replace_toc` makes a mis-ordered list
permanent, so the adapter refuses rather than saving one.

## [IMPL] novel543.com adapter — 2026-09-06

Implemented to the plan. Three things the plan flagged as open questions were measured
during implementation, and two of them changed the code.

### The plan held up

`timotxt.py` really is the same CMS — verified against `timotxt.py:112-116` — so the
parsing layer is close to a port. The contiguity guard, the `ul.all` container selection,
the direct-child `<p>` rule and the `div.intro`-over-meta-description decision all came
across unchanged and all validated against the live site on the first run: 439 refs,
contiguous 1…439, unique, `stated_total` 439 agreeing exactly, the 12-entry duplicate
block excluded, and no 溫馨提示 / 下一章 / `(N/M)` leakage into any body.

### What changed: the site needs a slower delay than the app's default

The live tests failed on the first run, differently each time — the signature of
rate-limiting, not a code bug. Measured it directly, walking 14 consecutive chapter pages
at two delays:

| delay | result |
|---|---|
| 1.5 s (`DEFAULT_REQUEST_DELAY`) | 12/14 ok, **2 hard failures**, 3 challenge stalls — one of 28.7 s, past `cf_browser`'s 20 s settle deadline |
| 3.0 s | **14/14 ok**, 0 failures, 1 stall of 6.5 s |

twkan self-heals at 1.5 s; novel543 does not. The plan's risk #7 predicted this exposure
and said the lever would be the configured delay — but the app's default *is* 1.5 s, so
leaving it to the user meant a 439-chapter novel stranding a double-digit percentage of
chapters as errors out of the box. Added `_MIN_DELAY_SECONDS = 3.0` as a floor under the
configured value (`max()`, never assignment — a user who deliberately set a slower delay
keeps it), with the measurements in the constant's comment, plus a README note so the
slowness reads as deliberate rather than as a hang.

### What changed: a pre-existing race in `cf_browser`, not in this adapter

The CLI smoke run failed with `Page.content: Unable to retrieve content because the page
is navigating and changing the content`, thrown from inside `_settle_challenge` — whose
own docstring says "Never raises."

`page.content()` throws while the document is being replaced, which is *precisely* the
event that loop exists to wait for. So a challenge clearing itself at the wrong instant
aborted the whole download on the moment of success. This is not novel543-specific:
**twkan and 69shuba are exposed to the same race**, and novel543 only surfaces it because
it challenges often enough to hit it.

Fixed in `cf_browser._settle_challenge`: a poll that throws now means "not settled yet",
not "failed". `_settle_challenge` also now takes the caller's already-read challenge
markup as its fallback, so a loop where *every* poll throws still returns something that
`looks_like_challenge`, and `get_html` raises its proper refusal rather than handing back
empty markup that a parser would report as "layout may have changed". Both new tests were
confirmed to fail against the unpatched function before the fix was kept.

### What changed: the sub-page self-check is load-bearing, not defensive

The plan listed three possible behaviours for an out-of-range sub-page and noted all three
were handled. Measured, it is the worst one — **the site serves page 1 again, with a 200
and no error**:

    /8096_120_2.html  (chapter 120 is unpaginated)  -> page 1 of ch.120, no suffix
    /8096_1_3.html    (chapter 1 has only 2 pages)  -> page 1 of ch.1, still "(1/2)"

Both parse perfectly as prose. So any over-estimate of the page count would duplicate a
chapter's opening into its own middle, silently, and `replace_toc` would preserve it. The
`(k/M)` self-check is the only thing that distinguishes them; the comment was upgraded
from hypothetical to measured and both shapes now have a test.

### Also settled

- **Open question #4 (trailing-slash detail page).** It serves the detail page directly —
  `_detail_page` fetches `read_url(url)` and the live metadata test passes. No
  `detail_url()` split needed, so `read_url` stays both identity and fetch target.
- **Open question #1 (is M ever > 2?).** Still unobserved; the code reads M and loops
  rather than assuming 2, and `test_the_pagination_distribution_has_not_flipped` is the
  live canary.
- A test bug during the run surfaced something worth keeping: the detail page's 開始閱讀
  button is a chapter-shaped anchor, so a flat scrape of *that* page yields a plausible
  one-chapter novel — and `[1]` is contiguous, so the guard could not catch it either.
  `fetch_chapter_list` fetching `/dir` and nothing else is what makes it unreachable, and
  `test_the_detail_pages_start_reading_button_is_chapter_shaped` records why.
