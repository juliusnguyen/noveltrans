# 068.01 — Initial plan: vertical novel bar, hover names, one naming rule

> Every measurement in this plan was taken from offscreen Qt experiments against the real
> theme, not inferred from documentation. Where a number appears, it was observed.

## Summary

The outer workspace bar becomes a left-hand column of full-width rows with **horizontal**
text, driven by a `WorkspaceTabBar(QTabBar)` subclass that transposes `tabSizeHint` and
repaints each tab as if it were a North tab — keeping the entire `QTabWidget` API
(`addTab`, `setTabText`, `setTabToolTip`, `indexOf`, `removeTab`, `setCurrentIndex`,
`setTabButton`) intact, so `main_window.py` and every existing test keep working. The same
bar object serves both orientations via a `vertical` flag, so the setting flips live with
all tabs, labels and the current index preserved (verified). Two things the prompt did not
anticipate must be solved: **Qt gives corner widgets zero geometry for West/East tab
positions**, so the ⚙/＋ buttons must be relocated in vertical mode; and **`QTabBar.initStyleOption`
pre-elides the label against the *vertical* text rect**, so a naive custom `paintEvent`
renders nothing but "…". `_MAX_TAB_LABEL` is dropped in favour of elision plus a full-name
tooltip, and the tab label is finally wired to `novel_label()` — which Part 1 did not do.

## Flags: things in the framing that turn out to be wrong or incomplete

1. **The tab label does not use `novel_label()` yet.** `ScrapeTab.current_title()`
   (`src/noveltrans/gui/tab_scrape.py:685-687`) still returns `self.project.meta.title` —
   the bare original. `Workspace.title_changed` (`workspace.py:27`, emitted at
   `workspace.py:92`) carries that string to `MainWindow._set_ws_title`. Part 1 changed the
   picker and the header only. Step 4 fixes this; without it the whole naming decision is
   invisible on the bar.
2. **Corner widgets are dead on a vertical bar.** Measured with plain Fusion, no custom
   code: `TabPosition.West` → `settings_button.geometry() == QRect(0,0,0,0)` while
   `isVisible()` is still `True` and `sizeHint()` is `80x25`. Same for East; North/South are
   fine. Qt reserves the vertical space (the bar starts at y=25) but never sizes the
   widgets. So in vertical mode the ⚙ Cài đặt and ＋ Truyện mới buttons simply vanish.
   Step 3c relocates them.
3. **`QToolButton` close-button placement transposes.** With West and a `RightSide` tab
   button, Qt computes the rect from the *transposed* tab frame. Measured, with our
   transposed size hint (tab rect `0,0,190,32`): Qt puts the button at `(86, 0, 18, 16)` —
   horizontally centred, flush with the top edge. The same option with
   `shape = RoundedNorth` yields `(171, 8, 18, 16)` — right edge, vertically centred, which
   is what we want. So the button must be positioned by us.
4. **`QProxyStyle` is not a viable fix for #3 in PySide6.** `QProxyStyle(app.style())` under
   an app-wide stylesheet segfaulted twice (exit 139) — the proxy takes ownership of the
   app's `QStyleSheetStyle`. Do not go down this road; place the button by geometry instead.
5. **The label goes stale.** `title_changed` is emitted only from
   `Workspace._on_scrape_project`. Before 068 the label was the original title, which never
   changes; now the first slot is the translation, so a novel translated *after* it was
   opened keeps showing "原文 — site.com" until the app restarts. Step 4b fixes this.
   Slightly beyond the literal ask, but without it the format is half-dead.
6. **Minor gap in Part 1's `novel_label`:** no de-duplication. If `display_title == title`
   (a plausible override) or an English-source novel where `translated_title == title`, the
   label reads `X — X — site.com`. One `if` fixes it.
7. Prompt said `_set_ws_title` is at `main_window.py:169` and `_MAX_TAB_LABEL` at line 29 —
   both correct and unchanged by Part 1. `self.workspaces` is constructed at
   `main_window.py:56-63` and **does** have `setObjectName("workspaceTabs")` (line 57).

## Design decisions

### Item 1 — text orientation: custom `QTabBar` (option b). Recommended.

| option | verdict |
|---|---|
| (a) plain `setTabPosition(West)`, rotated text | Rejected. Measured: each tab becomes 37px wide × 216px tall — a column of sideways Vietnamese. Also every `style.py` outer-tab rule (`border-bottom: none`, `border-top-*-radius`, `margin-right`, `min-width/max-width`) is interpreted in the rotated frame and reads as garbage. Zero code, unusable result. |
| (c) stylesheet-only trick | Rejected — does not exist. QSS has no tab-text rotation property; the rotation is done by the *style* in `QCommonStyle::drawControl(CE_TabBarTabLabel)` based on `option.shape`, which QSS cannot reach. |
| (d) `QListWidget` sidebar + `QStackedWidget` | Rejected. Breaks `addTab`/`setTabText`/`setTabToolTip`/`indexOf`/`removeTab`/`count`/`widget`/`currentIndex`/`setCurrentIndex`/`setCurrentWidget`/`tabBar().setTabButton`/`setCornerWidget`/`setMovable`/`setUsesScrollButtons` — all used in `main_window.py:56-76,123-175,196,249-250` — plus `main.workspaces.count()/widget(0)` in eight existing tests. An adapter shim would be ~150 lines of re-implemented `QTabWidget`. |
| **(b) `QTabBar` subclass: transposed `tabSizeHint` + `paintEvent` painting a North-shaped tab** | **Recommended.** ~55 lines, no API surface lost, no test rewrites, and the existing QSS applies almost unchanged. |

**Why (b) works — verified, not assumed.** With `apply_theme(app)` and the real
`QTabWidget#workspaceTabs` object name:

- `tabSizeHint` returning `QSize(190, fontMetrics().height() + 16)` gives tab rects
  `(0,0,190,32)`, `(0,32,190,32)`, … — a proper stacked column. Qt lays vertical-shape tabs
  along the y axis, so the transposed hint and Qt's layout axis agree; `tabAt()`, hover,
  `setMovable(True)` dragging and `setUsesScrollButtons(True)` scrolling all keep working on
  the right axis (scroll verified: after `setCurrentIndex(11)` in a 200px-tall bar,
  `tabRect(0)` becomes `(0,-215,190,32)` and `tabAt(tabRect(11).center()) == 11`).
- Painting with `opt.shape = RoundedNorth` makes `QStyleSheetStyle` render the tab from the
  *existing* `QTabWidget#workspaceTabs > QTabBar::tab` rules. Pixel-checked: the selected row
  paints `#23272f` (`SURFACE`) with `#454e5e` (`BORDER_HI`) border, unselected `#1b1e24`
  (`BG`) with `#353c49` — exactly the current theme. The QSS type selector `QTabBar` matches
  the subclass, and `QTabWidget#workspaceTabs > QTabBar` still matches because the bar's
  parent is the tab widget.

**The trap.** Qt 6's `QTabBar::initStyleOption` elides `option->text` itself using
`SE_TabBarTabText` computed with the *real* (West) shape — a ~20px-wide rect — so the option
arrives pre-elided to `"…"`. First render showed exactly 3 rows of text pixels at x≈96 (a
centred ellipsis). Fix: after overriding `shape` and `rect`, re-set `opt.text = self.tabText(i)`
and elide manually against `subElementRect(SE_TabBarTabText, opt, self)`. After the fix: text
pixels across 24 rows spanning x 16→175. **This must be in the plan or the feature ships
blank tabs.**

**Alignment note.** The style-drawn label is centred (measured: short label "Abc" spans
x 85→107 in a 190px row). Left-aligned would read better in a sidebar, but getting it means
drawing the text by hand and losing the QSS-resolved selected/hover text colours.
Recommendation: ship centred (it matches the current horizontal tabs), and treat left-align
as a follow-up if the user dislikes it.

### Item 2 — the close button

`QTabBar.ButtonPosition.RightSide` on a West bar lands **horizontally centred, flush to the
tab's top edge** (`(86,0,18,16)` in a `(0,0,190,32)` tab). The `QToolButton#tabCloseButton`
*styling* (`style.py:112-125`) is unaffected — 16×16 box, transparent, `#c0433f` on hover —
only the geometry is wrong.

Alternatives: (i) `QProxyStyle` overriding `SE_TabBarTabRightButton` — **segfaults in
PySide6** under an app stylesheet, rejected; (ii) drop the per-tab ✕ in vertical mode and
rely on ⌘W / a context menu — a real UX regression on the new default, rejected; (iii) paint
the ✕ ourselves and hit-test in `mousePressEvent` — loses QSS hover styling and adds
hit-testing code, rejected; **(iv) keep `setTabButton` and re-set the geometry ourselves —
recommended.**

Call `_layout_close_buttons()` from **`paintEvent`** (not just `tabLayoutChange()`):
scrolling calls `QTabBarPrivate::layoutWidgets` — which re-applies Qt's wrong rect — without
calling `tabLayoutChange`, but it always repaints. Verified: after scrolling to tab 11, its
button sits at `(171,145,18,16)` inside tab rect `(0,137,190,32)`. Also call it from
`tabLayoutChange()` so the geometry is right before the first paint. Setting a child's
geometry from `paintEvent` converges (the move repaints the exposed strip, the next pass is a
no-op). Clicks still work: `QTest.mouseClick` on the button fired `clicked` and a click on a
tab body still selected it.

**Text/button overlap:** with `padding-right: 8px`, the text rect ends at x=178 while the
button starts at x=171. Reserve the slot by shrinking the label rect before eliding, and
`padding-right: 26px` in the vertical QSS block. Both; belt and braces.

### Item 4 — `_MAX_TAB_LABEL = 24`: **delete it.**

Alternatives: keep 24 (chops a three-part name mid-original-title, and is redundant with
elision), bump to ~48 (an arbitrary second cap doing nothing the elide doesn't), derive from
bar width (re-implements `QFontMetrics.elidedText`).

Elision already bounds the label in both orientations, measured with the real theme:

- horizontal: a 60-char three-part label gives `tabSizeHint == 217x31` (QSS `max-width: 190px`
  applies to the contents box) and `initStyleOption` elides to
  `'Xuyên thư thành phản diện  …'`. No layout blow-up.
- vertical: our `tabSizeHint` is a fixed 190px and we elide ourselves.

So set the **full** `novel_label()` as the tab text and let elision do the visual work; the
tooltip carries the untruncated name. Replace the constant with `TAB_COLUMN_WIDTH = 190` in
`style.py` (shared with the QSS so the column width and `max-width` cannot drift).
`_MAX_TAB_LABEL` has exactly two references (`main_window.py:29,173`) and no test touches it.

### Item 5 — the naming helper: already decided and implemented; two residual items

`NovelMeta.novel_label(*, with_source=True)` (`models.py:97-121`) is in the tree: `" — ".join`
of `[display_title or translated_title]`, `[title]`, `[source_host()]`, empty parts dropped
whole, `display_title` stripped before falling through, separator ` — `. The header uses
`with_source=False` (`tab_scrape.py:634`), the picker `with_source=True` (`widgets.py:82`).
That is one function with a flag, not two functions — acceptable against the "one rule"
decision, and the reason is recorded (the header sits under the URL box).

Remaining: **wire slots 3 and 4** (tab label + tooltip, Step 4), and **de-duplicate** when
`translated == original` (flag 6).

### Item 6 — applying the setting: **live, immediately.** Verified.

`setTabPosition` can be flipped on a populated `QTabWidget` with nothing lost. Measured round
trip West → North → West on a 6-tab widget with close buttons: `count() == 6`, every
`tabText` intact, `currentIndex()` preserved, close buttons re-placed correctly by Qt in
horizontal and by us in vertical.

The one thing that must **not** happen is swapping the tab-bar *object*:
`QTabWidget.setTabBar()` replaces the bar that owns all tab metadata, so it must be called
before any tabs exist. Hence one `WorkspaceTabBar` installed at construction, with a
`set_vertical(bool)` flag that makes `tabSizeHint`/`paintEvent`/`_layout_close_buttons` fall
through to `super()` in horizontal mode. That is what makes live switching free.

Corner-widget relocation also round-trips cleanly (verified): `setCornerWidget(None, corner)`
→ `layout.insertWidget(i, button)` → `button.show()` and back, twice, with correct geometry
each time (`(0,0,41,32)` in the row, `(0,-1,41,30)` in the corner).

## Risks / out of scope

- **Offscreen ≠ on-screen.** Every measurement here is `QT_QPA_PLATFORM=offscreen` with
  Fusion + the real theme. Rounded corners, the 3px row gap, the pane seam (`left: -1px`) and
  the ✕ hover hit area need one look on a real macOS window before shipping — this is the
  default-on path.
- **Scrolled-out close buttons.** With more novels than fit, a scrolled-away tab's ✕ is moved
  off-view like Qt's own, but may overlap the scroll arrows. Same as stock Qt; worth an
  eyeball with 12+ tabs.
- **Centred label text** in a 190px column. Cheap to revisit, but revisiting means
  hand-drawing the text and re-deriving the QSS text colours.
- **`display_title` in the tab.** With the override winning slot 1, a user who set a video
  display title sees it on the tab — the first place that override becomes visible outside
  video output.
- **Out of scope:** the inner five-tab stack (`workspace.py:37-47`), the tray/menu-bar novel
  list (`gui/tray.py`), and remembering the bar width per user.
