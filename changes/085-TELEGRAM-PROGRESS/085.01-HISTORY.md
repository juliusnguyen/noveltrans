## [DECISIONS] Transport chosen before any code — 2026-09-08
Presented three options with their real trade-offs; user picked **Telegram bot**:

- **Telegram** — no server, reliable mobile push, and `editMessageText` keeps ONE message
  per job updating in place instead of a stream of notifications. The only option that can
  later answer a message sent back to it.
- **Discord webhook** — simplest setup (one URL, no token) and already in the project, but
  mobile push for your own channel is unreliable unless the message @mentions you.
- **ntfy.sh** — least work, no account, but pure notifications with no way to ask anything.

Also settled: start → live-edited progress → a NEW message on finish (so it pushes) →
immediate message on failure; the notifier must never be able to break a job (own thread,
swallow every error) and must throttle rather than fire on every `progress` tick.

Hook point identified: `gui/jobs.py`'s `JobRegistry` already carries every running job
app-wide with the signals and fields needed, so this costs zero changes at the call sites.

## [DECISIONS] Commands — 2026-09-08
User asked whether the bot could answer a request sent FROM the phone, not just push.
Answered yes (long polling; a desktop app cannot receive a webhook) and settled the command
set: **`/status` + `/pause` + `/resume`**, all read or reversible. **No `/stop`** — a mistap
on a phone must not discard hours of quota already spent; cancelling stays at the keyboard.

## [STEP] Implemented — 2026-09-08
- **`notify.py`** — pure except `TelegramClient`: credentials, `Update.authorised` (the
  security boundary), `parse_command`, all message formatting, `eta_seconds`, and
  `JobTracker`, which holds the throttle so it can be tested by moving a clock rather than
  by running timers. `urllib`, not `requests`: one less thing to be missing in a frozen build.
- **`gui/notifier.py`** — `JobNotifier` listens to `JobRegistry` and keeps every network call
  off the GUI thread. Two background threads for two different reasons: a single-worker
  `ThreadPoolExecutor` for sends (ordered, non-overlapping) and a plain **daemon** thread for
  polling, because a long poll sits inside `urlopen` for 30 s and cannot be interrupted — a
  `QThread` there would make quitting wait it out or print "destroyed while running".
  Commands cross back as a Qt signal, so a phone `/pause` runs on the GUI thread through the
  same `JobRegistry.pause` the menu-bar popup uses.
- **Config** — five keys; `telegram_update_seconds` and `telegram_announce_after` clamped.
- **Settings dialog** — token (password field), chat id with a **Lấy chat id** button that
  reads the id off the last message sent to the bot (far kinder than "visit this API URL and
  read the JSON"), and a **Gửi thử** button. Re-reads settings on close, so a new token takes
  effect without restarting.
- **`main_window`** — one notifier for the whole app (the registry is app-wide), started at
  launch, restarted after Settings, stopped in `shutdown_all`.
- **README** — setup steps, the command table, and the limits stated plainly.

### Design decisions worth keeping
- **Announce only after 60 s.** A duration threshold rather than a per-job-kind allow-list:
  new workers are covered automatically, and a 20-second export never buzzes a phone.
- **Edit one message, but send a NEW one on finish** — an edit does not push, and finishing
  is the event actually worth a notification.
- **Throttle on time AND on the line having changed.** Time alone rewrites an identical
  message for a stalled job; change alone fires on every one of a thousand progress ticks.
- **ETA from the average since the job started**, not a rolling window: chapter times swing
  from 10 s to 3 minutes on this workload, and a jittery estimate reads as broken.

## [STEP] One bot, two machines — 2026-09-08
User asked whether one bot can serve two machines (they run the app on a Mac and a PC). The
answer is not symmetric, and the code had it half right:

- **Sending is unrestricted** — any number of machines may `sendMessage`/`editMessageText`
  with one token. This already worked.
- **`getUpdates` allows exactly ONE consumer.** Two pollers get HTTP 409 and each one's poll
  knocks the other off, so commands become intermittent on BOTH machines. The code would
  have hit this and retried silently every 3 seconds forever.

Three additions:

1. **`machine_prefix` on every message** (`🖥 Mac mini · …`), so two streams in one chat are
   readable. `telegram_machine_name` defaults to this computer's name — via
   `default_machine_name()`, which exists because `platform.node()` returns the IP address
   on a DHCP macOS box (measured here: `192.168.2.8`) and naively splitting it on "." yields
   the label "192". Falls back to "Mac"/"PC".
2. **`telegram_accept_commands`** (default True) — turn it off on the second machine. It
   still reports everything; it just does not poll.
3. **409 is the one error not swallowed.** `TelegramClient.conflict` is set, and the poll
   loop stands down after sending one message explaining why, rather than fighting. Every
   other network failure keeps retrying, as before.

README gained a "Dùng một bot cho hai máy" section, including the two-bots-in-one-group
setup for anyone who wants BOTH machines to answer commands.
