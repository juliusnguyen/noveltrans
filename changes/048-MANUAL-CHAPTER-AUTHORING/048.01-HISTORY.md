The three-step flow from the prompt, working end-to-end:

1. **Tải truyện** — **✍️ Truyện tự viết** creates a novel with no source URL; **＋ Thêm
   chương** adds chapters by name, one per line.
2. **Dịch** — the `Bản gốc` pane is now editable; paste your text and it saves on blur.
3. **Nghe audio** — pick the **Bản gốc** source and generate.

### The hard part was identity, not the UI

A hand-written novel has no URL, and the obvious `url=""` is **destructive**. The project
folder is `<slug>-<sha1(meta.url)[:8]>`, so a blank URL gives every local novel the same
hash — two novels whose titles slugify alike land in the *same folder*, `mkdir(exist_ok=
True)` succeeds without a word, and the second one's chapters merge into the first one's
`chapters.db`. Separately, `Library.find_by_url("")` would match the first blank-URL
project it walked past, so a later scan could attach to someone's own writing.

So a local novel gets `site="local"` **and** `url="local://<uuid4hex>"`: `site` carries the
behaviour, the URL carries identity. `NovelMeta.is_local` checks both, so a hand-edited
`meta.json` that loses one field can't turn the novel back into something the download
path will try to fetch. `find_by_url` now refuses a blank URL outright — one line that
permanently closes that class of bug.

The `local://` scheme also means no `SiteAdapter.matches` will ever claim it, so
`adapter_for_url` returns `None` — which the download worker already treats as "nothing to
fetch". A test pins that.

### Gaps are kept; nothing renumbers

`idx` is not just a row key. It is baked into the audio filename (`{index+1:04d}-…`), the
merged part names and the YouTube upload records beside them. Renumbering after a delete
would invalidate all of them at once, so a deleted chapter leaves a permanent gap.
`plan_merge_windows` already ranges and batches by 1-based chapter number precisely so a
missing chapter can't shift later boundaries — pinned by a test that deletes a middle
chapter and checks the batches don't slide.

**One number does come back**: delete the *last* chapter and `MAX(idx)` shrinks, so the
next chapter takes its number again. Nothing remembers a trimmed tail, and giving it that
memory would mean persisting a high-water mark. It stays safe because
`ScrapeTab._delete_chapter` unlinks the deleted chapter's audio and cue sidecar, so there
is no stale take left to inherit. This was found by a test asserting the opposite — the
docstring had overclaimed, and now says what actually happens.

### Add/delete are local-only, deliberately

On a scraped novel `replace_toc` overwrites `url` and `title_source` unconditionally on
the next scan (`title_custom` protects only the *title*), so a hand-inserted row would end
up carrying the site's chapter, and a delete would silently undo itself. Refusing is the
honest answer; both the context menu and `_delete_chapter` enforce it.

### The `Bản gốc` pane mirrors the pane beside it

Same save-on-blur machinery as `Bản dịch`, same "first line is the chapter title"
convention, same "an emptied pane is an accidental clear" guard. Two different rules for
two panes sitting side by side would be a trap. Enabled for **all** projects, not just
local ones — find & replace already writes `content` project-wide, so a per-project
read-only rule would be inconsistent and would need a second code path.

Two details worth naming:

* **`edit_title` only fires on a real change.** It sets `title_custom`, which puts "Lấy
  lại tên gốc" in the context menu; calling it on every blur would offer that on chapters
  nobody renamed.
* **`edit_content` now promotes pending/error → downloaded.** Every other query already
  gates on `content != ''`, but the status column reads `status` — so a chapter whose text
  the user had just typed still said "Chưa tải" with its content plainly on screen. The
  promotion is one-way: a `translated` chapter is never demoted, or a text correction
  would re-queue it for translation.

While writing the tests it turned out `setPlainText` *clears* the modified flag rather than
setting it (verified, not assumed) — so tests that pasted with `setPlainText` passed for
the wrong reason. They now edit through the cursor, like typing. A comment in
`_load_preview` that claimed the opposite was corrected.

### Nghe audio needed no code, and works either way

Verified end-to-end: the "Bản gốc không phải tiếng Việt" warning is already gated on
`source_lang != "vi"` (the create dialog defaults to `vi`), the `counts["downloaded"] == 0`
guard passes once text is pasted, and `pending_audio(voice, use_translation=False)` gates
on `content`. Only a status-line hint was added, pointing at the **Bản gốc** radio when
there is no translation — it deliberately does *not* flip the radio, which writes a
persisted preference.

**Bonus, already implemented:** with `source_lang == target_lang == "vi"`, "Dịch tất cả"
takes `TranslateWorker._run_identity`, copying `content` → `translated` *and* filling
`meta.translated_title` — the value the video slug is keyed to. So a self-written
Vietnamese novel works with either radio button, and the video tab gets a proper title,
for free. Pinned by a test.

### No schema change

Nothing new is stored per chapter (`add_chapters` writes `url=''` into the existing NOT
NULL column) or per novel (`site`/`url` already exist). `_migrate()` is untouched and
existing projects are unaffected. That was a design constraint, not luck — it is why
`site="local"` beat a new `meta.json` boolean.

### Exporters no longer print a fake source

The three exporters printed `Nguồn: {meta.url}` unconditionally, which would have put
`local://3f9c…` into the user's own book and implied their writing came from somewhere
else. `exporters/base.source_note()` returns `""` unless the URL is http(s). The EPUB's
`set_identifier(meta.url)` stays — a uuid is a *better* unique identifier than a title.
