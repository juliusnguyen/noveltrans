# 051 — Upload into OneDrive (plan)

The prompt is one line — *"support upload into onedrive"* — and the decisions that shape it were made in conversation, not in the prompt:

* **Transport: browser automation**, the same shape as `youtube_upload.py` — a dedicated persistent Playwright profile driving the OneDrive web UI. Microsoft Graph (device-code OAuth + resumable chunked upload) was offered and declined. This plan does not re-open that; see *Known trade-offs* for the one honest paragraph it deserves.
* **Payload: the whole project folder** — `meta.json`, `chapters.db`, `exports/` including `exports/audio/` and `exports/video/<part>/` with every `.mp4` and its `.title.txt` / `.txt` / `.tags.txt` / `.jpg` / `.srt` / `.upload.json` sidecars.
* **Destination: derived, not picked** — `/NovelTrans/<tên truyện>/`, created on demand, mirroring the local tree. No folder picker, no Settings path field.

## Design decisions

| Decision | Rationale |
| --- | --- |
| **A new module `src/noveltrans/onedrive_upload.py`**, sibling of `youtube_upload.py`. | Same shape, same optional-Playwright discipline, same "selectors in one block at the top" layout. It shares `browser.py` for launching and nothing else — the DOM, the state model and the safety calculus are all different, and a shared module would be a pile of `if service == …`. |
| **Its own profile, `DEFAULT_LIBRARY_DIR / ".onedrive-profile"`.** | Chromium refuses a second instance on one `user-data-dir`, so a shared profile would make an OneDrive push and a YouTube upload mutually exclusive at the OS level. They are also different identities: a Google channel login has no business in a Microsoft profile. Separate dirs mean the two can genuinely run at the same time. |
| **One file-list surface, driven by URL for the root and by clicking for the rest.** | Personal OneDrive (`onedrive.live.com`) addresses items by opaque `cid`/`id`, not by path; OneDrive for Business (`<tenant>-my.sharepoint.com/personal/<user>/_layouts/15/onedrive.aspx`) does accept `?id=/personal/<user>/Documents/…`. A path-based deep link therefore works on one flavour and silently lands on "item not found" on the other. Navigating by clicking (or creating) each folder in turn works identically on both and is verifiable from the breadcrumb. |
| **We create the folders ourselves and upload flat batches of files into each.** | `input[webkitdirectory]` looks like the obvious answer and is a trap: Playwright's `set_input_files` does not populate `webkitRelativePath`, so a directory upload arrives at OneDrive as a flat pile with the tree lost. Per-folder batches also give per-folder verification and a resume point every few files instead of one at the very end. |
| **"Transfer finished" = the file is listed in the destination folder with the right name**, with OneDrive's own status text used only for progress messages and stall detection. | The status callout is localized, animated and A/B tested; the file list is the thing we actually care about. This is the deliberate inverse of `transfer_state`, where Studio's progress line was the only signal available. Here there is a better one, so the parsed text is demoted to advisory. |
| **State is ONE manifest per project**, `<project>/.onedrive-upload.json`, mapping relative path → size, mtime, uploaded-at. | Per-file sidecars would add several hundred tiny files to the very tree we are uploading, and they would then need uploading too. One manifest is one atomic write per batch and one file to delete when a human wants a clean re-push. |
| **A corrupt manifest reads as EMPTY, not as "unknown".** | This is the load-bearing difference from YouTube and it must be written down where someone will find it. `read_upload_state` treats a truncated file as `unknown` because guessing wrong there publishes an episode twice to an audience. Re-uploading to OneDrive replaces a file in a private folder: the cost of guessing wrong is bandwidth and time, not a public mistake. So the safe default flips — when in doubt, upload again. |
| **Default conflict policy: replace.** | We are mirroring a local tree, so the local copy is the intended truth. "Keep both" produces `phan-1 1.mp4` next to `phan-1.mp4`, which is worse than either outcome and invisible until someone opens the folder. If OneDrive silently auto-renames instead of prompting, the post-batch listing check catches the ` 1.` name and fails loudly. |
| **Skip rule: same relative path + same size + mtime not newer than the recorded upload.** | Cheap, local, and correct for the actual workflow (re-render part 7, push again, move 3 GB instead of 60). Deliberately *not* a checksum: hashing 40 GB to save a re-upload of 200 MB is the wrong trade. |
| **We never read the cloud copy's timestamp to decide.** | This is a one-way push, not a sync. The Modified column is localized, coarse and only sometimes rendered. If someone edits a file in OneDrive, the next push overwrites it — that is stated in the confirmation dialog, not discovered later. |
| **`chapters.db` is uploaded from a `sqlite3` backup snapshot, never straight off disk.** | The database is open in WAL mode while the app runs. Copying the `.db` file alone while the WAL holds uncommitted pages produces a file that opens but is missing recent chapters — the worst kind of backup, one that looks fine. `sqlite3.connect(src).backup(dst)` gives a consistent single-file copy, and the `-wal`/`-shm` files are then correctly excluded. |
| **Host the action on the Export tab**, not a sixth tab. | "Everything this novel produced, out of the app" is exactly what tab 3 already means. The Video tab owns per-part YouTube actions; a whole-project push is not a per-part action. |
| **A dry-run preview before the first byte.** | The confirmation has to state a file count and a total size, because the difference between "12 files, 4 GB" and "3 200 files, 61 GB" is the difference between a coffee break and an overnight run, and the user cannot tell which they have without being told. |

## The OneDrive web surface

Everything in this section is a **guess** until `scripts/diagnose_onedrive.py` (step 2) has been run against a real account. The selector block must say so, in the house style, in the constants themselves — the 044 lesson is that four rounds of guessing cost more than one round of observing.

### Flavours and URLs

```python
_ROOT_URLS = (
    "https://onedrive.live.com/",          # personal, redirects to ?id=root&cid=…
    "https://www.office.com/onedrive",     # business, redirects into <tenant>-my.sharepoint.com
)
_LOGGED_OUT_URL_RE = re.compile(r"login\.live\.com|login\.microsoftonline\.com|/signin")
_LOGGED_IN_URL_RE  = re.compile(r"onedrive\.live\.com/\?|-my\.sharepoint\.com/personal/")
```

`flavour(url) -> "personal" | "business" | ""` is a **pure function on the landed URL** and is unit-tested. It exists because two things genuinely differ and only two:

1. **Where the root is.** Personal lands on `?id=root&cid=<CID>`; business lands on `…/_layouts/15/onedrive.aspx?id=/personal/<user>/Documents`.
2. **Whether a path deep-link works.** Business: yes. Personal: no. So `_open_folder` uses the deep link as a *fast path* on business and falls back to click-navigation everywhere, and click-navigation is the only path that is ever assumed to work.

The command surface (New ▸ Folder, Upload ▸ Files, the details list, the conflict dialog) is the same ODSP React app on both, so one selector set covers them — but the code must never *assume* that: every step that matters checks its own postcondition (breadcrumb says the folder, listing shows the file) rather than trusting that a click landed.

### Sign-in

`open_login(timeout_ms=300_000, *, switch=False) -> str` (returns the signed-in account name/email, `""` if unreadable), a straight port of `youtube_upload.open_login`:

* headed always — Microsoft throws MFA, "stay signed in?", and new-device checks that only a human can clear;
* `switch=True` calls `clear_profile()` first, because a valid session loads straight through and closes the window before the user can change account — the same trap 033 documented for Google;
* `clear_profile()` reuses the youtube version's guard verbatim: it only deletes `profile_dir()`, and only when `Default` or `Local State` is present. It deletes a directory tree; it verifies what it is aiming at.

`_is_logged_out(page)` is URL-based (`_LOGGED_OUT_URL_RE`) plus a DOM fallback on the sign-in form, and every entry point raises `OneDriveUploadError(..., needs_login=True)` rather than timing out on a selector that will never appear.

Generic helpers (`_first_present`, `_click_any`, `_click_by_text`, `_check_cancel`, `_report`, `_dom_inventory`, `_page_actions`) are **re-implemented locally**, not imported from `youtube_upload`. ### Failing loudly

Every step has a postcondition that is checked, and the error names the step and quotes what the page actually showed:

| Step | Postcondition | Failure message shape |
| --- | --- | --- |
| open root | URL matches `_LOGGED_IN_URL_RE` | `needs_login=True` if `_LOGGED_OUT_URL_RE` matched, else "không mở được OneDrive (URL: …)" |
| enter/create folder | breadcrumb's last segment == folder name | "không vào được thư mục `<name>` (breadcrumb: …)" |
| hand files to the input | the input accepted the paths and a status line or new row appeared | "không đưa được file vào OneDrive — giao diện có thể đã thay đổi. Hãy tải lên thủ công lần này và báo lỗi để cập nhật selector." |
| batch finished | every expected filename is in the listing | "OneDrive báo xong nhưng thiếu N file trong thư mục: …" |
| no auto-rename | no `name 1.ext` twin appeared | "OneDrive đã tạo bản sao `…` thay vì ghi đè — dừng lại để không tạo file trùng." |
| quota | `_QUOTA_RE` never matched | "Tài khoản OneDrive đã hết dung lượng — cần dọn bớt hoặc nâng gói." |

### `scripts/diagnose_onedrive.py`

Modelled directly on `scripts/diagnose_subtitles.py`, and written **before** the selectors are trusted rather than after they fail:

```
python scripts/diagnose_onedrive.py                 # open root, report everything
python scripts/diagnose_onedrive.py --upload FILE   # additionally push one small file
```

It opens the app's own OneDrive profile, prints the landed URL and the detected flavour, dumps `_page_actions` (clickable labels) and `_dom_inventory`, then reports `matches=N visible/hidden` for every selector constant in the block, tries to open the New menu and the Upload menu and says which one moved, and reports whether a file input became reachable. Read-only by default: it never creates a folder and never uploads unless `--upload` is passed, in which case it targets `/NovelTrans/_diagnose/` and says so.

## Feeding a folder tree to a web UI

### What we send, and in what shape

`collect_payload(project_path) -> list[PayloadItem]` — **pure, tested**, no browser:

```python
@dataclass(frozen=True)
class PayloadItem:
    path: Path        # absolute source
    relpath: str      # POSIX-style, relative to the project folder, e.g. "exports/video/…/x.mp4"
    size: int
    mtime: float
```

Included: everything under the project folder. Excluded, each for a reason worth a comment:

* `.onedrive-upload.json` — our own manifest; uploading it would make every run's payload depend on the previous run's bookkeeping.
* `chapters.db-wal`, `chapters.db-shm` — transient, meaningless without the exact process that wrote them, and *actively harmful* next to a snapshot taken at a different instant.
* `*.tmp` — half-written by `write_upload_state` and friends.
* `.DS_Store`, and any other dot-file or dot-directory.
* Zero-byte files: uploaded, but counted separately in the preview so "0 B" rows are visible rather than mysterious.

`chapters.db` is special-cased: `snapshot_database(project_path, dest_dir) -> Path` runs the sqlite backup API into the scratch dir and the payload item points at the snapshot while keeping `relpath == "chapters.db"`. Testable with a real sqlite file, no browser, no Qt.

### Batching

`batch_payload(items, *, max_files=20, max_bytes=4 * 1024**3) -> list[list[PayloadItem]]` — pure, tested. Batches never span folders (each batch targets exactly one destination folder), and are capped both ways:

* by **file count**, because one `set_input_files` with 3 000 chapter MP3s is an unbounded gamble on the page's own upload queue, and because a failure costs the whole call;
* by **bytes**, because the batch is the resume granularity — a batch that dies loses only its own files.

Both caps are constants with the reasoning next to them, and both are deliberately conservative on first release. A folder with 2 000 files simply becomes 100 batches; between batches the worker checkpoints (pause/cancel) and paces itself.

### Handing files over

```python
def _send_files(page, paths: list[Path]) -> None:
    """Hand a batch to OneDrive, then confirm OneDrive took it.

    Two strategies, same order and same reasoning as `youtube_upload._send_file`:
    1. `set_input_files` on the hidden `input[type=file][multiple]` — no text matching,
       no OS dialog, works while the element is hidden (state="attached").
    2. Upload ▸ Files inside `expect_file_chooser`, which intercepts the chooser before
       the OS shows it. Text-dependent and slower, but it does not care where the input
       lives.
    Then verify the page reacted at all — a silent no-op that sails on is how the first
    live Studio run presented, and it would present identically here.
    """
```

Never the `webkitdirectory` input, for the reason stated in the selector block.

### Detecting "transfer finished"

Three layers, in increasing order of authority:

1. **`upload_status(text) -> (finished, remaining, percent)`** — pure and tested, the analogue of `transfer_state`. Parses "Đang tải lên 3 mục", "Uploading 3 items — 45%", "Đã tải lên 3 mục", "1 minute remaining". Unrecognised text reads as *still going*, never as finished: erring that way costs time, erring the other way abandons a transfer when the browser closes.
2. **Stall detection.** `_wait_for_batch` records the last time either the status text changed or a new expected filename appeared in the listing. `_STALL_MS = 10 * 60_000` with no movement fails the batch with "OneDrive ngừng tiến triển ở “…” trong 10 phút" — this, not the ceiling, is the guard that actually fires on a dead network.
3. **Listing verification — the authority.** After the status says done (or the stall timer is about to fire), read the folder's rows and require every expected filename. Only then is the manifest written.

Timeouts sized for multi-GB, each derived rather than magic:

```python
_ASSUMED_FLOOR_BPS = 512 * 1024      # 0.5 MB/s — a pessimistic floor, not an estimate
_BATCH_MIN_WAIT_MS = 10 * 60_000
_BATCH_MAX_WAIT_MS = 6 * 3600_000    # backstop; the stall detector should always win
def batch_timeout_ms(total_bytes: int) -> int: ...   # pure, tested
```

A 4 GB batch therefore gets ~2¼ hours before the ceiling, and 10 minutes of silence kills it long before that.

## State and resume

### The manifest

`<project>/.onedrive-upload.json`:

```json
{
  "version": 1,
  "remote_root": "/NovelTrans/Tên truyện",
  "account": "someone@example.com",
  "updated_at": "2026-08-05T21:14:02+07:00",
  "files": {
    "exports/video/xxx-0001-0010/xxx-0001-0010.mp4": {
      "size": 3221225472, "mtime": 1754400000.0,
      "uploaded_at": "2026-08-05T20:02:11+07:00", "status": "done"
    }
  }
}
```

`status` is `"sending"` (written **before** the batch goes out) or `"done"` (written after listing verification). Only those two — there is no `committed` fence here, because there is no irreversible public act to fence.

* `read_manifest(project) -> Manifest` — missing file → empty manifest. **Corrupt or unreadable file → empty manifest, with a note in the returned object so the GUI can say "không đọc được trạng thái cũ — sẽ tải lại từ đầu".** The docstring must spell out why this is the opposite of `read_upload_state`: there, "I can't tell" must never read as "never uploaded", because the cost is a double-publish; here the cost is bandwidth and the cost of the *other* mistake is a missing file the user believes is backed up. Silence about a missing backup is the expensive failure.
* `write_manifest(project, manifest)` — atomic (temp + `os.replace`), same as `write_upload_state`, and for the same reason: it is written between real operations and a torn write must not produce something we have to interpret.
* A `"sending"` entry found on a later run is simply re-uploaded (with replace). No dialog, no "dở dang" state, no human in the loop — because the operation is idempotent in a way a YouTube publish never is.

### Skip rule

`plan_uploads(items, manifest, *, force=False) -> (to_upload, to_skip)` — **pure, tested, and the brain of the feature**:

* no manifest entry → upload;
* entry with `status != "done"` → upload;
* size differs → upload;
* `mtime` newer than the recorded `mtime` (2-second tolerance, for filesystems that round) → upload;
* otherwise → skip, and count it.
* `force=True` → upload everything, ignoring the manifest. This is the "tải lại toàn bộ" checkbox.

### Escape hatches

1. **"Tải lại toàn bộ"** checkbox on the confirmation — one run, ignores the manifest, replaces everything.
2. **"Quên trạng thái OneDrive"** button — deletes `.onedrive-upload.json` after a confirmation that states plainly that the next push will re-upload everything and how many GB that is. Unlike `clear_upload_state`, this needs no scary warning about duplicates: it cannot create one. Saying so in the dialog is part of the design — a warning that is not warranted trains people to ignore the ones that are.

## Errors

```python
class OneDriveUploadError(Exception):
    """A push could not be completed.

    `needs_login` marks the recoverable case where the dedicated profile has no valid
    Microsoft session — the fix is the one-time sign-in, not a retry. `relpath` names
    the file the run died on, so the report says which one instead of leaving the user
    to diff a 3 000-file tree.
    """
    def __init__(self, message: str, *, needs_login: bool = False, relpath: str = ""): ...

class OneDriveCancelled(Exception):
    """The user cancelled the run. Carries how far it got."""
    def __init__(self, message: str = "Đã huỷ tải lên OneDrive.", *, uploaded: int = 0): ...
```

`OneDriveCancelled`, not `UploadCancelled`: `workers.py` imports both services' exceptions (function-locally today, but that is an implementation detail one refactor away from being module-level), and two same-named exception classes in one file is a shadowing bug waiting to be written.

## Public API of `onedrive_upload.py`

```python
# identity / session
def profile_dir() -> Path                       # DEFAULT_LIBRARY_DIR / ".onedrive-profile"
def clear_profile() -> bool
def open_login(timeout_ms=300_000, *, switch=False) -> str      # account name/email

# pure, tested
def onedrive_folder_name(title: str) -> str     # OneDrive-safe folder name
def flavour(url: str) -> str                    # "personal" | "business" | ""
def collect_payload(project_path: Path) -> list[PayloadItem]
def batch_payload(items, *, max_files=..., max_bytes=...) -> list[list[PayloadItem]]
def plan_uploads(items, manifest, *, force=False) -> tuple[list[PayloadItem], list[PayloadItem]]
def upload_status(text: str) -> tuple[bool, int | None, int | None]
def batch_timeout_ms(total_bytes: int) -> int
def read_manifest(project_path: Path) -> Manifest
def write_manifest(project_path: Path, manifest: Manifest) -> None
def clear_manifest(project_path: Path) -> bool
def snapshot_database(project_path: Path, dest_dir: Path) -> Path

# the drive
@dataclass
class PushRequest:
    project_path: Path
    novel_title: str
    force: bool = False

@dataclass
class PushResult:
    uploaded: int; skipped: int; failed: int
    bytes_sent: int; remote_root: str

def push_project(request, *, headless=False, on_progress=None,
                 on_file_done=None, should_cancel=None, on_checkpoint=None) -> PushResult
```

`push_project` opens **one** browser for the whole run (same reasoning as `upload_batch`: the launch costs seconds and a login-upload-quit cycle per file looks exactly like what it is). Internally: `_open_root` → `_ensure_folder("NovelTrans")` → `_ensure_folder(novel)` → for each destination folder, `_ensure_folder` down the relative path → per batch: mark `sending`, `_send_files`, `_resolve_conflicts`, `_wait_for_batch`, verify listing, mark `done`, `write_manifest`, checkpoint.

A failed **batch** does not abort the run — the rest still upload and the failure is reported per file via `on_file_done(relpath, error)`, exactly as `upload_batch` handles a failed part. `needs_login` and quota-exhausted are the two exceptions: every remaining batch would fail identically, so they re-raise.

`onedrive_folder_name` is the small pure function that will otherwise become a bug: OneDrive rejects `" * : < > ? / \ |`, leading/trailing spaces, trailing dots, and a handful of reserved names. Vietnamese diacritics are fine and must be preserved (`slugify` would turn *Tên truyện* into `ten-truyen`, which is not what "a folder named after the novel" means to the user). Falls back to `slugify(...)` only when sanitisation leaves nothing. The chosen name is recorded in the manifest as `remote_root` and **the manifest wins on later runs**, so renaming the novel in the app does not strand an already-uploaded tree in an orphaned folder.

## Workers

`src/noveltrans/gui/workers.py`, next to the YouTube ones and with the same signal vocabulary:

```python
class OneDriveLoginWorker(QThread):
    done = Signal(str)       # account name/email ("" if unreadable)
    failed = Signal(str)
    def __init__(self, parent=None, *, switch: bool = False): ...

class OneDrivePushWorker(PausableWorker):
    progress = Signal(int, int, str)     # files done, total, status line
    file_done = Signal(str, str)         # relpath, error ("" on success)
    finished_ok = Signal(int, int, int)  # uploaded, skipped, failed
    failed = Signal(str)                 # the run could not start / was cancelled
    needs_login = Signal(str)
```

`PausableWorker` because a 60 GB push is exactly the job someone wants to pause when they need the bandwidth. The gate holds **between batches**, never mid-transfer — same contract as every other pausable worker in the file, and stated in the docstring because it is the question people ask.

Requests are built on the GUI thread (they only stat files); the worker opens nothing but its own browser and never touches a `NovelProject`.

## GUI surface

### Export tab (`gui/tab_export.py`) — the host

A new `QGroupBox("OneDrive")` under the existing action row:

* **`Đẩy lên OneDrive`** — the push. Disabled while an export or a push is running.
* **`Dừng`** — cancel; enabled only during a run.
* **`Quên trạng thái OneDrive`** — the escape hatch above.
* `QProgressBar` + a wordy `QLabel` status line, matching the Video tab's `⬆️ (3/48) …` shape.
* A muted hint under the group: what gets pushed, where it lands, and that automating OneDrive is at the user's own risk — same tone as the existing Discord/YouTube hints.

The confirmation dialog is built from the dry run and must state, in this order: the destination path, the file count and total size to be uploaded, the count and size being skipped as unchanged, and the one sentence that matters — *"Các file trùng tên trên OneDrive sẽ bị GHI ĐÈ bằng bản trên máy."* Plus the "Tải lại toàn bộ" checkbox, unticked.

`has_running_workers()` and `shutdown()` on the tab must both grow to include the new worker — the tab currently only knows about `ExportWorker`, and a push that outlives the window is a Chrome process nobody owns.

The worker is registered with `job_registry.register(worker, kind="Tải lên OneDrive", novel=…)` and wrapped in `track_worker(...)` so the Mac does not idle-sleep three hours into a transfer. Both are one line each, next to each other, as everywhere else.

### Settings (`gui/settings_dialog.py`)

Directly under the YouTube row, mirroring it exactly:


`_refresh_onedrive_status()` reports on `profile_dir().is_dir()`, same as `_refresh_youtube_status`. `_onedrive_switch` confirms first ("Sẽ đăng xuất tài khoản đang kết nối… Các file đã tải lên tài khoản cũ vẫn còn"). A muted hint below covers the Playwright install line and the ToS note.

No path field, no folder picker — the destination is derived. That is a decision, so the hint says where files go: *"Mỗi truyện được đẩy vào `/NovelTrans/<tên truyện>/` trên OneDrive."*

## What is testable, and what is not

**Pure and unit-tested** (`tests/test_onedrive_upload.py`):

* `test_profile_dir_is_dedicated_and_separate_from_the_others` — including from `.youtube-profile`, the whole point of it existing.
* `TestFolderName` — illegal characters stripped, diacritics preserved, trailing dot/space trimmed, reserved names escaped, empty title falls back to the slug.
* `TestFlavour` — personal URL, business URL, a login URL, garbage.
* `TestCollectPayload` — meta.json/chapters.db/exports tree all present with POSIX relpaths; `-wal`/`-shm`/`.tmp`/`.DS_Store`/the manifest itself excluded; part sidecars (`.title.txt`, `.txt`, `.tags.txt`, `.jpg`, `.srt`, `.upload.json`) all included.
* `TestSnapshotDatabase` — a snapshot of a WAL database with uncommitted-to-main pages contains the rows; the snapshot is a single file with no sidecars.
* `TestBatchPayload` — never spans folders; respects both caps; a single file larger than `max_bytes` still gets its own batch rather than being dropped.
* `TestPlanUploads` — **the load-bearing suite.** Unchanged file is skipped; changed size uploads; newer mtime uploads; 1-second mtime jitter does not; a `sending` entry re-uploads; `force=True` uploads everything; an empty manifest uploads everything.
* `TestManifest` — round-trip; **`test_a_corrupt_manifest_reads_as_empty_not_unknown`** with a comment naming the deliberate divergence from `read_upload_state`; atomic write leaves no `.tmp`; a manifest whose `remote_root` differs from the computed name keeps the recorded one.
* `TestUploadStatus` — Vietnamese and English "uploading"/"uploaded" forms, percent extraction, "1 minute remaining" is still in flight, unrecognised text is **not** finished.
* `TestBatchTimeout` — monotonic in bytes, never below the floor, never above the ceiling.

**Fake-page tests** (`_FakeOneDrivePage` in the house `_FakeUploadPage` style):

* `_send_files` prefers the hidden multiple input, falls back to the file chooser, **never touches a `webkitdirectory` input**, and raises when neither path works.
* `_ensure_folder` enters an existing folder, creates a missing one, and raises when the breadcrumb does not end up where it was told.
* `_wait_for_batch` returns when every expected name appears; raises on stall; raises when the status says done but a file is missing from the listing.
* `_resolve_conflicts` picks Replace, never Keep both, and detects an auto-renamed ` 1.` twin.
* Logged-out landing raises `needs_login=True`; a quota message raises with the quota text.
* `push_project` writes `sending` before a batch and `done` after; a failed batch does not abort the remaining batches; cancel between batches raises `OneDriveCancelled` with the count.

**GUI** (`tests/test_tab_export.py`, new; `tests/test_settings_dialog.py`, extended): the buttons exist and are wired; the confirmation text names the destination, the counts and the overwrite warning; "Tải lại toàn bộ" reaches `PushRequest.force`; the push and export buttons interlock; `has_running_workers`/`shutdown` see the new worker; the Settings row exists and its status label flips with `profile_dir()`.

**Not tested, by design:** the selector constants and everything that touches a real OneDrive DOM. Same boundary as `youtube_upload`, and the same compensating control — `scripts/diagnose_onedrive.py`.

## Known trade-offs

1. **Browser automation is the fragile choice, and this is the one place that says so.** Microsoft Graph with device-code OAuth and resumable chunked upload would be sturdier in every dimension that matters here: no selectors to drift, real per-chunk resume so a dropped connection costs one 10 MB chunk instead of a 3 GB file, no dependence on a browser tab staying alive for hours, and a supported API rather than a tolerated one. The user was told this and chose browser automation. So the design compensates where it can — postconditions on every step, listing verification as the authority instead of a status string, a diagnose script before the first live run, a stall detector, and small batches so a failure is cheap. What it cannot compensate for is a redesign of the OneDrive web app, which will break this feature outright and will announce itself as a run that stops and names the step it stopped on. That is the best available outcome, not a good one.
2. **ToS.** Automating the OneDrive web UI sits in the same grey zone as `discord_unlock` and `youtube_upload` do for their services. The Settings hint says so in Vietnamese, and the pacing between batches is deliberate. Unlike YouTube, the target is the user's own private storage, which lowers the stakes but does not change the rule.
3. **Multi-GB through a browser.** The browser holds the upload queue in the tab. A crashed tab, a laptop sleeping (mitigated by `track_worker`), or Chrome's own memory pressure ends a batch, and the batch restarts from the beginning of its files — there is no mid-file resume. The byte cap on batches is what bounds that loss. A first run on a 60 GB project should be expected to take overnight and to need at least one restart, and the manifest exists precisely so the restart is cheap.
4. **Thousands of small files.** `exports/audio/` can hold one MP3 per chapter. Uploading 2 000 files in 100 batches is slow, chatty, and the most likely thing to trip a throttle. If it proves painful in practice, the follow-up is an opt-in "zip the audio folder before pushing" — not in this feature.
5. **One-way, and destructive on collision.** This is a push, not a sync. A file edited in OneDrive is overwritten on the next run without being asked about. The confirmation says so; nothing else protects it.
6. **`.upload.json` sidecars travel with the payload.** They record YouTube video ids and publish state. That is what "everything" means and it is what the user asked for, but it is worth knowing that the OneDrive folder therefore contains the channel's publication record.
