New `src/noveltrans/onedrive_upload.py` and `tests/test_onedrive_upload.py`.

local generic helpers (`_first_present`, `_click_by_text`, `_click_any`, `_check_cancel`,
`_report`, `_dom_inventory`, `_page_actions`).

Notes on what was decided while writing it:

* **`_LOGGED_IN_URL_RE` is deliberately permissive**, with `_LOGGED_OUT_URL_RE` always
  checked first. A tight pattern would be a guess about a URL shape nobody has observed,
  and guessing wrong makes `open_login` wait five minutes on a page the user already
  signed into. Loose + ordered fails the cheap way instead.
* **`flavour()` tests business before personal.** A tenant URL contains "onedrive" in its
  own path (`…/_layouts/15/onedrive.aspx`), so the personal pattern would otherwise claim
  it. A login URL is neither flavour — answering "personal" for `login.live.com` would
  send the caller navigating a page with no file list on it.
* **`_dom_inventory` counts `data-automationid` values**, not custom element tags. The
  Studio version censuses `ytcp-*` elements; React gives us no such tag names, but it
  does give us these — and they are what every selector in this module is built on.
* **`_first_present` catches every exception, including the Playwright import.** A miss
  is a miss however it presents, and it keeps the helper callable in an environment
  without Playwright — which is what lets the fake-page tests run bare. (First version
  imported `playwright.sync_api.TimeoutError` at call time, like the YouTube one; the
  test then only passed because this machine happens to have Playwright installed.)
* **`_account_name` never raises and never gates the flow.** A name we cannot read costs
  a confirmation message its detail and nothing else; the session is in the profile
  either way.

The sign-in selectors (`_SIGNED_IN_ACCOUNT_SELS`, `_SIGNIN_FORM_SELS`) and both URL
patterns are **guesses**, labelled as such in the source. Step 2 is the diagnose script
that replaces them with measured values.

## [STEP 2] Selector block + diagnose script — 2026-08-05

The full file-list selector block in `onedrive_upload.py`, and
`scripts/diagnose_onedrive.py`.

**This step is NOT finished.** Its whole point is to replace guesses with measured
values, and that needs a live signed-in account. Everything committed here is still a
guess and still labelled as one in the source. The script has been lint- and
import-checked (its imports are a real check that every constant it names exists), but
never run against OneDrive.

Selector block covers: New ▸ Folder (`_NEW_MENU_SELS`, `_NEW_FOLDER_TEXTS`,
`_FOLDER_NAME_INPUT_SELS`, `_CREATE_TEXTS`), Upload ▸ Files (`_UPLOAD_MENU_SELS`,
`_UPLOAD_FILES_TEXTS`, `_UPLOAD_INPUT_SELS`), the breadcrumb and row list
(`_BREADCRUMB_SEL`, `_BREADCRUMB_ITEM_SEL`, `_ROW_SEL`, `_ROW_NAME_SEL`), the progress
bar (`_UPLOAD_STATUS_SEL`), and the conflict dialog (`_CONFLICT_DIALOG_SEL`,
`_REPLACE_TEXTS`, `_KEEP_BOTH_TEXTS`).

Decisions made while writing it:

* **`_UPLOAD_DIRECTORY_INPUT_SEL` exists only to be refused.** OneDrive ships both a file
  input and a directory input, and `set_input_files` on the directory one *looks* like it
  works: Playwright does not populate `webkitRelativePath`, so every file lands flat and
  the tree is silently lost. Every other selector here can miss and the run stops with a
  message; this one can miss and the run reports success — so it gets a test
  (`TestUploadInputSelectors`) rather than a comment, asserting every upload selector
  carries `:not([webkitdirectory])`.
* **`TestBilingualTexts` pins every text ladder to at least one Vietnamese and one ASCII
  form.** The app is Vietnamese; the OneDrive account may be anything. A one-language
  ladder works on this machine and fails on a user's.
* **The status regexes (`_UPLOADING_RE`, `_UPLOAD_DONE_RE`, `_QUOTA_RE`) were deferred to
  step 3**, against the plan, which put them in this block. They are parsing, their only
  consumer is `upload_status()`, and landing them now would mean shipping constants with
  no caller and no test.
* **`--upload` does not choose where the file goes.** The plan had it target
  `/NovelTrans/_diagnose/`, but folder navigation is step 4 — so rather than guess a path
  or drop a test file in the user's root, the script hands the browser over, waits for
  the user to navigate somewhere they don't mind, and only then feeds the input. It then
  polls the *listing* rather than the status bar, because the listing is what
  `_wait_for_batch` will treat as the authority and is therefore the thing worth proving.
* The script bails immediately if `_is_logged_out` — every section below it would be
  reporting on a login page.

## [STEP 3] The pure core — 2026-08-05

All browser-free, all tested: `PayloadItem`, `collect_payload`, `snapshot_database`,
`swap_in_database_snapshot`, `onedrive_folder_name`, `remote_root_for`, `batch_payload`,
`Manifest` + `read_manifest` / `write_manifest` / `clear_manifest`, `plan_uploads`,
`total_bytes`, `format_size`, `upload_status`, `is_quota_error`, `batch_timeout_ms`.
Plus the status regexes deferred from step 2.

Decisions and discoveries:

* **`_effective_mtime` counts `chapters.db-wal`.** Not in the plan, and it would have been
  a silent bug: in WAL mode sqlite writes to the log and need not touch the main file's
  mtime until a checkpoint, so the skip rule would read "unchanged" about a database that
  gained fifty chapters that afternoon and never push them again. The db item's mtime is
  now `max(db, db-wal)`.
* **The WAL failure `snapshot_database` prevents is worse than the plan assumed, and is
  now pinned by a test.** The plan said a naive copy "opens but is missing recent
  chapters". Measured: with the WAL un-checkpointed, a `shutil.copy` of `chapters.db`
  does not contain the `chapters` table *at all*. `test_a_naive_file_copy_of_a_wal_database_loses_everything`
  asserts that, so nobody simplifies the backup API back into a file copy.
* **The snapshot swap became its own function** (`swap_in_database_snapshot`) rather than
  a flag on `collect_payload`. It keeps `collect_payload` a straight description of the
  file tree, and it isolates the subtle part: the swapped item takes the *snapshot's*
  size (that is what goes up) but the *source's* mtime (taking the snapshot's would stamp
  "now" every run and re-upload the database forever).
* **Illegal characters in a folder name become spaces, not deletions** — `Phần A/B` reads
  as `Phần A B` rather than silently merging into `Phần AB`. Trailing dots and spaces are
  stripped because the server strips them silently, which would make our "is this folder
  here?" check compare against a name that does not exist.
* **`format_size` uses a Vietnamese decimal comma** (`4,2 GB`). It is read by the user and
  every other number in the app uses one.
* `upload_status` returns `(finished, item_count, percent)`; "còn lại"/"remaining" counts
  as still-in-flight, since a time estimate is something only a live transfer has.

Tests: 99 more (135 in the file). Full suite: 1516 passed, ruff clean.

## [STEP 4] Navigation and folder creation — 2026-08-06

`_settle`, `_names_match`, `_texts_of`, `_breadcrumb`, `_list_names`, `_open_root`,
`_row_named`, `_enter_folder`, `_create_folder`, `_ensure_folder`, `_ensure_path`, and
the pure `folder_segments`. Tested against a new `_FakeOneDrivePage` that models a real
folder tree rather than a bag of selectors — clicking a row changes what the breadcrumb
and listing say, so the postconditions are exercised rather than stubbed.

Decisions and discoveries:

* **`_names_match` is case-insensitive**, because OneDrive is: it preserves the case you
  typed but will not let `NovelTrans` and `noveltrans` coexist. A case-sensitive check
  would make us try to create a folder the server then refuses or auto-renames.
* **Opening a folder needs two gestures tried, not one.** The name is a link and takes a
  single click; the row around it takes a double-click, because a single click only
  selects it. We do not know which selector will match on the live page, and guessing
  wrong presents *identically* to a dead selector — so `_enter_folder` tries the natural
  gesture for whichever selector matched and falls back to the other before concluding
  anything. Costs a second; saves a false "giao diện đã thay đổi". (First version
  double-clicked the name link and gave up after one gesture.)
* **`_enter_folder` returning False and raising are different answers, deliberately.**
  False means "no such folder", a normal state `_ensure_folder` answers by creating it.
  Clicked-but-did-not-land raises — that is drift, and carrying on would upload a whole
  novel into whatever folder happened to be open.
* **List virtualisation is a real hole, and the guard is `_create_folder`'s
  postcondition.** OneDrive virtualises long lists, so a folder that exists may not be in
  the DOM; we would then try to create it. That is *safe* rather than fixed: OneDrive
  answers the collision by making `NovelTrans 1`, and `_create_folder` looks for exactly
  that twin and stops the run rather than building a second divergent tree. Documented in
  `_list_names`; the first live run should settle whether it needs more than that.
* Every rung of the create ladder fails with its own message naming the rung
  (`menu “Mới”` / `mục “Thư mục”` / `ô nhập tên` / `nút “Tạo”`), each with a test —
  retuning selectors from "it didn't work" is guesswork.
* The fake's `evaluate` raises on purpose, so every error path exercises `_page_actions`
  and `_dom_inventory` falling back rather than the happy path.

Tests: 32 more (167 in the file). Full suite: 1548 passed, ruff clean.

## [STEP 5] The transfer — 2026-08-06

`_renamed_twin`, `_status_text`, `_resolve_conflicts`, `_send_files`, `_upload_started`,
`_missing_from_listing`, `_verify_batch`, `_wait_for_batch`. The fake page grew a
transfer model: files handed to an input land in the tree after N polls, the status line
advances on a script, and the conflict dialog can appear mid-transfer.

Decisions and discoveries:

* **`_wait_for_batch` is three layers with the listing on top.** The status text feeds the
  user's progress line and the stall detector; the *listing* decides the batch is done.
  A test pins the consequence directly: a status line saying "Đã tải lên 3 mục" while the
  files are absent reports `thiếu 3 file`, not success.
* **The stall detector is the guard that fires, not the ceiling.** Ten minutes without
  movement — neither a changed status line nor a new file in the listing — fails the
  batch, where the size-derived ceiling would sit for up to six hours. There is a test
  asserting the poll count stays inside the stall window rather than running to the
  ceiling, and a complementary one proving the ceiling still catches a status line that
  changes forever without ever delivering.
* **`_upload_started` accepts either a progress line or a file in the listing.** Gating on
  the progress line alone would fail a batch of small text files that finished before the
  first poll; gating on the listing alone would fail a multi-GB batch that has not
  delivered anything yet. Both signals mean "OneDrive took it".
* **`_resolve_conflicts` raises rather than pressing whatever is there.** If the dialog is
  up and Replace cannot be found, that is a stop. The "we somehow clicked Giữ cả hai"
  branch should be unreachable and says so, but it reports loudly instead of returning
  quietly — it would have just created the duplicate the function exists to prevent.
* **The twin check runs before the missing check** in `_verify_batch`. A `phan-1 1.mp4`
  means the upload happened and went wrong; reporting that as "missing" would send
  someone looking in the wrong direction.
* Fixing the fake surfaced nothing about the module, but is worth noting: `wait_for` had
  to learn about file inputs separately from buttons and rows, because an
  `input[type=file]` is neither.

Tests: 26 more (193 in the file). Full suite: 1574 passed, ruff clean.

## [STEP 6] push_project — 2026-08-06

`PushRequest`, `PushResult`, `PushPreview`, `_resolve_remote_root`, `_prepare`,
`preview_push`, `push_project`. Plus a `fatal` flag on `OneDriveUploadError`.

Decisions and discoveries:

* **`fatal` was added to `OneDriveUploadError`** to express the rule the plan stated in
  prose: a failed batch does not end the run (a drifted selector in one folder must not
  cost the user the other fifty-nine gigabytes), but no-session and exhausted-quota do,
  because every remaining batch would fail identically. `needs_login` implies `fatal`.
* **`preview_push` shares `_prepare` with `push_project`**, so the numbers the user
  confirms are the numbers the run acts on — including the database, whose size must be
  the *snapshot's* on both sides or the dialog offers to upload a file the run then skips.
  A test asserts the preview's `chapters.db` size equals what the run records.
  Consequence, documented: a preview's `chapters.db` item points into a temp dir that is
  gone by the time it returns. Fine — a preview is counted, never sent.
* **An empty plan launches no browser.** A no-op push must not cost a Chrome window and
  thirty seconds; there is a test that fails the run if `_require_playwright` is called.
* **Navigation is only re-walked when the destination folder changes**, and `_open_root`
  at the start counts as already being at the root. Five batches across three folders cost
  three page loads, not five (first version cost four — the initial `_open_root` was
  immediately thrown away by the first batch). This matters when `exports/audio` is two
  thousand files and a hundred batches.
* **The fake wasn't modelling navigation, and `push_project` found it.** Its `goto` only
  recorded the URL without resetting `cwd`, so the second batch walked down from *inside*
  the novel folder and built `NovelTrans/Đấu La/NovelTrans/Đấu La/exports`. Real bug in
  the test double, caught by the first end-to-end test rather than by inspection.
* `on_checkpoint` fires between batches only — pausing mid-transfer would mean holding a
  half-sent batch open. There is a test asserting each checkpoint happens before its
  batch is handed over.
* The manifest is written on every exit path including cancellation, so a cancelled run
  does not re-send what already landed.

Both ordering guarantees were mutation-checked: moving `mark_sending` to after
`_send_files` fails `test_the_manifest_says_sending_while_the_batch_is_in_flight` and
`test_a_crash_mid_batch_leaves_sending_which_re_uploads`.

Tests: 22 more (215 in the file). Full suite: 1596 passed, ruff clean.

## [STEP 7] Workers — 2026-08-06

`OneDriveLoginWorker` and `OneDrivePushWorker` in `gui/workers.py`, beside the YouTube
ones and with the same signal vocabulary. New `tests/test_workers_onedrive.py`.

Decisions:

* **`needs_login` is a separate signal from `failed`**, and most of the new tests exist to
  keep it that way. They mean different things to the user — "sign in once" is actionable,
  "something broke" is not — and routing a login failure down `failed` buries the one
  message that says what to do about it.
* **The cancellation message is deliberately unlike the YouTube worker's.** There,
  cancelling mid-part can leave a draft on a public channel, so the message warns. Here a
  file is either fully on OneDrive or not, and the manifest was flushed on the way out —
  so it says how many landed and that a re-run will skip them. A warning that is not
  warranted trains people to ignore the ones that are.
* **A run that sent nothing does not claim it did.** The closing "Đã tải lên …" progress
  line is only emitted when `bytes_sent` is non-zero; "Đã tải lên 0 B" on an
  already-mirrored project would be a strange thing to put on screen.
* `OneDrivePushWorker` was added to `test_workers_pause.py`'s `WORKERS` list, so it is
  covered by the cancel-always-resumes-the-gate guard — the one that stops a paused job
  freezing the GUI on quit.

Tests: 19 more (17 new in `test_workers_onedrive.py`, 2 parametrized cases picked up in
`test_workers_pause.py`). Full suite: 1615 passed, ruff clean.

## [STEP 9] Export tab surface — 2026-08-06

“Sao lưu OneDrive” group box on the Export tab: **Đẩy lên OneDrive** / pause / **Dừng** /
**Quên trạng thái**, a progress bar, a status line and a muted hint. Wired to
`job_registry` and `track_worker`, with `has_running_workers`/`shutdown` extended.
New `tests/test_tab_export.py` (30 tests) — the tab had none before.

Decisions:

* **The confirmation is built from `preview_push`, and the counts are the point.** Twelve
  files / 4 GB and three thousand files / 61 GB are a coffee break and an overnight run,
  and nothing else on screen says which one this is. It also names the destination, the
  skip count, any manifest note, and the overwrite in capitals.
* **An already-mirrored novel is told so, not offered a pointless run** — with a pointer
  at “Quên trạng thái”, rather than opening a browser to do nothing.
* **Export and push interlock through one switch** (`_set_push_running`). They write into
  and read out of the same project folder; a push that read a `.docx` mid-write would
  mirror half a file.
* **`shutdown` cancels before waiting.** A push can be hours from finishing on its own and
  owns a Chrome process, so waiting without cancelling would hang the quit for two
  minutes and then abandon a live thread. `showEvent` also stops re-picking the project
  while a push runs — it can outlive many visits to other tabs.
* **`needs_login` opens an *information* box pointing at Settings, not a warning.**
  Dressing "sign in once" as a failure buries the fix.
* **“Quên trạng thái” says plainly that nothing on OneDrive is deleted.** Unlike
  `clear_upload_state` it cannot create a duplicate or publish anything; the worst it
  costs is a re-upload. A warning that isn't warranted trains people to ignore the ones
  that are. It quotes the size of the re-upload it would cause, and treats a size it
  cannot work out as advisory rather than a reason to block the fix.
* The push is named after the *translated* title when there is one — a CJK source title is
  not what the user is looking for in their file browser.

Verified by rendering the tab offscreen in both the idle and mid-push states, not only by
assertions.

## [FIX] The login path — 2026-08-06

Reported from a real attempt: **“Đăng nhập OneDrive chưa hoàn tất: Page.goto: Timeout
30000ms exceeded … navigating to "https://onedrive.live.com/", waiting until
"domcontentloaded"”**.

My miss. Step 10 fixed `_open_root` and the diagnose script and **left `open_login` on
`domcontentloaded`** — the same measured defect, one function over.

Behind it was a second, larger problem the timeout was hiding: even with the goto fixed,
`onedrive.live.com` signed out shows the *product brochure*, which has no sign-in form.
`open_login` would have waited its full five minutes for a URL that could never arrive.

### Measured, of four sign-in candidates (signed out)

| URL | Lands on | Email box? |
|---|---|---|
| `onedrive.live.com/` | product marketing page | no |
| `onedrive.live.com/login/` | itself | no |
| `login.live.com/` | itself | no |
| **`www.office.com/onedrive`** | `login.microsoftonline.com/common/oauth2/v2.0/authorize` | **yes** |

## [FIX] Create-folder hung on a substring collision — 2026-08-06

### The bug

`_click_by_text` builds `button:has-text("Tạo")`, and **`has-text` is a substring match**.
“Tạo” is a substring of **“Tạo hoặc tải lên”** — the command-bar button. Measured live:

| Selector | Matches | `.first` is |
|---|---|---|
| `button:has-text("Tạo")` | 2 | **“Tạo hoặc tải lên”** ← the command bar |
| `button:text-is("Tạo")` | 0 | never matches, even unscoped |
| `.ms-Dialog-actions button:has-text("Tạo")` | 1 | “Tạo” ✓ |

So it found the command-bar button *behind the modal*, and Playwright retried a click the
overlay was blocking until it gave up — a hang, from the user's side.

### Finding the dialog took two goes

The obvious scope failed too. MEASURED shape:

```
button.ms-Button < span.ms-Dialog-action < div.ms-Dialog-actionsRight
  < div.ms-Dialog-actions < div.ms-Dialog-inner < div.ms-Dialog--close
  < div.ms-Modal-scrollableContent
```

comma-joined string. Interpolating a comma list yields `rootA, rootB button:has-text(…)`,

## [NEW] Cleanup — reclaim disk once something else provably holds the file — 2026-08-06

Asked for: delete audio already rendered into a video, and videos already on YouTube and
synced to OneDrive. New `src/noveltrans/cleanup.py` + `tests/test_cleanup.py` (36 tests,

Measured on the real 21 GB novel: **3.9 GB of audio deletable now**, plus 11.8 GB of video
*candidates*.

### The finding that changed the design

The obvious rule for video was “YouTube-published AND `done` in the OneDrive manifest”.
Before offering it I spot-checked three against OneDrive:

* **All three folders were not where the manifest said** — and `exports/video/…/1381-1382`,
  which does exist, is **empty**.
* The manifest claims **28** part-videos are `done`.

So the manifest is a record of what a run *believed*, and it is wrong. Shipping the
obvious rule would have deleted **~10 GB whose only remaining copy is YouTube** — a
publishing platform, not an archive you can get bytes back out of.

`plan_video_cleanup` is therefore gone. In its place:

* `video_cleanup_candidates` — YouTube-published only, explicitly labelled unverified;
* `verify_on_onedrive` — opens a browser, opens each part folder, and confirms the remote
  copy is **the size the local file is now**. Folder missing, file missing, size different
  or listing unreadable all land in `unconfirmed` and are never offered;
* `manifest_claims_backed_up` — advisory, and documented as insufficient;
* `plan_cleanup` returns **audio only**, because audio needs no network to verify: the
  rendered `.mp4` is right there on disk.

A test asserts the manifest claiming `done` still does not get a video deleted.

### The other rules

* Chapter `.mp3`/`.wav` — safe once a **rendered** part covers that chapter. A part folder
  with no `.mp4` protects its audio; a chapter no part covers is never offered.
* `.cues.json` waits additionally for the part's `.srt`, which is what cues become.
* **`.upload.json` is never offered, ever.** Deleting it makes the app believe the part was
  never uploaded and the next run publishes the episode to the channel a second time.
  Sidecars, `chapters.db` and `meta.json` are likewise never offered — all small, all
  needed to re-render or re-upload.
* `remove_files` re-derives nothing: it deletes exactly what the plan listed, so safety
  lives in one place.

## [NEW] Cleanup UI — 2026-08-06

`gui/cleanup_dialog.py`, `OneDriveVerifyWorker`, and a **Dọn dẹp ổ đĩa…** button in the
Export tab's OneDrive group. New `tests/test_cleanup_dialog.py` (18 tests).

The dialog's job is to make an irreversible action legible, so every row names the file,
its size, **and why it is safe** — never just a count. A user who cannot see why a file is
offered has no way to catch a mistake before it costs them a video.

Decisions:

* **Audio and video are presented differently, because their evidence is.** Audio arrives
  ticked (the rendered `.mp4` holding it is on disk — nothing to check). Video rows are
  shown but **cannot be ticked at all** until “Kiểm tra OneDrive…” has run; the checkbox
  flag itself is removed, so `Chọn audio` and select-all cannot reach them either. Three
  tests guard that, including one asserting a manifest saying `done` changes nothing.
* An unconfirmed part is not hidden — its row changes to “⚠️ KHÔNG thấy trên OneDrive —
  giữ lại”, which is how the user learns they have a part with one copy.
* A failed or unauthenticated check leaves everything locked and re-enables the button.
* Cleanup is refused while a push is running: they touch the same files, and deleting one
  mid-upload would leave a half-mirrored folder.
* The dialog hands the planner's own `Removable` objects to `remove_files` rather than
  rebuilding paths from table text — a test pins that seam.

Rendered against the real novel: 1349 rows, “Đã chọn 1320 file — giải phóng 3,9 GB”, and
the 29 video rows correctly locked pending the check.

Full suite: 1825 passed, ruff clean.

## [FIX] Pagination — reach a folder by URL instead of by clicking — 2026-08-06

`_enter_folder` searched the rendered listing, and OneDrive renders ~60 rows however many
items a folder holds. `exports/video/` has more part folders than that, so folders that
plainly exist read as absent — which made `_ensure_folder` try to **create** them. The
auto-rename guard stopped the run rather than duplicating, but it stopped on a folder that
was there all along. Sorting newest-first helped only recently-touched folders.

MEASURED: OneDrive addresses a folder by path in the URL —
`onedrive.live.com/my?id=/personal/<cid>/Documents/<path>` — and a deep link opens
`exports/video/<part>` directly and lists its contents whatever the sort order.

* `_current_id` reads the `?id=` of the folder we are in ("" at the root, which carries
  none — so the first segment must still be clicked).
* `_goto_folder_id` jumps, and confirms it landed.
* `_open_path` and `_ensure_folder` try the jump first: **one click to learn where we are,
  then one hop for the whole remaining path.**

### The bug the fake caught before a real account could

A failed deep link leaves the browser **at the root**. Everything after it then searched —
or, in `_ensure_folder`, *created* — in the wrong folder: the novel would have been made
beside `NovelTrans` rather than inside it. Both call sites now restore position before
falling back to clicking, with a test named for it.

One test also had to be rewritten rather than repaired: it counted `goto` calls to prove
the tree is only re-walked when the folder changes, and deep links legitimately navigate
more. It now asserts the property itself — a batch whose folder is unchanged navigates
nowhere — instead of a number that only measured the implementation.

### And a rounding bug it exposed downstream

With navigation fixed, `verify_on_onedrive` still confirmed **zero of 29**. OneDrive shows
a *rounded* size in the grid: a 419,928,664-byte video displays as “400,0 MB” and parses
back as exactly 419,430,400. Exact equality rejected everything.

New `sizes_match_for_delete` with a **1%** tolerance — an order of magnitude wider than the
display's rounding, far tighter than any real difference, and deliberately much stricter
than the 12% the upload path uses, because this one authorises a delete. An unreadable
size is never a match here, the opposite of the upload path: there it costs a re-upload,
here it costs the file.

After the fix: **28 confirmed (11,4 GB), 1 refused.**

Tests: 5 deep-link navigation tests, 6 tolerance tests. Full suite: 1807 passed, ruff
clean.

## [INVESTIGATION] “Stuck at 0%” — it was slow, not stuck — 2026-08-06

Reported with a screenshot: the sync window on `exports/audio: 20 file`, 0%, apparently
frozen.

### Measuring rather than guessing

* The app's process started **after** the last source change, so it was not stale code.
* Its manifest had not advanced in **4+ minutes**.
* `nettop` on its Chrome: **0 bytes out** in a one-second sample.

That looked conclusive — hung, not slow. It was not.

To test without disturbing the running app (Chromium refuses a second instance on one
`user-data-dir`), the profile was **cloned** to a scratch dir; the copy is signed in and
drives a second session happily. Useful technique, worth keeping.

With that: an isolated batch of 20 audio files uploaded **64 MB in 15 seconds**, and
`_wait_for_batch` returned in 0 s on a batch already present. So nothing was broken.

The answer came from sampling the manifest over five minutes during a full run:

```
t=  0s  done=706
t=110s  done=706
t=165s  done=726   (+20 — one batch)
t=275s  done=726
```

**One batch per ~3 minutes.** At 2371 files that is roughly six hours, which is exactly
browser-speed for 8,9 GB. The `0 bytes out` reading was a one-second sample that landed
between transfers.

### The real defect is the reporting

The run was working the whole time; the UI could not show it. The progress bar counts
*files*, which move in steps of 20 every few minutes, and **OneDrive's own status region
stays empty** (measured earlier), so there is nothing to show inside a batch. A multi-
minute batch with a motionless bar reads as broken — correctly, from the user's side.

`_wait_for_batch` already tracked which files had landed; it now reports them through a
new `on_landed(n, of)` callback, and `push_project` turns that into
`⬆️ <folder>: 12/20 file` with the bar advanced by the partial count.

The advanced count is **display-only**. The manifest still records a file when its batch
completes, so a crash mid-batch cannot leave a file recorded as done that is not — a test
says so.

Tests: 3 more (284 in the file). Full suite: 1828 passed, ruff clean.
