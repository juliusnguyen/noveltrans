## [IMPLEMENTATION] — 2026-07-31

1365 tests pass (1264 before, +101), ruff clean.

Closing the window hides the app to the macOS menu bar and the work keeps going. The
menu-bar icon opens a panel with one row per running job — label, progress bar, counter,
and `⏸ Tạm dừng` / `▶ Tiếp tục` — plus `Mở cửa sổ` and `Thoát`. The same pause button also
sits beside `Dừng` in the four tabs that have one, because a control you can only reach by
hiding the window is undiscoverable.

### The hard part: pause must never deadlock cancel

Every tab's `shutdown()` does `worker.cancel()` then `worker.wait(30_000…120_000)`. A
worker that stayed parked through a cancel would freeze the GUI thread for up to two
minutes *per worker* on quit, then abandon a live QThread.

Defended twice, on purpose, so neither is a single point of failure:

* `PausableWorker.cancel()` calls `self._gate.resume()` — the fast path.
* `PauseGate.wait()` polls its `cancelled` predicate every 200 ms rather than blocking
  outright, so a future worker that forgets the first guard degrades to a 200 ms delay
  instead of a hang.

`tests/test_workers_pause.py` parametrizes "cancel resumes the gate" over all ten pausable
worker classes, so adding an eleventh without it fails the suite.

The gate is a plain `threading.Event` with no Qt import. `QWaitCondition` was rejected: it
needs a `wakeAll()` inside every cancel path *by construction*, needs a live `QMutex` on
`AudioWorker`'s pool threads as well as its QThread, and can't be unit-tested without a
`QApplication`.

### Pause stops at the item boundary, and that is a real limitation

Gating happens at the same nine places that already tested `_cancelled` — between one
chapter/part and the next. It deliberately does **not** reach into the `cancelled=`
callbacks handed down to ffmpeg and TTS:

* `tts/merge.py:175` and `tts/video.py:669` compute a hard deadline *before* their wait
  loop, so holding there would trip "ffmpeg quá thời gian" rather than pause anything.
* `tts/base.py` accumulates every synthesized chunk in a list and writes the WAV at the
  end, so a mid-chapter hold would pin hundreds of MB of float32 for hours.

Each of those four hand-offs now carries a "do NOT gate pause here" comment naming the
reason. The user-visible consequence is in the README: pausing a long ffmpeg merge or
video encode only takes effect when that file finishes.

### `AudioWorker`'s parallel path needed more than a checkpoint

The first attempt put a bare `_checkpoint()` at the top of `while inflight:` and claimed
in a comment that the gate would stop new work being submitted. **It wouldn't** —
`submit_next` only tested `_cancelled`, so pressing pause still queued a whole extra wave
of chapters (up to `n_workers`) before the loop came back round to hold.

Fixing it needed care: making `submit_next` return False while paused would drain
`inflight` to empty and fall out of the loop, reporting a *paused* run as finished. The
loop is now `while True` with an explicit "pool empty → ask submit_next whether we're done
or merely paused" branch. The cancel path is unchanged: `submit_next` returns False,
`inflight` drains, the loop exits, and `finally: pool.shutdown(wait=True)` still drains
in-flight chapters exactly as before.

### A frameless `Qt::Popup`, not a tray `QMenu`

macOS renders a tray menu as a native NSMenu, and while one is open AppKit owns the run
loop in `NSEventTrackingRunLoopMode` — queued cross-thread signal delivery, which is how
`worker.progress` reaches the GUI thread, is not reliably pumped there. Since the entire
point of the panel is a bar that *moves while it is open*, a native menu is the wrong
vehicle. Being an ordinary widget also means the popup styles with the app's QSS and gets
built and asserted in offscreen tests with no tray at all.

The popup is a top-level window, so it does **not** inherit the main window's styling
context — it needed its own `_POPUP_QSS` block. The first version added that block but
never applied it (the real call is `_QSS + _icon_qss(...)`, not a bare `_QSS`), which a
one-line assertion caught.

### Two bugs found by writing the tests

* **`PauseButton` hardcoded the global registry.** `JobPopup` accepts an injected
  registry, but its buttons drove the app-wide singleton regardless — invisible in
  production (one registry) and fatal for testing. Both now take an optional `registry`.
* **The browser-job warning vanished the moment it mattered.** Rows for upload jobs get a
  tooltip saying a pause parks a live Chrome and Google session. `PauseButton._apply`
  rewrites the tooltip on every state flip, so a tooltip assigned from outside was wiped
  by the first press. It is now `set_extra_hint`, appended on every rebuild.

### Quit semantics: one path, and a hard degrade rule

`app.setQuitOnLastWindowClosed(False)` is required — otherwise hiding the only window
quits instantly. That makes "can the user still quit?" a safety property:
`hide_to_tray_enabled` starts **False** and is set only by `TrayController` *after* a tray
icon actually installs. With no system tray (including under offscreen Qt) the close
button keeps its old shut-down-and-quit behaviour, so the app can never become
unquittable. Tested from both sides.

`closeEvent` on the hide path must not call `ws.shutdown()` — that cancels and joins every
worker, the exact opposite of the feature. Pinned by a test that spies on `shutdown` and
asserts it was **not** called.

One quit path: a `QAction` with `MenuRole.QuitRole` makes it *the* macOS Quit item, so ⌘Q,
the App menu and the popup's `Thoát` all converge on `MainWindow.quit_app` →
`app.quit()` → `aboutToQuit` → `shutdown_all` (idempotent). `shutdown_all` is connected
*before* `keep_awake.shutdown`, since slots fire in connection order and killing
`caffeinate` first could let the Mac sleep during a two-minute worker join.

Testing the quit action by walking the menu bar failed with a deleted-C++-object error —
macOS relocates a `QuitRole` action into the native application menu. The action is kept
on `self` and asserted directly, which tests the intent rather than Qt's menu plumbing.

### Job tracking is a side-channel and must never break a launch

`JobRegistry.register` declines rather than raises: a worker with no `finished` signal is
skipped outright (nothing would ever clear the row, and a stuck row is worse than none),
and `isFinished` is probed with `getattr`. Found because three existing `tab_video` tests
monkeypatch minimal duck-typed fakes with neither. The registry holds only the QThread and
strings — never a widget — so `_close_workspace`'s `ws.deleteLater()` can't strand it.

### Follow-up: the video tab needed TWO pause buttons, not one

> *"video có phần dừng và tạm dừng không?"*

Asking the question exposed a defect in the first pass. The video tab has **two** stop
buttons — `_cancel` for the render worker, `_cancel_upload` for the four browser runs —
but it got only **one** pause button, placed in the render row. So:

* pausing an upload meant reaching for a button in the render half of the tab, and
* starting an upload **rebound that button away from a running render**, leaving the
  render un-pausable from the tab (the popup still worked).

Fixed by mirroring the existing `Dừng` grouping exactly: `upload_pause_button` sits beside
`upload_cancel_button`, and each of the six registrations binds the button in its own
section. The "pausing parks a live Chrome session" hint now lives on the upload button,
where the people who need it will actually hover.

Pinned three ways: the two buttons are distinct objects, an upload no longer steals a
render's binding, and a source-level test asserts all six registrations target the button
beside their own `Dừng` (driving all six for real would need a browser and ffmpeg).

Noted, not fixed: **`Tạo phụ đề (.srt)` has no `Dừng` at all** — neither `_cancel` nor
`_cancel_upload` touches `_subtitle_worker`; it is only cancelled on shutdown. That
predates this feature. It now has a pause button but still no stop button.

### Not done / verified by inspection only

* **`on_checkpoint` in `youtube_upload.py`** is placed at the per-part boundary beside the
  existing `_check_cancel`, never inside `_wait_for_bytes_uploaded` (which would freeze a
  live transfer mid-stream and invite a Playwright timeout). The batch functions need a
  real browser, so the suite pins the API shape and asserts by source inspection that the
  hook follows the per-part cancel check. **That a pause actually holds a real upload
  between parts is untested — it needs a manual run.**
* **Manual verification still outstanding** (needs the real .app on the Mac mini): icon
  legibility in light and dark menu bars, the popup opening on click with a bar that moves
  live, Dock-icon re-show, and the "finished while hidden" notification.
* **`LSUIElement` stays unset** — deliberate, not an oversight. Setting it would drop the
  Dock icon, which breaks the badge in `notify.py` and the Dock-click re-show, and would
  make the app's many modal `QMessageBox`es awkward. `packaging/NovelTrans.spec` needs
  **no change at all**: the tray icon is drawn at runtime with QPainter as a macOS
  template image (`setIsMask(True)`, so macOS inverts it per theme), so there is no asset
  to bundle.
