### What was wrong

Two independent causes, both measured before any code changed:

| Part state | Table | Detail dialog / `.title.txt` |
|---|---|---|
| Rendered, NOT published | `Phần 75` ✅ | `Phần 75` ✅ |
| Rendered, **published** | `Phần 75` ✅ | `Phần 1` ❌ |
| `.title.txt` but `.mp4` deleted | `Phần 75` ✅ | `Phần 1` ❌ |

1. **Published parts** — `_renumber_title_sidecars` skipped them so the sidecar kept
   matching the channel. The assumption was that "Cập nhật tiêu đề" would then offer the
   part; it did not, because `_title_update_rows` diffed against `retitle(current, …)` and
   `retitle` carries `Phần N` over verbatim. Net effect: **no way in the app to push a
   corrected number to YouTube.** 099's plan flagged this as a follow-up and deferred it.
2. **A plain bug in 099** — the guard was `if not out.is_file() or is_published(out)`, but
   `_part_metadata` reads `.title.txt` whenever it exists, `.mp4` or not. A leftover
   sidecar from a video deleted after upload beat the correct computed title.

### The design decision that mattered

`_title_update_rows` now **rebuilds** the target (`_part_title` → `build_upload_title`)
instead of patching the channel title per-change. That is why there is no composition rule
for "rename + order flip + renumber all pending at once": the target is a pure function of
the three current facts, so every combination is covered by construction, and there is no
precedence to get wrong. It also makes the re-render agreement structural — the string
offered for a push, the string the sidecar holds and the string `VideoWorker` writes are
the same `build_upload_title(display_name, effective_num, order)` call.

`retitle` keeps the one thing only it knows — *is this title ours?* — extracted into
`rename.is_generated_title` via a shared `_recognise` helper. `retitle`'s public contract,
including lifting `Phần N` verbatim, is unchanged: 099 depends on it, since the
project-open resync would otherwise undo every correction. The three pinning tests in
`test_rename.py` pass unmodified, which is the proof.

### The trap the plan caught

Requirements 2 and 3 conflict for older projects. `_title_update_rows` takes the channel
title from `upload_state["title"]` **falling back to the `.title.txt`**, so for a part
uploaded before that key existed the sidecar is the only copy. Rewriting it would make
`current == target`, the part would drop out of the rows, and the bug would just move one
step along. The reported project has exactly that shape.

Fix: `_renumber_title_sidecars` backfills `upload_state["title"]` from the sidecar
immediately before overwriting it. Safe because that key has exactly one consumer
(`grep -rn '\.get("title"' src/` → one hit) and `write_upload_state` merges.

That also resolves an apparent contradiction with `rename.resync_title_sidecars`, which
still leaves published sidecars alone. The rule stated in both docstrings: **a published
part's sidecar may be rewritten only once the channel title is preserved elsewhere
first.** A renumber backfills, then rewrites; an order flip has nowhere to put it, so it
doesn't rewrite.

### Changes

- `rename.py` — `_known_set` + `_recognise` extracted; new public `is_generated_title`,
  documented as existing because `retitle`'s `""` conflates "hand-written" with "already
  right" and the renumber diff must tell those apart. `retitle` rewritten over the shared
  helper, behaviour identical.
- `gui/tab_video.py` — `_renumber_title_sidecars`: `out.is_file()` guard dropped, backfill
  added, ownership check routed through `is_generated_title`, docstring rewritten (it
  claimed a published part's number "can only be fixed on YouTube itself", now false).
  `_title_update_rows`: target rebuilt rather than patched. `_confirm_renumber` now points
  at "Cập nhật tiêu đề" instead of telling the user to fix YouTube by hand. New
  `_pending_title_push_note()` shared by the renumber, reset and order-flip status lines —
  the only place a *count* of pending pushes is truthful. Both `" … {moved} phần đã tạo."`
  notes lost "đã tạo", since a counted part's `.mp4` may be gone.
