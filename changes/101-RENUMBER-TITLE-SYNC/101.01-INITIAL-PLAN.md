## Design decisions (decide before coding)

### D1. How `_title_update_rows` notices a renumber — recommend (a)

This is the crux. Three candidates:

**(a) Recognise with `rename`, recompute the target with `_part_title` — recommended.**

```
part_num = None if whole_novel else self._part_number(window)
if not is_generated_title(current, meta.display_name(), known):  # new, in rename.py
    continue                                                     # hand-written
target = self._part_title(part_num)
if target == current:
    continue
```

Why this is the right composition rule: **there isn't one, and that's the point.** The
target is computed from the three current facts (display name, `video_title_order`,
effective part number) by the same builder that writes every other title in the app.
Diffing that single string against the channel title covers rename, order flip and
renumber *simultaneously and in any combination*, by construction — there is no
"which change wins" question to get wrong, because there is no per-axis logic. It also
makes requirement 6 structural rather than test-enforced: the string pushed to YouTube is
the identical string `_renumber_title_sidecars` writes and the identical string a
re-render writes, because all three are `build_upload_title(display_name, n, order)`.

`retitle` is kept for what only it knows — *is this title ours?* — and that knowledge is
factored out so there is one implementation (see D2).

**(b) Two diffs OR'd together** (keep `fresh = retitle(...)`, separately compare the number
lifted out of `current` against `_part_number(window)`, then splice). Same outcome, but it
needs the ownership oracle from (a) anyway (to tell "already right" from "hand-written"
when `retitle` returns `""`), plus a number-splicing step and an explicit precedence rule
between the two diffs. Strictly more code and more to get wrong, for an identical result.

**(c) Add an optional `part_num=` to `retitle`** so it emits `Phần {part_num}` instead of
lifting the group. Tempting — one function, one `""` contract — but `rename.py`
deliberately does not import `tts.video` (`rename.py:34-35`: "importing tts pulls in the
whole render stack for one string"), so this makes `rename.py` a **third** formatter that
must agree with `build_upload_title` about the exact `" - "` join. Under (a) there are
still only two, and the pushed title is the builder's own output.

**Rejected variant (a′): gate the number axis on `self._part_offsets` being non-empty.**
This would avoid widening behaviour beyond the renumber case (see A1) but it breaks the
undo: after `_reset_part_numbers` the offsets are gone while the published channel titles
still carry the corrected numbers, and those parts must still be offered so the user can
push the automatic numbers back. A2 is symmetric under reset; a′ is not.

### D2. One ownership predicate, in `rename.py` — recommend

Add beside `title_name`:

```python
def is_generated_title(current: str, new_name: str, known_names) -> bool:
    """Is this a title WE generated (either shape, for a name this novel has gone by),
    as opposed to a hand-written one? The recognition half of `retitle`, on its own."""
```

Refactor the recognition out of `retitle:182-196` into a private helper both use (e.g.
`_recognise(current, known) -> tuple[str | None, bool]` returning the `Phần N` group and
whether the title is ours), so `retitle`'s behaviour is defined by the same code and
cannot drift from the new predicate. `retitle`'s public contract — including lifting `N`
verbatim — **does not change**, so `tests/test_rename.py:184`, `:193` and `:270` stay green
untouched. That is a hard constraint, not a nice-to-have: 099 relies on `retitle`
preserving `N` so the project-open `resync_title_sidecars` cannot undo a correction.

Then route the two existing duplicate guards through it: `_title_update_rows` (which
currently gets ownership for free from `retitle`'s `""`) and
`_renumber_title_sidecars:1262` (`title_name(...) not in known`). Per the last row of the
facts table the substitution at `:1262` is **behaviour-preserving** — same predicate,
spelled once instead of twice.

### D3. Preserving "what is on the channel" before overwriting a published sidecar — recommend

This is the interaction requirement 2 creates with requirement 3, and it must be solved or
requirement 3 silently fails for older projects.

`_title_update_rows:4716-4719` takes `current` from `read_upload_state(path)["title"]`
**falling back to the `.title.txt`**. For a part uploaded before that key was recorded, the
sidecar *is* the only record of the channel title. Rewrite it with the new number and
`current == target`, so the part drops out of the rows — the exact bug we are fixing, moved
one step along. The `_publish` helper at `tests/test_tab_video.py:5343` writes
`{"status": "published"}` with no `title`, i.e. the real reported shape hits this.

**Recommendation:** in `_renumber_title_sidecars`, immediately before overwriting a
published part's sidecar, if the record has no `title`, backfill it:

```python
state = read_upload_state(out)
if state.get("status") == STATE_PUBLISHED and not str(state.get("title") or "").strip():
    write_upload_state(out, title=<the sidecar text about to be replaced>)
```

This moves the fact to its canonical home at the one moment the only other copy is about
to be destroyed. It is safe because `upload_state["title"]` has exactly one consumer
(facts table), and `write_upload_state` merges.

Note the consequence for `rename.resync_title_sidecars:268-271`, which deliberately skips
published parts on an order-only change. That stays, and it stays **consistent**, not
contradictory, once the rule is stated as: *the sidecar of a published part may be rewritten
only when the channel title has been preserved elsewhere first.* An order flip preserves
nothing and leaves the sidecar alone (its `test_order_only_switch_leaves_an_uploaded_part_alone`,
`test_rename.py:284`, stays green); a renumber backfills, then rewrites. Put that sentence in
both docstrings.

### D4. Re-render path — verified to agree, nothing to change

`workers.VideoWorker._write_metadata` writes the same bytes as `_renumber_title_sidecars`
(facts table), so a part renumbered-while-published and then re-rendered lands on the
identical text by either route. No fix needed; add the assertion as a test (Step 6) so it
stays true. One pre-existing wrinkle worth a docstring line but **out of scope**: a
re-render also overwrites a published sidecar without backfilling `upload_state["title"]`,
so a legacy record can still lose its channel title that way. It is pre-existing, and D3
closes the renumber route which is the one this feature opens.

## Ambiguities for you to decide

**A1 — D1(a) also offers parts whose number moved for reasons other than a renumber.**
Because the target is recomputed rather than lifted from the channel, a published part whose
computed number shifted from a manual split/merge of an *earlier* part is now offered too
(the split's own parts lose their records with their folder in `_delete_rendered_part:1346`,
but the untouched later parts keep theirs and shift by ±1). Today the app disagrees with
itself about those forever and never says so.
*Recommendation: accept it.* It is the same defect in the same direction, the confirm dialog
at `_launch_title_update:4770-4784` lists every title before anything moves, and the narrow
alternative (a′) breaks the reset case. If you would rather not widen it, say so and I will
re-cost (b) with an explicit "only when an offset anchors this part" clause and document the
reset asymmetry as a known gap.

**A2 — should a `marked_by_hand` published part's sidecar be rewritten?** It has no
`video_id`, so it can never be offered for a push; rewriting its sidecar makes the app's
files disagree with a channel we cannot address.
*Recommendation: rewrite it anyway* — the table already shows the corrected number, the
sidecar is what a future *re-upload* would use (`_upload_request:4007`), and we have no way to
know what that hand-uploaded video is called in the first place. Cheap to flip if you disagree
(one `state.get("marked_by_hand")` check).

**A3 — the legacy flat layout with the `.mp4` deleted.** `_part_output_path:889-893` falls
back to the flat path only when the flat `.mp4` exists, so a legacy part whose video was
deleted resolves to the per-folder path and its flat sidecars are invisible — to the renumber
pass *and*, today, to `_part_metadata` and `_upload_request`.
*Recommendation: out of scope*, noted in the history. Fixing it means teaching
`_part_output_path` to probe sidecars, which changes every caller's meaning.

**A4 — a renumber during a running render.** `_on_video_list_context_menu:937` has no
"worker is running" guard, and `VideoWorker.run` reads `part_offsets` once at `:2544`. A
renumber committed mid-render means the worker writes the pre-renumber number for parts it
renders afterwards while the GUI thread writes the new one — last write wins.
*Pre-existing for unpublished parts; this feature only widens it to published ones.
Recommendation: out of scope,* but a two-line guard (disable "Đổi số phần…" while
`self._video_worker.isRunning()`, matching how `_launch_title_update:4745-4756` refuses
overlapping sessions) is cheap if you want it folded in.
