# 065.03 — Tự động cập nhật mô tả khi đổi tên chương

Extends `065.01-INITIAL-PLAN.md` and `065.02-SHORTEN-BY-AI-PLAN.md`.

## 0. What is actually stale — and what is not

Traced through the code, **the computed description is already self-refreshing**:

`showEvent` (`tab_video.py:2168`) → `refresh_projects()` → `picker.refresh()`, which ends in
`_on_index_changed` → emits `project_selected` (`widgets.py:118`) → `_on_project_selected`
(`tab_video.py:2173`) closes and **reopens** the project → `_refresh_video_list()` →
`_windows_for_current_selection()` re-reads `self.project.chapters()` (`tab_video.py:629`).

So every activation of tab 5 rebuilds the parts table from fresh DB rows. `_compute_part_description`
therefore already reflects a rename the moment you switch to the video tab.

**The one stale surface is the `.txt` sidecar of an already-rendered part.** It is written
once, at render time (`workers.py:1693`), and never touched again — while two readers
*prefer* it over recomputation:

- `_part_metadata` (`tab_video.py:1488`) — so "Chi tiết phần" keeps showing the old chapter name.
- `_upload_request` (`tab_video.py:2915`) — so the **old name is what gets typed into YouTube**.

This is exactly the bug `_resync_tags_sidecars` (`tab_video.py:2288`) already solves for tags,
and its docstring describes this same failure mode almost word for word. The fix is its sibling.

## 1. Decisions

### 1.1 Detect by comparing content, not by hooking every rename

A chapter title can change through at least six routes:

| route | call |
|---|---|
| rename in "Tải truyện" | `tab_scrape._on_title_edited` → `edit_title` (`tab_scrape.py:653`) |
| undo a rename | `tab_scrape._reset_title` → `reset_title` (`tab_scrape.py:664`) |
| edit the original pane in "Dịch" | `tab_translate._save_original_edits` → `edit_title` (`tab_translate.py:408`) |
| edit the translated title in "Dịch" | `_on_translated_title_edited` → `edit_translation(idx, title=…)` (`tab_translate.py:416`) |
| Tìm & Thay thế | bulk update over `FIELD_TITLE` / `FIELD_TRANSLATED_TITLE` (`find_replace.py:23,26`) |
| a re-translation | the translate worker rewriting `translated_title` |

`chapter_marker_title` reads `translated_title or title` (`merge.py:157`), so **all six** move
the description. Wiring a signal into each is six edit sites, six chances to miss one, a new
cross-tab signal through `Workspace`, and it still would not fix a rename made in a previous
session or in another workspace.

**Instead: recompute and compare.** A generated description is a pure function of the DB, so
"is this sidecar stale?" is answered by generating it again and diffing strings. One code
path, covers every route including ones added later, and self-heals across restarts.

### 1.2 Enumerate rendered parts from disk, not from the current UI selection

`_resync_tags_sidecars` walks `_windows_for_current_selection()` — fine for tags (one string for
the whole novel) but wrong here, because a part's description depends on *its own* chapter span,
and the current mode/batch/range may not produce the windows that were actually rendered.

So the resync scans `self.project.video_dir` for the per-part subfolders and parses each
`{slug}-{first}-{last}` name back into a span — the same enumeration
`discover_committed_video_windows` (`video.py:388`) already does with `_COMMITTED_SUFFIX_RE`
(`video.py:385`). Rebuild each window's chapter list from `project.chapters()` filtered to
`first <= index + 1 <= last`. Result: the resync is entirely independent of what the user has
selected in the tab, so a batch-size spinbox tick can't change which sidecars are considered.

Factor the shared scan out of `discover_committed_video_windows` into
`iter_rendered_part_dirs(video_dir, slug) -> Iterator[tuple[Path, int, int]]` in `video.py`, and
have both call it — the existing function keeps its `effective_created` filter, the resync does not
(a part manually ticked "đã tạo" without a real render has no sidecar to fix).

### 1.3 Never overwrite a customised description

065.02 lets the user replace a part's `.txt` with an AI-shortened index. A blind resync would
silently destroy that on the next tab switch — the shortened titles are not recoverable from the
DB, so this is real data loss, not a regeneration.

**Classification, in order:**

1. Text equals the freshly computed rich description → **fresh**, do nothing.
2. Text equals what `build_youtube_description` would produce for this span → **legacy generated**
   (the simple form `render_video` writes at `video.py:791`), rewrite.
3. Text *structurally* matches the rich generated shape — first line starts with `Tên truyện: `,
   contains a `Mục lục chương:` line, and its last non-empty line starts with `Tạo bởi: ` →
   **generated but stale**, rewrite.
4. Anything else → **customised**, leave the file untouched and flag it (§1.4).

Check 3 is what actually does the work, and it is deliberately shape-based rather than
sentinel-based: existing sidecars on users' disks predate this feature and could never carry a
sentinel we add now. The AI-shortened form fails it on two independent counts (no `Tên truyện:`
first line, no `Tạo bởi:` last line), so it is structurally safe from clobbering.

A hand-edited description that kept the full header *would* be rewritten. Accepted: `desc_edit`
is read-only (`tab_video.py:1525`), so there is no hand-edit path today, and the `Shorten by AI`
output is the only customisation the app can produce.

### 1.4 A customised sidecar that went stale is flagged, not fixed

Row-level: reuse the ⚠️ + amber treatment 065.01 §2.5.4 adds to the "Chương" cell, with a third
warning sentence:

```
Tên chương đã đổi sau khi tạo video, nhưng mô tả của phần này đã được rút gọn bằng AI
nên không tự cập nhật — mở “Chi tiết” rồi bấm “Shorten by AI” lại, hoặc “Khôi phục mô tả gốc”.
```

Dialog-level: `_show_part_detail` gains **`Khôi phục mô tả gốc`** next to `Shorten by AI`, enabled
only when the sidecar is customised. It writes the freshly computed rich description over the
sidecar and into `desc_edit` — the deliberate, one-click way to discard a shortening.

### 1.5 When it runs: once per project open

`_on_project_selected` (`tab_video.py:2173`), at the end, right before its existing
`_refresh_video_list()` at line 2212 — after the per-project settings are restored so
`self.credit` and friends are current.

Not in `_refresh_video_list`: that fires on every spinbox tick (`tab_video.py:393-397`), and a
file read per rendered part per keystroke is a real cost on a 200-part novel. Once per project
open is enough because **a rename forces a reopen**: returning to tab 5 runs
`showEvent → refresh_projects → picker.refresh → project_selected → _on_project_selected`, which
closes and reopens the project unconditionally.

Known gap: a rename made in workspace A while tab 5 of workspace B is *already* visible is not
picked up until that tab is left and re-entered. Documented in §5; not worth a cross-workspace
watcher.

Cost when it does run: one `iterdir`, then per rendered part one small file read plus an O(chapters)
string build. Negligible next to reopening the project.

### 1.6 The rewritten text goes through the 5000-char fit

`_resync_description_sidecars` calls the same `fit_video_description` the render uses, so a
resynced description obeys 065.01's cap — including picking up a *longer* new chapter name by
dropping a chapter from the tail rather than busting the limit.

## 2. File-by-file changes

### 2.1 `src/noveltrans/tts/video.py`

```python
def iter_rendered_part_dirs(video_dir: Path, slug: str):
    """`(part_dir, first_num, last_num)` for every per-part subfolder of this novel.

    The shared scan behind `discover_committed_video_windows` and the video tab's
    description resync. Yields folders only — whether a part counts as "đã tạo"
    (a real render vs. a manual tick) is the caller's question.
    """
```

`discover_committed_video_windows` is rewritten over it, keeping its `effective_created` filter
and its return type unchanged so `plan_locked_video_windows` is untouched.

### 2.2 `src/noveltrans/tts/description.py` (the module 065.01 creates)

```python
def looks_generated(text: str) -> bool:
    """True when `text` has the shape `build_video_description` produces.

    Shape, not sentinel: sidecars written before this feature existed can't carry a
    marker, so staleness has to be judged from the text itself — first line
    `Tên truyện: `, a `Mục lục chương:` line, last non-empty line `Tạo bởi: `.
    An AI-shortened description (065.02) fails this on two counts and is therefore
    never mistaken for a regenerable one.
    """
```

### 2.3 `src/noveltrans/gui/tab_video.py`

**`_resync_description_sidecars(self) -> tuple[int, int]`** — returns `(rewritten, stale_customised)`,
placed next to `_resync_tags_sidecars` and sharing its docstring's framing:

1. `slug = slugify(self.project.meta.translated_title or self.project.meta.title)` (the same
   derivation `_part_output_path` uses at line 706 — and for the same reason: the slug, not
   `display_name()`, is what named these folders).
2. `chapters = self.project.chapters()`; `total_chapters = self.project.counts()["total"]`;
   `novel_title = self.project.meta.display_name()` — hoisted once.
3. For each `(part_dir, first, last)` from `iter_rendered_part_dirs`:
   - `sidecar = part_dir / (part_dir.name + ".txt")`; skip unless it and the `.mp4` both exist.
   - Build segments from the chapters in `[first, last]` exactly as `_compute_part_description`
     does (`MergeSegment(path="", seconds=c.audio_seconds, title=chapter_marker_title(c))`).
   - `fresh, _dropped = fit_video_description(...)`; `current = sidecar.read_text(...)`.
   - `if current == fresh: continue`
   - `if looks_generated(current) or current == build_youtube_description(segments, novel_title):`
     write `fresh`, `rewritten += 1`
   - `else: self._stale_descriptions.add(part_dir.name); stale_customised += 1`
4. `self._stale_descriptions: set[str]` is reset at the top of each run and consulted by
   `_chapter_range_item` for the §1.4 row warning; it is initialised in `__init__` beside
   `_locked_part_numbers`.

**`_on_project_selected`** — call it just before the existing `_refresh_video_list()` (line 2212)
and fold the counts into the status line, mirroring `_on_tags_ready`'s `(đã cập nhật N phần đã tạo)`:

```python
rewritten, stale = self._resync_description_sidecars()
```
→ appends `" (đã cập nhật mô tả {rewritten} phần)"` and/or
`" ⚠️ {stale} phần có mô tả rút gọn đã cũ"`.

**`_show_part_detail`** — the `Khôi phục mô tả gốc` button from §1.4, in the same
`desc_row` as `Shorten by AI`, `setEnabled(part_dir.name in self._stale_descriptions)`.
Handler `_restore_generated_description(window, desc_edit, status, whole_novel)`: recompute,
write the sidecar, update `desc_edit`, drop the name from `_stale_descriptions`, refresh the
character-count label from 065.01 §2.5.5.

**`_chapter_range_item`** — third warning sentence per §1.4.

### 2.4 Module docstring (`tab_video.py:8`)

The `<name>.txt` bullet should say the sidecar is re-synced from the DB when chapter titles
change, and that an AI-shortened one is flagged instead of overwritten.

## 5. Risks / follow-ups

- **A rename in another workspace while this tab is already visible** is not seen until the tab is
  re-entered (§1.5). A `chapters_changed` signal fanned out through `Workspace` would close it;
  deferred as disproportionate.
- **`.title.txt` and the thumbnail are not resynced.** The part *title* is `{vn_title} - Phần N`,
  which depends on the novel title, not chapter names — a novel rename already goes through
  `_refresh_video_list` (line 2236 notes exactly this). Out of scope, but if a novel rename should
  also restamp `.title.txt`, that is the same shape of fix and belongs in the same helper.
- **The resync silently upgrades legacy simple descriptions to the rich form** (check 2). This is a
  visible change to an existing part's description on first open after upgrading. Judged an
  improvement — the rich form is what every render since feature 025 produces — but it is a change
  the user did not ask for on that specific part, so the status line reports the count.
- **Deleting a chapter** changes a rendered part's span without changing its folder name, so the
  resync would rebuild the description from whatever chapters now fall in `[first, last]` — fewer
  lines, and timestamps that no longer match the audio in the mp4. Renaming is the asked-for case
  and is safe; deletion after a render is a pre-existing hazard this does not make worse, but the
  resync should skip a part whose recomputed chapter count differs from the sidecar's current
  timestamp-line count, leaving it flagged instead. Worth building in step 3.
