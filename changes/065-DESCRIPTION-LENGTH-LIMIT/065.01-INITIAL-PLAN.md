# 065.01 — Giới hạn 5000 ký tự cho mô tả video: Implementation Plan

## 0. Problem, restated precisely

`build_video_description` (`src/noveltrans/tts/video.py:487`) emits a description whose length grows linearly with the number of chapters in a part:

```
Tên truyện: {original_title} — "{vn_title}"      ┐
Tác giả: {original_author} "{vn_author}"          │ mandatory header
Số chương: {total_chapters}                       │
                                                  │
Mục lục chương:                                   ┘
0:00 {ch1 title}                                  ┐ grows with the batch size
2:05 {ch2 title}                                  ┘
                                                  ┐ mandatory footer
Tạo bởi: {credit}                                 ┘
```

Measured with a realistic header (`Tên truyện: 穿书反派 — "Xuyên sách phản diện"` / `Tác giả: …` / `Số chương: 1990` / `Tạo bởi: Fox Novel`) the mandatory skeleton costs **130 characters**, leaving ~4870 for the table. At ~63 chars per chapter line (`1:23:45 Chương 1234: <a longish Vietnamese title>`) that is **~74 chapters**; with shorter titles ~110. The default batch is 10 (`config.py:465`), so normal use is nowhere near the cap — but "tạo theo lô quá lớn" (batch 100/200, or a whole-novel `all`-mode video) blows straight through it, and `youtube_upload._fill_box` then `insert_text`s a >5000-char string into Studio, which truncates or rejects it.

Two writers produce the `.txt` description sidecar, and both currently write uncapped:

| writer | file | note |
|---|---|---|
| `VideoWorker._write_metadata` | `src/noveltrans/gui/workers.py:1684-1693` | the rich builder — this is what normally survives |
| `render_video` | `src/noveltrans/tts/video.py:791-793` | the simple `build_youtube_description`, written first, then overwritten by the above |

Three readers consume it: `_part_metadata` → the detail dialog (`tab_video.py:1477`), `_upload_request` → `UploadRequest.description` (`tab_video.py:2915`), and `_compute_part_description` (`tab_video.py:1457`) as the fallback when no sidecar exists.

## 1. Decisions

### 1.1 Where the cap lives

A **new pure module `src/noveltrans/tts/description.py`**, modelled directly on `src/noveltrans/tts/tags.py`: one module that owns one YouTube field budget, stdlib-only, no `MergeSegment`/ffmpeg/PIL dependency, unit-testable without a render.

Constant: **`YOUTUBE_DESCRIPTION_CHAR_LIMIT = 5000`** (sibling of `YOUTUBE_TAG_CHAR_LIMIT = 500`).

Why a new module rather than putting it in `video.py`: `youtube_upload.py` needs the defensive clamp (§1.6) and must not import `tts/video.py`, which drags in `subprocess`, `tts.merge`, and `tts.player_skin` (PIL). `tts/__init__.py` is light (a registry with lazy engine imports), so `from noveltrans.tts.description import clamp_description` costs nothing — exactly how `storage/project.py:876` already imports `noveltrans.tts.tags`.

### 1.2 How length is counted — plain count, but in UTF-16 code units, and **no headroom**

`tags.py`'s module docstring argues for a deliberately conservative worst-case cost model because *YouTube's tag counter is undocumented and was observed to disagree with a naive sum*. That reasoning **does not transfer** here, and the plan should say so out loud in the new module's docstring:

- The description limit *is* documented (`snippet.description`, max 5000 characters) and Studio's counter is a plain per-character count with no separator/quoting surcharges. There is nothing to guess at, so **no arbitrary safety margin is added** — burning 5% of the budget "just in case" would cost ~5 chapters per part for no known reason.
- The one place a naive Python `len()` genuinely diverges from Studio's counter is **astral characters** (emoji, rare CJK ext-B): Studio's counter is JavaScript `String.length`, i.e. UTF-16 code units, where an emoji counts **2**; Python's `len()` counts it as **1**. Vietnamese diacritics are BMP and count 1 in both. A translated chapter title with an emoji is uncommon but entirely possible.

So: **`description_length(text) = len(text.encode("utf-16-le")) // 2`** — exact for Studio's counter, cheap, and conservative only where Studio actually is. This is tags.py's *philosophy* (model the counter, don't guess) applied to a case where the counter is knowable.

### 1.3 The truncation algorithm

Only the chapter table is trimmed; the header block and the `Tạo bởi:` line are never touched (per the prompt's requirement).

**Which lines survive: a strict prefix (the earliest chapters), dropping the tail.** This is not arbitrary and is the key departure from `parse_tags`, which `continue`s past an over-budget tag and keeps scanning:

- YouTube only turns a description into clickable chapters when the **first timestamp is `0:00`** and the timestamps ascend (already documented in `build_youtube_description`'s docstring). Dropping from the head would destroy the chapter feature outright.
- Tags are an unordered set, so a hole in the middle is invisible; a chapter index is an ordered prefix, where a hole ("…0:00, 5:51, 47:02, then chapter 12 out of nowhere") reads as a bug. So the loop **`break`s at the first line that does not fit** rather than `continue`ing.

**Marker line — exact wording:**

```
… còn {dropped} chương nữa (mục lục rút gọn cho vừa giới hạn {limit} ký tự mô tả của YouTube).
```

(86 chars at `dropped=1990`, `limit=5000`.) It is appended as the last line of the chapter block, i.e. immediately after the surviving timestamps and before the blank line + `Tạo bởi:`. It deliberately carries **no leading timestamp**, so YouTube's chapter parser ignores it. The leading `… ` doubles as the machine-detectable sentinel (`TRUNCATION_PREFIX = "… còn "`) used by `was_truncated()` so the GUI can flag a description it read back from a sidecar without re-deriving it.

**How the marker's own length is accounted for** — the circularity (marker length depends on the digit count of `dropped`, which depends on how many lines fit, which depends on the marker length) is broken by **reserving the marker at its worst case**: render it with `dropped = len(chapter_lines)` (the largest value it can ever take) and reserve that length + 1 for its newline *before* the greedy loop. `len(str(n))` is monotonic in `n`, so the reservation can only ever be too generous — never too small. Worst case it wastes 1–3 characters. This is the same "reserve the worst case, accept a few fewer entries" trade `parse_tags` makes.

**Full algorithm** (`fit_description`):

1. Join `before + chapter_lines + after` with `"\n"` plus a trailing `"\n"`. If it already fits, return it with `dropped = 0` — the untruncated path is byte-identical to today's output, so no existing sidecar or test changes.
2. `fixed = description_length(join(before + after))`. This is exact: `join(A+C+B)` is `join(A+B)` plus `sum(len(line) + 1 for line in C)`, so the per-line cost is simply `description_length(line) + 1`.
3. `budget = max_chars - fixed - (description_length(worst_case_marker) + 1)`.
4. Greedily accumulate chapter lines in order while `used + cost <= budget`; `break` on the first that doesn't fit.
5. `dropped = total - len(kept)`; append the marker rendered with the real `dropped` when `dropped > 0`.
6. Re-join and pass through `clamp_description` as a final, unconditional guarantee (§1.4), then return `(text, dropped)`.

### 1.4 Edge cases

| case | behaviour |
|---|---|
| **Header block alone already over the cap** (absurd `original_title`/`vn_title`/`credit`) | `budget` goes negative → zero chapters kept → the final `clamp_description` cuts the whole text down to the cap on a line boundary. The mandatory block is preferred over the table, but the hard invariant "never exceeds 5000" wins over "never touch the header": sending a >5000 string to Studio means Studio truncates it wherever *it* likes, which is strictly worse. Unreachable in practice (needs a ~4900-char header); covered by a test. |
| **Zero chapters kept, `dropped > 0`** | The marker line is still emitted — it is what explains the empty table. The wording (`… còn 87 chương nữa (…)`) reads correctly with nothing above it, which is why it is phrased as a standalone parenthetical rather than a trailing ellipsis on the previous line. |
| **A single chapter line alone busts the budget** (pathological title) | The loop `break`s → that chapter and everything after it are dropped and reported by the marker. No per-title truncation: silently mangling a chapter title is worse than honestly reporting it as not listed. |
| **Very long chapter titles generally** | Naturally handled — fewer lines fit, marker reports the rest. |
| **`chapter_lines` empty** | `fixed` is the whole text; `dropped = 0`; no marker. |
| **Fewer than 3 surviving timestamps** | YouTube stops generating chapter markers (its documented minimum). Only reachable at absurd header sizes / a shrunk `max_chars`; noted in §5, not defended against. |

### 1.5 `build_youtube_description` — yes, capped too

It writes to `out_path.with_suffix(".txt")`, the **exact same path** `_write_metadata` writes the rich description to. In the normal GUI flow the rich one overwrites it, but if `render_video` succeeds and `_write_metadata` then raises (e.g. a `project.counts()` failure), the simple one is what `_upload_request` reads and types into Studio. Routing it through the same `fit_description` is 3 lines. Do it.

### 1.6 Upload path — yes, a defensive clamp, at `UploadRequest.__post_init__`

This is the direct analogue of the `save_tags` choke point (`storage/project.py:869-878`, whose docstring already states the principle: *"the single choke point every write goes through, so it's the one place that must never let an over-budget string reach disk"*). It is **not** redundant here, because `_upload_request` (`tab_video.py:2914`) prefers `self._read_sidecar(window, whole_novel, ".txt")` — a file possibly written **by an older version of this app**, before this feature existed. Every project with already-rendered oversized parts is exactly the population that reported this bug, and re-rendering them just to fix a description is unacceptable.

`__post_init__` (not `validate()`): `validate()` raises, and refusing an upload over a too-long description would be a regression. The clamp is silent and lossy-but-safe.

`clamp_description` cuts on a **line boundary** (back off to the last `\n` within budget) rather than mid-line, so a clamped legacy description ends on a whole timestamp line instead of `1:04:22 Chương 88: Ngư`. It falls back to a hard cut if there is no newline in budget. It cuts in UTF-16 space (`text.encode("utf-16-le")[:limit*2].decode("utf-16-le", errors="ignore")`) so a surrogate pair is never split. A clamped legacy description loses its `Tạo bởi:` line — accepted; re-rendering the part regenerates it correctly.

### 1.7 UI pre-warning at batch-selection time — **yes, in the parts table; no hard block**

**In scope:** a ⚠️ flag + tooltip on the **"Chương" cell** (`_chapter_range_item`, `tab_video.py:912`) of any part whose description will be truncated. This is the right surface and it is nearly free:

- It is the *cause* column (chapter count per part), and it already carries a ⚠️ + amber `#e5c07b` + tooltip treatment for the "locked short" case, so the pattern exists.
- `self.video_batch_size.valueChanged` is already connected to `_refresh_video_list` (`tab_video.py:395`), so the warning appears/disappears **live as the user drags the batch spinbox** — that *is* the batch-time pre-warning, with no new plumbing.
- The `_duration_item` sibling (`tab_video.py:946`) sets the precedent exactly: YouTube's 12-hour video cap is **flagged, never enforced**.

**Also in scope:** a character counter + truncation note in the part-detail dialog (`_show_part_detail`, `tab_video.py:1499`), and a tooltip on the batch spinbox.

**Explicitly out of scope (with reasons):**

- **Capping/refusing at batch-split time** (`plan_locked_video_windows`, `video.py:423`). Rejected: (a) the safe maximum is not a fixed number — it depends on the header and on this part's chapter title lengths, so any hard limit would be either wrong or absurdly conservative; (b) batch size is a deliberate user choice about video length and upload cadence, and the 12h cap is already only flagged; (c) committed windows are frozen by design and could not be re-split to satisfy a new rule anyway, so enforcing it would break existing projects. Warn, never block.
- **A new `VideoWorker` signal to report truncation during a render.** Requires a new `Signal(str)` plus handler wiring in `tab_video`, and it would fire *after* the user already committed to a render — whereas the table flag warns *before* and persists *after*. Not worth the surface area.
- **A confirmation modal on "Tạo video"** when parts would truncate. That is a render the user runs constantly; an extra modal in that path is worse than the passive flag.

## 2. File-by-file changes

### 2.1 NEW — `src/noveltrans/tts/description.py`

Module docstring in the style of `tags.py`: state the 5000 limit, state that unlike tags the counter is documented and deterministic so **no headroom is charged**, state that it is measured in UTF-16 code units because Studio's counter is JS `String.length`, and state the prefix rule (chapters must start at `0:00`, so the head survives and the tail is dropped — the opposite of `parse_tags`, which skips and keeps scanning).

```python
YOUTUBE_DESCRIPTION_CHAR_LIMIT = 5000

TRUNCATION_PREFIX = "… còn "
_TRUNCATION_LINE = (
    TRUNCATION_PREFIX
    + "{dropped} chương nữa (mục lục rút gọn cho vừa giới hạn "
      "{limit} ký tự mô tả của YouTube)."
)

def description_length(text: str) -> int: ...
def truncation_line(dropped: int, limit: int) -> str: ...
def was_truncated(text: str) -> bool: ...          # any line startswith TRUNCATION_PREFIX
def clamp_description(text: str, *, max_chars: int | None = None) -> str: ...
def fit_description(
    before: list[str],
    chapter_lines: list[str],
    after: list[str],
    *,
    max_chars: int | None = None,
) -> tuple[str, int]:                               # (text, chapters dropped)
```

**`max_chars: int | None = None`, resolved to the constant *inside* each function**, not bound as a default at `def` time. Rationale, worth a one-line comment: a bound default cannot be monkeypatched, which would force GUI tests to build 150-chapter fixtures just to reach the cap; resolving at call time lets a test shrink `YOUTUBE_DESCRIPTION_CHAR_LIMIT` and exercise the whole GUI path against the existing 5-chapter fixture.

Guarantee to assert in the docstring and in tests: **`fit_description` always returns text with `description_length(text) <= max_chars`.**

## 5. Risks / follow-ups

- **If Studio's counter turns out to disagree** (e.g. counting a newline as CRLF = 2 units, which would cost ~110 characters on a full table), the fix is a single subtraction inside `fit_description` — this is precisely the situation `tags.py`'s docstring records having been burned by. Deliberate call: ship with zero margin, because the field is documented and the failure mode is loud (Studio's counter turns red at upload time). Do **not** pre-emptively add slack.
- **YouTube's ≥3-timestamp minimum for chapter markers** is not defended: at a real 5000-char cap, `kept` is always ≥70, so it cannot be hit outside tests with a shrunk limit. Not worth a special case.
- **Legacy sidecars are clamped bluntly, not re-fitted** — a pre-feature oversized `.txt` uploaded today loses its trailing `Tạo bởi:` line rather than gaining a proper `… còn N chương nữa` marker. Re-rendering the part fixes it. A "rewrite the sidecars without re-rendering the video" action would fix it in place; deferred as a separate feature.
- **`VideoWorker` does not report truncation during a render** (§1.7). If the table flag proves too passive in practice, the follow-up is a `note = Signal(str)` on `VideoWorker` routed into `tab_video.status_label`.
- **Adjacent uncapped field, out of scope:** `build_upload_title` (`video.py`) has no cap, but YouTube titles max out at **100 characters** — `f"{vn_title} - Phần 12"` with a long Vietnamese title can exceed that. Exactly the same class of bug, same fix shape (`description.py` would become the natural home for a `YOUTUBE_TITLE_CHAR_LIMIT`). Flagged, not touched.
- **README** documents the `.txt` sidecar (line 252) but says nothing about description length; no update required, though a clause in the video-tab row would be reasonable if the user wants it.
