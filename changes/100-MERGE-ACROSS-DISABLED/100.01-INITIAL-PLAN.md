# Plan: merge two parts separated only by disabled chapters (feature 100)

## Verified facts this plan rests on

| Claim | Evidence |
|---|---|
| Adjacency is asserted in exactly two places | `grep -rn "+ 1 ==" src/noveltrans/` returns only `src/noveltrans/video_windows.py:97` (docstring) / `:102` (the raise) and `src/noveltrans/gui/tab_video.py:986` |
| `video_windows.py` is pure | its only imports are `json` + `pathlib` (`:25-26`); every test in `tests/test_video_windows.py` takes just `tmp_path` and never builds a project |
| `split_window` has no adjacency test | `video_windows.py:68-91` — validates only `0 < tail_chapters < total`. **Out of scope, confirmed.** |
| A window's displayed `first_num`/`last_num` are trimmed to *available* chapters | `tts/video.py:782` (`MergeWindow(sel[0].index + 1, sel[-1].index + 1, sel)`) and `tts/merge.py:142-143` |
| The grid walk itself is already 098-correct | `tts/video.py:783` advances `lo = hi + 1` over **grid** numbers, and `hi` comes from `_batch_window_end(..., disabled_numbers)` (`:778`, `tts/merge.py:98-115`) |
| Disabled set already has a canonical spelling | `{c.index + 1 for c in chapters if not c.enabled}` at `tts/video.py:764` and `tts/merge.py:64` |

So the bug is precisely: the planner reasons in **grid slots** (slot after 223-233 starts
at 234), the adjacency check reasons in **displayed spans** (part 14 displays as
235-241). 233 + 1 ≠ 235.

## Design decisions (decide before coding)

### D1. Signature of `merge_windows` — recommend (a), `disabled_numbers: set[int]`

```
merge_windows(project_path, first_a, last_a, first_b, last_b, *, disabled_numbers=None)
```

- **(a) `disabled_numbers: set[int]` — recommended.** A set of ints keeps the module
  `json`+`pathlib` only. It reuses the exact parameter name and meaning already
  established by feature 098 in `tts/merge.py:98` (`_batch_window_end`) and
  `tts/merge.py:169-170` (`part_number`), so one concept has one name across the
  codebase. It is trivially testable with no DB, which is what
  `tests/test_video_windows.py` currently buys (every test is `tmp_path` + ints; the
  whole file runs in milliseconds with no `NovelProject`, no Qt, no sqlite).
- **(b) chapters list / `enabled_numbers`.** Needs the whole chapter universe to tell
  "absent" from "enabled", drags the `Chapter` model (or a parallel notion of it) into a
  module that stores two ints, and invites a future reader to re-filter by voice/audio
  inside it — which is the planner's job, not the sidecar's.
- **(c) caller passes a boolean.** Directly violates requirement 3: the API boundary
  would enforce "whatever the GUI decided", which is one layer up the very failure mode
  being fixed (two sites, one rule, drift).
- **(d) read `chapters.db` inside `video_windows.py`.** Destroys the pure-module
  property, adds a sqlite dependency and an import path into `storage.project`, and
  makes a pure function's answer depend on hidden state.

**Keyword-only with `None` default**, treated as the empty set. Rationale: omitting it
can only make the merge *more* refusing, never wrongly permissive — the failure mode is
fail-safe, so a default costs little and keeps the existing 5-argument tests meaningful
as "no disabled chapters → pre-098 behavior, byte identical".

### D2. One predicate owns both the rule *and* the wording — recommend

Add to `video_windows.py`:

```
def merge_adjacency_error(last_a, first_b, disabled_numbers=None) -> str | None
```

Returns `None` when the merge is allowed, otherwise the exact Vietnamese message.
`merge_windows` raises `ValueError(reason)`; the menu does
`action.setEnabled(reason is None)` / `action.setToolTip(reason or "")`. This makes
requirement 3 structural rather than a convention: the gate and the guard cannot
disagree about the rule *or* the message, and the tooltip automatically names the
offending chapters.

Precedent for UI copy living in a pure module: `video_part_numbers.plan_renumber`
(`video_part_numbers.py:174-190`) raises messages explicitly "meant for a dialog", which
`tab_video._renumber_part:1129-1131` shows verbatim in a `QMessageBox`.

### D3. The rule, exactly — with the one trap

Allowed iff **`first_b > last_a`** *and* **every integer in `range(last_a + 1, first_b)`
is in `disabled_numbers`**.

The ordering clause is **not optional**: with only the interval clause, an
overlapping/reversed pair (`merge_windows(p, 91, 96, 95, 100)`) yields an empty `range()`
and passes vacuously, silently breaking the existing
`tests/test_video_windows.py::TestMergeWindows::test_rejects_overlapping_windows`.

Boundary cases:

| Gap between `last_a` and `first_b` | Result | Why |
|---|---|---|
| empty (`first_b == last_a + 1`) | **merge** | today's rule, preserved exactly |
| only disabled chapters | **merge** | the fix |
| any enabled chapter | **refuse**, message names it | a real gap; merging would reorder |
| number with no chapter at all (deleted/never scraped) | **refuse** | not in `disabled_numbers`. Consistent with 098's deliberate split (`tts/merge.py:102-106`: a missing number still fills a slot). If it is re-scraped later it would be silently swallowed into an already-rendered part. **See A1.** |
| chapter exists and is enabled but has no audio in this voice | **refuse** | same reasoning: audio can arrive from a background run and would be swallowed. **See A1.** |
| `first_b <= last_a` (overlap / out of order) | **refuse** | explicit ordering clause |

## Step-by-step implementation

### Step 1 — Failing regression first (`tests/test_video_windows.py`)

Add to `class TestMergeWindows` a single test built from the real data, expected to fail:

```
merge_windows(tmp_path, 223, 233, 235, 241, disabled_numbers={65,192,199,200,209,227,234})
→ (223, 241);  read_manual_windows(tmp_path) == {223: 241}
```

Independently reviewable: it is the bug, stated once, in the cheapest possible test.

### Step 2 — The pure rule (`src/noveltrans/video_windows.py`)

1. New public `merge_adjacency_error(last_a, first_b, disabled_numbers=None) -> str | None`
   implementing D3. Compute `blocking = [n for n in range(last_a + 1, first_b) if n not in disabled]`.
2. A private `_describe_gap(blocking)` producing `"chương 234"` / `"chương 234, 236"` /
   `"chương 234, 236, 238 và 4 chương khác"` so a wide gap does not produce a
   200-character dialog.
3. Rewrite `merge_windows` (`:94-110`) to take `*, disabled_numbers: set[int] | None = None`,
   call the predicate, and `raise ValueError(reason)` when non-`None`. Everything below
   the guard (`:105-110`) is unchanged.
4. Update the `merge_windows` docstring at `:97-101` — the parenthetical
   `(last_a + 1 == first_b)` is now wrong — and add a paragraph to the **module
   docstring** (`:1-21`) stating the 098 interaction, since that docstring is the design
   record for this file.

Proposed strings (tone matched to `split_window`'s `"Số chương cắt ra phải từ 1 đến {n}
(phần có {n} chương)."` and `plan_renumber`'s "state the rule, then the remedy"; the
app's own word for a disabled chapter is **"bỏ qua"** — see `gui/widgets.py:894`,
`"Bỏ qua chương này"`):

- real chapter(s) between:
  `f"Chỉ gộp được 2 phần liền kề: giữa 2 phần này còn {_describe_gap(blocking)} chưa bị bỏ qua.\n\nMuốn gộp thì hãy bỏ qua (các) chương đó trước, hoặc gộp lần lượt từng cặp phần liền kề."`
- out of order / overlapping:
  `"Chỉ có thể gộp 2 phần liền kề nhau — phần sau phải bắt đầu ngay sau phần trước."`

The old blanket `"(không có khoảng trống)"` disappears from both sites, because it is now
false: a gap of disabled chapters *is* allowed.

### Step 3 — Make the disabled set available to the tab, from the same read (`src/noveltrans/gui/tab_video.py`)

The gate must see *the same* enabled set the plan was built from, or the two can disagree
on a stale DB read.

1. New cache field next to the existing three, at `tab_video.py:136-138`:
   `self._locked_disabled: set[int] = set()`, with a comment pointing at
   `_locked_batch_windows`.
2. In `_locked_batch_windows` (`:767-816`): hoist `chapters = self.project.chapters()`
   into a local (currently inlined at `:802`), pass it to `plan_locked_video_windows`,
   and inside the existing `if honor_committed:` block (`:808-815`) set
   `self._locked_disabled = {c.index + 1 for c in chapters if not c.enabled}`. Using the
   *same list object* the planner consumed is what makes gate and planner structurally
   unable to disagree; the `honor_committed` guard and its existing comment apply
   unchanged.
3. In the source-edition branch of `_windows_for_current_selection` (`:753-755`), clear
   `self._locked_disabled = set()` alongside `_locked_committed`/`_locked_manual`, for
   the same reason its comment already gives (caches are per-plan). Merge is hidden for
   that edition anyway, so this is hygiene.

*Optional sub-step (recommend yes):* extract `disabled_chapter_numbers(chapters) -> set[int]`
into `tts/merge.py` next to `_batch_window_end`, and use it at `tts/merge.py:64`,
`tts/video.py:764` and the new tab site. It removes the fourth copy of a comprehension
whose correctness the whole feature hangs on. Pure refactor, covered by existing tests;
skip it if you want the diff minimal.

### Step 4 — The menu gate (`tab_video.py:984-992`)

Replace

```
adjacent = window_a.last_num + 1 == window_b.first_num
```

with a lazy `from noveltrans.video_windows import merge_adjacency_error` (matching this
file's lazy-import style) and


`self._locked_disabled` is guaranteed fresh: `_on_video_list_context_menu` calls

### Step 5 — Pass it through the action (`tab_video._merge_parts`, `:1064-1090`)

1. Pass `disabled_numbers=self._locked_disabled` to `merge_windows`.
2. Wrap the call in `try/except ValueError` → `QMessageBox.warning(self, "Gộp phần", str(exc))`
   and return, mirroring `_renumber_part:1129-1131`. Unreachable while the gate agrees —
   which is the point: it is the API guard, and the gate can go stale between right-click
   and click.
3. Extend the `_confirm_restructure` `action_desc` (`:1069-1073`) so the swallowed
   chapters are stated, since the re-enable semantics are a real (if intended) surprise:
   `"gộp thành 1 phần (chương 223–241; chương 234 ở giữa đang bị bỏ qua — nếu bật lại sẽ thuộc phần này)"`.
   Compute the in-between disabled numbers from `self._locked_disabled` and omit the
   clause when there are none, so the common case reads exactly as it does today. Update
   the `_merge_parts` docstring to say it now merges across skipped chapters.

## Requirement 4: is the merged span `(first_a, last_b)` safe? — traced, yes

1. `merge_windows` writes `{223: 241}` into `video_manual_windows.json`.
2. `tab_video._locked_batch_windows:800-803` reads it and merges it over disk-discovered
   commits as `{**committed, **manual}` (manual wins); `workers.VideoWorker.run:2578-2586`
   does the identical thing, so the tab and the render worker cannot diverge.
3. `plan_locked_video_windows` (`tts/video.py:724-784`): `avail` excludes disabled at
   `:754-757`; `frozen = sorted(committed.items())` at `:765`; at `lo == 223` the branch
   at `:773-775` takes `hi = 241` wholesale; `sel` at `:779` picks enabled+voiced
   223..241, i.e. **234 is absent**; `part_num` increments **once** (`:780`), and the
   window is `(223, 241)` from `sel`'s own ends (`:782`).
4. The preceding fresh window cannot overshoot: `limit = min(max_num, upcoming[0] - 1)`
   at `:777` caps it at 222, so the walk lands on `lo == 223` exactly.
5. Consequences of the swallow: chapter 234 is absent from the concat list, the chapter
   markers and the description — the same treatment it already gets as a standalone
   disabled chapter. Folder/file name is `{slug}-0223-0241` (`video_part_name` from the
   window's ends), so `discover_committed_video_windows` will rediscover the same span
   after the re-render.
6. **Re-enable later**: 234 re-enters `avail` only once it is enabled *and* has audio in
   that voice; it then falls inside the frozen span and the part becomes 19 chapters.
   Span, folder name and part number are unchanged; nothing is renamed and no sidecar key
   moves. This is the behavior the prompt asks for. Note the part's rendered `.mp4` is
   then silently short by one chapter with no ⚠️ — `_chapter_range_item`'s "locked short"
   warning (`:1340-1400`) does not cover it. Worth a follow-up, not this fix.

## Requirement 5: audit of other "`last + 1 == first` means contiguous" sites

- **`discover_committed_video_windows` (`tts/video.py:663-694`)** — regex → `{first: last}`,
  no ordering or adjacency reasoning at all. Clean.
- **`plan_locked_video_windows`'s walk (`:771-783`)** — `lo = hi + 1` is over **grid**
  numbers, and `hi` comes from `_batch_window_end(..., disabled_numbers)`. Already
  098-correct. A frozen span abutting a disabled chapter is exactly the reported case,
  and the planner handles it correctly (the next slot starts at 234, the next *part*
  merely displays as 235-241). Clean.
- **`tts/merge._group_windows` (`:150-162`)** and **`part_number` (`:169-207`)** — same
  grid walk, `part_number` already accepts `disabled_numbers`. Clean.
- **`split_window` (`video_windows.py:68-91`)** — no adjacency anywhere; splits one span
  by a tail count. Confirmed out of scope.

**Broader blind spot found while auditing (flagging, not planning).** Because a window's
displayed ends are trimmed to *available* chapters (`tts/video.py:782`), any unavailable
chapter at a boundary breaks the display-level adjacency test — not only a disabled one.
With batch 10 and chapter 11 simply *not yet voiced*, the plan shows `(1,10)` and
`(12,20)` and the merge is refused today and still after this fix. The fully general fix
is to gate on **grid slots** instead of displayed spans, which means
`plan_locked_video_windows` returning each window's `(lo, hi)` alongside its
`MergeWindow` — a return-type change with two production consumers (`tab_video.py:801`,
`workers.py:2583`) and ~15 test call sites. Not recommended now; the narrow disabled-only
rule fixes the reported bug with a pure-function change and no planner churn. **See A1.**

**Latent bug found, pre-existing, out of scope.** If the *first* chapter of a manually
merged/split span is later disabled, the window's `first_num` drifts off the sidecar key
(223 → 224): the "đã tách/gộp thủ công" badge silently vanishes (`tab_video.py:1385`
tests `window.first_num in self._locked_manual`), and a subsequent split writes a
*second* entry at 224 while `{223: 241}` survives (`video_windows.py:87` pops only
`first_num`). `plan_locked_video_windows` then walks two overlapping frozen spans: `fi`
still advances so there is no hang, but `lo` can move *backwards* at `:783`, producing
overlapping/duplicated parts. Unrelated to this fix, but this fix makes
merges-across-disabled routine, so the configuration becomes easier to reach. Worth its
own ticket.

## Feature 099 interaction: can a merge orphan an offset anchor?

Yes, and **no code change is needed** — but the behavior should be pinned by a test and
written down.

A merge deletes `first_b` as a window start. An offset anchored there
(`video_part_offsets.json`) survives, and `effective_part_number`
(`video_part_numbers.py:125-132`) sums every delta with `anchor <= first_num`, so:

- the **merged** part keeps `first_a`, which is `< first_b`, so it does **not** pick up
  the orphaned delta — it keeps the earlier part's numbering, which is the right answer
  (the merged part *is* the earlier part, extended);
- every part **after** the merged span still picks it up, so the tail numbering the user
  corrected is preserved. This is exactly the documented intent:
  `tests/test_video_part_numbers.py:108-111`
  (`test_an_orphaned_anchor_still_applies_from_that_chapter_on`) already pins it, and its
  comment literally describes a merge.

One real UX gap: the per-part "Bỏ tuỳ chỉnh số phần ở phần này" action only appears when
`window.first_num in self._part_offsets` (`tab_video.py:1004`), so an orphaned anchor
becomes unreachable from the menu — the only remedy left is the whole-novel "Đặt lại số
phần tự động". Pre-existing (it already applies to today's merges) and low-severity.
**See A2.**

Recommended, cheap: add one test to `tests/test_tab_video.py` (or
`tests/test_video_part_numbers.py`) that merges two parts with an offset anchored at
`first_b` and asserts the merged part's number and the tail's numbers are what the above
says. No production change.

## Ambiguities for you to decide

**A1 — Should the gap rule be "all disabled" or "all not-in-the-plan"?** This plan
implements the prompt's rule: only *disabled* chapters may sit in the gap. A gap
containing a deleted chapter, or a chapter that exists and is enabled but has no audio in
this voice yet, stays refused. Justification: disabling is an explicit per-chapter user
action, so swallowing such a chapter into the merged part is a consequence the user
chose; audio arriving from a background TTS run is not. If you would rather "the parts
look adjacent on screen, so let me merge them", say so — the predicate stays the same
shape but the caller passes a wider set, and the whole hazard shifts to "a part silently
grows when its chapters finish rendering".

**A2 — Orphaned 099 anchors.** Leave as is (recommended, pin with a test), or add a "Bỏ
tuỳ chỉnh số phần" entry for orphaned anchors somewhere reachable? The latter is a
separate small feature.

**A3 — `disabled_numbers` default.** Keyword-only defaulting to empty (recommended;
omission is fail-safe and keeps existing tests meaningful), or required so no caller can
forget?

**A4 — The optional `disabled_chapter_numbers` extraction in `tts/merge.py`** (Step 3
sub-step): take it, or keep the diff minimal?

Out of scope as instructed, and it does **not** constrain this fix: the all-disabled slot
that still consumes a part number ("Phần 10, then 12"). This change neither helps nor
worsens it — merging is about spans, that one is about numbering, and 099 already offers
the manual remedy.
