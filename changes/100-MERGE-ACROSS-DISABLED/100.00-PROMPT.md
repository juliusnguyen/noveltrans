# Feature: Merge two parts separated only by a disabled chapter

## Request (original, Vietnamese)

Nhưng tôi không thể merge 2 phần lại với nhau (cụ thể là Phần 13 và 14).

## Translation / summary

Two adjacent parts cannot be merged when the only thing between them is a **disabled**
chapter. "Gộp 2 phần liền kề" is greyed out even though the two parts are adjacent in
every sense that matters.

## The reported case (diagnosed against the real project)

Novel `https://sto9.com/book/13908/index.html` (`~/NovelTrans/novel-b1033b5d`), batch
size 20, voice "Ngọc Huyền", 241 chapters, 7 disabled (1-based: 65, 192, 199, 200, 209,
227, 234).

```
Phần 13: chương 223-233
Phần 14: chương 235-241
adjacency test: last_a + 1 == first_b  ->  234 == 235  ->  False
  chương 234: enabled=False audio=False
```

Chapter 234 is disabled, so `plan_locked_video_windows` starts Phần 14 at 235. The
adjacency test compares 233+1 against 235 and fails, so the merge is refused — even
though chapter 234 can never belong to any window and the two parts are contiguous in
renderable content.

## Root cause

Feature 098's rule — "a disabled chapter doesn't occupy a grid slot" — was applied to
window *planning* (`_batch_window_end`, `merge.part_number`) but never propagated to the
split/merge adjacency check. It is asserted in two places:

- `src/noveltrans/video_windows.py` — `merge_windows()` raises
  `ValueError("Chỉ có thể gộp 2 phần liền kề nhau (không có khoảng trống).")` when
  `last_a + 1 != first_b`.
- `src/noveltrans/gui/tab_video.py` — `_on_video_list_context_menu` computes
  `adjacent = window_a.last_num + 1 == window_b.first_num` and disables the action with a
  tooltip when false.

## Requirements

- Two parts count as adjacent when **every chapter strictly between them is disabled**
  (including the existing case of no chapters between them at all). A gap containing any
  *enabled* chapter must still be refused — that gap is real, and merging across it would
  reorder chapters.
- Both the menu gating and `merge_windows`'s own validation need the new rule; the pure
  function must keep enforcing it, since it is the API guard.
- `merge_windows` needs the disabled set to decide this, so its signature has to grow —
  or the adjacency decision has to move to the caller and be passed in. Decide which, and
  keep the pure module free of Qt/sqlite as it is today.
- The merged span should be `(first_a, last_b)`, swallowing the disabled chapter in the
  middle. That is correct: it is excluded from the render anyway, and if it is later
  re-enabled it legitimately belongs to the merged part.
- Check the same blind spot in `split_window` and in the "đã tạo"/committed-span logic:
  anywhere `last + 1 == first` is used to mean "contiguous".

## Related — not necessarily in scope

The same 098 blind spot produces a second visible symptom in this project: a part-number
gap (Phần 10, then 12, 13, 14). Slot 11 covers chapters 199-200, both disabled, so it has
nothing to render — no row appears, but the slot still consumes a part number.

Deciding whether an all-disabled slot should skip its number is a **separate and riskier
question**: it would renumber later parts automatically, which is exactly what the
current "count every slot" rule exists to prevent, and is dangerous once a part is
published. Feature 099 (`Đổi số phần…`) already gives a manual remedy. Worth a decision,
but it should not ride along with this fix.
