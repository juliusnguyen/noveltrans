# Implementation Plan — Editable part number in the Video tab (099-VIDEO-PART-RENUMBER)

## 0. What I verified first (grounding)

**Good news that shapes the whole design: the part number is never in a filename.**
`video_part_name` (`src/noveltrans/tts/video.py:623`) builds `{slug}-{first:04d}-{last:04d}.mp4`
from the **chapter range**, and `video_part_dir_name` (`:642`) is just its stem.
`discover_committed_video_windows` / `iter_rendered_part_dirs` parse that range back out with
`_COMMITTED_SUFFIX_RE` (`:661`), and `rename._SUFFIX_RE` (`src/noveltrans/rename.py:36`) does the
same. So a renumber:

- moves **no files**, orphans **no upload record**, needs **no `_delete_rendered_part`** call —
  the exact opposite of split/merge, which does all three;
- only changes text: the `.title.txt` sidecar, the `PHẦN N` line baked into `.jpg`, the upload
  title, and the table/progress labels.

**Every consumer of the number, traced:**

| Consumer | Where | Reads the number from |
|---|---|---|
| Parts table "Phần" cell + sort key | `tab_video.py:1401-1408` | `_part_number(window)` |
| Parts table "Tiêu đề" column | `:1417` → `_part_title` (`:1093`) → `build_upload_title` | `_part_number` |
| Row action buttons (chi tiết / tải lên / ảnh bìa) | `:1421` → `_build_row_actions` (`:1658`) | captured `part_num` |
| Per-row "Tạo lại" | `_render_one` (`:3448`) passes `part_num=self._part_number(window)` | `_part_number` |
| Multi-select "Tạo video" | `_render_selected_parts` (`:3526`) → `explicit_part_numbers` | `_part_number` |
| Upload rows / labels | `:3694`, `:3755`, `_upload_request` (`:3712`) title fallback | `_part_number` / `_part_title` |
| Subtitle + thumbnail + title-update row labels | `:3825`, `:4069`, `:4298`, `:4441`, `:4605`, `:4650` | `_part_number` |
| "Tạo lại tất cả ảnh bìa" | `:2204` → `_render_thumbnail_now` (`:2130`) → `render_thumbnail(part_num=…)` | `_part_number` |
| **Render worker** `.title.txt` | `workers.py:2696` `build_upload_title(novel_title, part_num, …)` | `workers.py:2630-2640` |
| **Render worker** `.jpg` "PHẦN N" | `workers.py:2729` `part_num=part_num or 1` | same |
| Subtitle worker progress label | `workers.py:2915` `part_number(first_num, batch, disabled_numbers)` | its own call |

`_part_number` (`tab_video.py:800`) resolves in two ways: batch mode reads
`self._locked_part_numbers` (built at `:795` from `plan_locked_video_windows`), everything else
falls back to `merge.part_number(window.first_num, self.video_batch_size.value())` (`:819`).
`VideoWorker.run` mirrors that exactly at `workers.py:2630-2640`: `explicit_part_numbers` →
`locked_part_numbers` (from `plan_locked_video_windows`, `workers.py:2569-2574`) →
`part_number(first_num, batch)`.

So there are **two independent number engines that must agree**, and both reduce to the same
shape: a `{first_num: part_num}` map plus an arithmetic fallback. That is the single seam to
insert the offset into.

**`rename.py` never recomputes N.** `retitle` (`:158`) lifts the `Phần N` group verbatim out of
the current title and re-emits it; `resync_title_sidecars` (`:216`) therefore *preserves* a
renumbered N across the project-open resync (`tab_video._resync_descriptions_and_report`,
`:2798`). That is exactly what we want, but it is load-bearing and currently untested against a
renumber.

**Source edition:** `_windows_for_current_selection` (`:708`) clears all three lock caches for
`SOURCE_AUDIO_KEY` (`:742-744`), so source windows always take the arithmetic fallback in both
tab and worker. `video_windows.py`'s docstring states the reason split/merge is hidden there: a
*flat* `{first: last}` map has no room for a second number space, and supporting both "would mean
a versioned schema (`{"chapters": {...}, "nguon": {...}}`)".

## Design decisions (decide these before step 1)

### D1. Offset lives in a **new per-novel sidecar**, not in `meta.json` or `video_manual_windows.json`

**Chosen:** new module `src/noveltrans/video_part_numbers.py` + new file
`video_part_offsets.json` at the project root, an exact structural sibling of `video_windows.py`
(pure, no Qt/sqlite, atomic temp+replace, tolerant reads).

- *Not `video_manual_windows.json`:* its values are `last_num` (a chapter number); deltas are a
  different quantity in the same key space. Merging them needs the versioned migration its own
  docstring warns about, and — worse — the manual map is fed straight into
  `plan_locked_video_windows`'s `committed` argument (`tab_video.py:788`, `workers.py:2569`). A
  stray delta arriving there would **reshape chapter spans**, which is precisely the thing
  requirement 4 forbids. Keeping the two files apart makes that mistake structurally impossible.
- *Not `meta.json`/`video_settings`:* `video_settings.effective()` resolves a flat key→scalar bag,
  and `snapshot(config)` does `getattr(config, key)` for **every** key (`video_settings.py:129`),
  so a nested per-novel plan map would need a fake `AppConfig` property. It is also neither
  "identity" nor "workflow" — it is plan data, like manual windows.
- *Back-compat:* the file is new; absent ⇒ `{}` ⇒ today's numbering exactly. No migration, no
  version bump for existing projects.

**Schema** (versioned from day one, learning from `video_windows.py`'s regret):

```json
{ "version": 1, "chapters": { "1501": -1 }, "nguon": {} }
```

Each edition maps **anchor `first_num` (string) → delta (int)**. `first_num` is the stable window
identity already used as the table's `UserRole` key (`tab_video.py:1409`), the
`_locked_part_numbers` key, and the `video_manual_windows.json` key.

### D2. Store a **delta**, not an absolute pinned number

Effective number = `base_part_num + sum(delta for anchor, delta in offsets.items() if anchor <= window.first_num)`.

- Composes: two independent corrections at different anchors just add up; no "which pin wins"
  rule needed.
- Matches the request's own words ("an offset", "every later part shifts by the same delta").
- Survives a later manual **split of an earlier part**: the split legitimately adds a real video,
  the base numbers after it all rise by 1, and the delta correctly rides along. An absolute pin
  would hold the anchor at its old number and swallow the new part.
- Survives an **orphaned anchor** (the user later merges the anchor away as the second half, so
  `first_b` disappears from the plan): a sum over `anchor <= first_num` still applies the
  correction from that chapter onward.

**Trade-off / ambiguity to confirm with the user:** with delta semantics, after a later
structural change the anchor row may no longer read the exact number the user typed. Absolute
pinning would keep the typed number literal but silently absorb real extra parts. I recommend
delta; flag it.

### D3. Semantics of the edit, and the two hard rules

"Edit part N → M" writes `offsets[anchor.first_num] += (M − N)` where N is the anchor's *current
effective* number.

Validation runs over the **whole recomputed sequence**, not just the anchor:

1. **Every effective number must be ≥ 1.** `build_upload_title` would happily emit "Phần 0".
2. **Strictly increasing in chapter order.** The part immediately before the anchor is untouched
   by construction, so M must be `> prev_effective`. Two parts of one novel sharing "Phần 74"
   would produce two YouTube videos with identical titles — and `youtube_upload.py:1306` / `:1989`
   match playlist entries and Studio rows by exact title, so a duplicate is an operational
   hazard, not just cosmetic. **Refuse**, don't warn.

**Parts before the anchor**: untouched, full stop — that is the whole point, since they are the
already-published ones.
**Parts at/after the anchor that are already rendered**: their `.title.txt` and `.jpg` still carry
the old N on disk. Handled in step 5 (rewrite unpublished sidecars, warn about published ones)
rather than by refusing the edit — refusing would block the normal workflow, where the anchor is
typically the first *pending* part.

### D4. Source edition **is** supported

The schema has a `"nguon"` key by construction, so the objection recorded in `video_windows.py`
("a flat map has no room for a second number space") does not apply. The two editions are already
fully partitioned on disk by `edition_slug` (`tts/video.py:613`), source parts get the same
`Phần N` titles through the same `build_upload_title`, and the tab already has
`_is_source_edition()` (`:821`) / the worker already has `self.source_audio` to pick the key.
Cost: one dict level. Benefit: no second asymmetry to explain.

*Alternative if you want the smallest possible surface:* write `"nguon": {}` but hide the menu
action for the source edition exactly like `splittable` does at `tab_video.py:951`. Lower risk,
but leaves a real gap. **I recommend supporting it.**

### D5. The edit is a **context-menu action**, not an inline table edit

`self.video_list.setEditTriggers(NoEditTriggers)` (`:414`) and `itemChanged` is wired to a single
dispatching slot `_on_status_toggled` (`:461`) whose comment explains that either status handler
may rebuild the whole table — making column 0 editable would route through that same signal onto
items that are about to be deleted. The action also needs a confirmation (it moves later parts),
which an inline edit can't carry. `_split_part` (`:981`) is the precedent: `QInputDialog.getInt` +
a confirm dialog.

## Step-by-step

### Step 1 — New pure core module (no Qt, fully unit-testable)

**File:** `src/noveltrans/video_part_numbers.py` *(new)*

Model it line-for-line on `video_windows.py` (module docstring explaining the "why", `_FILE_NAME`,
path helper, tolerant read, atomic write, action functions that raise `ValueError` with Vietnamese
messages).

Public API:

- `part_offsets_path(project_path) -> Path` — `video_part_offsets.json` at the project root.
- `read_part_offsets(project_path, *, source_audio=False) -> dict[int, int]` — one edition's
  `{anchor_first_num: delta}`. Missing file, unparseable JSON, wrong top-level type, non-int
  keys/values ⇒ `{}` (same defensive shape as `read_manual_windows`).
- `write_part_offsets(project_path, offsets, *, source_audio=False)` — read-modify-write the whole
  document so writing `"chapters"` can never drop `"nguon"`; always stamp `"version": 1`; drop
  zero deltas; atomic `.tmp` + `replace`.
- `effective_part_number(first_num, base_part_num, offsets) -> int` — the one-liner sum described
  in D2.
- `apply_part_offsets(numbers: dict[int, int], offsets) -> dict[int, int]` — map
  `{first_num: base}` → `{first_num: effective}`. **This is the single choke point** the two
  number engines call.
- `plan_renumber(numbers, offsets, anchor_first_num, new_part_num) -> dict[int, int]` — pure;
  returns the *new* offsets map. Raises `ValueError` on: unknown anchor; a result `< 1`; a result
  `<=` the preceding part's effective number. Messages in Vietnamese (draft in step 6).
- `renumber_part(project_path, numbers, anchor_first_num, new_part_num, *, source_audio=False) -> dict[int,int]`
  — the I/O wrapper (read → `plan_renumber` → write → return the new effective numbers),
  mirroring `split_window`'s "do it and hand back the result" shape.
- `clear_part_offsets(project_path, *, source_audio=False)` — the reset; also the per-anchor
  removal via `offsets.pop(anchor)`.

**Why here and not in `tts/merge.py`:** `merge.part_number` is pure grid arithmetic with no
project on disk and no notion of a plan; the offset is a persisted per-novel override, which is
the `video_windows.py` family. Keeping it out of `merge.py` also means **`merge.part_number` and
`plan_locked_video_windows` need no change at all** — which is the cleanest possible answer to
requirement 4 (numbers shift, spans cannot).

### Step 2 — Wire the offset into the two number engines

Two small edits, plus two fallback sites.

**File:** `src/noveltrans/gui/tab_video.py`

1. `_locked_batch_windows` (`:754`), at line `:795`: wrap the cache build —
   `self._locked_part_numbers = apply_part_offsets({w.first_num: pn for pn, w in plan}, read_part_offsets(self.project.path))`.
   Every downstream consumer of `_locked_part_numbers` is then correct for free. Keep the existing
   `if honor_committed:` guard — the redo-all preview must still not poison the cache.
2. `_part_number` (`:800`), the arithmetic fallback at `:819`: wrap the result in
   `effective_part_number(window.first_num, base, offsets)`, reading the offsets for the current
   edition (`source_audio=self._is_source_edition()`). This covers range mode **and** the source
   edition.
3. Cache the per-refresh offsets alongside `_locked_committed` / `_locked_manual` (new
   `self._part_offsets: dict[int,int]`, initialised next to them at `:136-138`, cleared in the
   source branch only if you take D4's "hide it" alternative). `_part_number` is called in tight
   loops (`_rebuild_video_rows`, `_pending_upload_rows`, `_thumbnail_update_rows`), so re-reading
   the JSON per row is wasteful; refresh it once per `_windows_for_current_selection`.

**File:** `src/noveltrans/gui/workers.py` (`VideoWorker.run`)

4. Batch branch (`:2569-2574`):
   `locked_part_numbers = apply_part_offsets({w.first_num: pn for pn, w in locked}, offsets)`.
5. Fallback at `:2640`:
   `part_num = effective_part_number(window.first_num, part_number(window.first_num, self.batch_size), offsets)`
   — this is the source-edition and range-mode path.
6. Read `offsets = read_part_offsets(project.path, source_audio=self.source_audio)` once, next to
   the existing `read_manual_windows` import/call (`:2564`).
7. **Do not touch** `explicit_part_numbers` (`:2536`): the tab already builds it from
   `_part_number`, which is now offset-aware. Double-applying here would be the bug.

**File:** `src/noveltrans/gui/workers.py` (`SubtitleWorker.run`, `:2915`) — optional, cosmetic.
Its label is progress text only, but it currently disagrees with the tab whenever offsets exist.
Fold the offset in for consistency. (Note a pre-existing inconsistency worth a one-line comment:
`SubtitleWorker` passes `disabled_numbers` to `part_number`, `tab_video._part_number`'s fallback
at `:819` does not.)

**Review checkpoint after this step:** with an empty offsets file the diff is provably a no-op,
and with one entry every one of the 14 consumers in the table above is already correct. Nothing
can reshape a span, because `plan_locked_video_windows` and `merge.part_number` are untouched.

### Step 3 — The context-menu entry points

**File:** `src/noveltrans/gui/tab_video.py`, `_on_video_list_context_menu` (`:903`)

Insert after the split/merge block (`:951-968`), reusing the existing `selected_windows` /
`by_first` machinery (which is already sort-safe — it looks rows up by `UserRole` `first_num`, not
by row index):

- **`"Đổi số phần…"`** — enabled when `len(selected_windows) == 1` and `mode == "batch"` and not
  `whole_novel`. Gate on `mode == "batch"` (same rule as `splittable`, minus the source exclusion
  under D4): in "range"/"all" there is no grid of parts for "and everything after" to mean
  anything, and "all" has a single `whole_novel` row with no number at all.
- **`"Đặt lại số phần tự động"`** — added only when `read_part_offsets(...)` is non-empty, so the
  menu stays clean for the 99% case.
- **`"Bỏ tuỳ chỉnh ở phần này"`** — added only when the selected row's `first_num` is itself an
  anchor. This is the fine-grained undo; the global reset above is the blunt one.

### Step 4 — `_renumber_part` handler + dialogs

**File:** `src/noveltrans/gui/tab_video.py`, new methods beside `_split_part` / `_merge_parts`

`_renumber_part(self, window, windows)`:

1. `current = self._part_number(window)`; `prev = ` the effective number of the last window with
   `first_num < window.first_num` (or `0`).
2. `QInputDialog.getInt(self, "Đổi số phần", <label>, current, max(1, prev + 1), 9999)` — the
   spinner's `min` enforces the collision rule in the UI; the pure layer enforces it again for the
   API.
3. Build `numbers = {w.first_num: self._part_number(w) for w in windows}` and call
   `renumber_part(...)`; catch `ValueError` into
   `QMessageBox.warning(self, "Đổi số phần", str(exc))` — same pattern as the split's `ValueError`
   messages.
4. Before writing, show a **dedicated confirm** — *not* `_confirm_restructure` (`:1047`), whose
   text promises "file cũ sẽ bị XOÁ", which is false here. Write a sibling `_confirm_renumber(...)`
   that reuses its `is_published` / `.is_file()` counting but says the right thing.
5. After writing: run the sidecar rewrite (step 5), `self._refresh_video_list()`, set the status
   line. **No `_delete_rendered_part`** — filenames don't change.

`_reset_part_numbers(self, *, anchor=None)`: confirm, `clear_part_offsets` or `offsets.pop(anchor)`
+ write, refresh, status line. Should it also rewrite sidecars back? Yes — route it through the
same step-5 helper so a reset is a true inverse.

### Step 5 — Keep already-rendered sidecars honest

**File:** `src/noveltrans/gui/tab_video.py`, new
`_renumber_title_sidecars(self, windows, numbers) -> tuple[int, int]` (rewritten,
skipped-because-published)

For each window at/after the anchor whose `.mp4` exists:

- read `.title.txt`; skip if missing;
- skip unless `rename.title_name(current)` is one of this novel's known names — i.e. reuse the
  existing "is this a title we generated?" test (`rename.py:200`) so a hand-written
  "Bản đặc biệt - Phần 3" is left alone, exactly as `resync_title_sidecars` does;
- skip if `youtube_upload.is_published(path)` — the sidecar should keep matching what the video
  was actually published under (the same rule `resync_title_sidecars` applies for order-only
  changes, `rename.py:271`);
- otherwise write `self._part_title(new_num)`.

**No change to `rename.py` is required** — `retitle` preserves N verbatim, so the project-open
resync will not undo the new number, and `title_name` already gives the guard. That preservation
is load-bearing and gets a regression test in step 7.

**Thumbnails:** the `.jpg` bakes `PHẦN N` (`tts/thumbnail.py:274`). **Do not auto-regenerate** —
`_regen_part_thumbnail` (`:2157`) would silently overwrite a cover the user may have tuned in the
editor. Instead end the status line with the same sentence `_save_display_title` already uses
(`:2851`): *"Bấm "Tạo lại tất cả ảnh bìa" để áp dụng lên ảnh bìa đã tạo."*
*Ambiguity for the user:* auto-regen for rendered-and-unpublished parts only would be more
convenient; I've chosen the conservative option to match the existing rename flow.

**Published parts:** the "Cập nhật tiêu đề" button will *not* offer them, because
`_title_update_rows` (`:4409`) compares against `retitle(current, …)`, which preserves N and so
returns `""`. That is acceptable and in fact expected: the anchor is normally the first
*unpublished* part, so published parts sit before it and are untouched by design. The confirm
dialog says so out loud. Extending `_title_update_rows` to also diff against a recomputed
`_part_title(part_num)` is a reasonable **follow-up**, but it widens the blast radius onto live
YouTube titles and should not ride along with this feature.

### Step 6 — Visibility in the table, and the Vietnamese strings

**File:** `src/noveltrans/gui/tab_video.py`, `_rebuild_video_rows` (`:1387`)

An invisible persisted offset is a trap. On the "Phần" cell (`:1408`), when the effective number
differs from the base, set a tooltip:
`f"Đã tuỳ chỉnh số phần — đánh số tự động là Phần {base}."` (the amber-⚠️ treatment used by
`_chapter_range_item` (`:1112`) is reserved for problems, and a deliberate renumber is not one).
The `SortableItem` sort key stays the **effective** number, so ordering still matches what the
user reads.

Draft strings, matching the tone in `_split_part` / `_confirm_restructure`:

- Input label:
  `f"Phần này đang là Phần {n} (chương {a}–{b}).\nSố phần mới (các phần SAU sẽ dời theo, các phần trước giữ nguyên):"`
- Confirm body:
  `f"Sẽ đổi Phần {n} → Phần {m}. {k} phần sau đó cũng dời {delta:+d} (Phần {x} → Phần {y}…). Các phần trước giữ nguyên.\n\nTên file KHÔNG đổi — chỉ số phần trong tiêu đề và ảnh bìa."`
  + `f"\n\n{r} phần trong đó đã có video — tiêu đề sẽ được ghi lại; bấm “Tạo lại tất cả ảnh bìa” để cập nhật ảnh bìa."`
  + `f"\n\n⚠️ {u} phần đã tải lên YouTube. Tiêu đề trên kênh sẽ KHÔNG tự đổi — bạn cần tự sửa trên YouTube."`
  + `"\n\nTiếp tục?"`
- Validation errors (raised from the pure layer):
  `f"Số phần phải lớn hơn {prev} — Phần {prev} ngay trước đó đã dùng số này."` /
  `"Số phần phải từ 1 trở lên."`
- Reset confirm: `"Bỏ mọi tuỳ chỉnh số phần của truyện này và quay lại đánh số tự động?"`
- Status lines: `f"Đã đổi Phần {n} thành Phần {m} — {k} phần sau dời theo."` /
  `"Đã đặt lại số phần theo đánh số tự động."`

## Sequencing & review boundaries

1. **Step 1** is standalone and pure — reviewable and mergeable with only
   `tests/test_video_part_numbers.py`, no behaviour change anywhere.

## Open questions for the user

1. **Delta vs absolute pin (D2)** — after a later manual split of an *earlier* part, should the
   renumbered row keep the number that was typed (absolute), or ride the shift like everything else
   (delta, my recommendation)?
2. **Source edition (D4)** — support renumbering the "nguồn" plan, or hide the action there like
   split/merge?
3. **Thumbnails (step 5)** — auto-regenerate the `.jpg` for affected rendered+unpublished parts, or

   flow)?
4. **Collision (D3.2)** — hard refusal when the new number would collide with the preceding part

5. **Scope of the trigger** — batch mode only (matching `splittable`), or also offer it in "range"
   mode where the number comes from the batch spinbox anyway?
