# 112.01 MEMBERS-SCHEDULE-PLAN

Feature: a "Lịch đăng" (schedule) column in the 5. Video table, and a members→public schedule chain: the next Members video goes public 3 days after the last scheduled one, or within the next 3 days if the last one is long past.

## 1. What exists now

**`src/noveltrans/youtube_upload.py`**
- `PUBLIC_SWITCH_DAYS = 3` (~L351), `PUBLIC_SWITCH_HOUR = 19` (~L353).
- `UploadRequest` (~L488): `publish_at` (scheduled mode) and `public_at` (members mode). `validate()` (~L527-545) checks presence and mutual exclusion, not the time itself.
- `schedule_times` (~L640) and `public_switch_times(launch, count, days)` (~L655). The latter anchors every part to the click: part k goes public at `launch + 3k` days, 19:00.
- `validate_schedule_start` (~L673) rejects times in the past, with a 15-minute lead (`_MIN_SCHEDULE_LEAD`, ~L355).
- `upload_batch` (~L3495-3500) validates `publish_at` only. `public_at` is not checked.
- `upload_one` writes `publish_at` / `public_at` at COMMITTED (~L3434) and PUBLISHED (~L3449).
- Timestamps are mixed: `_now_iso()` (~L895) is timezone-aware, but the schedule fields are naive `isoformat()`. Comparing them raises `TypeError`.
- Per-part state: `read_upload_state` (~L753) / `write_upload_state` (~L776), stored as `<stem>.upload.json` beside the mp4 (`upload_state_path`, ~L747).

**`src/noveltrans/gui/tab_video.py`**
- Table: `QTableWidget(0, 7)` with headers at ~L423-425. Column 5 "Đã tải lên", column 6 "Thao tác".
- Hard-coded indexes: `CheckableHeaderView(5, …)` (~L447), resize modes and `setColumnWidth(6, 420)` (~L453-460), `_upload_rows` reads column 5 (~L1595), `setItem` 0-5 and `setCellWidget(i, 6, …)` (~L1759-1769), `_on_status_toggled` dispatches on 4 and 5 (~L1821-1824).
- Tests in `tests/test_tab_video.py` use `cellWidget(row, 6)` at ~L392, L531, L539.
- `_refresh_schedule_preview` (~L690) and `_refresh_members_preview` (~L724-743) show "+3 ngày" offsets from the click.
- `_launch_upload` (~L4476-4500) anchors members parts with `public_switch_times(datetime.now(), …)`. This is the line that must change.
- Library root: `AppConfig.library_dir` (`config.py` ~L130). Projects' videos are under `project.exports_dir / VIDEO_DIR` (`storage/project.py` ~L357).

**Missing:** the chain function, the schedule column, a cross-novel scan, and a `public_at` check in `upload_batch`.

## 2. Recommended decisions

**A. Scope: channel-wide.** Scan every project under the library root. The members cadence is one channel-level rhythm; two novels scheduling independently would collide.

**B. Column value:** the part's effective release time, with a tooltip naming the kind. `public_at` for members parts, `publish_at` for scheduled parts. The chain reads only members `public_at`, so scheduled-mode times do not affect it.

**C. Excluded parts.** Private, public and unlisted parts show a blank cell and are ignored by the chain. The chain counts `visibility == "members_then_public"` parts with a `public_at` and status `committed` or `published`. `committed` is included because it is past the irreversible click, and excluding it risks double-booking a slot.

**D. The rule**, evaluated once per launch, against `now = datetime.now()`:
- `last` = the maximum members `public_at` from C.
- If there is no `last`, or `last < now - 3 days`: anchor = the latest 19:00 at or before `now + 3 days`. Stays inside "the next 3 days", at the usual switch hour.
- Otherwise (last is in the future, or within the last 3 days, inclusive): anchor = `last + 3 days`. A future-dated last is not reset.

**E. Batch chaining.** Part 1 = the anchor from D. Part k = part k-1 + 3 days, in memory. A failed part leaves its slot unused, and later parts keep their planned times. Document this.

**F. Derived, no new state.** The state files are the source of truth. The chain logic is a pure function with no Qt, and the disk scan happens in the tab. Parse every timestamp and normalize to naive local time before comparing.

**G. Validation.** Check the first part's `public_at` with `validate_schedule_start` at launch, and add the same check to `upload_batch` for `public_at`.

## 3. Implementation steps

1. `youtube_upload.py`: add `members_schedule_anchor(now, last)` (rule D) and `last_members_public_at(states)` (filter C, timezone normalization). Both pure.
2. `youtube_upload.py`: add `members_chain_times(now, last, count)` (rule E). Extend `upload_batch` to validate `public_at`.
3. `tab_video.py`: a helper that gathers state files across the library. It is the only code outside `youtube_upload.py` that touches disk for this.
4. `tab_video.py` `_launch_upload`: replace `public_switch_times(datetime.now(), …)` with the chain. The confirmation dialog shows absolute dates.
5. `tab_video.py` previews: show the chained absolute dates from the same helper.
6. Column: insert "Lịch đăng" at index 6, after "Đã tải lên". "Thao tác" moves to 7. Indexes 0-5 are unchanged, so `CheckableHeaderView(5)`, `_upload_rows` and `_on_status_toggled` stay as they are. Update the column count to 8, headers, resize modes and width for 7, `setCellWidget(i, 7, …)`, and the test references at ~L392, L531, L539.
7. The schedule cell uses a sortable item with a sort role, so blank cells sort last.
8. Refresh the column wherever the upload column refreshes (`_on_upload_part_done` → `_refresh_video_list`).
9. History log: `112.01-HISTORY.md`, following the 111 convention.

## 4. Test plan

Unit tests (no Qt), in the `youtube_upload` test module:
- No prior members schedule: anchor is the 19:00 at or before now + 3 days.
- Last older than 3 days: reset to the same anchor.
- Last within the last 3 days: last + 3 days.
- Last in the future: last + 3 days, no reset.
- Exactly now - 3 days: chained, not reset.
- Batch of N parts: N datetimes, 3 days apart, all at 19:00.
- Private, public, and not-yet-committed parts are excluded from `last`.
- Mixed naive and aware timestamps: no `TypeError`.
- `upload_batch` rejects a `public_at` inside the 15-minute lead.

Tab tests (`tests/test_tab_video.py`):
- Column count is 8, header "Lịch đăng" at index 6, actions widget at index 7.
- Schedule cell is blank for private parts, shows the time for a committed members part.
- The members preview shows absolute chained dates.

## 5. Risks

- **Column index shift:** inserting at 6 leaves 0-5 unchanged. The `cellWidget(…, 6)` references in code and tests must move in the same change.
- **Channel-wide scan:** cost grows with all parts. Cache per launch. Corrupt or unreadable state files are skipped, not fatal.
- **Timezones:** naive and aware timestamps are mixed in the same files. Normalize before comparing.
- **Failed batch slots:** a failed part leaves a gap in the chain (rule E).
- **Manual edits:** ticking or unticking "Đã tải lên" changes which parts count. The chain follows the state files, so it stays consistent, but this should be mentioned.

## 6. Open items to confirm before implementing

- Column value B: members `public_at` and scheduled `publish_at` in one column (recommended), or members only?
- `committed` parts counted as "last" (C, recommended), or only `published`?
