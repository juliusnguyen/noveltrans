# 071 — Leftover Chinese characters in translations from timotxt

## Report (user)

> phiên bản dịch bằng vẫn còn sót ký tự tiếng trung; ví dụ như
> `https://www.timotxt.com/2608569069/` trong novel này, chapter 376 phần dịch có đoạn
> `Phiêu Mi渺 Tiên Tông`

## Root cause — investigated before writing this, and it is ours

The reported symptom looks like a translator problem. It is not. **It is a direct
consequence of feature 070**, shipped hours earlier.

Verified against the live site:

- **Chapter 376's source contains no `渺` at all** (0 occurrences).
- It does contain an **undecoded Hangul character**: `꿫` (U+AFEB) → `仍`, which is
  **missing from the substitution table** shipped in `scrapers/timotxt.py`.
- The residue is **intermittent**: across six fetches of that chapter, two carried it and
  four came back clean. The site re-randomises which characters it scrambles on every
  request, so the user's stored copy simply caught a bad draw.

So the chain is: table misses a character → residual Hangul lands in the stored `content` →
the translator meets a glyph it cannot read and does something unpredictable with it. Here it
appears to have recognised the intended character and emitted it **raw and untranslated**,
producing `Mi渺` where the sect name should read `Phiêu Miểu Tiên Tông`.

Feature 070 predicted this exact failure and accepted it — its docstring and plan both say
the table is empirical and under-corrects by design, with the residue warning and the live
drift test as the detectors. What 070 did **not** anticipate is that a *single* missed
character per chapter is enough to corrupt the translation, which makes "the table is
incomplete but harmless" wrong in practice.

## Decisions taken with the user

| question | answer |
|---|---|
| How wide should the fix go? | **Fix the cause properly** — extend the table *and* make the adapter re-fetch when it detects residue, so the table's incompleteness stops mattering. |
| Chapters already downloaded with residue baked in? | **Offer to repair them.** The user has a novel in this state right now. |

Explicitly **not** in scope, per that first answer: a general leftover-CJK safety net for all
sites. `Translator._translate_with_retry` (`translators/base.py:65-92`) already scores
attempts by `cjk_count` and, when every attempt is dirty, keeps the cleanest one — "a few
stray chars beat failing the whole chapter". That is a real and separate issue; it is not
what caused this report, and it should be its own feature if the user wants it.

## Scope

### 1. Re-fetch on residue — the structural fix

`TimotxtAdapter.fetch_chapter` already computes `residual_hangul(body)` and warns. Instead,
when residue is non-zero it should re-fetch and **merge positionally**, taking the readable
character from whichever response has it.

Why this is cheap: the substitution is applied to a *random subset* per response, so a
character garbled in one fetch is very likely clean in the next — and because the decoded
body is normally residue-free, the second request only happens on the rare chapter that needs
it. Feature 070's plan rejected a two-fetch merge as the **default** path (it would have
doubled the request budget, 376 → 752 per novel, and still left ~p² residue). As a *targeted*
retry it has neither drawback.

Points for the plan to settle:

- **Merge positionally, do not just replace.** The second response may have a *different*
  subset garbled. 070 measured that a character garbled in both draws is what survives, so
  the merge must take the best of each position, not the better of the two bodies.
- Alignment safety: 070 established that repeat fetches return identical paragraph counts and
  lengths. What happens if they do not (the chapter was edited between requests)? Do not
  guess-align.
- How many retries before giving up, and what happens then — the current `_status` warning is
  the obvious floor.
- The existing `_OBFUSCATION_ALARM_RATIO` raise path must still work.

### 2. Extend the table

Re-run `scripts/build_timotxt_table.py` with a wider sample. The shipped table is 122
mappings from 20 chapters of one novel plus 8 of another. `꿫`→`仍` is a common enough
character that its absence shows how thin the tail still is.

The script already asserts zero conflicts and reports cross-novel agreement — both must stay
clean, since they are what proves the table is fixed and site-wide.

Note this is a *mitigation*, not the fix: no sampling can prove the table complete, which is
precisely why item 1 matters more.

### 3. Repair already-downloaded chapters

The user has a novel with residue baked into stored `content`. Re-fetching machinery already
exists — `DownloadWorker(force=True)` (`gui/workers.py:2186-2201`) re-fetches chapters that
already have content, and the chapter table's context menu has "Chỉ tải lại chương N"
(`gui/tab_scrape.py:411`).

**So the missing piece is a detector, not a fetcher**: something that scans stored chapters
for residual Hangul and offers to re-fetch just those. `residual_hangul()` is already the
primitive.

For the plan to decide: where this lives (a button on tab 1? part of an existing scan?), how
it presents (count + confirm, in the house style), and whether it should also flag chapters
whose *translation* already contains leftover CJK — those need re-translating, not just
re-fetching, and re-fetching alone would silently leave the bad translation in place.

## Test plan sketch

- The positional merge: a garbled-in-A / clean-in-B character is recovered; a
  garbled-in-both character still survives verbatim (never invented); mismatched paragraph
  counts do not attempt a merge.
- Re-fetch happens **only** when residue is detected — a clean chapter must still cost one
  request. Assert the call count.
- `꿫` → `仍` specifically, as the regression for this report.
- The detector finds a stored chapter with residue and leaves clean ones alone.
- The existing 070 tests must keep passing unchanged — particularly the under-correct-only
  guarantees in `TestDeobfuscation`.
