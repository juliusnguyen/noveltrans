## [CAPABILITY CHECK] This machine — 2026-07-22
- Apple M4, 10-core GPU, arm64, 24 GB unified memory, macOS 26.5.2.
- No NVIDIA/CUDA. `torch` not installed in `.venv`.
- **Verdict: GPU option is possible via Apple Silicon MPS only, not CUDA.**
- Recommended: keep **CPU (ONNX int8) as default**, ship GPU as an opt-in
  experimental extra. Reasons: the "batched on CUDA" speedup doesn't apply to
  MPS; feature 014's N-engine parallelism maps to CPU cores but contends on a
  single MPS device; unified memory isn't a fresh resource pool; `torch`
  bloats the packaged `.app`. If GPU is selected, worker count should clamp to 1.

## [INVESTIGATION] "Weird sound on long paragraphs" — 2026-07-22/23
User reported occasional garbled audio, hypothesised long paragraphs need
splitting into sentences. **Investigated before building — hypothesis was wrong.**

### Static analysis (scratchpad chunkdump.py / chunksim.py)
- Sentence-splitting **already exists**: `tts/base.py:98` calls
  `split_sentences(text, 400)`, renders chunk-by-chunk, concatenates with a
  0.4 s gap. The user's proposed design is the current design.
- Across 81 chapters / 7,178 chunks: **zero oversized chunks**. The oversized-
  single-sentence bypass bug (`base.py:34-38`) is real but never fires on this
  data.
- Lowering `max_chunk_chars` 400 → 200 changes total chunk count by 34/7,178 —
  paragraphs are already short, so `\n\n` boundaries do all the splitting.
- `vieneu.infer()` (fast.py:127) **re-chunks internally at `max_chars=256`**
  regardless of what we pass. It also exposes `silence_p`, `crossfade_p`,
  `top_k`, `repetition_penalty` — none currently surfaced.
- Note: lib `sample_rate=24_000` (base.py:43) vs our engine's declared
  `48000` — flagged, not yet chased.

### Empirical synthesis test (scratchpad synthtest.py) — problem project
`dm-edit-chao-mung-den-voi-phong-livestre-3c512475` is the project the user
hears the problem in (10% "risky" chunks vs 0.1–0.4% elsewhere; only project
with bare `\n` newlines). Synthesized 147 representative chunks, measured
actual audio duration vs expected (chars/15 per sec). **Drift = ratio ≫ 1.**
- Drift clusters on **SHORT fragments**, not long ones: 5 chars→4.08,
  15→2.56, 26→2.35, 17→1.76. Long chunks (200–396 chars) all ~0.75–0.85 (clean).
- Implication: splitting long paragraphs into sentences would make it WORSE by
  creating more short fragments.
- "latin" category tag was noise — `[A-Za-z]{3,}` matches diacritic-free
  Vietnamese words too.

### CONCLUSIVE — drift is a function of chunk length (147 chunks)
| chunk length | drift rate (ratio>1.6) |
|---|---|
| 0–10 chars | 80% |
| 10–20 | 21% |
| 20–40 | 5% |
| **40+** | **0%** |

All 8 drift cases ≤26 chars; every chunk ≥40 chars clean regardless of
digit/latin/no-terminal. Classic autoregressive-TTS runaway: too little context
→ end-of-speech misfires → babble until token cap (ratio up to 4.08). Root cause
is SHORT fragments, the inverse of the reported "long paragraph" hypothesis.
`split_sentences` packs *up to* max_chars but has no *floor*, so a one-word
paragraph becomes a doomed micro-chunk. `dm-edit` is worst because livestream
prose has many short lines.

### Proposed fix — min-length merge pass (quantified, mergesim.py)
Coalesce chunks below a ~30-char floor into a neighbour, respecting max_chars.
- Problem project: 22.0% sub-floor → **0%** after merge, 0 oversized created.
- All 81 chapters: 16.0% → **0%**, 0 oversized.
Secondary guard to consider: surface `repetition_penalty` (vieneu default 1.2)
and/or a duration-sanity retry for the stochastic tail. NOT YET IMPLEMENTED —
awaiting user go-ahead + decision on branch (this is the GPU branch).
