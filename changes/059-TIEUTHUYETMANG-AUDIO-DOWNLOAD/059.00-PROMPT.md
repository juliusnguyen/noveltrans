# 059 — Download audio from `tieuthuyetmang.com`

## The ask

> add the function to download the audio from this site (only for this site) in
> the Audio tab of this app

Scope is deliberately narrow: **`tieuthuyetmang.com` only**. The other six
scrapers in `src/noveltrans/scrapers/` are out of scope — no generic
"download audio from any source" abstraction unless it falls out for free.

## Where it goes

- **UI**: `src/noveltrans/gui/tab_audio.py` (`AudioTab`, 746 lines). Today the tab
  *generates* audio via TTS and merges it. This adds a third mode: pull
  pre-existing narration from the source site instead of synthesising it.
- **Fetching**: `src/noveltrans/scrapers/tieuthuyetmang.py`
  (`TieuthuyetmangAdapter`) already handles this site's Next.js flight-payload
  format and owns the HTTP client. The audio fetch belongs alongside it.

## Sample URL

https://tieuthuyetmang.com/truyen/toi-la-bach-nguyet-quang-cua-cac-co-ay-khong-phai-la-tra-nam-phu-a

## What we already know (established 2026-08-24)

Reconnaissance done against the sample URL before this feature was opened:

- The chapter manifest is embedded in the page's Next.js flight payload, and each
  chapter entry carries `hasAudio`, `isLocked` and `audioLocked` flags —
  the same payload `iter_objects` / `story_chapters` already parse.
- For the sample novel: **122 chapters, 21 with audio** (the volumes titled
  "YTB TẬP 1…21"), and **all 21 are `audioLocked: true`**.
- Audio is gated behind the site's VIP tier. **No audio URL of any kind appears
  in the anonymous page response** — the media URL is only issued to an entitled
  session. So an unauthenticated fetch cannot work, by construction.
- The `hasAudio` flag is sparse and does not line up 1:1 with chapters — audio is
  published per *volume* (~5 chapters each), not per chapter. The UI and the
  on-disk layout both need to handle that mismatch.

## The authentication problem (the main open question)

The user has a paid VIP account, so the entitlement exists; the difficulty is
getting the session into this app. Routes tried and their status:

- **Read cookies from the local Chrome profile** — blocked twice over. macOS TCC
  denies the terminal access to `~/Library/Application Support/Google/Chrome`
  (`Operation not permitted`, surfaced as an empty directory), and the installed
  Chrome is **v151**, where app-bound cookie encryption defeats external cookie
  extraction even with Full Disk Access granted. Not a viable foundation.
- **Claude browser extension** — not connected in that session; untested.
- **User-supplied session** — pasting a captured request from DevTools works but
  is a manual, per-session step and the token expires.

Whatever this feature does, it needs a story for "the app has a logged-in
tieuthuyetmang session" that a normal user can complete and repeat. Deciding
that is the first job of `/plan`, not something to settle here.

## Open questions to settle before implementing

- **Auth**: where does the session come from — a login form in the app, a
  cookie/token pasted into settings, or an embedded web view? How is it stored
  (the app already has `AppConfig` — is a secret safe to put there)? What happens
  on expiry?
- **Media format**: is the gated asset a plain MP3, or HLS/`.m3u8` segments? The
  page bundles an `<audio>` element, but the real URL was never observable
  unauthenticated. If HLS, `ffmpeg` is already a dependency and can remux.
- **Mapping**: 21 audio volumes vs 122 chapters — how are downloaded files named
  and attached to the project? Does a volume become one row, or does it attach to
  the first chapter of its range?
- **Interaction with existing flows**: downloaded audio must coexist with
  TTS-generated audio in the same project. Does the merge step treat them alike?
  Do the multi-select regenerate actions from 057 apply to downloaded rows (they
  probably must not — there is nothing to regenerate)?
- **Failure surface**: what does the tab show for a chapter that has no audio, or
  audio the account is not entitled to?

## Constraint

Only fetch what the signed-in account is actually entitled to. This feature must
not attempt to work around the paywall for locked content — if the session is not
entitled, the correct behaviour is to report that clearly and skip the item.
