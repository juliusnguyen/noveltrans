# Plan: feature 106 MEMBER-SCHEDULE-PUBLIC

Branch `changes/106-MEMBER-SCHEDULE-PUBLIC`. No source files were edited while planning. Everything below is a proposal.

## 0. Decisions and interpretation

- **Adopted interpretation:** each upload goes live as members-only immediately. A new visibility mode, `members_then_public`, switches it to public at `launch + 3*k` days, where `k` is the 1-based position in the batch. A single video has `k=1`.
- **Timing anchor:** the public-switch times are computed in `_launch_upload` (GUI) at click time, not when the dialog opens. The preview shows relative offsets ("+3 ngày, +6 ngày"). The confirmation dialog shows absolute dates.
- **Fixed rule:** the 3-day spacing is a constant (`PUBLIC_SWITCH_DAYS = 3`). The existing `upload_spacing` spinbox (default 1, range 0–30) is not reused. It is hidden in this mode.
- **No local timer:** the app does not poll or flip visibility later. The switch date is set inside Studio's upload dialog, so YouTube performs the switch. This only works if Studio offers that control (see Step 0). Fallback in Risks.
- **15-minute lead check does not apply** to this mode. `validate_schedule_start` runs on `min(publish_at)` and only for `schedule`. `public_at` must never be added to that list.

## 2. Step 0 (blocking): live DOM probe, user session required

This cannot run unattended. It needs the user's logged-in dedicated profile and a real Studio upload dialog.

**Probe setup**
1. Use a throwaway video under 1 MB (a generated 1-second black MP4 in the scratchpad). Use a channel with memberships enabled, since members-only may not appear otherwise. Record whether it does.
2. Write the probe script in the scratchpad, not the repo. It calls `_launch_context(sync_playwright, headless=False)`, then `_open_upload_dialog`, `_send_file`, `_advance_to_visibility`, and stops at the visibility step.
3. Do not click Publish or Schedule. Cancel the dialog and delete the test draft afterwards.

**What to dump at the visibility step**
- Every radio: `tp-yt-paper-radio-button` with `name`, `id`, `aria-label`, `textContent`, `checked`, and visibility state. Also `_dom_inventory(page)` and `_page_actions(page)`.
- Every element matching `hội viên|thành viên|member` (case-insensitive), with its tag and ancestors up to `ytcp-video-visibility-select` or the nearest `ytcp-*`.
- Any `ytcp-datetime-picker`, `#datepicker-trigger`, `#time-of-day-container`, or `input` in the members section, plus attributes.
- Whether the public-switch control is its own date/time picker, a checkbox, or a radio under the members option.
- Whether `#schedule-radio-button` is still present when members is chosen.
- The `html lang` value and any warning text shown when members is picked.

**Decision outcomes**
- Members radio and public-switch control found: proceed with Section 3 selectors. Record exact `name`, `id`, and label text.
- Members radio found, no public-switch control: stop and report. The feature cannot be a Studio-side switch. See Risks for the fallback.
- Members radio absent: the channel is not eligible, or the option lives elsewhere. Raise `YouTubeUploadError` with a clear message. Do not fall back silently to another visibility.

## 4. Time computation (pure, `youtube_upload.py`)

Add next to `schedule_times` (~line 603):

```python
def public_switch_times(launch: datetime, count: int, days: int = PUBLIC_SWITCH_DAYS) -> list[datetime]:
    """Public-switch time for each of `count` parts launched at `launch`.

    Part k (1-based) switches at launch + days*k. Uses timedelta so the wall-clock time of
    the launch is kept, the same reason as schedule_times.
    """
```

- Raises `ValueError` for `count < 0` or `days < 1`, matching `schedule_times`.
- Returns `[launch + timedelta(days=days * (i + 1)) for i in range(count)]`.

**Tests** (`tests/test_youtube_upload.py`, new class next to `TestScheduleTimes`):
- `count=0` returns `[]`.
- `count=3` gives `[+3d, +6d, +9d]`.
- Default `days` is 3.
- Negative `count` and `days < 1` raise `ValueError`.
- Month boundary keeps the wall-clock hour: launch `2026-08-30 20:00`, `count=2` gives `Sep 2 20:00` and `Sep 5 20:00`.

**Validation tests** (`TestUploadRequestValidation`):
- `members_then_public` without `public_at` raises.
- `members_then_public` with `publish_at` set raises.
- `schedule` mode is unchanged.

## 10. Risks

- **Studio DOM drift.** The probe fixes selectors at one point in time. Keep text fallbacks and `_first_present`. Use `_dom_inventory` and `_page_actions` in error messages.
- **Missing option.** Members-only may be absent for non-member channels. The error must say so. The draft stays recorded as `draft`, which `needs_attention` treats as unresolved, so a human must clear it. This matches the existing schedule failure path.
- **Public-switch control may not exist in Studio.** Fallback: an app-side job that opens the edit page (`_open_edit_page`, ~1589) and sets visibility, similar to `_edit_batch` (~3146). That needs the app running at the right time, so it is a larger change. Stop and ask before building it.
- **Time zone.** The app uses naive local datetimes. Studio interprets the picked date and time in the account or browser time zone. If they differ, the switch lands at the wrong moment. The schedule path has the same risk. Check the Studio time zone during the probe.
- **Resume after partial batch.** Resumed runs restart `k` at 1 for the remaining parts (Section 7, item 8). See Open Question 4.
- **Failed mid-batch part.** A part that fails after `committed` is `needs_attention` and is not re-uploaded automatically. Its public switch may or may not be set. This matches the existing contract.
- **Studio rejects a too-close switch.** Unknown. The probe can test a date one hour out to see the error text, if the user agrees.

## 11. Open questions (recommended defaults)

1. **Members-only at upload or scheduled?** Default: immediate, as the request implies.
2. **"Trong vòng 3 ngày" exact or random?** Default: exact 3k days, as the request's example says.
3. **Does the members-only window apply to the first video only?** Default: every video is members-only at upload and switches at its own 3k date. The request's wording supports this.
4. **Resume after partial batch: recompute or anchor?** Default: recompute at launch, as the spec says. Show per-part dates in the confirmation. Alternative: store a batch anchor in the first `committed` record and reuse it on resume. More correct, but needs a new state key.
5. **Minimum gap for public switch in Studio?** Unknown. Default: no app-side minimum beyond `days >= 1`. Confirm through the probe.
6. **Fixed hour or launch wall-clock?** Default: launch wall-clock time. The request does not ask for a chosen hour.
