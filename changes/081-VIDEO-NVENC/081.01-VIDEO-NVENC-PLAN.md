# Plan: 081-VIDEO-NVENC — GPU (NVENC) video encode on Windows

This is the video half of the original combined investigation
(`changes/082-AUDIO-CUDA-TTS` has the audio/TTS half — see that feature's
prompt for the split rationale). Shared background facts (machine capability
check, ffmpeg binary) were established once and are reproduced here plus
there.

## Summary

The Windows video pipeline hardcodes CPU (`libx264`) encoding. The bundled
Windows ffmpeg binary already has NVIDIA NVENC support built in and directly
verified working on this machine — no new dependency, no packaging change.
This feature adds GPU (NVENC) as an encoder option with runtime detection and
automatic fallback to CPU on failure.

## Current state

- `src/noveltrans/tts/video.py:891-902` is the **only** encode call site (`render_video`). It hardcodes `"-c:v", "libx264", "-preset", "veryfast", "-pix_fmt", "yuv420p"`. No codec choice exists anywhere in config/UI.
- `VIDEO_QUALITY_PRESETS` (`video.py:75-83`, keys `high`/`high_static`/`fast`/`fastest`) only controls resolution/fps/vinyl-spin — not codec/encoder.
- `packaging/NovelTrans-windows.spec:23-34` bundles `packaging/ffmpeg/win/ffmpeg.exe`/`ffprobe.exe` into the frozen app if present (optional at build time; falls back to PATH otherwise, same as `runtime_env.augment_tool_path()` handles for macOS/Windows — see `runtime_env.py`). `README.md:146-152` documents fetching the **"essentials"** (not "full") gyan.dev build to keep installer size down.
- **Directly verified the binary actually committed in `packaging/ffmpeg/win/`**: `ffmpeg version 8.1-full_build-www.gyan.dev`, configured with `--enable-nvenc --enable-cuvid --enable-nvdec --enable-cuda-llvm --enable-amf --enable-d3d11va --enable-dxva2 --enable-libvpl`. `-encoders` lists `h264_nvenc`, `hevc_nvenc`, `h264_amf`, `hevc_amf`, `h264_qsv`, `hevc_qsv`.
- Confirmed (via gyan.dev's own build documentation) that the **essentials** variant also ships NVENC/CUDA/CUVID/NVDEC/AMF/QSV/VAAPI — the "full" vs "essentials" split only differs on OpenCL/Vulkan (general compute, not encode/decode). So the README's existing size-conscious recommendation to fetch "essentials" is **compatible** with adding NVENC — no need to switch to a larger ffmpeg build.
- `VideoWorker` (`gui/workers.py:1565` on) renders one window/part at a time in a single `QThread` loop (structurally similar to `MergeWorker` — "same one-file-per-window loop") — **not** parallelized like `AudioWorker`. This means there's no in-app NVENC session-contention risk to design around; only one ffmpeg encode runs at a time regardless of GPU/CPU choice.
- `_run_ffmpeg` (`video.py:662-694`) raises `TtsError` on nonzero exit and already writes stderr to a file for diagnostics — a natural place to catch an NVENC-specific failure and retry with libx264.
- `gui/tab_video.py:234-247` is where the quality-preset `QComboBox` lives — the natural place for an encoder choice, and `video_preset()` (`video.py:86-88`) / `VIDEO_QUALITY_PRESETS` is the natural place to add an `encoder` key.

## Capability check (already run, real hardware)

| | |
|---|---|
| OS | Windows 11 Pro 10.0.26200 |
| GPU | NVIDIA GeForce RTX 3060 Ti |
| VRAM | 8192 MiB |
| Driver | 610.88 (reports CUDA 13.3 UMD) |
| Bundled ffmpeg (`packaging/ffmpeg/win/ffmpeg.exe`) | `8.1-full_build-www.gyan.dev`, built with `--enable-nvenc --enable-cuvid --enable-nvdec --enable-cuda-llvm --enable-amf` |
| `h264_nvenc` / `hevc_nvenc` real encode test | **both succeed**, ~7x realtime at 1080p25 |

**Verdict: yes — this machine, and presumably most Windows gaming/desktop PCs the user targets, can do NVENC video encode today with the ffmpeg binary already in the repo.**

Since this can't be assumed for every user's machine, the app needs an equivalent runtime check:

- `noveltrans.tts.video.nvenc_available() -> bool` — a cheap real-encode probe (`ffmpeg -f lavfi -i nullsrc -t 0.1 -c:v h264_nvenc -f null -` or similar, matching the pattern just verified manually above), cached for the process lifetime. Real hardware/driver verification, not just "is the encoder name in `-encoders`" (a listed encoder can still fail at runtime with no CUDA driver present, e.g. `Cannot load nvcuda.dll` on a machine with only integrated graphics).
- If unavailable: Settings shows CPU-only, GPU option grayed out with a tooltip explaining why (mirrors the `tts_speed_spin` ffmpeg-unavailable pattern at `settings_dialog.py:440-444`). No behavior change from today.

## Implementation steps

1. **`src/noveltrans/tts/video.py`**: add `nvenc_available() -> bool` (cheap real-encode probe as described above, cached via `functools.lru_cache` or module-level memo so it's not re-run per render).
2. **Encoder selection in `render_video`**: replace the hardcoded `["-c:v", "libx264", "-preset", "veryfast", ...]` (video.py:899) with an encoder-args builder, e.g. a small dict/function returning the right flag set per encoder:
   - `libx264` (today, unchanged fallback): `-c:v libx264 -preset veryfast -pix_fmt yuv420p`
   - `h264_nvenc`: `-c:v h264_nvenc -preset p4 -pix_fmt yuv420p` (NVENC presets are `p1`-`p7`, not `libx264`'s named presets — **not** a drop-in flag, confirmed via `ffmpeg -h encoder=h264_nvenc`; `p4` ~ "medium", a reasonable default). Consider `-cq <n>` for quality-based rate control instead of NVENC's default fixed-bitrate CBR (observed in testing above) to better match libx264's default CRF-based quality.
   - `hevc_nvenc` as a possible higher-efficiency option, gated behind the same detection.
3. **Fallback on encode failure**: wrap the `_run_ffmpeg(...)` call for the video-encode step (video.py:891-902) so that if `nvenc_available()` was true and the actual render still fails (driver hiccup, VRAM contention with another GPU-heavy app, session limit), catch the `TtsError`, delete the partial `out_path`, and retry once with `libx264` before surfacing an error to the user.
4. **Config/UI**: add an `encoder`/`gpu_encode` choice, most simply as a new key alongside `video_quality` in `config.py` (`DEFAULT_VIDEO_QUALITY` pattern at config.py:53) and a checkbox or combo in `tab_video.py` near the existing `video_quality` combo (`tab_video.py:234-247`), e.g. "Dùng GPU để encode (NVIDIA NVENC)". Default **off** for safety on the first ship, or **auto-on when detected** since the downside (a failed encode with fallback) is low-risk — pick one and note the choice in the PR.
5. **`video_preset()`/`VIDEO_QUALITY_PRESETS`** (video.py:75-88): either add an orthogonal `encoder` selector (separate from quality preset, since resolution/fps and codec are independent choices) or extend each preset dict with a `speed` multiplier note that NVENC is faster still — the existing `speed` field's docstring already says "measured on Apple Silicon" so any new numbers should be captioned "measured on Windows/NVENC" to avoid conflating them.
6. **Packaging**: no ffmpeg binary change needed — confirmed the currently-committed "full" build already has NVENC, and confirmed via gyan.dev's own documentation that the README-recommended "essentials" build also ships NVENC/CUDA/CUVID/NVDEC/AMF, so this is a **zero-cost** capability already sitting in the existing binary once the app is told to use it. No `pyproject.toml`/extras change is needed at all — it's pure `video.py`/`config.py`/`tab_video.py` work.

## Open questions / risks

- **This machine vs. the "real" target machine.** This capability check was run on the actual Windows machine available for this task, which happens to have an RTX 3060 Ti. If the app's actual end-user machine differs, this table needs re-running there — but the runtime-detection code makes this a non-blocking risk (the app degrades gracefully either way).
- **Full vs. essentials ffmpeg build.** The binary currently committed under `packaging/ffmpeg/win/` is labeled a "full" build, while `README.md:149` instructs fetching "essentials" for a smaller installer. This investigation confirmed (via gyan.dev's build documentation, not by re-downloading and testing the essentials zip directly) that essentials also ships NVENC/CUDA. Worth a one-time real-file confirmation (download essentials, run `-encoders`) before shipping, since gyan.dev's build matrix changes over time.
- **NVENC session limits on consumer GeForce cards.** Older NVIDIA drivers capped concurrent NVENC sessions (historically 2-3) on consumer (non-Quadro) cards; `VideoWorker` only ever runs one encode at a time so this shouldn't bite in-app, but a user simultaneously screen-recording/streaming (OBS, Discord, NVIDIA Broadcast) could hit it. Worth a clear error message rather than a silent hang if it happens (surfaced via the existing `_run_ffmpeg` error-detail mechanism, video.py:692-694).
- **Quality/bitrate parity.** NVENC's default rate-control (fixed-bitrate CBR observed) differs from libx264's default CRF-based quality target; matching perceived quality between the two encoders needs a short manual eyeballing pass (not just "it encodes without erroring") before calling the feature done — recommend a `-cq`-based setting as noted above.

## Recommendation

Proceed now — low risk, zero new dependencies, zero packaging risk, and already verified end-to-end on real hardware.
