# 096-COVER-AND-TITLE — History

## [FEAT] The cover preview tells the truth; the title breaks and reads where you say — 2026-09-18

Three reports from one session on one novel (*Đại Càn Đỉnh Lưu: Phò Mã Gia Trốn Hôn*),
each one uncovering the next.

### 1. The cover editor's preview did not match the cover it saved

Reported as "vị trí tiêu đề không đúng": the preview showed the title on two lines where
the saved `.jpg` put it on three, the last word (`Hôn`) below the bottom edge.

The editor composed its preview at 720×405 and the real cover at 1280×720. Positions are
fractions, so that was believed to be equivalent — it is not. Font sizes round to whole
pixels (`405 * 0.11 * 1.02 → 45`, `720 * 0.11 * 1.02 → 81`) and glyph widths do not scale
linearly, so a line measuring 61.9% of the frame in the preview measured over the 62%
wrap budget at full size and broke again.

- `gui/thumbnail_editor.py`: compose at 1280×720, scale to the label with LANCZOS. A full
  compose is ~76 ms, inside the editor's own 80 ms debounce, so dragging still feels live.
  A test spies on `compose_thumbnail` and pins the size it is called at.

### 2. The title could not be broken where the user wanted

- `tts/thumbnail.py`: `_wrap_title_lines` wraps each `\n`-separated line on its own
  (blank lines dropped), and `cover_title(display_name, custom)` decides whether a stored
  layout still applies — it does while it spells the same title, compared on letters and
  digits only, so line breaks, spaces and a dropped ":" are layout while different words
  are not. A novel renamed afterwards falls back to the new name, auto-wrapped, rather
  than pinning every cover to the old one.
- A line the user typed is wrapped only against the frame's room, not the 62% budget:
  with the cap, `Phò Mã Gia Trốn Hôn` broke again and put `Hôn` off the frame — the very
  thing the break was typed to prevent. Auto-wrap (no typed break) keeps the 62% cap that
  stops the title running under the photo's subject.
- `gui/thumbnail_editor.py`: a "Tiêu đề (Enter để xuống dòng)" box, prefilled with the
  display name. Typing different words shows a warning and is not used — the box changes
  layout, never the title. "Đặt lại" clears it. Stored per novel as
  `video_thumbnail_title_text` (an identity key), so the YouTube title and the description
  are untouched.

### 3. The YouTube title order, and the parts already on the channel

Asked for `Phần 1 - {tên}` instead of `{tên} - Phần 1`. A free template was rejected: the
rename resync has to recognise a title it generated in order to rewrite it, and two fixed
shapes stay recognisable where a template would not.

- `tts/video.py`: `build_upload_title(..., order)`, `TITLE_ORDERS`.
- `rename.py`: `retitle()` (pure) is now the single answer to "is this title one we
  generated, and what should it read now" — shared by the sidecar resync and by the new
  YouTube push, so disk and channel cannot disagree about the rules. `title_name()` reads
  the name half. Both shapes are recognised, so a rename still finds a part-first title.
- `gui/tab_video.py`: a "Tiêu đề video" picker beside "Tên hiển thị". Switching it
  re-titles every rendered part that is not yet uploaded.

**The follow-up report — "chi tiết không đổi, tải lên cũng không đổi" — was the published
parts.** The order switch deliberately left parts 1 and 2 alone (they were on the channel,
private), and the app never re-uploads a part with an upload record, so nothing could ever
change them. Their `.title.txt` was left matching what YouTube shows, and a way to push
the change was added instead:

- `youtube_upload.py`: `TitleRequest` (validates YouTube's 100-character cap and `<>`),
  `update_title_one` and `update_title_batch`. `update_thumbnail_batch`'s per-part loop is
  now the shared `_edit_batch` — one browser, a failing part does not abort the rest,
  `needs_login` does. `_thumbnail_accepted` → `_edit_accepted` (the Save-enabled gate is
  not image-specific); `_save_edits(..., what=)` names the field in its messages.
- `gui/workers.py`: `YouTubeTitleWorker`, the thumbnail worker's sibling.
- `gui/tab_video.py`: "✏️ Cập nhật tiêu đề" beside "🖼️ Cập nhật ảnh bìa". It lists only
  published parts whose recorded title differs from what would be written now, confirms
  with the exact new titles, and writes the sidecar **only** for a part Studio confirmed —
  so "Chi tiết phần" never claims a rename that did not happen. The status line after an
  order switch says how many published parts still need the push.

### Known limits

- The edit page's title box (`#title-textarea #textbox, ytcp-video-title #textbox`) has
  not been exercised against live Studio — only the upload dialog's copy of that selector
  has. A miss fails loudly (Save never enables) rather than reporting a rename that did
  not happen.
- Covers already rendered keep their old line breaks until "Tạo lại tất cả ảnh bìa".
