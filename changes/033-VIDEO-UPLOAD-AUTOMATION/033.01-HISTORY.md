## [IMPLEMENTATION] — 2026-07-27

### New — `src/noveltrans/youtube_upload.py`
The third browser-driving module, built on `browser.py` unchanged and shaped after
`discord_unlock.py` (dedicated `.youtube-profile`, `open_login()`, an error class with
`needs_login`, module-level retunable selectors, Vietnamese user strings).

- **Upload-state sidecar** `<stem>.upload.json`, beside the `.mp4` in the part's own
  folder (the layout feature 026 created "so a single video can be uploaded without
  hunting through the others"). State machine
  `started → draft → committed → published`, plus `unknown` for an unreadable file.
  Written atomically (temp → `os.replace`) because it runs immediately before an
  irreversible click. Only a part with **no record at all** is auto-uploadable.
- **`schedule_times` / `validate_schedule_start`** — pure; naive local wall-clock so
  "20:00 every day" stays 20:00. Rejects a start in the past or under 15 minutes out
  (a multi-GB part is still transferring by then).
- **`_format_date` / `_format_time`** — Studio parses what it renders, so both the
  Vietnamese ("1 thg 8, 2026" / "20:00") and English ("Aug 1, 2026" / "8:00 PM")
  forms exist; `?hl=vi` pins the UI and `_page_is_vietnamese()` reads `<html lang>`
  rather than trusting the pin.
- **The Studio flow** — `upload_one(page, request)` and `upload_batch(requests)`, the
  latter reusing one browser across a run with 20 s pacing between parts. Guard before
  commit: every required control is verified present, and a missing one raises *before*
  the publish click. Required vs optional split — file/title/MFK/visibility/publish are
  fatal; description/tags/playlist/language warn and continue.
- Waits for the **bytes**, never for processing: the gate is the publish button
  becoming enabled, and publishing is allowed while YouTube processes. Waiting for
  processing would turn a 12-part batch into a multi-day job.

### Changed
- `gui/workers.py` — `YouTubeLoginWorker` and `YouTubeUploadWorker` (signals mirror

- `gui/tab_video.py` — new "Tải lên YouTube" group box (visibility combo, start

  `_launch_upload` and handlers. Batch and row paths both funnel into `_launch_upload`,
  as `_render_one`/`_start_video` both funnel into `_launch_video`.

### Corrections applied after the plan landed
The first implementation pass was written in parallel with the Plan agent; four real
defects it flagged were fixed:
1. A corrupt/truncated state file read as `{}` — i.e. as **"never uploaded"**, the exact
   confusion that re-publishes a live video. Now reads as `unknown`.
2. State writes weren't atomic, which is what produces such a file in the first place.
3. No `committed` state: a crash right after the publish click left the part as `draft`.
   `committed` is now written *before* the click and never downgraded.
4. Description was typed per-keystroke — a multi-KB chapter-timestamp table would take

Also added: `?hl=vi` pinning, publish-button-enabled as the transfer gate (instead of
regex-matching a localized progress string), a per-session created-playlist guard so a

## [FIX] No way to change channel after signing into the wrong one — 2026-07-27
Reported by the user, who logged into the wrong channel. Real design gap: `open_login`
waits for `studio.youtube.com/channel/`, so with a valid session it matched immediately
and closed the window **before the user could pick anything**. Re-clicking "Đăng nhập
YouTube" was therefore a no-op, and the only escape was deleting
`~/NovelTrans/.youtube-profile` by hand.

- `clear_profile()` — deletes the dedicated profile, returns whether one existed.
  Chosen over YouTube's own channel switcher because that only moves between brand
  channels *within* one Google account and so can't fix "wrong account" at all — and it
  would be one more piece of Studio DOM to keep working. Guarded: it refuses unless the
  directory actually looks like a Chromium profile (`Default` / `Local State` present),
  since it is a recursive delete.
- `open_login(switch=False)` — `switch=True` clears the profile first, so Google opens
  its account chooser. Now returns `(channel_id, channel_name)`.
- `_current_channel(page)` — reads the `UC…` id from the URL and the account name from
  Studio's header, so the app can report *which* channel got connected. The failure mode
  being fixed is not noticing the wrong channel until a video is public on it.
- `YouTubeLoginWorker(switch=…)`, `done` now carries `(channel_id, name)`.
- Settings: an "Đổi kênh…" button beside "Đăng nhập YouTube", a connected/not-connected
  status label, a confirm dialog that notes already-uploaded videos stay on the old
  channel, and a post-login box naming the channel and inviting a re-pick if wrong.
- Tests (+8): profile removal; missing profile is not an error; **refuses to delete a
  directory that isn't a browser profile**; `switch=True` clears before launching and
  plain login does not; `_current_channel` with id+name, id only, and neither.

The failed live run left parts stuck at `started`, which the app refuses to retry — and
the only way out was deleting `.upload.json` by hand. That was listed as a follow-up;

## [BUGFIX] The upload dialog is attached but never *visible* — 2026-07-27
Second live stall, and the error log named the cause exactly:

```
waiting for locator("ytcp-uploads-dialog").first to be visible
36 × locator resolved to hidden <ytcp-uploads-dialog workflow-step="SELECT_FILES">
```

`ytcp-uploads-dialog` is a zero-size wrapper whose content renders in an overlay, so
Playwright computes it as **hidden** while it fills the user's screen. `_first_present`
always waited for `visible`, so `_open_upload_dialog` blocked until the 60 s timeout —
`_send_file` was never even reached, which is why the previous fix changed nothing.

- `_first_present(..., state=)` — `attached` for Studio's `ytcp-*` wrappers, `visible`
  kept for real controls (contenteditable boxes, radios, buttons), which genuinely are.
- `_open_upload_dialog` waits for `attached`.
- **`_finish` had the same flaw, inverted and far worse.** It confirmed a publish by
  waiting for the dialog to become `hidden` — which it is from the moment it mounts. The
  check passed instantly, so every publish would have been recorded `published` without
  verifying anything, including ones YouTube rejected for a missing required field. Now
  it waits for the dialog to **detach** or Studio's share / still-processing dialog to
  appear, and raises naming the step otherwise.
- `workflow-step` turned out to be the best signal in the whole flow: a
  language-independent enum straight from Studio's own state machine.
  `_dialog_step(page)` reads it, `_file_accepted` uses it as the primary check
  (title box / progress label remain fallbacks), and failures now quote it — so the next
  report says *where* it stopped instead of just that it did.

Tests (+7): a fake page that is attached-but-never-visible, exactly like the real one.
Asserts `_open_upload_dialog` never waits on visibility; `_dialog_step` reads the
attribute; `_file_accepted` keys off it; and — the important ones — a hidden dialog is
**not** accepted as publish confirmation, while a detached dialog or a share dialog is.
Verified by restoring both old behaviours and watching three tests fail.

**770 passed, ruff clean.**

## [BUGFIX] Nothing ever waited for the transfer — 2026-07-28
First run that got all the way through: of 31 parts, 4 published and the rest sat at
16–18% "Uploading" — **all at once**, then died when the browser closed. The user's own
diagnosis was right.

Cause: `_wait_for_bytes_uploaded` gated on `#done-button` becoming enabled, on the
assumption (from the plan) that Studio disables it during a transfer. **It doesn't** —
Studio lets you publish while bytes are still moving and finishes in the background. So
the gate was true on the first poll, every part published immediately, and the loop
queued all 31 uploads before `_close` killed every one still in flight.

This is why the earlier "wait for bytes, not processing" comment was actively
misleading: the code claimed a distinction it never implemented.

- `transfer_state(text) -> (finished, percent)` — pure and tested, because it is the
  decision that says when moving to the next part is safe. Finished once the line stops
  saying *uploading*; anything about processing or checks happens after the bytes land.
  A full `100%` also counts. Unrecognised text reads as *not* finished — erring that way
  costs time, erring the other way abandons an upload.
- `_wait_for_bytes_uploaded` polls that instead of the button, and raises rather than
  guessing if it never finds the progress line at all (publishing blind is what
  abandons the transfer). Timeout messages quote the last line seen.
- `_SETTLE_BEFORE_CLOSE_MS` — a short grace period before tearing the context down, since
  YouTube commits the publish asynchronously.
- Tests (+20): `transfer_state` over real Studio strings in both languages, including
  `Uploading 99%` (not finished) vs `Uploading 100%` (finished), processing/checks lines,
  and unrecognised text; `_wait_for_bytes_uploaded` returns only after completion,
  reports progress on the way, times out rather than returning early while still
  uploading, and refuses to proceed when no progress line exists.

## [KNOWN GAP] Selectors are unverified against a live channel — 2026-07-27
The Studio selectors are written from the documented `ytcp-*` / `tp-yt-paper-*` id and
`[name=…]` enum hooks, but **have not been run against a real logged-in channel** — that
needs the user's own account and a throwaway upload. Expect to retune the constants
block at the top of `youtube_upload.py` on first live run; it is grouped by step for
exactly this. The guard-before-commit design means drift should surface as "nothing was
published, here is the step that failed" rather than a bad video going live.

Not implemented (noted as follow-ups in the plan): the `youtube_channel_id`
wrong-channel guard, config persistence of visibility/schedule preferences, and the
"đánh dấu đã đăng" / "xoá trạng thái tải lên" escape hatches in the Chi tiết dialog —
today the escape hatch is deleting the `.upload.json` by hand, which the tooltip says.
