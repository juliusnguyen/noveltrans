# 033.01 — Automated YouTube upload from the Video tab (Playwright / YouTube Studio) — PLAN

## Summary

Add a browser-automation upload path to the Video tab that drives **YouTube Studio**
in a real Chrome, consuming the sidecars feature 025/026 already writes next to every
part (`<stem>.mp4`, `.title.txt`, `.txt`, `.tags.txt`, `.jpg`). No Google Data API, no
OAuth, no quota.

The shape is `discord_unlock.py`, scaled up:

| `discord_unlock.py` | this feature |
| --- | --- |
| `profile_dir()` → `.discord-profile` | `profile_dir()` → `.youtube-profile` |
| `open_login(timeout_ms)` — visible window, blocks | same |
| `DiscordUnlockError(needs_login=…)` | `YouTubeUploadError(needs_login=…, video_id=…)` |
| module-level selector constants "easy to retune when the DOM drifts" | same, ×4 (Studio drifts far more) |
| `_command_offered()` guards before pressing Enter | **every** required field is verified before the publish click |
| one-shot `run_unlock()` | `upload_batch()` — one browser, N parts |

## Decisions taken before planning (user)

1. **Run scope** — one "Tải lên YouTube" button queues every not-yet-uploaded part and
   uploads them in sequence reusing ONE browser session; a per-row "Tải lên" button
   stays for one-offs and retries.
2. **Visibility** — configurable per run: công khai ngay / không công khai / riêng tư /
   **hẹn giờ đăng**, the last with "start datetime + every part N days apart".
3. **Fields set** — title, description, tags, thumbnail, "không dành cho trẻ em"
   (mandatory before YouTube will publish), per-novel playlist (created on first
   upload if missing), video language = Tiếng Việt. Everything else keeps the
   channel's Studio defaults.
4. ToS/fragility risk accepted; mitigations noted, not argued.

---

## Where upload state lives

**A per-part sidecar `<stem>.upload.json`, in the part's own folder, is the single
source of truth.**

Feature 026 already gave every part its own folder (`video_dir/<stem>/<stem>.mp4` +
sidecars) *specifically* "so a single part can be uploaded without hunting through the
others" — the upload record belongs there with the artifact it describes.

- The tab already has `_part_sidecar(window, whole_novel, ext)`; reading upload state
  is one more call. It inherits the legacy-flat-render fallback in `_part_output_path`
  for free.
- The identity key is the **file stem** (`slug-0001-0010`), which encodes the chapter
  range and so is stable when the user changes batch size — unlike the part *number*,
  which reshuffles.
- Crash safety: the record is rewritten immediately before an irreversible click, and
  must be written atomically (`write .tmp` → `os.replace`). Rewriting all of
  `meta.json` (as `save_tags` does — read-modify-write, non-atomic) before every
  publish would put the entire novel's metadata in the crash window on every part.

**Rejected:** `NovelMeta.uploads` in `meta.json` (crash window above; nested mutable
dict fits `asdict()` badly); a `chapters.db` table (state is per *part*, not per
chapter — no natural row); `video_dir/uploads.json` (a shared file two windows can
clobber, and it doesn't travel if a part folder moves).

## The state machine, and where it is written

Write points are chosen so the local record is always **at least as committed as
reality on YouTube** — we may claim a video exists when it doesn't, never the reverse.

```
  (no sidecar)                                    ← the ONLY auto-uploadable state
       │  ①  {status: started}                    ← BEFORE set_input_files()
       ▼
   started (no id)        ← failure window W1
       │  ②  {status: draft, video_id, url}       ← as soon as Studio shows the share link
       ▼
   draft
       │      … title, description, thumbnail, playlist, MFK, tags, language …
       │      … verify every REQUIRED control was found (guard-before-commit) …
       │      … Tiếp ×N, visibility / schedule …
       │  ③  {status: committed}                  ← BEFORE clicking the publish button
       ▼
   committed              ← failure windows W2, W3
       │  ④  {status: published, video_id, url, published_at}
       ▼
   published
```

Any exception keeps the highest state reached. A `committed` record is never
downgraded to failed — that would make it look retryable.

### Remaining failure windows — stated honestly

- **W1 — crash between ① and ②.** A draft may exist with no id recorded. The row shows
  `⚠️ Dở dang`, the batch skips it, the user is told to check Studio → Bản nháp. Never
  auto-retried: a retry here creates a second draft.
- **W2 — crash between ③ and the click landing.** Record says `committed`; nothing was
  published; a draft sits in Studio.
- **W3 — the click landed but confirmation was never observed.** Record says
  `committed`; the video probably *is* live.
  W2 and W3 are indistinguishable from the app's side, deliberately: they collapse to
  one user-visible state ("kiểm tra Studio") with an explicit escape hatch — delete the
  `.upload.json` to allow a re-upload, behind a warning about double-publishing.
- **W4 — the user deletes the video on YouTube.** Record still says `published`; we
  never poll. Same escape hatch.
- **W5 — two app windows uploading the same project.** Chrome's own `SingletonLock` on
  the profile dir makes the second launch fail loudly — an acceptable backstop.
- **W6 — cancel between "file uploaded" and "published".** By design this leaves a
  draft; the UI says so and does not try to delete it.

## `src/noveltrans/youtube_upload.py`

Sits beside `discord_unlock.py` and `cf_browser.py` as the third browser-driving
module, named after its job like both of them.

### Errors, profile, launch — the `discord_unlock` triplet

```python
class YouTubeUploadError(Exception):
    """needs_login → the one-time login, not a retry (same contract as
    DiscordUnlockError). video_id is set when the failure happened AFTER Studio
    accepted the file, so the user is told which draft to look at."""

class UploadCancelled(Exception):
    """User pressed Dừng. Carries the draft id. Same role as tts.merge.MergeCancelled."""

def profile_dir() -> Path        # DEFAULT_LIBRARY_DIR / ".youtube-profile"
def _require_playwright()        # → YouTubeUploadError with the pip/playwright text
def _launch_context(sync_playwright, *, headless)   # → browser.launch_persistent_context
```

`browser.py` is reused unchanged — its launch args
(`--disable-blink-features=AutomationControlled`, dropping `--enable-automation`,
real-Chrome-first) are exactly what Google's bot checks care about.

### Login — and why headless is wrong

```python
def open_login(timeout_ms: int = 300_000) -> None
```

Opens a **visible** Studio window, blocks until the URL reaches `/channel/UC…`.

1. Google's sign-in actively refuses automation-flavoured clients ("This browser or app
   may not be secure"); a headless fingerprint fails outright. `browser.py`'s docstring
   already records this for Discord; Google is the strictest of the three.
2. 2FA, brand-account selection and captchas **require** a human at the keyboard.
3. An upload batch is a multi-hour ToS-adjacent session. A mid-run re-challenge in an
   invisible window is unrecoverable; in a visible one the user solves it and the run
   continues. The whole run is therefore headed by default, same as `run_unlock`.
4. The user watching is itself a safety feature — they can see what is about to be
   published and hit Dừng.

### Pure helpers (tested)

```python
def schedule_times(start: datetime, count: int, spacing_days: int = 1) -> list[datetime]
    """start, start+N days, … Naive local wall-clock on purpose: Studio takes a
    wall-clock date+time, so timedelta(days=) keeps 20:00 at 20:00. spacing 0 = all
    at the same moment."""

def validate_schedule_start(start, *, now=None) -> None
    """YouTube rejects a past schedule, and a 12-part batch takes real time to upload,
    so require start >= now + 15 minutes and say so in Vietnamese."""

def _format_date(when, *, vietnamese) / _format_time(when, *, vietnamese)
    """Studio parses what it renders: "27 thg 7, 2026" + "20:00" in Vietnamese,
    "Jul 27, 2026" + "8:00 PM" in English."""
```

**Locale strategy — pin first, match second.** Every Studio navigation appends `?hl=vi`,
collapsing localisation to one known language and date format. Bilingual text matching
stays as belt-and-braces, and `_page_is_vietnamese()` reads `<html lang>` rather than
trusting either.

### Selectors — the retunable block

Module-level, grouped by step, commented as retunable — exactly as `discord_unlock`
does. **Ranked by stability, and the ranking is the design:**

1. `#id` on `ytcp-*` elements — Studio's own hooks, stable for years, language-free
2. `[name=…]` enum values on radios — literal API enums, language-free
3. `input[type=file]` — plain HTML, cannot be shadowed away
4. `aria-label` — localized but structural
5. visible text — **last** resort, always matched in BOTH vi and en

Playwright's CSS engine pierces the open shadow roots of `ytcp-*` / `tp-yt-paper-*`
for free, which is what makes id-based selection viable at all.

### The Studio flow

1. **Get to the upload dialog.** `goto(youtube.com/upload)` → if
   `accounts.google.com|youtube.com/signin` → `needs_login=True`. Wait for
   `ytcp-uploads-dialog`.
2. **① write the record**, then `input[type=file].set_input_files(mp4)`. Using the raw
   input avoids the OS file-chooser entirely — an OS window Playwright can't drive and
   which would block the page the way an alert does.
3. **Share link → video id → ② write the record.** Studio reveals `youtu.be/<id>` while
   bytes are still transferring; grabbing it here is what makes W1 narrow.
4. **Title / description.** `contenteditable` divs, not `<input>`s — `fill()` is
   unreliable. Click, select-all (Studio pre-fills the filename, so this is mandatory),
   then `insert_text` — per-key typing a multi-KB chapter-timestamp description takes
   ~40 s and drops characters.
5. **Thumbnail** → the *thumbnail* file input, scoped so the `.jpg` can't reach the
   video uploader. Absent ⇒ unverified channel.
6. **Playlist.** Open → search → exact-title match ticks it, else create-new. Exact
   match matters: a substring match ticks "Phần 1" for "Phần 10". A name already
   created *in this session* that goes missing is an **error**, not a second create.
7. **Made for kids = No** — `[name='VIDEO_MADE_FOR_KIDS_NOT_MFK']`, language-free.
   Mandatory: Studio blocks publishing until it is answered.
8. **"Hiện thêm"** → tags (already comma-joined and inside the 500-char budget by
   `tts/tags.py`) and video language = Tiếng Việt.
9. **Guard-before-commit checkpoint** — assert every required field was set. Raise
   *before* the publish click: nothing is published, the draft stays, the record is
   still `draft`. Same philosophy as `_command_offered()` refusing to press Enter.
10. **Tiếp ×N** — `#next-button` has the same id on every step; loop until the
    visibility radios appear rather than assuming exactly three (Studio has shipped
    2-step and 4-step variants).
11. **Visibility / schedule.** For a schedule, type the date and time, then **read both
    fields back and assert** — a mis-parsed date is the most damaging silent failure
    here (a part published *now* instead of in three weeks).
12. **Wait for the bytes, never for processing.** The gate is the publish button
    becoming enabled — Studio disables it until 100% of the bytes are in, which is far
    more robust than scraping progress text. YouTube processes an 8-hour video for
    hours, and publishing is allowed while processing continues; waiting for
    processing would make a 12-part batch take days. This distinction is the
    difference between a usable feature and an unusable one.
13. **③ `committed`**, then click publish **once**, guarded by a flag so no retry path
    can double-click it.
14. **Confirmation** = the dialog closing (a validation error keeps it open) → **④
    `published`**.
15. **Human pacing** between parts — cheap, and the main thing separating "automation"
    from "hammering".

**Required vs optional — the split that decides whether a failure is fatal:**

| field | missing ⇒ |
| --- | --- |
| file input, title, made-for-kids, visibility, publish button | **fatal** — cannot publish correctly |
| thumbnail | **fatal, pre-commit** — almost always an unverified channel; the user needs to know once, loudly |
| description, tags, playlist, language | **warn and continue** — a correct video without tags beats no video |

### Public API

```python
@dataclass
class UploadRequest:   # plain paths and strings only — no MergeWindow/NovelProject, so
    video: Path        # the GUI builds these on the Qt thread and the worker never
    title: str         # touches the project's sqlite handle
    description: str; tags: str; thumbnail: Path | None; playlist: str
    visibility: str    # public | unlisted | private | schedule
    publish_at: datetime | None   # required iff visibility == "schedule"
    label: str         # "Phần 3" — progress messages only
    def validate(self) -> None    # reject what can't succeed, before any browser opens

@dataclass
class UploadResult:
    video_id: str; url: str; visibility: str; publish_at: datetime | None; skipped: bool

def upload_one(page, request, *, on_progress, should_cancel) -> UploadResult
    """One part on an already-open page — so a batch reuses one browser and a test can
    drive the flow with a fake page."""

def upload_batch(requests, *, headless=False, on_progress, on_part_done, should_cancel)
    """One browser, N parts. A part that fails does NOT abort the run — mirrors
    AudioWorker's per-chapter handling, not VideoWorker's fail-fast, because parts are
    independent and a batch is expensive to restart. A needs_login failure DOES abort:
    every remaining part would fail identically."""
```

### Cancellation

Checked at the top of each part, at each stage boundary, and every poll of the upload
loop (the long one, so Dừng feels immediate). **Honoured only up to the `committed`
fence** — once publish is clicked we finish reading the confirmation and write
`published`; aborting mid-publish would produce exactly the "we don't know if it's
live" state we are working to avoid.

A cancelled part leaves its draft on YouTube. We do not delete it: deletion is a second
irreversible automated action with its own confirm dialog, and getting it wrong deletes
the wrong video. The status line says so.

## `gui/workers.py`

Appended after `DiscordLoginWorker`, house shape exactly.

- **`YouTubeLoginWorker`** — a near-copy of `DiscordLoginWorker`.
- **`YouTubeUploadWorker`** — signals mirror `VideoWorker` (`progress(int,int,str)`,
  `finished_ok`, `failed`) plus `part_done(int,str,str)` and `needs_login(str)`, so the
  tab's existing progress/cancel plumbing carries straight over. Playwright's sync API
  blocks and cannot run on the Qt event loop (same reason as `UnlockWorker`);
  `youtube_upload` is imported inside `run()` so a missing Playwright only bites when
  the user actually uploads.

State records are written **on the worker thread, synchronously, at the ①②③④ moments** —
never via a queued signal, which would put the Qt event loop between us and the click.

## `gui/settings_dialog.py`

Directly after the Discord block, the same three-widget shape: an "Đăng nhập YouTube"
button → `YouTubeLoginWorker`, and a muted hint mirroring `discord_hint`'s tone (ToS

```
│ Chế độ hiển thị: [Riêng tư ▾]   Bắt đầu: [28/07/2026 20:00 ▾]              │

│ ⓘ Cửa sổ Chrome riêng sẽ tự điền form Studio — đừng bấm vào nó khi chạy.   │
└────────────────────────────────────────────────────────────────────────────┘
```

Private is first **and the default**: the safe failure mode for a feature whose worst
bug is publishing something. The schedule row hides when visibility ≠ schedule.

The **schedule preview** is not decoration: "cách nhau 1 ngày" from a start already in
the past silently means YouTube refuses several parts mid-run, and seeing the real
dates catches that before the browser opens.

**Parts table 6 → 7 columns** — `"Đã tải lên"` inserted at index 5, actions move to 6
(width 250 → 320 for the fourth button). Cell text per state: `⬜ Chưa tải` /
`⚠️ Dở dang` (red, with the check-Studio tooltip) / `✅ <date>` with the URL as tooltip.

**`_build_row_actions`** gains a "Tải lên" button, disabled unless the part exists and
hasn't gone up.

**Launch path** — `_start_upload()` (batch) and `_upload_one()` (row) both funnel into
`_launch_upload(rows)`, exactly as `_render_one` and `_start_video` both funnel into
`_launch_video`. Schedule indices count over the **queued** parts, not part numbers, so
a re-run covering only parts 5–12 schedules them from the chosen start.

An upload is public and effectively irreversible, so `_launch_upload` shows a
confirmation the render step doesn't need: how many parts, which, the visibility or
first→last publish times, and that the browser window must be left alone.

`_cancel` handles whichever worker is running; `has_running_workers()` and `shutdown()`
gain the upload worker; `track_worker` keeps the Mac awake through an hours-long batch.

## Tests

All use the fake-Playwright injection established by `tests/test_discord_unlock.py`.
**No test launches a browser.**

`tests/test_youtube_upload.py`:
- `profile_dir()` is `.youtube-profile` and differs from the Discord and CF profiles.
- **Upload-state truth table**, parametrized over every (status × has-id) combination —
  this test *is* the never-double-publish guarantee.
- Corrupt/truncated state file → **never** reads as "never uploaded" (the single most
  dangerous confusion in the module).
- Atomic write: no `.tmp` left behind; a mid-write failure leaves the original intact.
- `schedule_times`: `count=0` → `[]`; `spacing=0` → all identical; `spacing=2, count=4`
  → +0/+2/+4/+6 days at the **same wall-clock time**; a month-boundary crossing.
- `validate_schedule_start` rejects the past and "in 5 minutes", accepts tomorrow.
- `_format_date` / `_format_time` for both locales — regression-proofs the "published
  now instead of in three weeks" bug.
- Guards: `upload_one` raises **before touching any locator** for a missing `.mp4`, an
  empty title, `schedule` with no `publish_at`, an already-`published` part.
- Flow, against a fake page recording every call in order: title select-all'd *then*
  written; the `.mp4` and the `.jpg` reach *different* inputs; MFK clicked; publish
  clicked **exactly once**; and `committed` is recorded **before** the publish click —
  asserted on the interleaved call log, since that ordering is what the whole
  idempotency design rests on.
- Negative: publish button never enabled → raises, publish **never clicked**, state
  still `draft`.
- `upload_batch`: one part failing does not abort the rest; `needs_login` does.

`tests/test_tab_video.py` (extend): 7 columns with the "Đã tải lên" header; the cell
text/tooltip per state; `_pending_upload_rows()` skips parts with no `.mp4`, already
published, and `⚠️ Dở dang`; the schedule preview text; `_start_upload` with nothing
eligible starts no worker.

## Ordered implementation steps

Each step compiles and passes `pytest` + `ruff` on its own.

1. **Upload-state core + tests** — pure, no browser, no Qt. The idempotency invariant
   lands first and in isolation, because everything else depends on it being right.
2. **`youtube_upload.py` pure half** — errors, `profile_dir`, `_launch_context`,
   `open_login`, schedule/locale helpers, and the selector block (values provisional).
3. **The Studio flow + fake-page tests.** Then verified by hand against a real channel:
   a short test render, `private`, a scratch playlist. **This is where the provisional
   selectors get corrected against the live DOM.** Budget real time for this step.
4. **`upload_batch`** — session reuse, playlist guard, pacing, cancellation, the ①②③④
   writes.
5. **Workers.**
6. **Settings login button** — after this the login is usable end-to-end with no upload UI.
7. **`tab_video.py`** — the box, the column, the buttons, the handlers.
8. **History doc** + a "what to do when Studio changes" note pointing at the selector block.

## Risks

- **DOM drift is the permanent tax.** Mitigations in order of value: id/enum hooks over
  text; `?hl=` pinning; bilingual text only as a last resort; one central commented
  constants block; and — most important — **guard-before-commit**, so drift produces
  "nothing happened, here is which step failed" rather than a video published with a
  blank description.
- **ToS / bot detection.** Accepted by the user. Mitigations, not arguments: opt-in;
  headed always; a real Chrome profile; jittered pauses; one browser per batch instead
  of N launches; no parallelism; genuinely manual login. Worst case is an account
  challenge, visible in a window the user can resolve.
- **Schedule off-by-a-timezone.** Studio schedules in the *channel's* timezone, which
  may not be the machine's. We type wall-clock and read it back, but a differing channel
  timezone shifts times. A channel-timezone probe is a follow-up.
- **Unverified channel** blocks custom thumbnails and >15-minute uploads — both fatal
  here. Detected pre-commit. (The tab already warns at 12 h in `_duration_item`; the
  15-minute limit is the more common trap.)
- **Multi-GB, multi-hour transfers.** Polled with a ~4 h ceiling plus `track_worker` to
  keep the Mac awake — but a closing laptop lid still kills a batch, and the record
  correctly reports the in-flight part.
- **Playlist ordering** follows upload order, which is right for a sequential batch; a
  later one-off retry appends at the end. Not automated.

## Out of scope

- Any Google Data API / OAuth / quota.
- The rendering pipeline (`tts/video.py`), thumbnail editor, tag generation — consumed,
  not changed.
- Editing an uploaded video's metadata, deleting videos or drafts, reordering playlists.
- End screens, cards, captions, monetization, Premieres, Shorts, comment settings,
  licence, category, recording date, location — everything outside the agreed field
  list stays at the channel's Studio defaults.
- Channel / brand-account switching inside the automation.
- Headless upload as a supported mode.
- Cross-process locking, resumable uploads, and any automatic retry of a part that
  reached `started` or beyond.
