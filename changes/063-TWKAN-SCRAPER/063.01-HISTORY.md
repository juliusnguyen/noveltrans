## [IMPL] twkan.com adapter — 2026-08-25

Implemented `063.01-INITIAL-PLAN.md` in full. All 8 steps landed; nothing deferred.

### Reconnaissance that shaped the design

Done live through the repo's own `cf_browser.BrowserSession` before any code was written.
Four findings drove every decision:

1. **Cloudflare is fingerprint-level.** A plain `curl` with our `USER_AGENT` gets 403
   (`cf-mitigated: challenge`); so does a full hand-forged real-Chrome header set
   (accept-language, sec-ch-ua, sec-fetch-*, upgrade-insecure-requests). `HttpClient`
   cannot read this site at all. `BrowserSession` cleared it on the first navigation and
   served 5 distinct URLs in one session with zero challenges. **So twkan takes its
   transport from `shuba69`, not `sto9`.**
2. **The sto9 truncation trap is present, identically.** The TOC page ships 36 of the
   reference novel's 188 chapters behind `LoadMore()`, and they are not a prefix —
   `data-num` jumps 15 -> 168. The ajax fragment returns all 188, contiguous.
3. **A phantom chapter sto9 does not have** — see below.
4. **A 字數 false alarm, chased down and cleared** — see below.

### The phantom `<li>` — the one genuinely new bug

twkan wraps its hidden bookmark widget in an `li[data-num]`, inside the *same* `<ul>` as
the chapters: `<li data-num="7"><a href="#" id="bookcase" style="display:none"></a></li>`.

Copying `sto9.py` verbatim would have broken **two** things, not one:

- **Bug A — the chapter list.** `li[data-num] a[href]` matches it, filing a titleless ref
  at index 0 and shifting every real chapter by one. Symptom would be a blank first
  chapter failing to download, which reads as a network hiccup rather than an off-by-one.
- **Bug B — `stated_total`.** `max(data-num)` reads the phantom's `7`. On a *complete*
  short novel (no `#loadmore`, so `max(data-num)` is the only signal) that makes
  `truncated` true, and the adapter would refuse a perfectly good list while quoting
  "4/7" — a total that appears nowhere on the site. Bug B was found during planning, not
  recon, and is the reason `index_full.html` carries the phantom.

One rule fixes both: an `<li>` counts only if it holds a real `/txt/<id>/<cid>` anchor
(`_CHAPTER_HREF_RE`). Its trailing `\d+` also rejects `/txt/<id>/end.html`, the last
chapter's 下一章 sentinel — at the parse layer as well as in `url_patterns`.

### The 字數 discrepancy is NOT a paywall — deliberately no code

Chapter prose measures ~55-63 % of the site's declared 字數 and clusters near ~2000 chars
regardless of the declared figure, and chapter pages load `crypto-js` + `/js/newread.js`.
Every one of those is a truncation signature; all are red herrings. Measured:

- the **raw pre-JS server response and the post-JS rendered DOM give a byte-identical
  `#txtcontent0`** (2014 chars / 87 lines for ch.1) — nothing is lazy-loaded or decrypted;
- `inner_html` of `#txtcontent0` is **3352** chars against a declared **3370** (~0.5 %),
  and the relationship holds on chapters 1, 2 and 188.

字數 counts the stored *markup* — `<br/>` tags and `&emsp;` indents included — not the
prose. Chapters are served complete. A length guard here would reject every chapter on the
site; feature 061 shipped exactly that false positive on bookqq and had to be reverted
(`1f9eb6f`). Recorded in the module docstring **with the numbers**, because the docstring
is what the next person reads.

### Files

- **`src/noveltrans/scrapers/twkan.py`** (new) — `TwkanAdapter` plus a pure parsing layer.
  `_get_html` is the only method that touches a browser; everything below `parse_*` is
  pure and takes markup, so the whole parsing surface is fixture-tested with no Chrome.
- **`src/noveltrans/scrapers/__init__.py`** — one line adding `twkan` to
  `_import_adapters`. Omitting it registers nothing and every twkan URL would report
  "Chưa hỗ trợ trang web này". Guarded by `test_the_adapter_is_registered`.
- **`tests/test_scrapers_twkan.py`** (new) — 71 offline tests + 3 live.
- **`tests/fixtures/twkan/`** (new) — 10 fixtures, hand-built to the measured structure
  with **invented filler text** (repo policy: no novel prose in the repo).
- **`tests/test_workers_scan_canonical_url.py`** — one added class. Not a code change:
  `ScanWorker` already does `find_by_url(pasted) or find_by_url(meta.url)`, so twkan
  inherits the fix; the class pins it, and pins the suffix-less chapter URL specifically.
- **`README.md`** — one row in the Chinese-source table.

No change to `SiteAdapter`, `cf_browser`, the workers, the models, the config or the GUI.

### Decisions worth remembering

- **Canonical `read_url`.** All three paste forms fold to
  `https://twkan.com/book/<id>/index.html`, because `Library.find_by_url` is exact string
  equality — echoing the pasted URL would make three projects for one novel.
- **`ORIGIN` is pinned**, not derived from the pasted URL (diverging from `shuba69`, which
  preserves the host for its `.cx` mirror). No twkan mirror is known, and pinning is what
  makes the canonicalisation actually collapse `http://`, `www.` and the bare host.
- **Chapter URLs carry no `.html`.** `_ID_RE` handles it unchanged; any regex written as
  `/txt/(\d+)/\d+\.html` would match nothing. Its own named test.
- **`_clean_description` IS needed** (og:description carries literal `<br />` *text* in
  the attribute value) — this is where twkan follows `shuba69` rather than `sto9`.
- **Container is `div.txtnav`, not `#txtcontent0`.** Both give byte-identical output
  today; `div.txtnav` matches what the two sibling adapters already use, and would pick up
  a future `txtcontent1` that the tighter selector would silently drop.
- **Chrome is decomposed by name.** `div.txtad` and `div.txtcenter` sit *inside*
  `#txtcontent0`, mid-prose — stripping only around the container would leak `loadAdv`
  into the middle of a chapter.
- **No placeholder-cover rule.** No `nocover`/`noimage` form was observed anywhere;
  inventing a filename would be dead code or a rule that eats a real cover. Documented as
  a known gap with the one-line fix.
- **Live fixture is class-scoped.** On this site a fresh adapter means a fresh Chrome, so
  per-test construction would clear Cloudflare three times over.

## [FIX] Transient Cloudflare challenge aborted the download — 2026-08-25

**Reported:** a real download died at chapter 11 with
`Không đọc được trang twkan — trình duyệt bị đóng hoặc không vượt được kiểm tra
Cloudflare. Thử tải lại. (Cloudflare returned a challenge for .../txt/114283/57238555)`

### Why the tests missed it

`TestLive` fetches exactly two chapters (first and last). The failure needs a *sustained*
batch, so nothing in the suite — or in the recon, which fetched 5 URLs — ever exercised it.
That is the real gap: the live test proved the browser path *works*, not that it *keeps*
working.

### What is actually happening

Measured with a 20-chapter sequential run at the default 1.5 s delay:

- chapter 10 came back **HTTP 429** with a Cloudflare interstitial — a **rate-based**
  challenge, not the fingerprint rejection the module was written against;
- it **cleared itself after 3 s** with the page simply left alone, and the real content
  was underneath it (2181 chars);
- the other 19 chapters were clean 200s.

So the site was never refusing us. `get_html` navigated with `wait_until="domcontentloaded"`
— which fires on the *interstitial* — read `page.content()` immediately, saw challenge
markers, and raised. A three-second pause was being reported as a hard failure, and one
chapter in ~11 killed the whole 188-chapter download.

### The fix — `src/noveltrans/cf_browser.py`

`get_html` now hands a detected challenge to a new `_settle_challenge()`, which polls the
live DOM once a second for up to `challenge_wait_seconds` (default 20) and returns as soon
as the interstitial is gone. Only a challenge still standing at the deadline raises.

Three deliberate choices:

- **Wait in place; do not re-navigate.** The challenge resolves itself in the page. A
  second navigation would put another request into a host that has just said "429".
- **A persistent challenge does not close the session.** The browser is healthy — the site
  is saying no. Closing would make the next chapter pay for a fresh launch *and* a fresh
  fingerprint check. (Navigation failures still close, as before.)
- **Bounded.** A dead-stuck challenge fails in 20 s rather than hanging the download.

This edits a **shared** module, which `063.01-INITIAL-PLAN.md` §7.9 predicted would not be
needed. The prediction was wrong: the bug is in the shared fetch path, not in twkan's
parsing, and 69shuba gets the same improvement for free.

### Verification

| Check | Result |
|---|---|
| 20-chapter raw run (pre-fix diagnosis) | challenge at ch.10, self-cleared in 3 s |
| **30-chapter soak through the real adapter (post-fix)** | **30 ok, 0 failed**; challenges at ch.11 and ch.22, each waited out in ~3 s |
| `pytest tests/test_cf_browser.py` | 19 passed (4 new) |
| Full suite | 2414 passed, 14 deselected |
| `ruff check .` | clean |

New tests: a transient challenge is waited out and cleared **by waiting, not by
re-navigating** (asserts `goto_urls` stays at one entry); the wait is bounded and gives up
at the deadline; a persistent challenge leaves the session open. The pre-existing
"raises on a challenge" test was retained, now passing `challenge_wait_seconds=0` — the
behaviour it pins is unchanged, it just has to say how long it will wait first.

### Also documented

- `twkan.py` docstring: a mid-download challenge is normal, self-healing, and must **not**
  be "fixed" by raising the delay — the pauses cost ~50 s across a 188-chapter novel,
  less than slowing every request would.
- `README.md`: the app pausing ~3 s mid-download is expected, not a hang.

## [UI] Novel picker shows the Vietnamese title and the source site — 2026-08-25

Requested mid-branch and landed here at the user's explicit choice, though it is unrelated
to the twkan scraper: the "Truyện gần đây" dropdown showed only the scraped title, so a
Chinese novel was identifiable only by its original name.

Now each row reads:

    穿書反派，把陰濕女主養成病嬌了  —  Xuyên thư thành phản diện, ... — twkan.com

### Where it lives

The dropdown is `ProjectPicker` (`gui/widgets.py`), **shared by all five tabs** — scrape,
translate, export, audio, video — so this is one edit, not five. `Library.project_meta()`
already parses the whole `meta.json` into a `NovelMeta`, so `translated_title` was in hand
at the row-building line: no project open, no extra disk read, no SQLite handle.

### Decisions

- **Reused the app's existing pairing format rather than inventing one.**
  `ScrapeTab._show_meta` already rendered `f"{title}  —  {translated}"` for the "Thông tin
  truyện" panel — em dash, two spaces each side. That is now `NovelMeta.bilingual_title()`,
  used by *both* call sites, so the panel and the picker cannot drift apart. The
  duplicated format string in `_show_meta` is gone.
- **Not `display_name()`.** That helper *replaces* the original title (override →
  translated → original) and exists to decide what a video says. The picker wants both
  titles at once, which is a different question.
- **The site suffix is the domain, not `meta.site`.** `site` holds the adapter name
  ("twkan", "69shuba"); what reads naturally in a list is what the user pasted
  ("twkan.com"). `NovelMeta.source_host()` takes it from the URL and drops `www.` so one
  site cannot appear under two spellings.
- **Local novels get no suffix.** A hand-written novel's URL is a synthetic
  `local://<uuid>`, whose netloc is a UUID — printing that would be worse than printing
  nothing. Guarded with the existing `is_local`.
- **Each half is optional.** An untranslated novel is `Tựa — site.com`, never a title
  trailing a dangling separator. A whitespace-only translation counts as none.

### Tests

- `tests/test_widgets.py::TestProjectPickerLabel` (new, 7 tests) — both titles + site,
  the untranslated and whitespace-only cases, domain-not-adapter-name, `www.` stripping,
  the local-novel case, and that the scrape header uses the same pairing.
- `tests/test_main_window.py` — 6 expectations updated. Those three tests are about the
  picker being *relisted* on a library change, but they assert its exact display text, so
  the new suffix had to appear in them. Their subject is unchanged.

Full suite: **2421 passed, 14 deselected**. `ruff check .` clean.

## [FIX] Google policy refusals during translation — 2026-08-25

**Reported:** translating with the `agy` CLI engine, chapter 10 failed with Google's raw
English notice — *"The prompt could not be submitted. The prompt contains sensitive words
that violate Google's Generative AI Prohibited Use policy…"*

### What was and wasn't broken

The batch was **fine**: `TranslateWorker` already catches `NovelTransError`, calls
`mark_error`, emits `chapter_error` and continues (`workers.py:308-311`). Only that one
chapter failed. But nothing in the message said so, so the failure reads like the run died
and like the app is at fault.

### The real bug found while reading the code

`complete()` returned `result.stdout` as the translation whenever the exit code was 0. If
the CLI ever prints the refusal to stdout and exits 0, **Google's English notice would be
saved as that chapter's Vietnamese translation** and exported straight into the EPUB —
silently, with the chapter marked done. That is a much worse outcome than a loud error,
and it was reachable without anything else going wrong.

### Changes — `src/noveltrans/translators/cli_agent.py`

- **`_friendly_error(detail)`**, one classifier for CLI failures. Returns `""` when it
  recognises nothing, so every existing passthrough is untouched — an unrecognised error
  still surfaces verbatim, tail-truncated, exactly as before.
- **Policy refusals** are mapped to a Vietnamese message that says the three things the
  English blob does not: it is Google's decision about *that chapter*; retrying the same
  text on the same engine will be refused identically; the rest of the batch is unaffected
  — then points at what actually works (another engine, or LM Studio running locally).
- **The quota mapping moved into the classifier**, so `RESOURCE_EXHAUSTED` / `429` is now
  recognised on stderr too, not only in the agy log.
- **stdout is checked before being accepted as a translation** — a refusal there raises
  instead of being stored. Scoped to the specific markers, which no Vietnamese chapter
  could plausibly contain.

Deliberately **not** done: nothing that rewrites, splits or obfuscates chapter text to get
past the filter. That would be circumventing the provider's enforcement rather than fixing
an app bug. The supported answer is a different engine, and the app already supports
re-translating selected chapters (`TranslateWorker.indices`).

### Tests — `tests/test_translators.py` (4 new, 40 total in file)

- a policy refusal is explained, not dumped (asserts the advice is present *and* the raw
  English is gone);
- ★ a refusal on stdout with exit 0 raises instead of being saved as a translation;
- a refusal found in the agy log gets the same treatment;
- an ordinary translation is not mistaken for a refusal — the stdout guard must not fire
  on real output.

Full suite: **2425 passed, 14 deselected**. `ruff check .` clean.
