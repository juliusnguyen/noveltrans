## 1. Summary of the approach

One new file `src/noveltrans/scrapers/twkan.py`, one line in `_import_adapters`, one new test module, one new fixture directory, one README row, and one added class in an existing test module. No change to `SiteAdapter`, no model change, no schema change, no new dependency, no config entry, no GUI change.

**twkan is the child of two existing adapters, and takes a different half from each.**

* From **`sto9.py`** it takes the *shape*: the same PHP novel CMS, the same three-page split (`/book/<id>.html` for metadata, `/book/<id>/index.html` for the canonical read URL, `/ajax_novels/chapterlist/<id>.html` for the real TOC), the same `LoadMore()` truncation trap, the same `div.txtnav` body, the same canonical-`read_url` policy.
* From **`shuba69.py`** it takes the *transport*: a fingerprint-level Cloudflare gate that `HttpClient` cannot pass at all, so every fetch goes through `cf_browser.BrowserSession` behind a single `_get_html` seam, with `close()`, the `delay_seconds` hand-off, the pre-Chrome `_status` line, and the two Vietnamese error mappings. It also takes `_clean_description`, which sto9 did not need and twkan does.

Three things are genuinely **new** to this adapter and none of them exist in either parent:

1. **The phantom `<li data-num="7">`.** The TOC page's hidden bookmark widget is wrapped in an `li[data-num]`, in the same `<ul>` as the chapters. `sto9.py:67`'s selector would match it and produce a phantom chapter at index 0, shifting every real chapter by one. Worse — and this is the part the recon does not spell out — it *also* poisons `sto9.py:178-184`'s `max(data-num)` signal, which would make a short, complete novel look truncated (§2.4.3). Both need the same fix: **an `li` is a chapter only if it holds a real `/txt/<id>/<cid>` anchor.**
2. **Chapter URLs have no `.html` suffix.** `https://twkan.com/txt/114283/57238545`. The id regex and both `url_patterns` must be written for that, and must still reject the `/txt/<id>/end.html` sentinel.
3. **The browser path multiplies the cost of the three-page scan.** sto9's 3 requests are 3 cheap HTTP GETs; twkan's are 3 browser navigations in a Chrome window the user is watching. §2.7 argues the budget is still correct and says exactly what the user sees.

The 字數-vs-prose gap that looked like a paywall is a **resolved false alarm** — 字數 counts the stored markup, not the prose, and raw-vs-rendered `#txtcontent0` is byte-identical. Feature 061 shipped a paywall false positive on bookqq and had to be reverted; this plan's job is to make sure nobody re-derives that mistake here, which is why it goes in the module docstring (§3.2) and gets no code at all.

## 2. Decisions

### 2.1 Identity and URL patterns

**Recommendation:**

```python
name = "twkan"
display_name = "台灣小說網 (twkan.com)"
url_patterns = [r"twkan\.com/book/\d+", r"twkan\.com/txt/\d+/\d+"]
content_is_translated = False   # inherited from base.py:101, with a comment
```

**`name = "twkan"`** — written into `NovelMeta.site` and into `meta.json` forever, so it must be short, ASCII and stable. It is also the module name, and unlike 69shuba (`shuba69.py:162-166` records that `69shuba` is not a valid Python identifier) `twkan` needs no workaround.

**`display_name = "台灣小說網 (twkan.com)"`** — the site's own `bookinfo.siteName` and `<title>` suffix are both `台灣小說網`. The `(domain)` suffix matches every sibling (`sto9.py:244`, `shuba69.py:169`, `ixdzs.py:29`, `xbanxia.py:25`). This string is currently **decorative** — nothing in `src/noveltrans/gui/` reads `SiteAdapter.display_name` (§0) — but set it right anyway; it costs nothing and it is what a future supported-sites list will show.

**Both patterns are host-anchored, and that is load-bearing here in a way it was not even for sto9.** `ADAPTERS` is ordered by the import tuple at `scrapers/__init__.py:25-35` and `adapter_for_url` returns the *first* match (`scrapers/__init__.py:16-20`). Three sites in this repo now serve chapters at `/txt/<id>/<cid>`:

| Site | chapter URL | pattern |
|---|---|---|
| 69shuba | `https://www.69shuba.com/txt/59024/38369377` | `shuba69.py:173` — book pages only, so it never claims a `/txt/` URL |
| sto9 | `https://sto9.com/txt/13908/7671958.html` | `sto9.py:250` — host-anchored |
| **twkan** | `https://twkan.com/txt/114283/57238545` | must be host-anchored |

A bare `r"/txt/\d+/\d+"` would match all three, and since `twkan` sorts after `sto9` and `shuba69` in the alphabetical tuple it would *not* win today — which is worse than winning, because the bug would be invisible until someone reordered the tuple. Anchor the host and pin it with tests in both directions (§5).

**Two patterns, not one.** `twkan\.com/book/\d+` covers *both* book forms because `matches()` uses `re.search` (`base.py:118`): `/book/114283.html` and `/book/114283/index.html` both contain the substring `/book/114283`. The second pattern exists only to accept chapter URLs, which is the realistic address-bar paste after the user clicks into chapter 1.

**The `end.html` sentinel is rejected for free.** `https://twkan.com/txt/114283/end.html` does not match `twkan\.com/txt/\d+/\d+` because `end` is not `\d+` — measured as the last chapter's 下一章 target. `test_scrapers_sto9.py:243` pins the equivalent for sto9; do the same here. This matters more than it looks: `book_id()` uses a *different* regex (§2.2) and would happily extract `114283` from the sentinel, so the registry pattern is the only thing standing between a stray paste and a scan of a page that is not a chapter.

**Mirrors: none known.** Do not speculatively widen the host the way `xbanxia.py:26` and `ixdzs.py:30` do for domains that were actually observed. Adding one later is a one-character edit — and it would also require revisiting `ORIGIN` (§2.2), so it should be a deliberate change, not a drive-by.

### 2.2 Canonical `read_url` — and the missing `.html`

**Recommendation: `NovelMeta.url` is always `https://twkan.com/book/<id>/index.html`, regardless of which of the three forms was pasted.** This copies `sto9.py:95-103` deliberately and for the same reason.

`Library.find_by_url` is **exact string equality** on `meta.url` (`library.py:46-50`). If the adapter echoed the pasted URL — the `shuba69.py:96-98` / `xbanxia.py:54` convention — then `/book/114283.html`, `/book/114283/index.html` and `/txt/114283/57238545` would become **three projects for one novel**, each with its own folder, its own `chapters.db`, its own translation progress and its own video settings. `shuba69`'s echo rule exists to avoid orphaning projects already on disk; twkan has none, so the better rule is free. It is also what the site itself nominates: `og:novel:read_url` on the detail page is exactly `https://twkan.com/book/114283/index.html` (measured).

Four pure helpers, mirroring `sto9.py:87-114`:

```python
ORIGIN = "https://twkan.com"

# Chapter ids carry NO .html suffix — /txt/114283/57238545 — so this must stop at the
# first path segment and must not assume an extension anywhere.
_ID_RE = re.compile(r"/(?:book|txt)/(\d+)")

def book_id(url) -> str        # -> "114283", else ScrapeError
def read_url(url) -> str       # ORIGIN + f"/book/{bid}/index.html"      <- canonical
def detail_url(url) -> str     # ORIGIN + f"/book/{bid}.html"            <- the og: tags
def chapterlist_url(url) -> str# ORIGIN + f"/ajax_novels/chapterlist/{bid}.html"
```

`_ID_RE` is **identical to `sto9.py:53`** and that is not an accident worth "simplifying": it already works for a suffix-less chapter URL, because it anchors on `/book/` or `/txt/` and captures the *first* `\d+` after it, never touching what follows. The thing that would break on twkan is any regex of the shape `/txt/(\d+)/\d+\.html` — do not write one. A test that `book_id("https://twkan.com/txt/114283/57238545") == "114283"` is the guard, and it is worth its own line precisely because it is the one place sto9's code would have silently failed.

**`ORIGIN` is a pinned module constant, not derived from the pasted URL.** This diverges from `shuba69.py:67-70`, which preserves the pasted scheme+host so its `.cx` mirror keeps working. Diverging is right here for the same reason `sto9.py:47-51` gives: no twkan mirror is known, and a fixed origin is what guarantees `http://twkan.com/…`, `https://www.twkan.com/…` and `https://twkan.com/…` all fold to *one* canonical string. Carry the comment across so a future mirror is an intentional edit.

**No `ScanWorker` change is needed.** `workers.py:122` already does `library.find_by_url(self.url) or library.find_by_url(meta.url)`, which is exactly the canonicalising-adapter case:

| Re-scan pasted as | `find_by_url(pasted)` | `find_by_url(meta.url)` | Result |
|---|---|---|---|
| `/book/114283/index.html` | hit | — | reuses project ✅ |
| `/book/114283.html` | miss | hit | reuses project ✅ |
| `/txt/114283/57238545` | miss | hit | reuses project ✅ |

So twkan inherits the fix, and this feature adds a **characterisation test** (§5, §3.6) rather than code. `test_workers_scan_canonical_url.py:1-12` documents what the hole cost when it shipped: `translated_title`, `tags`, `thumbnail_prompt` and `video_settings` silently wiped by `NovelProject.create`.

### 2.3 The browser fetch path

**Recommendation: copy `shuba69.py:175-219` almost verbatim, changing only the site name in the two error strings and the `_status` line.** Recon is unambiguous: plain `curl` with `base.py:15-18`'s UA gets **403 / `cf-mitigated: challenge`**, a full hand-forged real-Chrome header set *also* gets 403, and `cf_browser.BrowserSession` cleared it on the first navigation with no interstitial and served 5 distinct URLs in one session. The gate is at TLS/browser fingerprint, which is precisely what `cf_browser.py:8-13` describes for 69shuba. There is no token to harvest, so there is no `HttpClient` variant of this adapter to build.

```python
def __init__(self, client, *, headless: bool = False):
    super().__init__(client)
    self._headless = headless          # fingerprinted; the flag exists in case that changes
    self._session: BrowserSession | None = None
    self._detail: tuple[str, str] | None = None   # §2.5

def _get_html(self, url: str) -> str:
    if self._session is None:
        self._status("🌐 Đang mở trình duyệt để vượt kiểm tra Cloudflare của twkan — "
                     "giữ cửa sổ mở…")
        self._session = BrowserSession(
            headless=self._headless,
            delay_seconds=self.client.delay_seconds,
        )
    try:
        return self._session.get_html(url)
    except BrowserUnavailableError as exc:
        raise ScrapeError("Cần trình duyệt để đọc twkan (trang này có kiểm tra "
                          "Cloudflare). Cài Google Chrome, hoặc chạy:  pip install "
                          "'noveltrans[browser]' && playwright install chromium", url) from exc
    except BrowserSessionError as exc:
        raise ScrapeError("Không đọc được trang twkan — trình duyệt bị đóng hoặc không "
                          f"vượt được kiểm tra Cloudflare. Thử tải lại. ({exc})", url) from exc

def close(self) -> None:
    """Release the browser. Idempotent; never raises."""
    if self._session is not None:
        self._session.close()
        self._session = None
```

Each piece, and why it is not negotiable:

* **One seam, not a decorator or a mixin.** `_get_html` is the *only* method in the module that touches a browser; every `parse_*` below it is pure and takes markup (`shuba69.py:16-18`, `sto9.py:31-32`). That is what lets the entire parsing surface — including both new traps — be tested against fixtures with no Chrome anywhere in CI.
* **Lazy construction.** `BrowserSession.__init__` (`cf_browser.py:86-104`) does not launch; `get_html` launches on first use (`cf_browser.py:148-149`). Building the session lazily *inside `_get_html`* rather than in `__init__` matters on top of that, because `adapter_for_url` constructs an adapter for URLs that are then never scanned, and for every test that touches the registry. Pin it: `test_scrapers_shuba69.py:289-291` asserts `adapter._session is None` after construction.
* **Session lifetime is one scan or one download batch.** The session is created on the first fetch and reused for every subsequent URL — 3 navigations for a scan, 188 for a full download. `cf_browser.py:6-15` explains why: no `cf_clearance` cookie is issued at all, so the *live session is the clearance*. Re-launching per chapter would be 188 Chrome launches and, far worse, 188 fresh fingerprint checks.
* **`delay_seconds=self.client.delay_seconds`.** `HttpClient`'s throttle (`base.py:49-52`) is bypassed entirely on this path; `BrowserSession._throttle` (`cf_browser.py:136-139`) is the *only* thing between a 188-chapter download and hammering a CF-protected site. `test_scrapers_shuba69.py:293-306` pins this by faking the constructor and asserting the kwarg — copy that test.
* **The `_status` line fires *before* the session is constructed**, not after. A Chrome window is about to appear on the user's screen; unexplained, it reads as the app misbehaving. `workers.py:108` and `workers.py:2123` wire `on_status` to the progress signal, and `base.py:111-114` makes it a no-op outside the GUI.
* **Two exception types from two different modules.** `BrowserUnavailableError` lives in `browser.py:37-41` (Playwright missing / no browser launchable); `BrowserSessionError` lives in `cf_browser.py:74-75` (window closed, crash, navigation timeout, or a challenge body). Both must be imported (`shuba69.py:28-29`) and both must be mapped to Vietnamese `ScrapeError`s — an unmapped one escapes as `Lỗi không mong đợi: …` at `workers.py:135`, which tells the user nothing actionable. The install instructions in the first message are the whole point of separating them.
* **`close()` is idempotent, never raises, and is safe before any fetch.** `workers.py:136-138` and `workers.py:2171` call it in a `finally` on paths that are already failing, and `cf_browser.py:127-132` / `browser.py:91-97` are both written to swallow. A leaked session is a Chrome window the user has to force-quit. Three tests (`test_scrapers_shuba69.py:280-291`): double-close, close-before-fetch, and construct-never-launches.
* **`headless=False` default.** `cf_browser.py:12-15` records the measurement: headless is fingerprinted and never clears the challenge (180 s timeout vs instant headed). Keep the flag for the day that changes; keep the default headed.
* **Do not parallelise.** `cf_browser.py:21-23` states it: N sessions is N Chromes and the fastest route to an IP block, which would kill the only path this site has. Put it in the module docstring the way `shuba69.py:12-14` does. Downloads are sequential today (`workers.py:2109-2171`), so this is documentation, not code.

**One twkan-specific consequence of the browser path, worth stating because it shapes the fixtures:** `get_html` returns `page.content()` (`cf_browser.py:155`), which is a **serialisation of the live DOM**, not the bytes the server sent. Two follow-ons. (a) Encoding is a non-issue — `page.content()` is already a decoded `str`, so the site's `charset=utf8` declaration and `HttpClient.get_html`'s CN-encoding fixup (`base.py:80-87`) are both irrelevant. (b) Chrome has already repaired the markup, which is why twkan's ajax fragment arrives with **closed `<li>`s wrapped in `<html><head></head><body>`** while sto9's arrives with the CMS's raw unclosed ones (measured; contrast `sto9.py:192-195`). The fixtures must be captured in the DOM-serialised shape, or they would be testing markup the adapter will never see.

### 2.4 `fetch_chapter_list` — ajax-first, refuse-don't-fall-back, and the phantom `li`

This is the load-bearing part of the feature, and it has one more moving piece than sto9's.

#### 2.4.1 The shape

```python
def fetch_chapter_list(self, url: str) -> list[ChapterRef]:
    page = self._get_html(read_url(url))
    total = stated_total(page)
    try:
        page_refs = parse_chapter_list(page, ORIGIN)
    except ScrapeError:
        page_refs = []
    truncated = total is not None and total > len(page_refs)

    try:
        ajax_refs = parse_chapter_list(self._get_html(chapterlist_url(url)), ORIGIN)
    except ScrapeError:
        ajax_refs = []

    if ajax_refs:
        if total is not None and len(ajax_refs) < total:
            self._status(f"⚠️ twkan chỉ trả về {len(ajax_refs)}/{total} chương. "
                         "Quét lại sau để lấy đủ.")
        return ajax_refs

    if truncated:
        raise ScrapeError(
            f"Không lấy được danh sách chương đầy đủ của twkan "
            f"(trang mục lục chỉ hiện {len(page_refs)}/{total} chương). Thử quét lại sau.",
            chapterlist_url(url),
        )

    if page_refs:
        self._status(f"Lấy danh sách chương từ trang mục lục ({len(page_refs)} chương).")
        return page_refs

    raise ScrapeError("Chapter list not found — page layout may have changed", url)
```

Structurally identical to `sto9.py:277-316`, with `self.client.get_html` swapped for `self._get_html`. The `try/except ScrapeError` around each parse is what turns "this markup has no list" into an empty list, so the decision table below is the only place that decides anything.

#### 2.4.2 Why "refuse" and not "fall back to the 36 we already have"

Measured on the 188-chapter reference novel: the TOC page ships **36 chapters** and the `data-num` sequence jumps **15 → 168**. So `page_refs` is *not a prefix* of the real TOC. `ChapterRef.index` is a dense 0-based positional key (`models.py:119`) with nowhere to record the site's own number, so `page_refs[15]` would be stored as `idx = 15` while actually being chapter 168. Then:

* `create_project` writes 36 rows, each with a plausible-looking Chinese title. Nothing in the library view says "incomplete".
* The user downloads and translates them, spending real API quota.
* A later re-scan succeeds against the fragment. `replace_toc` (`project.py:273`) **upserts by `idx`, preserving `content`** — so row 15 keeps chapter 168's Chinese text and Vietnamese translation while its title and URL are rewritten to chapter 16's.
* The EPUB, the TTS audio and the video now contain chapter 168's story under chapter 16's heading, and **no row is marked as an error**.

Unrecoverable short of hand-deleting rows. A `ScrapeError` costs the user a retry. **When the page has told us it is truncated, an incomplete list is worse than no list.** The message names both numbers so it reads as a diagnosis rather than a mystery, and §6 puts a sentence in the README so a user who hits it knows the app is behaving correctly.

#### 2.4.3 The phantom `<li>` — two bugs, one fix

Measured on the TOC page:

```html
<li data-num="7">
  <a href="#" id="bookcase" style="display:none"></a>
</li>
```

It is the hidden bookmark widget, and it is the **first** `li[data-num]` in the same `<ul>` as the chapters. This breaks `sto9.py` in two independent places:

**Bug A — the chapter list.** `sto9.py:67`'s `li[data-num] a[href]` matches it (37 hits vs 36 real `/txt/` anchors, measured), producing `ChapterRef(index=0, title="", url="https://twkan.com/book/114283/index.html#")` and shifting every real chapter down by one. Every downstream index — `pending_download`, `replace_toc`, the EPUB TOC, the SRT sidecar — is then off by one, and the symptom is a blank first chapter that fails to download, which reads as a network hiccup.

**Bug B — the `stated_total` signal, which the recon does not call out.** `sto9.py:178-184` takes `max(int(li["data-num"]))` over **all** `li[data-num]`. On the reference novel the phantom's `7` is harmless because the real max is 188. But consider a genuinely short novel — the case §2.4.4's fallback branch exists for. A 4-chapter novel's TOC page has no `#loadmore`, so `max(data-num)` is the *only* signal; with the phantom included it returns `max(7, 4) = 7 > 4 = len(page_refs)`, so `truncated` is `True` and **the adapter refuses a complete list**. If the fragment is also unreachable, a perfectly healthy short novel becomes unscannable, and the error message reads `chỉ hiện 4/7 chương` — a number that appears nowhere on the site and that nobody will be able to explain.

**One fix serves both: an `<li>` counts only if it holds a real chapter anchor.**

```python
# Chapter hrefs carry NO .html suffix: /txt/114283/57238545. The trailing \d+ is also
# what rejects /txt/<id>/end.html, the last chapter's 下一章 sentinel.
_CHAPTER_HREF_RE = re.compile(r"/txt/\d+/\d+")

def _chapter_anchors(soup) -> list:
    """The <a>s that are really chapters, in document order.

    Not `li[data-num] a[href]` (sto9.py:67): twkan's TOC page wraps a hidden bookmark
    widget — `<a href="#" id="bookcase">` — in an `li[data-num]`, inside the SAME <ul>
    as the chapters. A bare href test picks it up as a phantom chapter at index 0 and
    shifts every real chapter by one.
    """
    return [
        a for a in soup.select("li[data-num] a[href]")
        if _CHAPTER_HREF_RE.search(urljoin(ORIGIN, a["href"]))
    ]
```

…and `stated_total` walks the *same* filter:

```python
numbers = [
    int(li["data-num"])
    for li in soup.select("li[data-num]")
    if str(li.get("data-num", "")).isdigit()
    and any(_CHAPTER_HREF_RE.search(urljoin(ORIGIN, a["href"])) for a in li.select("a[href]"))
]
```

Verified on the captures: TOC page 37 `li` -> **36 kept**, `max(data-num)` still **188**; fragment 188 -> **188 kept**, max **188**. Both signals unchanged on the reference novel, both fixed on the hypothetical short one.

Design notes on the filter:

* **Keep `li[data-num]` in the selector, don't replace it with a bare `a[href*="/txt/"]`.** The `li[data-num]` scope is what keeps the trailing `<div class="clear">`, the breadcrumb and any future wrapper out; the href test is what keeps the bookmark widget out. They guard different things and the cost of both is one list comprehension.
* **Match against the `urljoin`ed URL, not the raw href.** Hrefs are absolute today (measured, on both the fragment and the page), but joining first means a future relative `/txt/…` still passes, and it keeps `parse_chapter_list` and `stated_total` testing the identical string.
* **A regex, not `href*="/txt/"`.** The substring form would also admit `/txt/114283/end.html`. The trailing `\d+` is what makes the sentinel fail — the same property §2.1 relies on in `url_patterns`, applied a second time at a second layer, deliberately.
* **The filter is strict, and a too-strict filter drops chapters silently — but not here.** If the CMS ever changed its chapter URL shape, the filter would drop everything and `parse_chapter_list` would raise "Chapter list not found", or drop *some* and trip the `len(ajax_refs) < total` warning at §2.4.1. Both are loud. That is the reason to keep `stated_total` independent of the anchor count rather than deriving one from the other.

#### 2.4.4 The decision table

Let `truncated = total is not None and total > len(page_refs)` — *the page itself told us it is incomplete*.

| Situation | Action | Why |
|---|---|---|
| `ajax_refs` non-empty and `len >= total` (or `total` unknown) | **use `ajax_refs`** | happy path, 188/188 |
| `ajax_refs` non-empty but short of `total` | **use `ajax_refs`** + loud `_status` naming both numbers | still the only list that is *contiguous from chapter 1* (measured: 1…188, zero gaps), so it is safe under `replace_toc` and a re-scan just extends it. Never silently. |
| fragment dead **and** `truncated` | **raise `ScrapeError`** naming the fragment URL | <- §2.4.2 |
| fragment dead, `truncated` false, `page_refs` non-empty | **use `page_refs`** + `_status` note | a genuinely short novel has no `LoadMore` button and its page list really is complete. **Inferring** — not observed on twkan — but §2.4.3's filter is what makes the guard on this branch trustworthy. |
| both empty | **raise** `"Chapter list not found — page layout may have changed"` | family wording: `sto9.py:199`, `shuba69.py:123` |

#### 2.4.5 Building the refs

```python
ChapterRef(index=i, title=a.get_text(strip=True), url=urljoin(base_url, a["href"]))
for i, a in enumerate(_chapter_anchors(soup))
```

* **`index` is `enumerate()`, never `data-num`.** `data-num` is the site's *display* number, measured non-contiguous on the TOC page (`7, 1…15, 168…188`), and `ChapterRef.index` is the dense positional key `replace_toc`, `pending_download` and every exporter depend on. Same rule as `sto9.py:200-202`.
* **`get_text(strip=True)` and nothing else.** Every anchor has a trailing space (measured), which `strip=True` removes. Do **not** normalise further. twkan's own titles are internally inconsistent — measured `第1 章 …`, `第4章 …`, `第 188 章 …` — and it is tempting to regularise them. Resist: titles are persisted, exported into the EPUB and read aloud by TTS, and `shuba69.py:44-56`'s `_clean_title` exists only because 69shuba prefixes a *duplicate* index (`1.第1章 …`) that carries no information. twkan's spacing carries no information either, but normalising it is invisible rewriting of the site's own text for a cosmetic gain, and it would make the §2.6 title comparison disagree with the stored title.
* **`urljoin(base_url, href)`** even though hrefs are absolute — costs nothing and survives the CMS going relative. `sto9.py:208`, `shuba69.py:128`.
* **Do not read the `title=` attribute.** twkan's anchors carry `title="第1 章 … 字數：3370 更新時間：…"` (measured) — sto9's do not, so this is genuinely new. It is tempting as a richer source, but it splices the chapter name together with the 字數 and the timestamp, and 字數 is exactly the number §2.8 spends a paragraph telling people to ignore. Take the anchor *text*. Say so in a comment.
* **Document order is reading order** in both sources (fragment measured ascending 1…188). Do not sort by `data-num`.
* **One `parse_chapter_list` for both sources.** The markup shape is identical, so the difference is entirely *which* markup you hand it, and the decision logic stays in one visible place. `sto9.py:189-195` makes the same call.

### 2.5 `fetch_metadata` — detail page only

**Recommendation: `fetch_metadata` always fetches `detail_url(url)` = `/book/<id>.html`, whichever form it was handed, and caches it per adapter instance.**

The TOC page has **zero** `meta[property]`, no `<h1>`, no `div.bookbox` and no `div.booknav2` (measured); chapter pages have zero `meta[property]` too. So reading metadata off the pasted URL would give a title-less novel for the *most common* paste form. Same split as `sto9.py:271-275`.

```python
def _detail_page(self, url: str) -> str:
    bid = book_id(url)
    if self._detail is not None and self._detail[0] == bid:
        return self._detail[1]
    markup = self._get_html(detail_url(url))
    self._detail = (bid, markup)
    return markup
```

**Per-instance, never module-level** (`sto9.py:258-260`): the GUI process is long-lived and the user switches novels, so a module cache would answer novel B's questions with novel A's page. Keyed by book id so a same-instance switch is a miss rather than a stale hit. On the browser path the cache is worth more than it was for sto9 — a saved fetch is a saved *navigation*, not a saved HTTP GET.

Fields, via the `og()` closure from `sto9.py:124-126` / `shuba69.py:101-103`:

| Field | Source | Fallback |
|---|---|---|
| `title` | `og:novel:book_name` -> `og:title` | `div.booknav2 h1` text; then `ScrapeError("Novel title not found — page layout may have changed")` |
| `author` | `og:novel:author` | the `作者：` row of `div.booknav2 p`, split on `[:：]`; else `""` |
| `description` | `_clean_description(og("og:description"))` | `""` |
| `cover_url` | `og:image` — **stored as-is** | `""` |
| `url` | `read_url(url)` — §2.2 | — |
| `site` | `self.name` | — |
| `source_lang` | `"zh"`, written explicitly | — |

**Title is the only required field.** Everything else degrades to `""` — the family convention (`sto9.py:128-145`, `xbanxia.py:53-60`) and the GUI renders blanks fine.

**`_clean_description` IS needed — this is where twkan follows 69shuba, not sto9.** `og:description` carries literal `<br />` **text** inside the attribute value plus em-space indents (measured). It arrives as an attribute, so BeautifulSoup never sees those as tags and cannot strip them (`shuba69.py:85-87`). Copy `shuba69.py:83-90` — `_BR_RE` -> `\n`, then collapse 3+ newlines to 2, then strip. `sto9.py:154` deliberately has no such helper because sto9's blurb is plain prose; the divergence is measured, not stylistic. Pin it with `"<br" not in meta.description` (`test_scrapers_shuba69.py:100-107`).

**Diverge from sto9: ship NO placeholder-cover check.** `sto9.py:58-62` blanks `og:image` when it ends in `/images/nocover.jpg`, because a grey "no cover" JPEG renders into the EPUB and the video thumbnail as a *broken* cover rather than an absent one. That reasoning transfers, but the constant does not: **no string containing `nocover` or `noimage` appears anywhere in any twkan capture** (measured), and the reference novel has a real cover at `/files/article/image/114/114283/114283s.jpg`. Inventing a filename would produce a check that is either dead code or — worse — accidentally matches a real cover path. `RECON-FINDINGS.md` §3 says "do not invent a specific filename that has not been measured", and the honest reading of that is: no check. Record it in the module docstring as a known gap with the exact fix (add a `_PLACEHOLDER_COVER` suffix constant, `sto9.py:62`'s shape) so whoever *observes* a coverless twkan novel closes it in one line. Add a `TestLive` note, not a unit test — there is nothing to assert.

**`source_lang = "zh"`, written explicitly**, not inherited from `models.py:42`. Content is Traditional Chinese and the site's s/t toggle is client-side only. There is no script field on `NovelMeta` and adding one is out of scope; the two places script actually matters already cope — translators pass `source_lang` straight to the engine, and the name extractor `t2s`-converts before its dictionary lookup. Writing it out means a future change to the dataclass default cannot silently reclassify this adapter (`sto9.py:154-156`).

**Do not parse `var bookinfo = {...}`.** It exists on both the detail and TOC pages and carries `articleid`, `articlename`, `author`, `siteName`, `sortName`, `tags` — nothing the og: tags lack, in single-quoted JS rather than JSON. Reading it would mean a second, weaker parser for zero new fields. Note it in the docstring as *deliberately* unused, exactly as `sto9.py:24-26` does, so nobody rediscovers it as a fix.

### 2.6 `parse_chapter`

**Recommendation:**

```python
SEL_CONTENT = "div.txtnav"
# Chrome living INSIDE the container, named rather than blanket-decomposing every <div>.
# div.txtad and div.txtcenter are the ones that matter: measured, they sit INSIDE
# #txtcontent0, in the middle of the prose — not only around it.
SEL_CHROME = "h1, div.txtinfo, div.txtad, div.txtcenter, script, style, ins"
```

1. `container = soup.select_one(SEL_CONTENT)`; `None` -> `ScrapeError("Chapter content not found — page layout may have changed", url)`.
2. `for el in container.select(SEL_CHROME): el.decompose()`.
3. `lines = [l.strip() for l in container.get_text("\n").split("\n") if l.strip()]`.
4. Drop at most one leading line if `_norm(lines[0]) == _norm(title)`.
5. `if not lines: raise ScrapeError("Chapter content is empty", url)`.
6. `return "\n\n".join(lines)`.

**Measured end-to-end on two captured chapters: 87 lines / 2186 chars (ch.1) and 74 / 2262 (ch.188), with zero residual em-spaces, `loadAdv`, `上一章`, `下一章`, `目錄` or `作者：`.**

**Container: `div.txtnav`, not `#txtcontent0`.** Measured, both produce **byte-identical output** on both chapters, so this is purely a robustness argument — and it goes to `div.txtnav`:

* `div.txtnav` is the selector `shuba69.py:36` and `sto9.py:69` already use for this same CMS. Three adapters agreeing on one selector is a real asset when the CMS changes and someone has to fix all three.
* `#txtcontent0` carries a numeric suffix, which is CMS-speak for "there may be a `txtcontent1`". Measured there is exactly one today and no pagination markers anywhere — but if the site ever splits long chapters, `div.txtnav` picks up both halves for free while `#txtcontent0` silently returns the first.
* The cost is having to decompose `h1` and `div.txtinfo` as well, which is two selector entries.

Mention `#txtcontent0` in the docstring as the tighter alternative and the reason it was not chosen, so the decision is visible.

**The chrome list is named, never blanket.** `xbanxia.py:79` decomposes `span, div, script, ins` wholesale; `shuba69.py:37-39` documents why that is a loaded gun — the day the CMS wraps a paragraph in a `<div>`, a blanket rule eats it silently. Name what was measured:

* `h1` — the chapter heading, structurally removed rather than string-compared (measured identical to the TOC title on ch.1 and ch.188, so removal is exact where a comparison could drift).
* `div.txtinfo` — matches `div.txtinfo.hide720`; holds the timestamp and `作者：` byline. Written as the single class rather than `div.txtinfo.hide720` (`shuba69.py:41`'s form) so a responsive-class change does not reintroduce a date line into the prose.
* `div.txtad`, `div.txtcenter` — **the interesting pair, and the reason this list is longer than sto9's.** Measured, one of *each* sits **inside `#txtcontent0`**, mid-prose, alongside 148–212 `<br>`s. `container.select(...)` is a descendant search, so scoping to `div.txtnav` reaches them; a naive "decompose the container's direct children" would not. Each holds only a `loadAdv(...)` `<script>` — `decompose`, not `unwrap`, not extract-and-keep-text.
* `script, style, ins` — the defensive tail every adapter in this family carries. Non-optional here: the page loads `crypto-js` and `/js/newread.js`, and the 2 `<script>`s inside `#txtcontent0` are exactly what would otherwise leak.

**`<br>`-splitting needs no code.** The body is text nodes separated by `<br>` with no `<p>`, so `get_text("\n")` produces one line per node and step 3's strip-and-drop-blanks collapses the `<br><br>` runs for free. Same as `sto9.py:226`, `shuba69.py:145`.

**`&emsp;` indents need no special handling.** They decode to U+2003, which is Unicode category Zs, so `str.strip()` removes them — measured zero residual across both chapters. **Do not write a blanket `replace(" ", "")`**: it would also eat em-spaces *inside* a line, where the CMS uses them for alignment. Pin it with a `" " not in body` assertion (`test_scrapers_sto9.py:179-184`).

**Whitespace normalisation is `.strip()` only.** No `re.sub(r"\s+", " ", line)` on stored text — CJK prose contains meaningful full-width spaces, and every sibling strips only the ends (`sto9.py:226`, `shuba69.py:145`).

**The tolerant title-drop stays, biased hard to under-strip.** `h1` is decomposed in step 2, and measured the title is *not* repeated as prose (the first body line is real prose on all three captured chapters). So step 4 fires only if the CMS ever drops the `<h1>` and echoes the title as a text node. Keep it anyway, with sto9's `_norm` whitespace-collapse comparator (`sto9.py:79-81`, `:231-232`) — which is the *right* comparator here for a twkan-specific reason: the site's own titles vary between `第1 章`, `第4章` and `第 188 章`, so an exact-string comparison would miss a real echo whenever the `<h1>` and the TOC anchor happened to space it differently. `_norm` is used **only** for the comparison, never for the stored title. Drop **at most one** line: a duplicated heading is cosmetic; an eaten opening line is data loss the reader will not notice (`shuba69.py:147-151`).

**No pagination.** Measured: exactly one `[id^=txtcontent]` per page, and zero `_2.html` / `chapterpage` / `nextpage` / `下一頁` markers across three chapters. Do not build a pager. The 上一章/下一章 links are siblings outside `div.txtnav` and are never followed — `fetch_chapter` only ever fetches `ref.url`.

**Which error, and why raising matters:**

| Case | Error | Why |
|---|---|---|
| `div.txtnav` missing | `ScrapeError("Chapter content not found — page layout may have changed", url)` | family wording (`sto9.py:218`, `shuba69.py:139`); says "the site changed", which is the true diagnosis |
| container present, zero lines after stripping | `ScrapeError("Chapter content is empty", url)` | a **different** message on purpose — the two failures need different fixes |
| — | **never** `ObfuscatedContentError` | `errors.py:16-17` reserves it for content that cannot be *decoded*. twkan serves plain readable text through the browser; nothing is obfuscated |
| — | **never** `RateLimitedError` | `workers.py:33-34`, `:2083-2100` would retry 8× at 60 s — 8 minutes per unparseable chapter, and on this adapter each retry is a browser navigation |
| — | **never** return `""` | <- the important one |

**Returning `""` is the silent failure.** `save_content(idx, "")` (`project.py:518`) leaves `content = ''`, and `pending_download` keys *only* on empty content (`project.py:362`) — so the chapter re-queues forever, every "Tải các chương" refetches it, the progress bar never shrinks, and because `mark_error` was never called the row shows **no error at all**. The family-wide `if not lines: raise` (`sto9.py:234-235`, `shuba69.py:155-156`) is a convention for this reason, not a formality.

### 2.7 Request budget — 3 navigations per scan, 1 per chapter

| Call | Navigations | Which |
|---|---|---|
| `fetch_metadata` | 1 (cached after) | `/book/<id>.html` |
| `fetch_chapter_list` | 2 | `/book/<id>/index.html`, then `/ajax_novels/chapterlist/<id>.html` |
| `fetch_chapter` | 1 | `ref.url` |

A scan is 3 navigations plus one Chrome launch. That is materially more visible than sto9's 3 HTTP GETs — the user watches a window open and three pages flash past — which is why the `_status` line (§2.3) exists. It is still the right budget:

* **Drop the detail fetch** -> lose author, blurb and cover entirely (0 og: tags on the TOC page, measured). Unacceptable.
* **Drop the TOC-page fetch** -> lose `stated_total`, i.e. lose the ability to tell "the fragment is complete" from "the fragment is short", and lose the safe-fallback branch. That trades the feature's one real safety property for one navigation per novel.
* **Fetch only the fragment and skip the page** is the tempting shortcut. It fails silently in exactly the case that matters: a fragment that returns 100 of 188 chapters looks perfectly healthy with nothing to compare against.

`cf_browser.py:51-53` already aborts image/font/media/stylesheet, so each navigation is close to text-only — most of the bytes of a 188-chapter batch. Do not add to `_BLOCKED_TYPES`: `document`, `script` and `xhr` must stay allowed because Cloudflare's own check is JS-driven.

**No delay floor and no cookies.** `BrowserSession` inherits `client.delay_seconds` (default 1.5 s). No login exists on twkan, so `config.SITE_COOKIES` is untouched and `client.set_cookies` (called unconditionally at `workers.py:107`) is a no-op with a blank string (`base.py:45-47`).

### 2.8 The 字數 discrepancy gets **no code at all**

Rendered prose is ~55–63 % of the site's declared 字數, and actual lengths cluster near ~2000 chars regardless of the declared figure. That is the classic paywall signature, `crypto-js` and `/js/newread.js` *are* loaded, and someone will eventually notice and "fix" it. Recon resolved it: the raw pre-JS server response and the post-JS rendered DOM give a **byte-identical** `#txtcontent0` (2014 chars / 87 lines for ch.1), and `inner_html` of `#txtcontent0` is **3352** chars against a declared 字數 of **3370** — ~0.5 %, holding across chapters 1, 2 and 188. **字數 counts the stored markup, not the prose.** The `<br/>` tags, `&emsp;` indents and ad divs are the difference.

So: **no completeness guard, no length heuristic, no `AuthRequiredError` path.** A 字數-based guard would reject every chapter on the site. Feature 061 shipped precisely this class of false positive on bookqq and had to be reverted (`1f9eb6f`, *"stop refusing free chapters on their own prose"*), so this belongs in the module docstring with the numbers, not just in a changes file — the docstring is what the next person reads.

The one *legitimate* completeness signal already exists and is structural rather than statistical: `parse_chapter` raises when the container is missing or empty (§2.6). That is enough.

## 4. What breaks if this is done naively

### 4.1 Copying `sto9.py:67`'s selector — the phantom chapter

`li[data-num] a[href]` matches the hidden `<a href="#" id="bookcase">`, producing a titleless `ChapterRef` at index 0 and shifting all 188 real chapters by one. Symptom: a blank first chapter that fails to download, which reads as a network hiccup rather than an off-by-one. §2.4.3.

### 4.2 Copying `sto9.py:178-184`'s `stated_total` — the un-scannable short novel

The phantom's `data-num="7"` becomes the `max()` signal on any novel with fewer than 7 chapters and no `#loadmore`, so `truncated` is `True` and the adapter refuses a **complete** list with a message quoting a number that appears nowhere on the site. This is the bug the recon does not name and the reason `index_full.html` must carry the phantom. §2.4.3.

### 4.3 Writing the id regex with a `.html` suffix

twkan chapter URLs are `/txt/114283/57238545` — no extension. Any regex shaped `/txt/(\d+)/\d+\.html` returns nothing, and `book_id` raises for every chapter-form paste. §2.2.

### 4.4 Un-anchored `url_patterns`

`/txt/\d+/\d+` also matches sto9's and 69shuba's chapter URLs. `ADAPTERS` is first-match-wins by import order (`scrapers/__init__.py:16-20`), so the theft would be order-dependent and silent — and today it would *not* fire, because `twkan` imports last, which makes it worse: the bug lies dormant until the tuple is reordered. §2.1.

### 4.5 Reaching for `HttpClient`

It cannot read this site at all — 403 with the repo's UA and 403 with a full forged Chrome header set. An adapter written on `self.client.get_html` fails 100 % of the time, and its failure surfaces as `ScrapeError("Request failed after 3 tries", …)` from `base.py:67`, which reads like a transient network problem rather than "this site needs the browser". §2.3.

### 4.6 Building a completeness guard on 字數

It would reject every chapter on the site. The gap is markup length vs prose length, measured to ~0.5 % on `inner_html`. Feature 061 shipped this exact class of false positive on bookqq and had to be reverted. §2.8.

### 4.7 Scraping the TOC page instead of the fragment

36 of 188 chapters, non-contiguous, looking completely normal. An adapter written against that page passes every smoke test a developer would think to run — metadata correct, TOC non-empty, chapter 1 downloads, chapter 36 downloads — and loses 152 chapters silently, then lets `replace_toc` bake the mismatch in on the next re-scan. §2.4.2.

### 4.8 Using `data-num` as `ChapterRef.index`

It is a display number, measured non-contiguous (`7, 1…15, 168…188`). `ChapterRef.index` is dense positional and every exporter depends on that. §2.4.5.

### 4.9 Reading the anchor's `title=` attribute for the chapter title

It splices the chapter name together with `字數：NNNN 更新時間：…`, which would land the 字數 — the number §2.8 exists to discourage anyone from trusting — into every EPUB heading and every TTS read-aloud. §2.4.5.

### 4.10 Only decomposing chrome *around* `#txtcontent0`

Both ad slots are **inside** it, mid-prose, with two `<script>`s. Chrome that is only stripped from around the container leaks `loadAdv(...)` into the middle of a chapter. §2.6.

### 4.11 Blanket-decomposing `<div>` inside `div.txtnav`

`xbanxia.py:79` does this; `shuba69.py:37-39` documents why it must not be copied. Here it happens to work today because the only `<div>`s are the ad slots — which is exactly what makes it dangerous: a rule that is correct by luck and will eat a paragraph the day the CMS wraps one.

### 4.12 Leaking the browser session

`close()` must be idempotent, must never raise, and must be safe before any fetch. `workers.py:136-138` and `workers.py:2171` call it in `finally` on paths that are already failing. A leak is a Chrome window the user must force-quit. §2.3.

### 4.13 Ignoring `client.delay_seconds`

`HttpClient`'s throttle is bypassed on the browser path (`cf_browser.py:17-19`), so `BrowserSession._throttle` is the only politeness left. Forgetting the kwarg means a 188-chapter download navigates as fast as Chrome can go, against a Cloudflare-protected host — the fastest route to an IP block, which would kill the only path this site has.

### 4.14 Building fixtures with unclosed `<li>`s

Copied from sto9's fragment fixture, which is raw CMS output. twkan's fragment arrives through `page.content()`, i.e. already DOM-repaired. The fixture would then be testing markup the adapter will never see, and the test would pass while proving nothing. §2.3.

### 4.15 Echoing the pasted URL into `NovelMeta.url`

Three paste forms -> three projects for one novel, each with its own translation progress and video settings. §2.2.

### 4.16 A module-level page cache

Long-lived process, user switches novels, novel A's markup answers novel B's questions. Instance attributes only. §2.5.

## 5. Testing strategy

Saved fixtures only. **No test in the default suite launches a browser or makes a network request.** The browser is faked with the `_FakeSession` shape from `test_scrapers_shuba69.py:214-242` — a dict of URL -> markup that records what was asked and raises `AssertionError` on an unexpected URL, assigned to `adapter._session` so the lazy launch at `cf_browser.py:148` never fires.

```python
def make_adapter() -> tuple[TwkanAdapter, _FakeSession]:
    adapter = TwkanAdapter(HttpClient(delay_seconds=0))
    session = _FakeSession({DETAIL_URL: fx("book.html"),

                            AJAX_URL:   fx("chapterlist.html"),

    return adapter, session
```

## 7. Risks and genuinely open items

1. **The ajax fragment is an undocumented internal endpoint.** It is the only complete source of the TOC, so if the site removes or renames it, twkan scanning stops working for long novels — by design, with a clear error, rather than by silently producing a 36-chapter novel. Mitigations: two independent truncation signals, the `TestLive` count assertion as the drift detector, and a docstring naming `LoadMore()` in `index.html` as where to re-derive the URL. **Accepted deliberately, because the alternative is corruption.**

2. **`data-num="7"` on the phantom is an arbitrary observed value.** The filter (§2.4.3) does not depend on it — it keys on the href, not the number — which is exactly why the href test is the right fix rather than "skip `data-num == 7`" or "skip the first `li`". But if the CMS ever wraps a *second* widget in an `li[data-num]` with a plausible-looking chapter href, nothing catches it. Not defensible further without observing one.

3. **The "safe fallback" branch is inferring.** No short twkan novel has been observed, so "fewer than ~35 chapters => no `#loadmore` => the page list is complete" is reasoning from the CMS's behaviour, not a measurement. The branch is written so that being wrong about it is harmless: it fires only when `stated_total` gives no evidence of truncation, and if the assumption is wrong the two signals disagree and the hard-error branch takes over. Worth confirming on a short novel during the first live run — and note that §2.4.3's Bug-B fix is a *precondition* for this branch working at all.

4. **Cloudflare could tighten.** `BrowserSession` cleared the gate on the first navigation with no interstitial, and 5 URLs in one session saw zero challenges. That is the current state, not a guarantee. If challenges start appearing, `cf_browser.get_html` already detects the interstitial (`cf_browser.py:41-47`, `:160-161`) and raises rather than handing challenge markup to a parser, so the failure mode is a clean Vietnamese error. The first diagnostic if 403s appear is emptying `_BLOCKED_TYPES` (`cf_browser.py:51-53`).

5. **The shared `.cf-profile` is persistent, and twkan has a client-side 繁/簡 toggle.** `cf_browser.profile_dir()` (`cf_browser.py:60-66`) is one Chromium profile reused across 69shuba, webtruyendich and now twkan, and it persists cookies and localStorage. twkan's `zh_tran('s')/('t')` toggle is served from `/js/chinese.js`, which was **not captured and which I could not verify** — if it persists a preference, a profile that once had Simplified selected would render Simplified prose into `page.content()` and the adapter would store it without noticing. No trace of such persistence appears in the captured chapter markup, so this is a *possible* rather than an observed problem. **Flagged, not designed against.** If it ever bites, the fix is a `zh_tran('t')` evaluation after navigation, which would be a new argument to `BrowserSession.get_html` and therefore a shared-module change — out of scope here.

6. **The browser path is slow and visible.** 3 navigations to scan and 188 to download, at 1.5 s apiece plus page load, in a window the user must leave open. That is inherent to the site, matches 69shuba, and is why §2.5's detail-page cache and the `_status` line both matter more here than they did for sto9. It also means the `TestLive` class is genuinely expensive — correctly kept out of the default suite.

7. **Traditional vs Simplified.** `source_lang="zh"` with no script field on `NovelMeta`. Translators pass it straight through and the name extractor `t2s`-converts before its lookup, so nothing is broken — but Simplified output would be a whole-app feature (a script field plus an OpenCC pass), not an adapter change. Out of scope; recorded.

8. **No placeholder-cover handling.** §2.5. A coverless twkan novel — if the CMS has such a form — would store whatever `og:image` says, which could be a grey placeholder rendered into the EPUB and the video thumbnail as a *broken* cover. Deliberate: inventing an unmeasured filename is worse than a documented gap. The docstring carries the one-line fix.

9. **Nothing shared is edited.** No `SiteAdapter` change, no `cf_browser` change, no worker change, no model change, no config change, no new dependency. The blast radius is one new module, one import line, one README row, one new test module and one added test class — so if twkan turns out to be wrong about something, nothing else in the app is affected.
