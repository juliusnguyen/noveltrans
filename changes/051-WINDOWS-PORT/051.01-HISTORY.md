## [IMPLEMENT] Fix "'NoneType' object has no attribute 'write'" on TTS init — 2026-07-31
User reported this crash when opening tab 4 (Nghe audio) in a real detached launch of
the packaged exe. Diagnosed as a classic PyInstaller Windows gotcha: `NovelTrans-windows.spec`
builds with `console=False` (no console window), and a console-less Windows process gets
`sys.stdout`/`sys.stderr`/`sys.stdin` = **`None`**, not merely redirected. `VieneuEngine.load()`
(`tts/vieneu.py`) constructs `Vieneu(...)`, which — like most first-run-download libraries
(tqdm/huggingface_hub progress bars, ONNX Runtime logging) — writes to stdout
unconditionally; that write is what raised `'NoneType' object has no attribute 'write'`,
caught by `load()`'s blanket `except Exception` and re-raised as the Vietnamese
`TtsError` the user saw.

- Confirmed the diagnosis empirically before writing any fix: a temporary diagnostic
  build showed `sys.stdout` was a real stream when the exe was launched from an existing
  shell (git-bash pipes it a stream regardless of the GUI subsystem), but **`None`** when
  launched via `Start-Process` with no redirection — the actual "double-click from
  Explorer" scenario. This matters because testing only via a shell would have missed the
  bug entirely.
- Added `runtime_env.ensure_std_streams()`: replaces any `None` stdio stream with a
  devnull sink. Wired into `app.py::main()` as the very first line (ahead of even
  `augment_tool_path()`), since anything downstream could try to print before TTS ever
  loads.
- Verified the fix the same way the bug was found: rebuilt with a temporary diagnostic
  launcher, launched via `Start-Process` (detached), confirmed `sys.stdout`/`sys.stderr`
  were `None` *before* `ensure_std_streams()` and valid, writable devnull streams *after*
  — then reverted the diagnostic and confirmed the real app still launches cleanly
  detached.
- Added `TestEnsureStdStreams` to `tests/test_runtime_env.py`. Full suite: 1391 passed
  (+2), 4 skipped, 0 failed. `ruff check`: 249 (baseline, unchanged).
- This fix is macOS/Linux-safe: `ensure_std_streams()` only touches a stream that is
  already `None`, which essentially never happens outside a console-less Windows launch.
