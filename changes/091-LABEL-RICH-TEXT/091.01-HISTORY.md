# 091-LABEL-RICH-TEXT — History

## [FIX] The Rewrite dialog's intro drew its own markup — 2026-09-14

Spotted in a screenshot while verifying 090 in the running app, not by a test: the intro
label of **Viết lại văn phong** displayed a literal `<b>Giữ nguyên tên riêng Hán-Việt và
xưng hô</b>` — angle brackets and all — instead of bolding the phrase.

### Cause

A `QLabel` defaults to `Qt::AutoText`, which asks `Qt::mightBeRichText()` whether the
string is markup. That heuristic scans from the start and **stops at the first newline**:

```cpp
while (open < text.length() && text.at(open) != '<' && text.at(open) != '\n') ++open;
if (open < text.length() && text.at(open) == '<') { … }   // never reached
return false;
```

The string had `…sắp xếp lại trật tự từ,\nbỏ chỗ lặp thừa. <b>…` — a `\n` ahead of the
first tag — so the scan bailed at the newline and the label settled on plain text.

### Changes

- `gui/rewrite_dialog.py`: the two `\n` became `<br>`, and the label is now
  `self.intro` with `setTextFormat(Qt.TextFormat.RichText)` stated outright rather than
  left to the heuristic. The `<br>` is needed regardless of detection — in rich text a
  newline is only whitespace, so keeping `\n` would have merged the three lines into one.
  Named `self.intro` (the QC dialog's equivalent is a local) so a test can reach it.

### Scope — this was the only one

An AST sweep of every `QLabel` / `setText` / `setToolTip` / `setPlaceholderText` string
literal in `src/`, re-implementing `mightBeRichText` to find any that contains an HTML tag
the heuristic would miss, returned **exactly this one label**. `qc_dialog`'s intro uses the
same `<b>` markup but has no newline before it, so it has always rendered correctly. The
sweep only reads plain string literals (adjacent-literal concatenation included); an
f-string built label would not have been caught, and none of the flagged call sites used
one.

### Verification

Looked at it, since a green test cannot see a rendering bug: drove the real dialog against
an INI **copy** of the user's registry settings (so nothing of theirs was written) and
grabbed the widget before and after — literal `<b>…</b>` on three lines before, the phrase
bold on three lines after.

1 new test (`textFormat` is RichText, the markup is present, and no `\n` hides ahead of
it). Rewrite modules: 96 passed. Full suite with `test_tts.py` and `test_workers_pause.py`
excluded (see 090): **3523 passed** — 090's 3522 plus this one — 4 skipped, the same 43
pre-existing environmental failures and none outside them. Ruff: 3 findings on the touched
files before and after.

### Not done / noted

- No repo-wide guard test for the trap. The sweep is a one-off in the history rather than
  a test that walks the AST on every run; with a single site to protect that seemed the
  wrong trade. The comment at the call site carries the reason.
- `setWordWrap` deliberately not added: the label uses explicit breaks and the dialog has a
  minimum width, so wrapping behaviour is unchanged from before this fix.
- `uv.lock` stays uncommitted, as in 088–090.
