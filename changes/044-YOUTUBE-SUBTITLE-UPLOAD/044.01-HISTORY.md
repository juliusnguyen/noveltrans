# 044 — Upload the `.srt` files to YouTube — history

## The ask

> create the button that auto upload all subtitles file into the youtube video
> (like `Cập nhật ảnh bìa` button)

## [IMPLEMENTATION] — 2026-07-29

1077 tests pass (1060 before, +17), ruff clean.

A "💬 Tải phụ đề lên" button beside "🖼️ Cập nhật ảnh bìa", the same shape as 034: eligible
parts are those with **both** a recorded `video_id` and a `.srt` on disk; one browser
session for the batch; interlocked with the other three browser runs under the one `Dừng`.

### Every 039 lesson applied up front, not after three failed live runs

This is the **fourth** Studio surface, and the previous one took three live failures to get
right. Those fixes are built in from the first commit here:

| 039 failure | Applied here |
| --- | --- |
| Trusted a guessed URL; a wrong Studio URL renders an error page, not a 404 | `_open_subtitles_page` tries three shapes and checks `_page_shows_studio_error` between them |
| Gated on a guessed container element and walked away from a page that had loaded | **No container gate.** The gate is the `input[type=file]` — the thing the step actually needs, and plain HTML that cannot be renamed away |
| Failure said "giao diện có thể đã thay đổi" and named nothing | Failure attaches `_dom_inventory(page)`, naming the components actually present |
| Confirmed on a state that was true before the click | `_subtitle_is_published` requires Studio to *show* a published track; a click alone is never success |

`_reach_subtitle_file_input` clicks through the language row / "Thêm" / "Tải tệp lên" /
"Có mã thời gian" ladder, but treats none of those as required — it re-checks for the file
input after each and stops as soon as one appears. Only failing to reach an input is fatal.

### Why this is the least dangerous of the four

A caption upload cannot duplicate a video (033), overwrite a live cover (034) or empty a
playlist (039). The worst outcome is a video that keeps the captions it already had. The
record write is correspondingly narrow — `subtitle_uploaded_at` and `subtitle_file` only,
never `status`, asserted by `test_success_records_only_the_subtitle_fields`.

### A fake that lied, caught before it cost anything

The first `_FakeSubtitlePage` returned `True` from `is_visible` for *any* `has-text`
selector — including `body:has-text("Oops, something went wrong")`, the Studio-error probe.
Every URL candidate therefore looked like an error page and all four tests failed at
navigation. Fixed by making the fake answer the error probe honestly.

Worth noting because it is the **fourth** fixture problem this session, and the first one
that failed loudly instead of passing vacuously — the failure mode is much cheaper when the
fake is wrong in the direction of "nothing works" than "everything works".

### KNOWN GAP

Unverified against a live channel, like every Studio selector since 033. The click ladder
in `_reach_subtitle_file_input` is the most speculative part: Studio's subtitle flow differs
depending on whether the video already has a track, and neither variant has been observed.

The mitigation is that failure is **cheap and self-describing**: no file is sent unless an
input was found, nothing is recorded unless Studio confirms a published track, and the
error names the components on the page so the next attempt is a selector edit rather than
another round of guessing.

Test it on one video before running it across the library.

## [FIX] The "Set language" gate — 2026-07-29

First live run: `/translations` loaded correctly and showed

```
Languages
  Video language  [ Set language  v ]
  [x] Make this the default for my channel
  [ Confirm ]
```

instead of the subtitles table. **A video with no language set cannot have captions
uploaded**, and YouTube blocks the whole surface until that is answered.

So there was no file input to find — correctly — and `_reach_subtitle_file_input` reported
"không tìm thấy chỗ tải phụ đề" for a page working exactly as designed. The click ladder
also could not have answered it: `Set language` is a **dropdown**, not a text button.

### The fix

- `_subtitle_language_gate` detects the gate by its **Confirm button**, which the subtitles
  table does not have.
- `_answer_subtitle_language_gate` opens the dropdown, picks Vietnamese and confirms,
  reusing the pattern `_set_language` already drives in the upload dialog rather than
  inventing a second way to pick a language.
- The "Make this the default for my channel" checkbox is left exactly as YouTube presents
  it (ticked). Changing a channel-level default is not this feature's business, and
  unticking it would make every later video hit this same gate again.
- A gate that will not clear refuses **with instructions** and sends no file.

### What this says about the approach

The 039 lessons did their job: the URL was right first time, no container gate got in the
way, and the error named what it could. What they could not cover is a **precondition** —
a state of the video, not of the DOM. No amount of selector discipline predicts "this video
has no language set".

That is the honest limit of writing browser automation without the browser: structure can
be defended in advance, but preconditions have to be discovered. The design's job is to
make that discovery cheap, and here it was — one screenshot, one round.

1077 tests pass, ruff clean. `TestSubtitleLanguageGate` covers detection, answering,
carrying on to the upload, and refusing when the gate will not clear.

## [FIX 2] The gate control is not a button — 2026-07-29

Second live run: still parked on the Languages page, `Confirm` greyed out because no
language was selected. The dropdown never opened.

Cause: `Set language` is a **dropdown**, and both strategies only look at buttons.
`_click_any` tries guessed ids (`#video-language-select`, `ytcp-form-select#language`, …)
and then `_click_by_text`, which builds `ytcp-button:has-text(…)` /
`tp-yt-paper-button:has-text(…)` / `button:has-text(…)`. A control that is none of those is
invisible to the whole ladder — so the run sat on a page whose control was plainly on
screen.

### `_click_text_anywhere`

Playwright's `:text()` matches the **smallest element containing the text**, whatever tag
it is, and `.last` keeps that innermost match rather than a wrapper. It needs no knowledge
of Studio's component names — the part that has been wrong at every attempt.

Applied to all three gate steps (open the dropdown, pick Vietnamese, press Confirm), not
just the first: any of them can be a non-button, and fixing only the one that failed today
would leave the next two to fail tomorrow.

`test_the_button_only_search_would_have_missed_it` pins why the helper exists — remove it
and the control is unreachable again.

### Honest tally

Four attempts at this one surface: the URL, a container gate, the language precondition,
and now the control's tag. Every one died on something only observable by looking at the
page. The diagnostic that would have shortened this — `_page_actions`, listing the visible
clickable labels — was written *after* the third failure rather than before the first.

The general lesson, recorded because it keeps recurring: when automating a UI that cannot
be inspected, **build the observation tool first and the interaction second**. Structure can
be defended in advance; specifics cannot be guessed, and each guess costs a full round trip
through the user.

## [FIX 3] Measured instead of guessed — 2026-07-29

After a fourth failure, stopped guessing and wrote `scripts/diagnose_subtitles.py`: it
opens the page in the app's own logged-in profile and reports what is there. Output:

```
:text("Set language")   matches=1  visible
:text("Vietnamese")     matches=1  visible      <- after clicking the dropdown
:text("Tiếng Việt")     matches=0
#video-language-select  matches=0               <- every guessed id
ytcp-form-select#language  matches=0
:text("Set language") -> span.dropdown-trigger-text < div.left-container
                         < ytcp-dropdown-trigger < ytcp-text-dropdown-trigger#trigger
```

Three facts, none of which were guessable:

1. The control is `ytcp-text-dropdown-trigger#trigger`. Every id tried across four rounds
   matched nothing.
2. Clicking it **already worked** — the dropdown opened.
3. **The page renders in ENGLISH despite `?hl=vi`.** `:text("Vietnamese")` matches;
   `:text("Tiếng Việt")` matches nothing.

### The actual bug

`_answer_subtitle_language_gate` typed `_VIETNAMESE_TEXTS[0]` — "Tiếng Việt" — into the
dropdown's search box *before* looking for the item. On an English list that filters the
options down to **nothing**, so the item it then searched for genuinely did not exist. The
run parked on the Languages page with Confirm greyed out, and every diagnosis blamed the
click.

`_pick_vietnamese` now looks for the item first and only falls back to the search box for a
list long enough to need one — typing the same name it then looks for, never a different
one. `test_it_does_not_type_into_the_search_box_before_looking` is the bug in one assertion.

### Also fixed

- `_LANGUAGE_ITEM_SEL` gained `tp-yt-paper-icon-item`, the tag actually present (the plain
  `paper-item` forms stay for the upload dialog).
- `_page_actions` returned "(không đọc được các nút trên trang)" on its first real use and
  swallowed the reason — a diagnostic that fails silently is worse than none. It now
  reports the exception.

### A self-inflicted detour worth recording

The first attempt at this fix computed a replacement slice as
`s[s.index(A):s.index(B)]` where B is defined **before** A in the file — so the slice ran
backwards and the new functions were prepended above the module docstring, moving every
import below it. Caught by ruff (E402) immediately, and repaired surgically rather than by
`git checkout`, which would have destroyed the uncommitted 044 work in the same file.

### The lesson, now paid for four times over

**Build the observation tool before the interaction.** Four rounds of "try this selector"
cost four full round trips through the user; the diagnostic took ten minutes and answered
everything at once. `scripts/diagnose_subtitles.py` stays in the repo for the next surface.

1105 tests pass, ruff clean.

## [LIVE FIX] — 2026-07-31 — the run that stopped at the OS file window

> `Tải phụ đề lên` stuck at the step chosing the srt file
> (`Select subtitles file type to upload` -> With timing -> Continue -> table popup)

Not a selector miss this time — every label was found. The dialog opened, "With timing" was
ticked, Continue was pressed, and macOS put its file window on top of Chrome. Then nothing,
forever: **no exception, no timeout, no error message.**

### Why it hung

Studio's Continue calls `.click()` on the picker's `input[type=file]`, which opens the
operating system's file window. Playwright can only intercept that while an
`expect_file_chooser` expectation is armed. Un-intercepted, the native window is a modal the
automation cannot see or dismiss, and the browser stops answering commands — the one failure
mode in this module with no self-describing error, because the code never gets to run again.

The old `_send_subtitle_file` had two paths and armed the expectation on only one of them:

```python
for selector in _SUB_FILE_INPUT_SELS:      # ends with a page-wide input[type=file]
    ...
    locator.set_input_files(str(srt))
    _click_text_anywhere(page, _SUB_CONTINUE_TEXTS)   # <- unguarded. The hang.
    return
try:
    with page.expect_file_chooser(...):    # guarded, but only reached when NO input matched
```

Both halves had to be wrong together, and they were:

1. `_SUB_FILE_INPUT_SELS` ended with a bare page-wide `input[type='file']`. Studio's app
   shell carries its own file inputs, so **something always matched** — the loop's `return`
   was taken on every run and the guarded fallback was dead code.
2. `set_input_files` against the wrong element is a silent success. The flow believed the
   file was in and pressed Continue to "advance the dialog"; Continue instead asked the OS
   for a file that no longer had anywhere to go.

### The rule the function is now built around

**Continue is only ever clicked inside `expect_file_chooser`.** A behavioural test and a
structural one both hold it: `_FakeSubtitlePage(native_chooser=True)` raises
`_NativeFileWindow` from an unguarded Continue click where a live run would simply stop, and
`test_every_continue_click_is_inside_the_chooser_interception` reads the source so a future
edit cannot reintroduce a second, unguarded press.

The direct input set stays first — it needs no OS window at all — but is no longer treated
as proof of anything. If the dialog is gone afterwards the file was taken; if Continue is
still up, the guarded click covers the case where the set landed on the wrong element.

### Two more things found while fixing it, both live hazards

- **`_SUB_FILE_INPUT_SELS` is dialog-scoped now**, and `_input_takes_subtitles` reads the
  element's own `accept` attribute before feeding it anything. Handing an `.srt` to Studio's
  *video* input is not a harmless no-op — it starts an upload of the wrong file.
- **The Vietnamese "With timing" label could select "Without timing".** `:text()` is a
  case-insensitive *substring* match and `_click_text_anywhere` takes `.last`, so
  `:text("Có mã thời gian")` also matches "**Không** có mã thời gian" — the later of the two
  radios, and the one that discards the timings 040 measured out of the TTS run. `_choose_with_timing`
  uses the exact `:text-is()` form and re-reads whatever it lands on before clicking.

Latent only because the page renders in English, where the first candidate matches first —
which is exactly the kind of bug that surfaces the day Studio starts localising.

1115 tests pass (1105 before, +10), ruff clean. Still unverified against a live channel; the
difference is that a wrong guess now fails with a message instead of hanging.

## [LIVE FIX 2] — 2026-07-31 — the upload only makes a draft

> I saw the notify `Vietnamese subtitles uploaded`, the next thing should be publish that
> subtitles. Click on `Edit subtitles` then click `Publish`

The file went in — Studio said so itself. But sending the `.srt` produces a **draft**, and a
draft is invisible to viewers. Publishing is a second surface:

    translations page  ->  "Edit subtitles"  ->  caption editor  ->  "Publish"

The old code pressed Publish on the translations page, where no such button exists. Nothing
was clicked, `_subtitle_is_published` correctly refused to confirm, and the part failed with
a perfectly good caption file sitting in Studio unpublished. The gate did its job; the step
in front of it was missing.

### `_click_subtitle_edit` scopes to the language row

`_click_text_anywhere` takes `.last`, and the page lists **one row per language**. Page-wide,
a video that already carries an English track would have its *English* row opened and
published. The click is scoped to a row matching Tiếng Việt/Vietnamese first, using
`tr` / `[role=row]` alongside the `ytcp-*` names — plain HTML and ARIA outlive renames, the
same reasoning that made the file input the gate in `_send_subtitle_file`.

Scoping is a preference, not a gate: a one-row video (the common case here) finds no such
row and falls through to the page-wide click. Both paths are tested.

`_SUB_STATE_SEL` picked up the same row selectors, because the published state is a cell
inside that row and a confirmation that cannot see it fails a part whose captions are live.

### The failure now tells the user what they have

Not "không xác nhận" and nothing else — the message says the track is probably a draft, and
names the two clicks that finish it by hand. The file is already uploaded at that point;
what the user needs is the last two steps, not a bug report.

1119 tests pass (1115 before, +4), ruff clean.

## [LIVE FIX 3] — 2026-07-31 — Publish pressed before the editor had the cues

> when open the `Edit subtitles`, need to wait sometime until the subtitles loaded then
> publish. If not, it will cause the no subtitles error.

The only step in this flow where **being early is worse than being slow.** Publish is not a
no-op on a half-loaded editor: Studio publishes what is on screen, and for a second or two
after "Edit subtitles" that is nothing — so the press replaces a perfectly good draft with
an empty track and answers "no subtitles".

Every other selector in this module fails by doing nothing. This one fails by doing damage,
which is why it gets a real gate rather than a `wait_for_timeout` guess.

### The gate: the editor must be showing OUR track

`_wait_for_subtitle_editor` polls for up to a minute on two independent signals, either
sufficient:

1. **Our own first cue is on screen.** `_cue_probe` reads the `.srt`, skips the index and
   `-->` lines, and returns a snippet of the first spoken line — trimmed at 24 characters
   and cut at any `"` or `\` so it can go straight into a `:text("…")` selector. This is
   the strong signal: it proves the editor loaded *this* track, not merely that an editor
   mounted.
2. **A dense caption table**, for a file whose first line is too short to search for. A
   loaded editor carries a text box plus two timestamp boxes per cue; the translations list
   it was opened from carries none, so `_editor_caption_fields >= 3` separates them without
   naming a single Studio component.

Neither signal in a minute: **raise, do not press.** The `.srt` is already in Studio as a
draft at that point, so refusing costs a retry and pressing costs the track. The message
says exactly that and names the three manual steps.

A 2s settle follows the signal anyway — cues on screen and the editor fully wired are not
quite the same moment.

### The fixture that was lying about the interesting part

Every subtitle test wrote `...\nx\n` as its `.srt` body. `_cue_probe` correctly refuses a
one-character probe, so the new gate fell to its structural fallback in **every** test and
the cue path was never exercised. The fixtures now carry a real line ("Chương một: người
khách lạ"), and `_FakeSubtitlePage` grew `cue` / `editor_polls` so a test can watch the
editor finish loading — `test_publish_waits_for_the_editor_to_load_the_cues` asserts the
poll counter actually reached zero, not merely that Publish was eventually clicked.

1124 tests pass (1119 before, +5), ruff clean.
