# 077 — Audio goes stale when its text changes — History

## [PLAN] 077.01-INITIAL-PLAN — 2026-09-03

Generated plan: `077.01-INITIAL-PLAN.md`. The investigation behind it is in the prompt:
`edit_translation` never touches `audio_path`, `pending_audio` has no notion of the text
changing, and the two cannot be told apart from stored data because `edit_translation` and
`save_audio` both stamp the same `updated_at`.

## [IMPL] Fingerprint what was voiced — 2026-09-03

### The choice that shaped everything else

A fingerprint of the voiced text, compared against the current text — **not** a "needs
audio" flag set by each edit site. The text reaches the DB through `edit_translation`,
`save_translation`, `save_rewrite`, `restore_translation`, `apply_replacements`,
`edit_content` and `edit_title`. A flag needs all seven to remember, and the eighth writer
someone adds next year will not. A fingerprint needs none of them to know it exists.

It is also right for edit-then-undo, which a flag gets wrong — there is a test for that.

### `src/noveltrans/models.py`

- `Chapter.audio_text_hash` — what the audio was voiced from. **Empty means "unknown",
  never "stale"**: every row in every existing library has one.
- `Chapter.audio_source_text(use_translation=None)` — the `(title, text)` pair. `None`
  reads `audio_source`, so a row judges itself rather than being told which radio button
  the tab is showing.
- `Chapter.audio_fingerprint(...)` — sha1 over title + `\x00` + text. The separator is not
  decoration: without it `("ab", "c")` and `("a", "bc")` collide, and there is a test.
- `Chapter.audio_is_stale` — has audio, not downloaded, hash recorded, hash differs.

The title is in the fingerprint because `synthesize_chapter(title, text, …)` **speaks it
aloud**, and `slugify(title)` is in the audio filename. Confirmed in the code before wiring
it, as promised when the user chose title edits as a trigger.

### `src/noveltrans/storage/project.py`

- `audio_text_hash` column, in `_SCHEMA` and in `_migrate`'s added-columns map.
- `save_audio(..., text_hash="")`. Narration downloaded from the source site passes
  nothing — and in fact **no download path calls `save_audio` at all** (they use
  `save_source_audio` on the separate `source_audio` table), so that is doubly safe.
- `pending_audio` gains `_stale_audio`, a second pass, because a hash comparison cannot be
  expressed in SQL. It is narrowed to rows that HAVE audio and a recorded fingerprint, so
  rows with no audio (already pending by the cheap clause) and legacy rows never have their
  text loaded. Results are merged and re-sorted by `idx`, because `AudioWorker` walks the
  list in order.
- `clear_audio` clears the hash, and its docstring — which claimed `pending_audio` re-queues
  "never on the translation changing" — was corrected rather than left to rot.

### `src/noveltrans/gui/workers.py`

- `_title_text_for` is now a delegate to `Chapter.audio_source_text`. This is the one place
  the design could rot: if what is SPOKEN and what is HASHED were derived separately, every
  chapter would be permanently stale or permanently fresh and no predicate test would
  notice. There is a test asserting the two agree, for both sources.
- Sequential path fingerprints from the chapter; the parallel path computes it **on the
  pool thread** and carries it back in `_AudioResult.text_hash`. Deliberate: by commit time
  the orchestrator has only a row id, and re-reading the chapter to hash it could pick up an
  edit made mid-run — recording a fingerprint for text that was never spoken.

### `src/noveltrans/gui/widgets.py`

- `"Cần tạo lại"` in `_audio_status`, coloured as actionable rather than as an error —
  nothing is broken, the recording is just out of date and stays playable.
- `_AUDIO_RANK` renumbered so it sorts **with** `Chưa tạo`, not with `Đã tạo`: both mean
  "still needs a TTS run", which is the reason to sort by status at all.

### Tests — 41 new

`test_audio_staleness.py` (18), `test_project_pending_audio_stale.py` (14),
`test_workers_audio_fingerprint.py` (6), plus 3 in `test_widgets.py`.

Two worth calling out. `test_a_db_written_before_this_feature_gains_the_column` originally
asserted the column exists on a *fresh* DB — which passes with no migration at all. It now
drops the column back out to make a genuine pre-077 file before reopening. And
`test_a_rewrite_puts_it_back` / `test_a_find_replace_pass_puts_it_back` exercise writers
that never heard of this feature, which is the whole argument for the fingerprint.

### Verification

- `QT_QPA_PLATFORM=offscreen python -m pytest` → **3098 passed, 20 deselected** (was 3057).
- `ruff check src tests` → clean.
- **Dry run on a fresh copy of the real library**, never the live one:
  - Upgrade: **5124 voiced chapters across 16 projects → 0 stale.** The empty-hash rule
    holds at scale; nobody's existing audio is invalidated by installing this.
  - End-to-end on a real chapter: re-voice → fresh; edit the voiced text → stale and
    re-queued; re-voice → fresh; edit the *other* source → untouched; edit the title →
    stale and re-queued.

A first attempt at that simulation looked like a bug — `audio_is_stale` said fresh while
`pending_audio` returned the row. The simulation was wrong, not the code: that chapter is
voiced from the **original**, so editing its translation correctly left it alone, and it
appeared in `pending_audio(use_translation=True)` through the pre-existing source-mismatch
arm, as all 1444 of that novel's chapters do. Recorded because the same trap will catch the
next person who reaches for `pending_audio` to check staleness — `_stale_audio` is the
question they mean.

- Not exercised in the running app: no real TTS was synthesised.
