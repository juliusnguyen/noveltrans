# 050 — Hide the Dock icon while running in the menu bar — history

## [IMPLEMENTATION] — 2026-07-31

1380 tests pass (1370 before, +10), ruff clean.

Closing the window to the menu bar now drops the Dock tile as well; reopening puts it
back. Verified as a real round trip against a live `QApplication`:
`Regular → Accessory → Regular`.

### `setActivationPolicy:` at runtime, via ctypes

Qt has no API for this. It is `NSApplication.setActivationPolicy:` — `Regular` (0) has a
Dock icon and an application menu bar, `Accessory` (1) has neither, only the menu-bar
item. pyobjc is not a dependency and adding it for two calls would be disproportionate;
`libobjc` is reachable through `ctypes`, and both directions were measured before any of
this was written.

**Deliberately not `LSUIElement`.** That was already considered and rejected in 049: it
removes the Dock icon for the whole life of the app, including while the window is open.
`packaging/NovelTrans.spec` is still untouched.

### The setter's return value is a trap

`setActivationPolicy:` returns **NO when the policy is already the requested one**. The
first version returned that verbatim, so a second `hide_dock_icon()` reported failure —
a caller could reasonably have concluded the Dock icon was still there and acted on it.
Found by a test that hid twice. The result is now judged by *where the app ended up*
(`current_policy() == policy`), which is what callers actually mean. Both directions are
pinned.

### What this costs, and why it is still right

Three things stop working while the tile is gone. They are consequences, not bugs, and
they are in the README:

* **The Dock badge lands nowhere.** 049 badged the Dock when a job finished with the
  window hidden, and called that the *reliable* half of the signal because a tray
  `showMessage` can be silently dropped for an unsigned bundle. With no tile, the
  notification is now the only signal in exactly that case. The badge call is kept, with
  a comment, for when `hide_dock_icon()` declines and the tile is still there.
* **Dock-click re-show is gone** — the menu-bar icon is the only way back in.
* **⌘Q is gone while hidden.** In Accessory mode the app does not own the menu bar, so
  the key never arrives. `Thoát` in the panel remains, and ⌘Q still works whenever the
  window is open.

### Safety

`hide_dock_icon()` is only called on the hide path, which is only reachable when
`hide_to_tray_enabled` is True — and 049 sets that solely after a tray icon actually
installed. So the tile can never be dropped without a menu-bar item left to get back
through. Pinned by a test asserting the no-tray close leaves the Dock alone.

Every function in `gui/dock.py` returns False rather than raising: on a non-macOS
platform, and if the Objective-C lookup fails. Losing a Dock icon must never be able to
take the app down, and a caller that cannot hide the icon should still hide the window.
Both paths are tested (patched `sys.platform`, and a `CDLL` that raises).

The Dock icon is restored **before** the window is raised in `show_from_tray`: leaving
Accessory is what gives the app its menu bar back, and a window raised first can land
behind whatever the user was looking at. Ordering is pinned by a test.

`tests/test_main_window.py` patches the two calls out — unpatched they would change
pytest's own activation policy. `tests/test_dock.py` exercises the real runtime and
restores the policy in a fixture.

## [LIVE RUN 1] — 2026-07-31 — the menu-bar click opened the window instead of the panel

> *"when I click on the icon app on the bar, instead of showing the progress, it open the
> app in the dock"*

A bug in 049's `DockActivateFilter`, which 050 made both visible and pointless.

The filter re-showed the window on `QEvent.Type.ApplicationActivate` whenever the window
was hidden. But **clicking a menu-bar status item activates the application**, so the
filter fired on the user's own click, called `show_from_tray()` — restoring the Dock icon
and raising the window — and the progress panel never got a chance. `tray.activated` was
almost certainly firing correctly; it just lost the race to something that reopened the
whole app.

Worse, the filter's stated purpose was unreachable: since 050 there *is* no Dock icon
while hidden, so "clicking the Dock icon" cannot happen in that state. The only thing the
filter still did was hijack menu-bar clicks.

Fixed by gating it on `current_policy() == POLICY_REGULAR` — a Dock tile actually
existing to have been clicked. In the normal hidden state (Accessory) the filter now does
nothing and the tray click shows the popup. The Dock-click fallback stays alive for the
case where `hide_dock_icon()` declined and the tile is still there.

Deleting the filter outright was the alternative and would also have fixed the symptom;
the guard keeps the fallback for two lines, so it won. Pinned by a test named after the
report.

While rewriting those tests: they had been reading the **real** activation policy, which
is process-wide state that other tests and Qt itself can move — so they passed or failed
on test ordering. All four now monkeypatch it.
