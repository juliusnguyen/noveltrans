# 039 — Playlist picker + ordered add-all — PLAN

## Design decisions

| Decision | Rationale |
| --- | --- |
| **Read the playlists from Studio's `/channel/<id>/playlists` page.** | A plain list page, reachable in one navigation, that doesn't require being mid-upload. The upload dialog's own picker holds the same names but only exists inside an upload flow — fetching from there would mean starting an upload we then have to abandon. |
| **Fetching needs its own "Tải danh sách…" button.** | It opens a real browser on the shared profile, which takes seconds and can hit a login prompt. Doing that automatically on tab load would open Chrome every time someone clicks the Video tab. |
| **The combo is editable and free text still wins.** | The user chose this: an unknown name typed in is still created on upload, exactly as today. The list is an aid, not a gate — so nothing that works today stops working, and someone with 40 playlists doesn't have to fetch before they can upload. |
| **Add-all reuses 034's video edit page**, not a playlist-side "add videos" dialog. | Same page, same proven navigation and save-confirmation shape, and the existing `_PLAYLIST_*` selectors already drive the picker that page hosts. Iterating parts in order and appending each gives the order for free. |
| **Clear-then-add, with the clear as its own phase that must fully succeed before anything is added.** | The user chose clear-then-add for exact ordering. The failure mode to design against is a half-cleared playlist getting a partial re-add on top, which is worse than either end state. So: scrape → clear → **verify empty** → add. If the verify fails, stop and report; never add onto a mess. |
| **Scrape the existing contents before clearing.** | Clearing is destructive and per-row. If it fails halfway, the only thing that turns "your playlist is broken" into something actionable is a list of what was in it. Cheap to capture, and the one thing we cannot recover afterwards. |
| **The confirmation names the playlist and the count being removed, and says it may be public.** | It empties something viewers may be watching. The user accepted that trade; the dialog still has to state it, because accepting it once in a design conversation is not the same as remembering it three weeks later at 1 a.m. |
| **Eligibility: every part with a `video_id` in the current selection, in part order.** | Same rule as 034's thumbnail push, for the same reason — a `video_id` is exactly "there is a video on the channel to act on". |

## Implementation

### 1. `youtube_upload.py` — reading the channel's playlists

```python
_PLAYLISTS_URL = "https://studio.youtube.com/channel/{channel_id}/playlists"
_PLAYLIST_ROW_SEL = "ytcp-playlist-table-row, #playlists-table ytcp-table-row"
_PLAYLIST_TITLE_SEL = "#title, .playlist-title, ytcp-playlist-title"

def fetch_playlists(*, headless: bool = False) -> list[str]:
    """Every playlist title on the logged-in channel, in Studio's own order.

    Titles, not ids: the upload picker searches by title, so a title is what the rest of
    the flow can actually use. Duplicated titles are returned once — if a channel really
    has two playlists of the same name, this feature cannot tell them apart and neither
    can the picker it feeds.
    """
```

### 2. `youtube_upload.py` — the ordered sync

```python
    """Remove every entry. Returns how many went. Raises if any row refuses."""
def _verify_playlist_empty(page) -> bool: ...
def _add_to_playlist(page, video_id: str, playlist: str) -> None:
    """Open the video's edit page and tick `playlist`, then confirm the save.
    Reuses `_open_edit_page` / `_save_edits` from 034 and `_set_playlist`'s picker DOM."""

def sync_playlist_batch(
    playlist, requests, *, headless=False, on_progress=None,
    on_part_done=None, should_cancel=None,
) -> dict:
    """Empty `playlist`, then add every request's video in order. ONE browser session.

    Phased deliberately: the clear must fully succeed and verify empty before a single
    video is added. A half-cleared playlist that then gets a partial re-add is worse than
    either end state, and impossible to reason about afterwards.
    """
```

### 3. `gui/workers.py`

`PlaylistFetchWorker` (returns titles) and `PlaylistSyncWorker` (the 034 worker shape:
`progress` / `part_done` / `finished_ok` / `failed` / `needs_login`).

### 4. `gui/tab_video.py`

- `upload_playlist` becomes an **editable `QComboBox`**; `.text()` call sites become
  `.currentText()`.
- "Tải danh sách…" button beside it — fetches and repopulates, keeping whatever was typed.
- "Thêm vào danh sách phát" button — the ordered sync, interlocked with the other browser
  runs under the one `Dừng`, like 034.

## Risks

1. **Clearing is destructive and every selector is unverified** — the same KNOWN GAP as
   033/034, but here a wrong selector can *empty a public playlist*. Mitigations: scrape
   first, verify-empty as a hard gate, abort before adding, and a confirmation that states
   the count. This is the feature to test on a throwaway playlist first.
2. Studio has no bulk remove, so clearing is N menu interactions — slow on a long playlist
   and the most likely thing to drift.
3. A channel with two same-titled playlists is ambiguous end to end; the picker and the
   upload flow already share this limitation.
