# 039 — Playlist picker + ordered add-all — history

## [DECISIONS] — 2026-07-29

Settled with the user before planning:

- **Picker is editable** — a dropdown seeded from the channel, but an unlisted name can
  still be typed and gets created on upload (today's behaviour, plus the list).
- **Add-all is clear-then-add** — the playlist is emptied first, then every part added in
  order, so the order is exact every time. The user was shown the trade-off (destroys any
  manual arrangement; briefly empties a possibly-public playlist) and chose it anyway.

Generated plan: `039.01-INITIAL-PLAN.md`. The phase ordering is the safety story:
scrape → clear → **verify empty** → add, never overlapping.

### A real bug the tests found

The first `_clear_playlist` reset its stall counter whenever `_remove_first_entry` returned
True — but a menu item can be found and clicked and still remove nothing, which is exactly
the drifted-selector case the guard exists for. Result: the runaway stop degraded from
"give up after 3" to "hammer Studio 500 times", the opposite of the human-paced posture
this module is built on.

It only surfaced after the fake was made to *actually* remove entries. The first version of
`_FakePlaylistPage` never succeeded at removal, so `stuck=True` tested nothing and the
loop's success path was uncovered — the tests passed for the wrong reason. Rewritten so
the **count is the only source of truth**, never the click's return value, and the happy
path, the progress reporting and cancellation are all covered now.

### KNOWN GAP — worse here than anywhere else

Every selector is an unverified guess, as in 033/034. But this is the first feature that
**removes** things: a drifted selector can empty a playlist viewers are watching.
Mitigations, in order of importance:

1. `_playlist_entries` captures the contents *before* clearing — the one thing that cannot
   be recovered afterwards, and what turns "your playlist is broken" into something
   actionable.
2. `_playlist_is_empty` is a hard gate. A clear that doesn't verify raises and **nothing
   is added**; a half-cleared playlist with a partial re-add on top is worse than either
   end state. Pinned by `test_a_clear_that_does_not_verify_empty_never_reaches_the_add_phase`.
3. The stall guard stops after 3 non-reducing attempts.
4. The confirmation names the playlist, says `XOÁ HẾT`, and warns it may be visible to
   viewers while it runs.

**Test this on a throwaway playlist first.**

## [FIX] Live run: wrong playlists URL + a raw TargetClosedError — 2026-07-29

First live run of "Tải danh sách…" failed with:

```
TargetClosedError('Locator.wait_for: Target page, context or browser has been closed
  - waiting for locator("ytcp-playlist-section, #playlists-section, ytcp-video-section")')
```

and a screenshot of `studio.youtube.com/channel/<id>/playlists?hl=vi` showing Studio's
**"Oops, something went wrong."** page.

Two separate bugs, and the first one hid the second.

### 1. The URL was a guess, and a wrong Studio URL does not fail

`/channel/<id>/playlists` renders Studio's generic error page — a *successful* navigation
with a perfectly normal DOM. Nothing distinguished it from a page that was merely slow to
mount, so the code sat out the full 45-second wait and then reported "giao diện có thể đã
thay đổi", pointing at a selector bug that did not exist.

Fixed by not betting on one path. `_goto_playlists_page` walks a list of known shapes and
lets the DOM decide which worked:

```
/channel/<id>/content/playlists
/channel/<id>/videos/playlists
/channel/<id>/playlists
https://www.youtube.com/feed/playlists     <- not Studio at all
```

`_page_shows_studio_error` matches the error text, so a wrong candidate is rejected in a
second or two instead of burning the page wait. The youtube.com entry is last on purpose:
it is a different, far more stable surface, and the whole reason to keep it is that it is
not subject to Studio's reshuffles. If every candidate fails the error now *names them
all* and reminds the user the box accepts free text.

### 2. Closing the window produced a Playwright traceback

`_first_present` catches only `PlaywrightTimeoutError`, so a `TargetClosedError` went
straight to the UI. Closing a browser window mid-run is a normal thing for a person to do
— especially when staring at an error page — and it should read as one sentence.
`_browser_gone()` now recognises it by both type name and message, in the navigation
walker and around `fetch_playlists` as a whole.

### Note on the original diagnosis

The "unverified selectors" warning in the KNOWN GAP section above was aimed at the DOM.
This failure was a *URL*, which that framing did not cover — and the error message
inherited the same blind spot, blaming selectors for a navigation problem. The candidate
walker and the error-page check exist so the next drift of either kind reports itself
accurately.

972 tests pass (965 before, +7), ruff clean. The new URL shapes are still unverified
against a live channel — but now a wrong one is cheap and self-describing rather than a
45-second wait ending in a misleading message.

## [FIX 2] The URL was right; the container gate was the bug — 2026-07-29

The candidate walker reported all four URLs as failures. The user then supplied the fact I
had been guessing at:

> this is the right url: `https://studio.youtube.com/channel/<id>/content/playlists`

That is **candidate #1**. The URL had loaded correctly all along. What failed was the gate
immediately after it:

```python
if _first_present(page, _PLAYLIST_PAGE_SEL, ...) is not None:   # ytcp-playlist-section, …
    return page.url
```

No such container exists on that page, so the code waited 45 seconds and walked away from
a page that was working — then blamed the URL. Adding more URL candidates in FIX 1 made
the report longer without touching the actual defect; it had the diagnosis pointed at the
wrong layer twice in a row.

### What changed

- **The container gate is gone.** Navigation now accepts a page on the strongest claim the
  DOM actually supports: *it loaded and it is not the error page*. Requiring a component
  whose name we cannot know in advance was never a check on success — only on our guess.
- **Extraction is a wide net, and it is the step allowed to fail.** `_extract_playlist_titles`
  tries seven row shapes, then falls back to `a[href*='/playlist/'], a[href*='list=']`.
  The anchor pass matters most: an `href` is *structural*, so it survives the component
  renames that break tag- and id-based selectors.
- **Failures now carry the DOM.** `_dom_inventory` reports the distinct custom-element
  tags and their counts. "Giao diện có thể đã thay đổi" is useless on its own; naming the
  components is the difference between a bug report and a fix.
- `_open_playlist_page` uses the same wide net, still with an **exact** title match — a
  substring match would open "Phần 1" for "Phần 10", and the next thing that code does is
  empty whatever it opened.
- `/content/playlists` is now marked CONFIRMED in the URL list rather than guessed.

### The lesson, recorded because it recurred

Both live failures came from the same habit: gating on a guess and reporting the failure
in terms of that guess. FIX 1 detected Studio's error page but still required an unknown
container; FIX 2 removes the requirement entirely. **Gate on what is known, extract with a
wide net, and attach the evidence when extraction fails.**

978 tests pass (972 before, +6), ruff clean.
`test_navigation_no_longer_requires_a_container_element` is the regression, and
`test_a_page_with_an_unknown_row_tag_still_yields_titles_via_links` is the reason the next
rename should not need a code change at all.

## [FIX 3] The picker offered video counts as playlist names — 2026-07-29

Live run 3: the page was found and read, but the dropdown listed

```
No videos
75 videos
31 videos
10 episodes
```

— every row's **video-count cell**, not its title.

FIX 2 replaced a fragile container gate with a wide net, and then trusted *position*
within what the net caught: `_row_titles` took `splitlines()[0]`, and the anchor pass read
each `<a>` independently. A playlist row links to the same playlist from its thumbnail,
its title *and* its count, so reading anchors one at a time yields three unrelated strings
with no way to tell which is the name.

### What changed

- **`_is_playlist_metadata`** refuses the shapes that are decoration rather than a name:
  counts (`75 videos`, `10 episodes`, `12 video`, `5 tập`), the empty-playlist label
  (`No videos`, `Không có video`), visibility labels, bare numbers and dates — in both
  languages Studio may render.
- **`_best_title`** picks the longest *non-metadata* string in a row. A title is the
  substantive text; everything else in the row is short by nature, and length breaks ties
  without needing to know the column order.
- **`_titles_by_playlist_link` groups anchors by the playlist id in the `href`.** That is
  the fix for the anchor pass specifically: the id says which strings belong to the same
  row, so `_best_title` chooses among them instead of each link speaking for itself.
- A playlist whose row yields only metadata is **dropped rather than named after its
  count** — omitting one beats listing "No videos" as a playlist.

`test_a_real_title_is_never_mistaken_for_metadata` guards the obvious over-correction:
"10 Năm Cô Đơn" starts with a number but is a name, not a count.

### Three live failures, one habit

1. FIX 1 — trusted a guessed URL; a wrong Studio URL renders an error page, not a 404.
2. FIX 2 — trusted a guessed container element; walked away from the page that worked.
3. FIX 3 — trusted position within the row; read the count column as the name.

Each time the code asserted more about YouTube's DOM than it could actually know. The
posture that finally holds: **gate on what is known, extract with a wide net, identify by
structure (the `href` id) rather than position, and refuse what is recognisably not a
name.**

984 tests pass (978 before, +6), ruff clean.
