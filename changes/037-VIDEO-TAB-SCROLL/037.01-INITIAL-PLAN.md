# 037 — Make the Video tab scroll — PLAN

## Design decisions

| Decision | Rationale |
| --- | --- |
| **Wrap the tab's boxes in a `QScrollArea` with `setWidgetResizable(True)`.** | The content has a real natural height; the window may be shorter. Without somewhere to overflow *to*, Qt's only option is squeezing widgets below their sizeHint, which is exactly the clipping in the screenshot. A scroll area gives the overflow a destination. |
| **Progress bar and status line stay pinned *outside* the scroll area.** | They are live feedback during runs that take minutes to hours (a 75-part render, a YouTube upload batch). Feedback you have to scroll to find is feedback you don't see — and the one moment you most want it is the moment you're scrolled somewhere else looking at the parts table. |
| **The parts table gets an explicit `setMinimumHeight`, and keeps its own scrollbar.** | It is the widget that collapsed, because `stretch=1` made it the first thing Qt took space from. A minimum stops the collapse. Keeping its own scrollbar rather than letting it grow to fit 75 rows avoids nested scrolling, where a wheel gesture over the table does something different from the same gesture two pixels away. |
| **Minimum of ~6 visible rows (240 px), not more.** | Big enough to be usable and to show a batch's worth of parts at a glance; small enough that on a laptop screen the boxes *below* it are still reachable without scrolling past a wall of table. |
| **The table keeps `stretch=1`.** | On a tall window the content is shorter than the viewport, `setWidgetResizable` grows the inner widget to fill it, and the stretch hands that extra space to the table — so a big screen still gets a big table. The minimum only bites when space is short. |
| **Horizontal scrollbar `AsNeeded`, not `Off`.** | `Off` clips silently if any content turns out wider than the viewport, which is the failure this whole change exists to stop. `AsNeeded` is self-correcting: it appears only if genuinely needed, and it is honest when it does. |
| **Only the Video tab changes.** | It is the one with six group boxes and the one in the report. The other tabs share the pattern and could grow into the same problem, but changing five tabs to fix one reported bug is scope the user didn't ask for. Noted in the history file instead. |

## Implementation

### `src/noveltrans/gui/tab_video.py`

Import `QScrollArea`. In `__init__`, replace the single layout with content-in-scroll plus
a pinned footer:

```python
content = QWidget()
layout = QVBoxLayout(content)
layout.addLayout(top_row)
layout.addLayout(self._build_engine_row())
layout.addWidget(self._build_video_box())
layout.addWidget(self._build_video_list_box(), stretch=1)
layout.addWidget(self._build_upload_box())
layout.addWidget(self._build_thumbnail_box())
layout.addWidget(self._build_image_prompt_box())
layout.addWidget(self._build_tags_box())

self.scroll = QScrollArea()
self.scroll.setWidget(content)
self.scroll.setWidgetResizable(True)          # content fills the viewport, and grows past it
self.scroll.setFrameShape(QFrame.Shape.NoFrame)  # no double border around the tab
self.scroll.setHorizontalScrollBarPolicy(Qt.ScrollBarPolicy.ScrollBarAsNeeded)

outer = QVBoxLayout(self)
outer.setContentsMargins(0, 0, 0, 0)
outer.addWidget(self.scroll, stretch=1)
outer.addWidget(self.progress)      # pinned: live feedback during long runs
outer.addWidget(self.status_label)
```

In `_build_video_list_box`, after the existing sizing:

```python
# ~6 rows + header. Without a floor the table is the first thing Qt squeezes (it owns the
# only stretch), and on a short window it collapsed to a single clipped row.
self.video_list.setMinimumHeight(240)
```

## Test plan

`tests/test_tab_video.py`, new `class TestVideoTabScrolling`:

- `test_the_tab_scrolls` — a `QScrollArea` exists, is `widgetResizable`, and holds the
  group boxes.
- `test_progress_and_status_are_not_inside_the_scroll_area` — both are children of the
  tab, not of the scrolled content, so a long run's feedback can't scroll out of view.
- `test_the_parts_table_keeps_a_usable_height_on_a_short_window` — **the regression.**
  Size the tab to something shorter than its content (e.g. 900×420), lay it out, and
  assert the table is still at least its minimum tall and shows more than one row.
- `test_a_tall_window_still_grows_the_table` — the minimum is a floor, not a fixed size.
- `test_the_scroll_area_reaches_the_content_below_the_fold` — the inner widget's height
  exceeds the viewport on a short window, i.e. there is something to scroll to.

## Risks

1. Nested scrolling: the wheel over the parts table scrolls the table, elsewhere it
   scrolls the page. Standard behaviour, and the alternative (a table 75 rows tall inside
   a scrolling page) is worse.
2. `setWidgetResizable(True)` means the content widget can never be narrower than the
   viewport, so a very narrow window pushes the horizontal scrollbar rather than
   reflowing. Acceptable — the app is not used at phone widths.
