# 060 — Viết lại văn phong (rewrite word-by-word Vietnamese into natural prose)

## The ask

> một số truyện được dịch từ tiếng Trung sang Việt, theo kiểu word by word thay vì
> dịch với văn phong tự nhiên, có cách nào sử dụng AI để viết lại được không?
> Ví dụ:
> "Hắn nội tâm tràn ngập một loại không cách nào nói nói tư vị."
> câu trên nên được viết lại là: "Nội tâm hắn tràn ngập một loại tư vị khó nói."
> Có thể làm thành một feature trong Dịch không?

A **monolingual rewrite pass**: Vietnamese in → Vietnamese out. Not a translation.
The input is "convert"-style prose (máy dịch từng chữ, giữ nguyên trật tự từ tiếng
Trung); the output is the same sentences in natural Vietnamese word order.

Lives in **tab 2 (Dịch)**.

## Two sources of such text

1. **Vietnamese-source novels** — `medoctruyen.vn`, `tieuthuyetmang.com`,
   `giatocvuongtai.com`, `webtruyendich.com`. These arrive already in Vietnamese, so
   `source_lang == target_lang` and `TranslateWorker._run_identity`
   (`gui/workers.py:179`) merely *copies* `content` into `translated` — tab 2 does
   nothing for them today. This is the gap the feature fills.
2. **Anything already translated** by a weaker engine (notably Google free) that the
   user wants polished.

## What we already know (established 2026-08-25, pre-plan reconnaissance)

- The three LLM engines already expose free-form prompting: `supports_completion = True`
  + `complete()` on `claude.py:39`, `cli_agent.py:68`, `lmstudio.py:59`. Declared on the
  ABC at `translators/base.py:52`. **Google is translate-only and must be rejected.**
- There is already precedent for using those engines for non-translation work:
  `TagsWorker` and the generic `CompletionWorker` (`gui/workers.py:380-500`) generate
  YouTube tags and a thumbnail image prompt. Both check `supports_completion` and emit a
  Vietnamese error naming the three usable engines.
- `AppConfig.video_ai_engine` / `video_ai_model` (`config.py:501-520`) is the existing
  pattern for "an LLM engine chosen separately from the translator, defaulting to the
  translator when it is an LLM, else CLI Agent".
- Chunking helper `split_paragraph_chunks` and the retry/leftover-CJK loop live on the
  `Translator` ABC (`translators/base.py`).
- `_migrate()` (`storage/project.py:144`) adds columns idempotently via
  `PRAGMA table_info` + `ALTER TABLE` — the shipped way to grow the chapter row.

## Constraints the rewrite must respect

- **Keep Hán-Việt proper nouns exactly** (Phó Thanh Từ, Giang Dư…). They are already
  correct in the input; "normalising" them is a regression.
- **Keep the genre register** — `hắn / nàng / y / thị / ngươi`. Rewriting these to
  `anh / cô` destroys the tiên hiệp voice.
- **No summarising, no additions, no commentary.** Paragraph count must survive.
- Chapter title gets rewritten too, not just the body.

## Known risks to design against

| Risk | Note |
|---|---|
| LLM summarises instead of rewriting | The real failure mode. A short chapter silently loses a paragraph. Must be detected, not trusted. |
| Overwriting the only copy | The pre-rewrite text is the user's fallback; losing it makes the feature unusable on a 1000-chapter novel. |
| Cost / time | One request per chapter, same order as translating. Claude Haiku on 1000 chapters costs real money; CLI Agent is quota-backed but ~30s/chapter. |

## Out of scope

- Any new translation engine.
- Rewriting the original Chinese (`content`) — this pass only touches `translated`.
