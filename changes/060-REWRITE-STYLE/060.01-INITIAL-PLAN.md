## 1. Summary of the approach

Nothing new has to be invented. The app already has: three LLM engines with a free-form `complete()`; two shipped features that prompt them for non-translation work; a pure, GUI-free, unit-tested prompt-building module (`tts/tags.py`); an idempotent column-adding migration; a pausable, resumable, job-registered batch worker; and a table whose right-click menu is explicitly designed to be extended by the tab that owns it.

The feature is therefore assembled from those parts:

- **`src/noveltrans/translators/rewrite.py`** — new, pure, imports nothing from PySide6. Builds the prompt, normalises the reply, and **validates** it. Its retry loop takes a `send(prompt) -> str` callable, so the whole risky part is unit-testable against a fake LLM that summarises, and against one that renames a character.
- **`RewriteWorker(PausableWorker)`** in `gui/workers.py`, with signal signatures **identical** to `TranslateWorker`'s (`workers.py:135-139`) so `TranslateTab`'s `_on_progress` / `_on_chapter_updated` / `_on_failed` are reused verbatim.
- **Two new chapter columns**, `translated_raw` and `translated_title_raw`, added to both `_SCHEMA` and `_migrate`'s `added` dict. They make the rewrite *undoable* and make "already rewritten" a data fact rather than a guess.
- **One new button** in tab 2's bottom row, opening a **`RewriteDialog`** (modelled on the `FindReplaceDialog` already opened from that same row) that carries the engine picker, the chapter range, the one-chapter preview, the cost warning and the undo. Per-chapter rewrite/undo goes on the table's right-click menu via the `extra_actions` hook.

The single highest-risk decision is §2.5: **a rewrite that fails validation must never be written**. Every other choice in this document is subordinate to that one.

The second-highest is §5.6, which is easy to miss: **a rewrite silently desynchronises already-generated audio, subtitles and video from the text**, because `pending_audio` (`project.py:402-438`) compares paths and voices, never text.

## 2. Decisions

### 2.1 Storage — two new columns, `translated_raw` + `translated_title_raw`

**Recommendation.** Add to `_SCHEMA` (`project.py:43-66`) *and* to `_migrate`'s `added` dict (`project.py:147-159`):

```
translated_raw        TEXT NOT NULL DEFAULT ''
translated_title_raw  TEXT NOT NULL DEFAULT ''
```

Both are required in **both** places and this is not redundancy: `_SCHEMA` runs through `executescript` at `project.py:141` but every statement is `CREATE TABLE IF NOT EXISTS` (`project.py:44`), so for an existing `chapters.db` it does nothing at all — only the `ALTER TABLE` loop at `project.py:160-163` grows it. Conversely a brand-new project never enters the ALTER branch because the columns are already there. `_row_to_chapter` (`project.py:96-117`) reads columns **by name**, so omitting the migration would make every existing project fail to open, not degrade gracefully.

`Chapter` (`models.py:190-227`) gains the two fields plus:

```python
@property
def is_rewritten(self) -> bool:
    return bool(self.translated_raw)
```

**Semantics.**

- *"Already rewritten"* (the resume predicate) = `translated_raw != ''`. It is written at the same instant as the new `translated`, in one transaction, so a crash mid-run cannot produce a rewritten body with no backup or a backup with no rewrite.
- *Re-rewriting an already-rewritten chapter must not destroy the original.* `save_rewrite` uses the capture-once `CASE WHEN` that `edit_title` already ships (`project.py:539-549`):
  ```sql
  translated_raw = CASE WHEN translated_raw = '' THEN translated ELSE translated_raw END
  ```
  Reusing that exact shape is deliberate — the docstring at `project.py:533-535` records the app already getting this wrong once, when a second edit recorded the first edit as "the original and the way back was gone."
- *Undo* = `restore_translation(idx=None)`: copy `translated_raw` → `translated`, `translated_title_raw` → `translated_title` (only when non-empty), then blank both raw columns, `WHERE translated_raw != ''` (plus `AND idx = ?` for the per-chapter form). Blanking is what makes the chapter eligible for a fresh rewrite pass — undo and resume are the same predicate read two ways, which is why there is no third state to keep consistent.

**Why the `translator` label alone does not suffice** (the brief asks this explicitly):

1. **A label cannot undo.** The brief's own risk table calls losing the pre-rewrite text "makes the feature unusable on a 1000-chapter novel". A string that says *what ran* is not a copy of *what it replaced*. This alone is decisive.
2. **It is not a reliable flag either.** `edit_translation` (`project.py:502-523`) deliberately leaves `translator` untouched on a manual edit — "engine, language, timing and status stay as the original translation run left them". So a hand-edited chapter and a rewritten one would be indistinguishable if a hand edit ever ran after a rewrite.
3. **It is destroyed by the neighbouring feature.** `clear_translations` (`project.py:872-880`) blanks `translator`, so "Dịch lại từ đầu" would silently un-flag every rewritten chapter.
4. **It has one slot and two facts to carry.** `TranslateWorker.engine_label()` (`workers.py:167-177`) already owns that column's meaning: *which engine produced `translated`*. Overloading it with "…and then it was rewritten by X" makes the "Dịch bằng" column mean two things and makes the identity label `"(nguyên bản)"` (`workers.py:199`) a lie the moment a rewrite runs.

**`save_rewrite` does not touch `translator`.** The column keeps meaning "the engine that translated this". Rewritten-ness is shown separately (§2.8). Per-chapter *rewrite-engine provenance* — knowing that chapters 1-400 were rewritten by LM Studio and 401-1000 by Claude — is **deferred** (§2.12); it needs a third column and the first cut's users will run one engine.

### 2.2 The uniform engine call — `complete(prompt)`, positionally, no `system=`

**Recommendation.** The rewrite builds one self-contained prompt string and calls `translator.complete(prompt)` with no keyword arguments, exactly as `TagsWorker` (`workers.py:422`) and `CompletionWorker` (`workers.py:493`) already do.

Rationale:

1. **It is the only signature all three engines share** — and it is the ABC's own (`base.py:58`). `CliAgentTranslator.complete(prompt)` (`cli_agent.py:94`) physically cannot accept a system prompt: it appends the prompt as the final `argv` entry of a subprocess (`cli_agent.py:98`). There is no second channel to put a system prompt in.
2. **The other two degrade correctly.** `ClaudeTranslator.complete` defaults `system=""` and substitutes `"You are a helpful assistant."` (`claude.py:64`); `LmStudioTranslator.complete` simply omits the system message when it is empty (`lmstudio.py:89-90`). Neither needs anything.
3. **Widening the ABC is the wrong fix.** Adding `system=` to `Translator.complete` would force `cli_agent` to either ignore it (a silently-dropped instruction — the worst kind) or fold it into the prompt anyway, which is what this decision does directly and visibly.
4. **A system prompt is actively harmful here.** `cli_agent.py:29-30` records the finding that coding-agent CLIs *refuse prompts that try to redefine their role*, and `cli_agent.py:106-116` records a second lesson: launched in a code repo they behave like coding assistants. A rewrite prompt phrased as "Bạn là biên tập viên…" is a role redefinition and would be refused by exactly the engine most users will pick (it is quota-backed, not metered). §2.3's prompt is therefore **task-framed for all three engines**, not branched per engine.

Consequence to hold on to: because there is no system channel, the entire instruction set is re-sent with every chunk. That is fine and is what the existing engines already do for translation (`cli_agent.py:87-91`), but it is why §2.4 caps chunk size rather than sending a whole chapter.

### 2.3 The prompt

Lives in `translators/rewrite.py` as `build_rewrite_prompt(text, *, is_title=False)`, returning a `str`. Pure, no engine knowledge, unit-tested — the `tts/tags.py` precedent (`tags.py:32`, `:74`) exactly.

The body prompt:

```

Notes on specific lines, each earning its place:

- **The few-shot is the user's own sentence**, verbatim from the brief. It is the single most information-dense part of the prompt: it demonstrates word-order repair (`Hắn nội tâm` → `Nội tâm hắn`), duplicate removal (`nói nói` → one), and idiom repair (`không cách nào nói` → `khó nói`) — while showing that `hắn` survives untouched.
- **Rule 7 and the data-guard paragraph** are lifted in spirit from `cli_agent.py:40-41`, which already ships both ideas for the translation path.
- **No "Bạn là…"** anywhere — §2.2 point 4.
- **The `---` fence** before the text gives the validator's preamble-stripper (§2.6) an unambiguous landmark and gives the model an unambiguous boundary.

`is_title=True` swaps rules 3-4 for: `"Đây là TÊN CHƯƠNG — chỉ MỘT dòng ngắn. Trả về đúng một dòng. Nếu tên chương đã tự nhiên rồi thì chép lại y nguyên. Không hỏi thêm, không nhận xét là thiếu nội dung."` The "never ask for more text" clause mirrors the identical hazard already handled for short fragments at `claude.py:18-20` and `cli_agent.py:37-39`.

**Language scope.** The rewrite is Vietnamese→Vietnamese only. The dialog refuses when the project's `target_lang` is not `"vi"` (§2.8). An English "polish" pass would need a separate, differently-tuned prompt with no Hán-Việt or pronoun-register rules at all; it is **out of scope**, not a config flag.

### 2.4 Chunking — reuse `split_paragraph_chunks`, cap at 3000 chars

**Recommendation.** Reuse `split_paragraph_chunks` (`base.py:19-40`) verbatim, with
`max_chars = min(translator.max_chunk_chars, REWRITE_CHUNK_CHARS)` where `REWRITE_CHUNK_CHARS = 3000`.

Rationale:

1. **The helper is already exactly right.** It never splits a paragraph (`base.py:20-24`), which is a hard requirement here because the validator's primary check is paragraph-count equality — a mid-paragraph cut would make the count meaningless. It also keeps an oversized paragraph whole rather than cutting mid-sentence, which is the correct failure mode for a rewrite too.
2. **The rewrite's output is as long as its input**, unlike a tag list or an image prompt. `ClaudeTranslator` caps replies at `max_tokens=8192` (`claude.py:63`) while declaring `max_chunk_chars = 12000` (`claude.py:38`). For Chinese source that is comfortable — Vietnamese output is longer in characters but the input is small in tokens. For a *Vietnamese* input of 12000 diacritic-heavy characters, both sides are token-hungry and an 8192-token reply ceiling becomes a live truncation risk. A truncated reply is precisely the summarisation-shaped failure this feature must not commit.
3. **It bounds the blast radius of a retry.** A validation failure costs one 3000-char re-request, not one 12000-char one. On CLI Agent (quota-backed, ~30s/call) that matters.
4. `min()` rather than a flat constant so LM Studio's deliberately conservative 4000 (`lmstudio.py:58`, "local models often run with an 8k context window") still wins where it is smaller in future.

The chapter title is rewritten as its own single call, exactly as `translate_chapter` does (`base.py:98`).

### 2.5 Validation — `check_rewrite`, and what happens on failure

This is the part the feature lives or dies on. `translators/rewrite.py` exposes:

```python
class RewriteRejected(Exception):
    """A candidate rewrite failed validation. Carries a Vietnamese `reason`
    suitable both for the retry nudge and for mark_error."""
```
```python
def check_rewrite(source: str, candidate: str) -> str:
    """'' if the candidate is an acceptable rewrite of `source`; otherwise a
    Vietnamese reason string naming exactly what failed."""
```

**Checks, in evaluation order** (cheapest and most decisive first):

| # | Check | Threshold | Why |
|---|---|---|---|
| 1 | Non-empty after normalisation | — | An empty reply is a failure, never a "rewrite to nothing". |
| 2 | **Paragraph count equality** | exact | **The primary guard.** A dropped paragraph out of 30 changes total length by ~3% — no length heuristic can see it. Paragraph count sees it immediately. Counted as `[p for p in text.split("\n\n") if p.strip()]`, mirroring `base.py:25` so chunking and validation agree by construction. |
| 3 | Whole-chunk length ratio | `0.60 ≤ len(out)/len(src) ≤ 1.50` | Catches the *other* summarisation shape: a reply that is a one-line précis or "Đã viết lại xong." (ratio ≪ 0.2), and the opposite failure of the model appending commentary or expanding (>1.5). Deliberately **loose**, because check 2 is the tight one. The floor is 0.60, not 0.75: a genuine rewrite of the user's own example is 45/60 = **0.75 exactly**, i.e. right on a 0.75 boundary, and convert prose is full of removable duplication (`nói nói`) — a tight floor would reject good work. *(Inferring: the 0.75 figure is a character count of the brief's one example; the real per-chapter distribution has not been measured. §2.9's preview flow is how it gets measured before the constant is frozen.)* |
| 4 | Per-paragraph length ratio | `≥ 0.50`, **only for source paragraphs ≥ 80 chars** | Catches "kept all 30 paragraphs but replaced paragraph 17 with '…'". Restricted to long paragraphs because short ones ("— Ừ.") are noise. |
| 5 | No new CJK | `cjk_count(out) <= cjk_count(src)` | Reuses `base.py:14-16`. The input is Vietnamese; Chinese in the output means the model mis-read the task entirely (e.g. decided to "restore the original"). Written as `<=` not `== 0` because convert text occasionally carries a stray glyph the rewrite may legitimately keep. |
| 6 | Proper-noun preservation | every extracted name must appear as a substring of the output | The Hán-Việt constraint from the brief, mechanised. |

**Proper-noun extraction** (`proper_nouns(text) -> set[str]`, also in `rewrite.py`, also pure). `translators/names.py` cannot be reused — its `_NAME_RE` matches CJK codepoints (`names.py:88-94`) and it exists to convert Chinese to Hán-Việt, the opposite direction. The Vietnamese rule:

> Take every maximal run of ≥2 consecutive whitespace-separated tokens each beginning with an uppercase letter. If a run begins a sentence (start of text, or immediately after `. ! ? … : \n` or an opening quote/dash), drop its first token, because Vietnamese capitalises the first word of every sentence. Keep the run if ≥2 tokens remain.

`"Phó Thanh Từ nhíu mày."` at a paragraph start yields `"Thanh Từ"` — weaker than the full name but still a hard constraint the model cannot satisfy while renaming the character. Mid-sentence `"…nhìn Giang Dư."` yields `"Giang Dư"` in full. A run of two ordinary capitalised words mid-sentence essentially does not occur in Vietnamese prose, so false positives are rare; the ≥2-token floor after trimming is what keeps `"Nhưng"` and `"Anh"` out. This is a presence check on the whole chunk, not a positional one, so legitimate reordering is unaffected.

**Per-chunk, not per-chapter.** Validation runs on the unit that was sent, because the retry is also per unit — validating only the reassembled chapter would force re-requesting *every* chunk to repair one, at N× the cost. A **second, free** assertion runs on the assembled chapter (total paragraph count of the join equals total paragraph count of the source), which costs nothing and catches a chunk-reassembly bug rather than a model failure.

**Failure policy — the hard rule.**

```
attempt 1 → check_rewrite → ok?  write
                          → no?  attempt 2, with the reason appended to the prompt
attempt 2 → …             → no?  attempt 3, same
attempt 3 → …             → no?  raise TranslateError(reason)
```

`REWRITE_MAX_ATTEMPTS = 3` (matching `Translator.max_retries = 3`, `base.py:47`). The retry prompt appends a specific, Vietnamese nudge naming the measured failure — e.g. `"Lần trước bạn trả về 27 đoạn nhưng bản gốc có 30 đoạn. Giữ ĐÚNG 30 đoạn, đúng thứ tự, không gộp đoạn."` A generic "try again" wastes a call; a measured one is actionable.

On exhaustion the worker:

- **does not call `save_rewrite`** — `translated` and `translated_title` are left byte-identical to what they were;
- calls `project.mark_error(idx, reason)` (`project.py:614-619`) and emits `chapter_error`;
- **continues the batch**, exactly as `TranslateWorker` does (`workers.py:300-307`).

There is no "best attempt" fallback and there must never be one. `base.py:90-91`'s comment — *"a few stray chars beat failing the whole chapter"* — is true for translation, where the alternative is no text at all. For a rewrite the alternative is the **perfectly good text already in the database**, so accepting a truncated attempt is strictly worse than doing nothing. This is called out in `rewrite.py`'s module docstring so nobody harmonises the two loops later.

*Accepted trade-off, stated so it isn't "fixed":* `mark_error` flips a chapter whose translation is intact and readable to status "Lỗi" in the table (`widgets.py:44-49`). That is correct — the user must see which chapters were skipped and why (the "Lỗi" column already carries the reason with a hover tooltip, `widgets.py:574-575`) — but note that `reset_errors` (`project.py:882-891`) will then set the status to `downloaded`, i.e. "Đã tải", on a chapter that *is* translated. That is a pre-existing cosmetic quirk of `reset_errors`, not something this feature introduces, and nothing re-queues off it: `pending_translation` keys off `translated`, not `status` (`project.py:392-399`).

### 2.6 Normalising the reply before validating

Three cheap repairs, applied in `normalise_rewrite(raw) -> str` before `check_rewrite`, each pinned by a test:

1. **Strip code fences.** CLI agents and local models wrap prose in ``` far more often than they should. `lmstudio.complete` already strips `<think>` blocks (`lmstudio.py:118`) but not fences.
2. **Strip a preamble.** A leading line ending in `:` (`"Đây là bản viết lại:"`) or an isolated `---` echo. Applied **only when it would bring the paragraph count to the expected value** — a conditional repair cannot eat a real first paragraph.
3. **Rescue single-newline paragraphing.** If the source used `"\n\n"` separators, the candidate contains **no** `"\n\n"` at all, and its non-empty lines number exactly the expected paragraph count, promote the single newlines to blank-line separators. This is a common and entirely benign LLM output habit; without the rescue, check 2 would reject every such reply and burn three attempts on a rewrite that was actually correct. The three conjoined conditions keep it from ever merging or splitting real paragraphs.

Also collapse runs of ≥3 newlines to exactly two, and strip trailing whitespace per line.

### 2.9 Cost and time control — what is in scope

**In scope:** preview one chapter before committing (§2.8.6); chapter range; resume via `pending_rewrite`; pause via `PausableWorker` + `PauseButton` + the job registry (`workers.py:58-77`, `widgets.py:709`); cancel; per-chapter rewrite from the context menu; undo per chapter and whole-novel; the pre-run cost estimate.

**Deferred, with reasons:** parallel rewrite workers (the translate path is sequential too, and CLI-Agent quota — not CPU — is the binding constraint; `cli_agent.py:164-167` already parses quota-exhaustion messages); token/price estimation (needs per-model pricing tables the app does not have); per-chapter rewrite-engine provenance (§2.1); an English polish pass (§2.3); rewriting `content` (explicitly out of scope in the brief); auto-rewrite folded into the translate run (§2.10).

### 2.10 Relationship to `_run_identity` — a separate, user-triggered pass

**Recommendation: separate pass**, as the brief proposes. Reasons, in order of weight:

1. **`_run_identity` is currently free, instant and offline** (`workers.py:179-205`) — a `save_translation` loop with no engine. Folding a rewrite into it would turn the same "Dịch tất cả" button into an hours-long, possibly metered LLM run for a class of novels (medoctruyen, tieuthuyetmang, giatocvuongtai, webtruyendich) whose users currently expect tab 2 to finish in seconds. That is a surprise cost, and surprise costs on someone else's API key are not acceptable.
2. **A failed rewrite inside the translate pass has no good answer.** It would have to either leave `translated` empty — leaving the chapter permanently in `pending_translation` (`project.py:392-399`) and unusable by TTS/export — or write the un-rewritten text and silently claim success. The separate pass has no dilemma: `translated` is already populated, and a failure simply leaves it alone (§2.5).
3. **It only covers half the ask.** The brief's second source is *"anything already translated by a weaker engine (notably Google free)"* — not an identity-path novel at all. A rewrite bolted onto `_run_identity` would never reach those.
4. **Two independent passes compose.** Translate (or identity), inspect, then rewrite, with the pre-rewrite text preserved throughout.

**`pending_translation` is unaffected either way, and this is verified.** It selects `content != '' AND (translated = '' OR target_lang != ?)` (`project.py:392-399`). A rewrite leaves `translated` non-empty and never touches `target_lang`, so a rewritten chapter is **not** re-flagged as pending. `save_rewrite` must therefore *not* write `target_lang` at all — writing even the same value is an invitation for a later refactor to write a different one. A regression test pins this (§4).

The `"(nguyên bản)"` label (`workers.py:199`) is likewise untouched by `save_rewrite` (§2.1), which is right: the chapter's *translation* still is the original text — it has merely been restyled. The `✍️` suffix (§2.8) carries the new fact.

### 2.11 Audio, subtitles and video after a rewrite — warn, do not delete

`pending_audio` (`project.py:402-438`) gates on `audio_path`, `audio_voice` and `audio_source` — **never on the text**. So a chapter that already has an mp3 is *not* re-pending after its text changes, and the narration, the burned-in subtitles and the exported ebook silently diverge.

**Recommendation: warn loudly, delete nothing, in this feature.**

- `RewriteDialog`'s confirm text names the number of affected chapters that already have audio and says plainly that their audio will no longer match.
- `_on_finished` appends the same warning to the status line when `counts()["audio"] > 0`.
- The rewrite does **not** call `clear_audio` (`project.py:697-716`). That method is whole-novel-only and does not delete files (`project.py:700`) but does blank the rows — on a 1000-chapter novel with hours of generated audio that is a destructive act nobody asked for, and re-voicing costs far more than the rewrite did.
- **Deferred:** an opt-in *"Xoá audio của những chương được viết lại (để tạo lại)"* checkbox. It needs a new `clear_audio(indices=...)` overload; it is a clean follow-up and should not gate this feature.

### 2.12 Find-and-replace and the raw columns

`translated_raw` / `translated_title_raw` are **not** added to `EDITABLE_COLUMNS` (`project.py:41`) or `find_replace.ALL_FIELDS` (`find_replace.py:23-28`). Find-and-replace operates on what the user can see; a hidden backup silently mutated by a bulk replace is a worse surprise than a stale one.

Consequence, documented in the undo confirm dialog: **undo restores the text as it was at the moment of the rewrite** — later manual edits and later find-and-replace results on `translated` are lost. That is the honest meaning of "undo the rewrite" and no partial merge would be more predictable.

Nothing breaks by omission: `ALL_FIELDS` is a fixed tuple the dialog iterates, and `apply_replacements` validates against the whitelist (`project.py:605-607`).

- **a scripted summarising engine leaves `translated` byte-identical**, sets `status = error` with a reason, emits `chapter_error`, and the batch still reaches the next chapter — the single most important worker test;
- `dry_run=True` emits `preview_ready` and the DB is unchanged;
- `cancel()` before the second chapter stops after the first (the `_checkpoint` contract, `workers.py:72-77`);
- the project is closed on the failure path (extend `test_workers_adapter_close.py`).

## 5. What breaks if this is added naively

Each item is a concrete regression a straightforward implementation would ship.

1. **`clear_translations` (`project.py:872-880`) does not clear the new columns.** After "Dịch lại từ đầu" (`tab_translate.py:470-485`) every chapter would still carry a `translated_raw` from the *previous* translation — so the novel reads as fully rewritten (`is_rewritten` true everywhere), `pending_rewrite` returns nothing, and an undo would restore text belonging to a translation that no longer exists. **Must clear both.** Pinned by a test.
2. **`counts()` (`project.py:446-473`) has no rewritten count**, so the dialog cannot say how much is left and `_on_project_selected`'s status line (`tab_translate.py:281-292`) cannot report progress on an hours-long job.
3. **`_row_to_chapter` (`project.py:96-117`) reads by name**, so forgetting `_migrate` makes **every existing project fail to open**, not degrade. Both `_SCHEMA` and `_migrate` — `CREATE TABLE IF NOT EXISTS` (`project.py:44`) is a no-op on an existing DB.
4. **`tests/test_storage.py:262-291` DROPs a hard-coded column list**, so the migration is unpinned unless that list is extended — the test would keep passing while the migration silently rotted.
5. **`_translate_with_retry` is the wrong loop and must not be reused.** Three independent reasons: it calls `self.translate()` (`base.py:71`), which applies the *translation* system prompt and would try to translate Vietnamese into Vietnamese; its leftover-CJK heuristic (`base.py:83`) is meaningless for vi→vi and would make every first attempt succeed unconditionally; and `base.py:90-91` returns the least-dirty attempt rather than raising — for a rewrite that means **committing a truncated chapter over good text**, the exact failure the feature exists to prevent.
6. **Audio, subtitles and video silently desynchronise.** `pending_audio` (`project.py:402-438`) never compares text, so a chapter with existing audio is **not** re-pending after a rewrite: the mp3, the burned-in subtitles (features 041/042) and the exported ebook (`exporters/base.py:62-64`, which reads `chapter.translated`) drift apart with no signal anywhere. §2.11 handles this with a warning; a naive implementation gives no warning at all. **This is the least obvious and most user-visible breakage in the list.**
7. **A failed rewrite that writes anything is a data-loss bug.** The only correct action is `mark_error` (`project.py:614-619`) and move on. `save_rewrite` must never be reached on the failure path — hence §2.5's structure, where validation raises rather than returning a degraded string.
8. **Undo loses post-rewrite manual edits.** `edit_translation` (`project.py:502-523`) and find-and-replace both write `translated` without touching `translated_raw` (§2.12). Correct, but it **must** be stated in the undo confirm dialog or it is a surprise.
9. **Two workers, one tab.** `tab_translate.py`'s `_cancel` (`:515`), `_reset_buttons` (`:546`), `has_running_workers` (`:561`) and `shutdown` (`:566`) all assume a single `self._worker`. A second worker added without touching all four leaves a running QThread unjoined at quit — and `shutdown` is what stops the app abandoning a live thread (`tab_translate.py:569-571`).
10. **`save_translation` must not be reused for the rewrite.** It writes `target_lang`, `translator` and `translate_seconds` (`project.py:485-500`); doing so would relabel every rewritten chapter's engine and, if `target_lang` were ever written differently, re-flag the chapter in `pending_translation` (`project.py:392-399`) and queue the whole novel for re-translation.
11. **Chunk size.** Sending a whole 12000-char Vietnamese chapter to Claude with `max_tokens=8192` (`claude.py:63`) risks a truncated reply — which looks exactly like a summarisation to the validator and burns three attempts before failing. §2.4's cap is the fix.
12. **A system prompt passed to the CLI agent.** `CliAgentTranslator.complete` (`cli_agent.py:94`) takes no `system` kwarg; calling `complete(prompt, system=…)` uniformly raises `TypeError` at runtime on the engine most users will select — and only there, so it would pass every Claude/LM Studio test.

## 6. Risks and open questions

1. **Does the CLI agent actually do this task well?** *(Inferring.)* `cli_agent.py:29-30` establishes that coding-agent CLIs accept task framing and refuse role redefinition, but that was learned for *translation*. A monolingual Vietnamese style rewrite is a different ask, and an agent CLI may over-edit (a coding assistant's instinct is to improve). **Mitigation:** build the preview flow (§2.8.6) in the same step as the worker and measure on ten real chapters before running a novel. This is the first thing to do after Step 7.
2. **The length-ratio constants are estimates.** *(Inferring.)* `MIN_LENGTH_RATIO = 0.60` is derived from one example sentence measuring 0.75 plus headroom for duplicate removal. Too tight ⇒ good rewrites rejected and money burned on retries; too loose ⇒ a partial chapter slips through. **Mitigation:** paragraph-count equality is the real guard and is exact; the ratio is a backstop. Log the observed ratio per chunk during preview runs and tune the constant once, from data.
3. **Proper-noun extraction false positives.** A run of two capitalised words that is not a name (a title in quotes, a transliterated foreign term) would become a hard constraint. **Mitigation:** the sentence-initial trim plus the ≥2-token floor makes this rare in Vietnamese prose; and the constraint is only *presence*, which a faithful rewrite satisfies anyway. If it proves noisy, gate on names recurring ≥2× in the chunk — a one-line change with the extractor already isolated.
4. **Cost on a 1000-chapter novel is real.** ~3000 characters per request × several chunks per chapter. The dialog's estimate (§2.8.7) and the range selector are the controls; nothing here estimates money, only requests and wall-clock.
5. **Pause granularity.** `PausableWorker` holds between *chapters* (`workers.py:40-44`), so pausing mid-chapter waits for the in-flight chunk — up to the CLI agent's 360 s timeout (`cli_agent.py:70`). Acceptable and consistent with every other batch in the app, but the tooltip should say so; `PauseButton.set_extra_hint` (`widgets.py:742-745`) exists for exactly this.
6. **Idempotence of a re-rewrite.** Rewriting an already-rewritten chapter rewrites the *rewritten* text, not the original, and each pass drifts further from the source. `translated_raw` is preserved (§2.1) so the way back exists, but the dialog's "Tất cả chương trong khoảng" mode should say plainly that it re-processes already-rewritten chapters, and the undo-then-rewrite path should be the recommended way to change engines.
7. **`reset_errors` cosmetics.** After a batch with failures, `reset_errors` (`project.py:882-891`) sets a translated chapter's status to `downloaded` ("Đã tải"). Pre-existing, harmless (nothing re-queues off `status`), but it will look odd next to a `✍️` marker and is worth a follow-up.
