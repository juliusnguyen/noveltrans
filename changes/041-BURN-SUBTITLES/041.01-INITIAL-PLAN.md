# 041 — Burn narration subtitles, optionally — PLAN

## Design decisions

| Decision | Rationale |
| --- | --- |
| **Reuses 040's cues; no second timing path.** | `part_cues(segments)` is factored out of `part_srt` and feeds both. Two independently-derived timings for the same words is the kind of duplication that goes wrong quietly — the burned line and the `.srt` line drifting apart would be near-impossible to notice and infuriating to debug. |
| **Bottom-centre, ASS Alignment 2, `MarginV ≈ 6 %` of height.** | Everything below 75 % of the frame is empty gradient. Bottom-centre is also where every viewer already looks for subtitles. Growing upward from 6 % gives roughly three lines of clearance before the 72 % progress track. |
| **Side margins of 8 % each**, so lines wrap at ~84 % of the width. | Full-bleed text is hard to read and would run past the photo's edge on the left. |
| **Font ≈ 4.2 % of height (45 px at 1080p), white with a heavy outline and a shadow.** | Standard subtitle proportion. The heavy outline is not decoration: these sit over a pastel gradient whose lightness varies with the user's chosen background colour, so the text cannot rely on the backdrop being dark. |
| **The setting is persisted in config, and off by default.** | It changes what every future render looks like; a per-run toggle that silently resets would produce an inconsistent series. Off by default because it is a deliberate stylistic choice and the existing look is what users have already published. |
| **On + no cues = the video renders normally, and the status line says so.** | Legacy audio has no cues. Failing the render would be absurd; silently producing a video without the subtitles the user asked for would be worse. |
| **The title block is untouched.** | It is the player-skin identity. Narration is a separate layer with a separate style. |

## Implementation

### 1. `tts/subtitles.py`

Factor `part_cues(segments) -> tuple[list[Cue], int, int]` out of `part_srt`, which becomes
a thin wrapper over it. One traversal, one definition of "where does this chapter start".

### 2. `tts/video.py`

- `_ASS_STYLES` gains a `Sub` style (Alignment 2, the margins/size above).
- `build_ass_subtitles(..., narration=None)` appends one Dialogue per cue, `_escape_ass`d,
  when narration cues are given. Default `None` → byte-identical to today's output.
- `render_video(..., burn_subtitles=False)` pulls `part_cues(segments)` and passes them.
  Note `_with_real_durations` has already run, so the burned timings and the `.srt`
  timings come from the same corrected segments.

### 3. `config.py`, `gui/workers.py`, `gui/tab_video.py`

`video_burn_subtitles` bool; a "Chèn phụ đề vào video" checkbox in the Xuất video box with
a tooltip stating the cost (+~25 % file size) and that it is permanent; threaded through
`VideoWorker`.

## Test plan

`tests/test_video.py` / `tests/test_subtitles.py`:

- `narration=None` produces byte-identical ASS to before — the no-surprise guarantee.
- Narration cues become Dialogue lines with the `Sub` style, timed to the cue.
- Cue text is escaped: `{`/`}` neutralised, newlines → `\N`.
- The `Sub` style is bottom-anchored (Alignment 2) and its MarginV clears the progress
  track — asserted against `PlayerLayout`, not a hard-coded number.
- `part_cues` and `part_srt` agree: same count, same first/last timings.
- A part with no cues renders with the title block only.

`tests/test_tab_video.py`: the checkbox round-trips through config and reaches `VideoWorker`.

## Risks

1. A long cue (a chunk `merge_short_chunks` built from several sentences) can wrap to three
   or four lines and climb toward the progress track. Bounded by the wrap width; noted, not
   solved — the fix would be re-splitting chunks, which changes 040's timing contract.
2. Burned text is permanent: a typo means a re-render and a re-upload. That is the trade the
   option exists to let the user make deliberately, which is why it is off by default and
   the tooltip says so.
