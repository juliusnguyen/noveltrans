### `tts/subtitles.py`

`part_cues(segments)` factored out of `part_srt`, which becomes a thin wrapper over it.
**One definition of where a chapter starts inside a part**, shared by the sidecar and the
burned layer. Two independently-derived timings for the same words would be free to drift
apart, and a burned line disagreeing with the `.srt` line is near-impossible to notice and
miserable to debug.

### `tts/video.py`

- A `Sub` style: ASS Alignment 2 (bottom-centre), font ≈ 4.2 % of height, side margins 8 %,
  `MarginV` 6 %, white with a heavy outline and a shadow. Unlike the title block it does
  **not** adapt to `bg_color`: it spans the full width and crosses whatever the user's
  gradient happens to be doing there, so it cannot assume a backdrop lightness.
- `build_ass_subtitles(..., narration=None)` appends one Dialogue per cue. `None` — the
  default — is byte-identical to pre-041 output, asserted, so the option cannot change a
  video nobody asked to change.
- `sub_font_px()` / `sub_margin_v()` are module-level so the tests assert clearance
  against `PlayerLayout` at multiple resolutions rather than pinning 1080p numbers.
- `render_video(..., burn_subtitles=False)`.

### Verified by rendering, not only by assertion

Composed a real 1080p frame through ffmpeg + libass with the user's dark background:

```
Style: Sub,Noto Sans,45,&H00FFFFFF,...,1,4,2,2,154,154,65,1
                     ^size            ^outline ^align=2 ^L/R=154 ^V=65
```

The narration lands at y≈990 on a 1080-tall frame: below the photo (ends y≈710) and below
the progress track (y≈780), with the "now playing" block untouched at y≈490. Geometry
assertions alone would not have caught a style-field ordering mistake — the ASS `Style:`
line has 23 positional fields and getting Alignment in the wrong slot silently moves the
text somewhere else entirely.

(The chapter title is absent from that frame only because it was grabbed at t=0 and the
title carries a `\fad(400,400)` fade-in.)

### Known limits

- **A cue is a chunk**, which `merge_short_chunks` may have built from several sentences,
  so some lines run long. Bounded by the 84 %-width wrap; the fix would be re-splitting
  chunks, which would change 040's timing contract.
- **Burned text is permanent**: a typo costs a re-render and a re-upload. That is the trade
  the option exists to let the user make deliberately — hence off by default, and the
  tooltip says so.
- **Only audio voiced since 040 has cues**, so ticking the box does nothing for older
  parts. The render's status line already reports subtitle coverage (040).

## [FIX] Cues were never written for anyone using >1 TTS worker — 2026-07-29

Reported: re-voiced a chapter, re-rendered the video, no `.srt`. Checked the library —
**zero `.cues.json` files anywhere**, so the capture had never run once.

### Cause

`AudioWorker` has **two** `synthesize_chapter` call sites:

```python
if self.workers == 1:
    self._run_sequential(...)   # <- 040 wired this one
else:
    self._run_parallel(...)     # <- ...and not this one, via _synth_one
```

The user's setting is `tts_workers: 3`, so every chapter they have ever voiced took the
unwired path. Fixed by mirroring the sequential path inside `_synth_one` — cues are written
there on the pool thread, since each chapter owns a distinct file path and the orchestrator
has no business carrying subtitle data it never reads. `_drop_cues` added to the parallel
commit block too, so a re-voice invalidates stale cues on both paths.

### Why the tests didn't catch it

040 tested `_write_cues` in isolation and `synthesize_chapter`'s cue arithmetic. Both
passed, and both were about the *pieces*. Nothing asserted that anything **calls** the
helper — so a whole synthesis path could exist without it and every test stayed green.

Added `TestBothSynthesisPathsWriteCues`, including a structural guard:

```python
calls = src.count("engine.synthesize_chapter(")
wired = src.count("cues_out=cues")
assert calls == wired
```

A third synthesis path added later fails that assertion instead of silently shipping
videos without subtitles.

### The compounding factor

`_write_cues` swallows every exception (`except Exception: pass`) so a subtitle sidecar can
never cost someone their rendered audio. That is still the right call, but combined with a
missing *call site* it meant the feature failed in total silence: no error, no log, just an
absent file. The render's coverage line ("Phụ đề: N/M") is the only surface that would have
said anything — and it only appears after a render, long after the audio was made.

### Still outstanding, and worth doing before the user re-voices anything

The `.srt` is written by `render_video`, so producing one for an already-rendered part
means a full re-render — ~26 min and ~250 MB per part for a 40 KB text file. A "Tạo phụ đề"
button that writes sidecars from existing cues without touching ffmpeg belongs in 040 and
isn't there.
