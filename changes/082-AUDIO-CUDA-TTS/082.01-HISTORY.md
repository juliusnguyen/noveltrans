## [PLAN] 082.01-AUDIO-CUDA-TTS-PLAN — 2026-09-06
Re-verified the current code state directly rather than trusting the
original combined plan verbatim (081's work and the merged
080-VIENEU-3.4-UPGRADE PR both touched the TTS stack since that plan was
written).

Correction found: the original plan claimed no `vieneu` version bump was
needed for a `[cuda]` extra. Downloaded and inspected wheel METADATA for
vieneu 3.4.0/3.5.0/3.6.0/3.6.1/3.6.2/3.6.3 directly — the `cuda` extra
(bundling `torch`/`transformers`/`safetensors`) first appears in **3.6.1**;
the installed dev venv has 3.4.0, which lacks it (though the underlying
`device`/`backend` constructor params already exist in 3.4.0's
`V3TurboVieNeuTTS`, confirmed via `inspect.getsource`). `pyproject.toml`'s
new `tts-gpu` extra will specify `vieneu[cuda]>=3.6.1`.

`torch` is not installed in this dev venv; genuine GPU-audio verification
(not just static code reading) requires installing it here and running a
real synthesis — planned as an explicit Phase 7 manual-verification step
before considering the feature done.

Plan recommends proceeding: v1 stays source-install only (no frozen `.exe`
packaging), workers hard-clamped to 1 on GPU in the worker itself (not just
the UI), and CPU behavior stays byte-for-byte unchanged (`device="cpu"`
resolves to the same ONNX branch `vieneu` already takes today).

## [IMPLEMENTATION] CUDA audio device toggle — 2026-09-06
Implemented per the plan:
- `pyproject.toml`: new `tts-gpu = ["vieneu[cuda]>=3.6.1"]` extra.
- `src/noveltrans/tts/gpu.py` (new): `cuda_available()` / `cuda_device_name()`,
  guarded `import torch` so a CPU-only install just reads as no-GPU.
- `src/noveltrans/tts/vieneu.py`: `VieneuEngine` gained `device: str = "cpu"`,
  threaded into `Vieneu(precision=..., device=...)`.
- `src/noveltrans/tts/__init__.py`: `get_tts_engine(..., device="cpu")`.
- `src/noveltrans/config.py`: `tts_device` property (`cpu`/`cuda`, validated).
- `src/noveltrans/gui/settings_dialog.py`: new "Chạy TTS bằng:" combo next to
  the precision combo, GPU item disabled with a tooltip when
  `cuda_available()` is False; selecting GPU clamps+disables the workers
  spinbox live (authoritative clamp is in the worker, this is just the UI
  reflection).
- `src/noveltrans/gui/workers.py`: `AudioWorker` gained `device`, hard-clamps
  `self.workers = 1` whenever `device == "cuda"` regardless of the requested
  count, passed through both `get_tts_engine(...)` call sites (probe +
  per-pool-thread).
- `src/noveltrans/gui/tab_audio.py`: wired `device=self.config.tts_device`.

**Verified for real, not just mocked** (see plan's Phase 7 for full detail):
installed `torch` via `uv pip install -e '.[tts-gpu]'` — this actually
resolved a **CPU-only** `torch==2.14.0+cpu` wheel (118 MiB), correcting the
plan's assumption that Windows' default PyPI wheel is CUDA-enabled. Had to
explicitly install from PyTorch's CUDA index
(`uv pip install torch --index-url https://download.pytorch.org/whl/cu128`,
2.6 GiB) to get a real `torch==2.11.0+cu128` with `torch.cuda.is_available()
== True` on this machine's RTX 3060 Ti. Documented this two-step install in
`pyproject.toml`'s `tts-gpu` comment, the Settings tooltip, and a new "GPU
(NVIDIA CUDA)" section in README.md.

With the real CUDA build installed: ran actual `VieneuEngine(device="cuda")`
synthesis (confirmed via engine logs it took the `backend=pytorch` path, vs
`backend=onnx` for `device="cpu"`) — produced valid, non-degenerate audio
(duration/RMS/peak/silence-fraction all close to the CPU baseline for the
same sentence, no sign of the short-chunk "babble" runaway 027/028
investigated). Confirmed the worker clamp for real
(`AudioWorker(device="cuda", workers=6).workers == 1`). Re-ran the full test
suite with the real CUDA-enabled torch present (not just mocked): 3221
passed, 4 skipped, no regressions.

Also launched the actual app (`python -m noveltrans`) and screenshotted the
real Settings dialog with the CUDA build installed: "Chạy TTS bằng:" combo
renders correctly under "Chất lượng giọng:", both CPU and GPU items show
enabled (real detection, not a mock), and selecting GPU visibly grays out
and clamps "Luồng tạo audio song song" to 1 live in the running UI.

Residual, explicitly not closed: nobody has *listened* to the GPU output to
judge perceptual Vietnamese speech quality — only objective audio stats were
compared. Flagged as a pre-default-switch follow-up, not a blocker.

Added tests: `tests/test_tts_gpu.py` (new), `tests/test_tts.py`
(`TestAudioWorkerDevice`, device-threading cases in `TestVieneuEngine`,
`tts_device` config validation), `tests/test_settings_dialog.py` (device
