# Plan: 082-AUDIO-CUDA-TTS — GPU (CUDA) audio via VieNeu-TTS on Windows

Second half of the original combined GPU investigation (`changes/081-VIDEO-NVENC`
shipped the video/NVENC half first, lower risk). This plan re-verifies the
current code state directly (rather than trusting the original combined plan's
notes verbatim) since `081`'s work and the merged `080-VIENEU-3.4-UPGRADE` PR
both touched the TTS stack in between.

## Summary

VieNeu-TTS runs CPU-only (ONNX) today. The upstream `vieneu` package already
has a CUDA/PyTorch code path (`device`/`backend` params on its v3-Turbo
engine), unused here. This adds an opt-in GPU device setting: a `tts-gpu`
extra, a `cuda_available()` probe, `device` threaded through the engine and
worker, a Settings toggle, and a hard clamp of parallel workers to 1 on GPU
(a consumer 8GB card cannot hold N independent model copies). Source-install
only for v1 — the frozen `.exe` + `torch` packaging risk is out of scope.

### Upstream `vieneu` — re-verified directly (not assumed from the 027/081 notes)

- Installed in this dev venv: **3.4.0**. `Vieneu(mode="v3turbo", **kwargs)` is
  a factory (`vieneu/__init__.py`) that constructs `V3TurboVieNeuTTS`, whose
  `__init__` (`vieneu/v3turbo.py`) already has `device: str = "auto"`,
  `backend: str = "auto"` **in 3.4.0** — confirmed by direct
  `inspect.getsource`. Resolution logic:
  ```
  if device in (None, "auto"):
      dev_type = "cuda" if torch.cuda.is_available() else "cpu"   # guarded import
  else:
      dev_type = "cuda" if "cuda" in str(device).lower() else str(device).lower()
  use_onnx = backend == "onnx" or (backend == "auto" and dev_type == "cpu")
  ```
  Passing `device="cuda"` explicitly with `backend="auto"` (the default) makes
  `use_onnx` False regardless of `torch.cuda.is_available()` at construction
  time — it goes straight to the PyTorch path and lets `torch`/the driver
  raise its own error if CUDA truly isn't there. This repo's own capability
  check should be the gate (see Phase 1), not this internal fallback.
- **Correction to the original combined plan**: it claimed "no version bump
  needed" for a `vieneu[cuda]` extra. That extra's *packaging metadata*
  (`Provides-Extra: cuda` → `torch`, `transformers`, `safetensors`) does
  **not exist on 3.4.0** (only `legacy`/`pdf`/`watermark`) — checked by
  downloading and inspecting wheel METADATA for 3.4.0, 3.5.0, 3.6.0, 3.6.1,
  3.6.2, 3.6.3 directly. **The `cuda` extra first appears in 3.6.1.** The
  underlying `device`/`backend` code path has existed since at least 3.4.0
  (both work fine standalone if `torch` is present some other way), but the
  convenient `pip install vieneu[cuda]` bundling needs `vieneu>=3.6.1`.
- `torch` is **not installed** in this dev venv today; `torch.cuda.is_available()`
  cannot be checked here without installing it. The GPU hardware itself was
  independently confirmed in 081 (`nvidia-smi`: RTX 3060 Ti, driver 610.88) —
  installing `torch` here to smoke-test the CUDA path is a deliberate,
  reversible step this feature should actually take (see Phase 4), not just
  reason about statically.

## Phase 1: `pyproject.toml` — the `tts-gpu` extra

```toml
tts-gpu = [
    "vieneu[cuda]>=3.6.1",  # PyTorch+CUDA path for VieNeu-TTS v3 Turbo on NVIDIA GPUs.
                             # Needs >=3.6.1: earlier vieneu releases (incl. the >=3.4
                             # floor of the base `tts` extra) have the device="cuda" code
                             # path but no formal `cuda` extra to pull torch/transformers/
                             # safetensors. Installing this extra upgrades the resolved
                             # `vieneu` version project-wide (pip resolves one version
                             # satisfying every requested extra) -- expected, not a bug.
]
```
Kept separate from `tts` (multi-GB `torch` download, opt-in only, matches
027's and 081's precedent).

## Phase 2: `cuda_available()` probe

New `src/noveltrans/tts/gpu.py`:
```python
def cuda_available() -> bool:
    try:
        import torch
    except ImportError:
        return False
    try:
        return bool(torch.cuda.is_available())
    except Exception:
        return False

def cuda_device_name() -> str:
    """Best-effort GPU name for a Settings tooltip; "" if unavailable."""
    if not cuda_available():
        return ""
    try:
        import torch
        return torch.cuda.get_device_name(0)
    except Exception:
        return ""
```
No caching (unlike 081's `nvenc_available()`, which shells out to a
subprocess): `torch.cuda.is_available()` is a fast in-process check once
`torch` is imported, and `import torch` itself is already cached by Python's
module system after the first call.

## Phase 3: thread `device` through the engine and registry

1. **`vieneu.py`**: `VieneuEngine.__init__` gains `device: str = "cpu"`.
   `load()` becomes:
   ```python
   try:
       self._tts = Vieneu(precision=self.precision, device=self.device)
   except Exception as exc:
       raise TtsError(f"Không khởi tạo được VieNeu-TTS: {exc}") from exc
   ```
   When `device == "cpu"` (the default), this is `Vieneu(precision=..., device="cpu")`
   — `dev_type` resolves to `"cpu"` and `use_onnx` is True regardless of
   `backend`, i.e. **byte-for-byte the same ONNX path as today** (verified
   against the source above; passing `device="cpu"` explicitly rather than
   omitting it changes nothing about which branch is taken). When `"cuda"`,
   the exception handler already in place turns any CUDA init failure (no
   driver, OOM, `torch` missing despite the setting) into a `TtsError` with
   the real message — no new fallback-to-CPU logic needed at this layer,
   because the exception already surfaces cleanly and the *worker* layer
   (Phase 5) decides what to do with a failed device.
2. **`tts/__init__.py`**: `get_tts_engine(..., device: str = "cpu")`, passed
   through to `VieneuEngine(...)`.

## Phase 4: `config.py` + Settings UI

1. `DEFAULT_TTS_DEVICE = "cpu"`, `TTS_DEVICES = ("cpu", "cuda")` module
   constants (next to `DEFAULT_TTS_PRECISION`/`TTS_PRECISIONS`).
2. `tts_device` property/setter mirroring `tts_precision` exactly (validated,
   falls back to `"cpu"` on an unknown stored value).
3. `settings_dialog.py`: new `tts_device_combo` next to `tts_precision_combo`
   (lines 466-477), items "CPU (mặc định)" / "GPU (NVIDIA CUDA)", GPU item
   disabled with a tooltip when `cuda_available()` is False — same pattern as
   081's `video_encoder` combo (`gui/tab_video.py`, gated on
   `nvenc_available()`). Tooltip on GPU-unavailable should name the extra:
   `pip install -e '.[tts-gpu]'` needs a real NVIDIA GPU + driver.
4. **Clamp `tts_workers_spin` when GPU is selected**: connect
   `tts_device_combo.currentIndexChanged` to disable/greying
   `tts_workers_spin` (set it to 1, disable it) when the selected device is
   `"cuda"`, re-enable it when back to `"cpu"`. This is a UI-level nudge; the
   authoritative clamp is in the worker (Phase 5), so a stale saved
   `tts_workers=6` from a previous CPU session can never actually spawn 6 GPU
   engines even if the UI is somehow bypassed.
5. `accept()`: `self.config.tts_device = self.tts_device_combo.currentData()`.

## Phase 5: `workers.py` + `tab_audio.py`

1. `AudioWorker.__init__` gains `device: str = "cpu"`. Immediately clamp:
   ```python
   self.device = device
   self.workers = 1 if device == "cuda" else max(1, int(workers))
   ```
   This is the authoritative guard from 027's recommendation — no matter what
   `tts_workers` the caller passes, GPU never gets more than one engine.
2. Both `get_tts_engine(...)` call sites (the `run()` probe at ~945-951, and
   `_engine_for_thread`'s pool-thread build at ~1085-1091) pass
   `device=self.device`. Since `self.workers` is clamped to 1 for GPU,
   `_run_parallel`/`_engine_for_thread` never actually builds more than the
   one probe engine in practice for `device="cuda"` — but passing it through
   both call sites keeps the code correct rather than accidentally-correct.
3. `tab_audio.py:605-620`: `device=self.config.tts_device` added to the
   `AudioWorker(...)` call.

## Phase 6: packaging — explicitly out of scope for v1

No `packaging/*.spec` change. `torch`'s CUDA runtime DLLs are a large,
unverified PyInstaller surface (per 081's plan notes) — v1 ships GPU TTS as
source-install only (`pip install -e '.[tts-gpu]'`). Document this in the
Settings tooltip and in the PR description; revisit only if there's real
user demand once the opt-in path has been used.

## Phase 7: manual verification — DONE, ran for real on this machine

Static reasoning about `vieneu`'s source is not the same as it working. Ran
for real rather than just reasoning about it:

1. **`pip install torch` did NOT give CUDA — corrected assumption.** Installed
   `uv pip install -e '.[tts-gpu]'`: this resolved and installed
   **`torch==2.14.0+cpu`** (118 MiB) — a CPU-only wheel, confirmed via
   `torch.version.cuda is None` and `torch.cuda.is_available() == False`. The
   original plan assumed "the default PyPI wheel on Windows is CUDA-enabled
   unlike macOS" — **this is wrong**, at least for this torch release; PyPI's
   default index serves CPU-only wheels on Windows too. Getting the real CUDA
   build needed a second, explicit step:
   ```
   uv pip install torch --index-url https://download.pytorch.org/whl/cu128 --reinstall-package torch
   ```
   This downloaded a 2.6 GiB `torch==2.11.0+cu128` (note: an *older* torch
   minor than the CPU default — the CUDA index doesn't always track the same
   latest version) and replaced the CPU wheel. `pyproject.toml`'s `tts-gpu`
   comment, the Settings tooltip, and README.md were all updated to document
   this two-step install; a single `pip install -e '.[tts-gpu]'` alone will
   silently leave the user on CPU-only torch with no error, just a disabled
   GPU option in Settings.
2. **`cuda_available()` / `cuda_device_name()` confirmed real**, after the
   CUDA-build install: `True` / `"NVIDIA GeForce RTX 3060 Ti"`.
3. **Ran real synthesis, both devices, same sentence**, via `VieneuEngine`
   directly (not mocked):
   - `device="cpu"`: engine log confirms `backend=onnx`, loads the ONNX int8
     graph (already cached from prior use) — 4.08s of audio for the test
     sentence, RMS 0.103, peak 0.51, ~12% silence fraction.
   - `device="cuda"`: engine log confirms `backend=pytorch`, loads the
     PyTorch checkpoint (87.5s one-time HuggingFace download of the
     PyTorch-format weights + MOSS audio tokenizer, separate from the ONNX
     graph) — 4.00s of audio for the same sentence, RMS 0.107, peak 0.59,
     ~14% silence fraction, synthesis itself took ~4.0s (i.e. roughly
     realtime on this GPU for a short sentence).
   - Both outputs are close in duration/RMS/peak/silence-fraction — no sign
     of the short-chunk "babble" runaway 027/028 investigated (which would
     show as a duration wildly longer than the text implies). This is
     objective-but-not-perceptual verification: nobody has *listened* to
     confirm the Vietnamese actually sounds right on the PyTorch path —
     flagged below as a residual risk, not fully closed.
4. **Worker clamp confirmed** against the real install:
   `AudioWorker(..., device="cuda", workers=6).workers == 1`;
   `device="cpu"` leaves `workers=6` untouched.
5. Full test suite re-run with the real CUDA-enabled `torch` present in the
   venv (not just mocked): 3221 passed, 4 skipped — no regressions from
   having a real GPU detected during the run.

## Open questions / risks

- **Audio quality/correctness parity, perceptually** — the objective stats in
  Phase 7 (duration/RMS/peak/silence-fraction) are close between CPU and GPU
  and show no runaway-babble signature, but nobody has *listened* to the GPU
  output to confirm it's correct, clear Vietnamese speech. Recommend a human
  listening pass before ever defaulting anyone onto GPU.
- **`torch` install size/time** on first opt-in — confirmed for real: 118 MiB
  for the (useless, CPU-only) default install, then a further **2.6 GiB**
  download for the actual CUDA build, ~4.5 minutes on this connection. No
  progress UI in the app for this — it happens entirely outside NovelTrans,
  via the two `uv pip install` commands in README.md. Acceptable for a
  source-install-only v1 aimed at technical users, but a real cost, not a
  hypothetical one.
- **No `resemble-perth` regression repeat**: 080-VIENEU-3.4-UPGRADE's own
  fix commit title ("drop the wrong perth") suggests upstream dependency
  churn has bitten this project before. Checked here: `vieneu[cuda]>=3.6.1`'s
  transitive deps (`torch`, `transformers`, `safetensors`) installed and
  resolved cleanly on this Windows machine with no conflicts.

## Recommendation

Proceed — and this is no longer a theoretical recommendation. The riskiest
unknown from the original combined plan (packaging a frozen `.exe` with
`torch`) is explicitly deferred out of v1. The audio path was verified
end-to-end on real hardware in this session: GPU synthesis runs, uses the
correct backend, produces non-degenerate audio comparable to the CPU
baseline, and the worker/UI clamps hold up against the real install — not
just against mocks. The one thing still open is a human listening pass for
perceptual quality, which is a "nice to do before shipping to end users,"
not a blocker for the code itself.
