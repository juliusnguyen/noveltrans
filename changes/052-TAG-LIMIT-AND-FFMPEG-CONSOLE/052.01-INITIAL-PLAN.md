# 052 — Tag Limit and FFmpeg Console Fix: Implementation Plan

Two unrelated bug fixes bundled under one feature slug. They touch disjoint files and can be
implemented, tested, and committed independently, in either order.

## Part A — Enforce the 500-char tag cap at every point tags are persisted/used

**Root cause.** `src/noveltrans/tts/tags.py` already defines `YOUTUBE_TAG_CHAR_LIMIT = 500` and
`parse_tags(raw, *, max_total_chars=YOUTUBE_TAG_CHAR_LIMIT)` correctly implements YouTube's real
budget (tag length + 2 if it contains a space, running total capped at 500). It's correctly
applied in two places already:

- `src/noveltrans/gui/workers.py` `TagsWorker.run` (~line 429): LLM-generated tags go through
  `format_tags(parse_tags(raw))`.
- `src/noveltrans/gui/tab_video.py` `_save_tags` (~line 1636): re-caps whenever the user clicks
  "Lưu tags" (Save).

**The gap — two real bypasses:**

1. `Project.save_tags(tags)` (`src/noveltrans/storage/project.py` ~line 610-618) stores whatever
   string it's given verbatim (`self.meta.tags = tags`). It trusts every caller to have already
   capped — an invariant enforced by caller discipline, not by the method itself.
2. `_launch_video` (`src/noveltrans/gui/tab_video.py`, tags read at ~line 1978:
   `tags = self.tags_edit.toPlainText().strip()`) reads the raw textbox with **no** `parse_tags`
   call. That raw string flows into `VideoWorker(..., tags=tags)` →
   `VideoWorker._write_metadata` (`src/noveltrans/gui/workers.py` ~line 1197-1198), which writes
   it verbatim to the `.tags.txt` sidecar, which `src/noveltrans/youtube_upload.py` (~line
   1311-1318) later types into YouTube's tag field verbatim. If a user pastes/edits tags and
   clicks "Tạo video" without first clicking "Lưu tags", nothing caps them before they reach the
   sidecar/upload.

**Fix — two changes, defense-in-depth (neither alone covers every path):**

1. **`src/noveltrans/storage/project.py`, `save_tags`** — cap centrally so it's impossible to
   persist an over-budget string into `meta.json` through any caller, present or future:
   ```python
   def save_tags(self, tags: str) -> None:
       from noveltrans.tts.tags import format_tags, parse_tags
       tags = format_tags(parse_tags(tags))
       self.meta.tags = tags
       ...
   ```
   Local import inside the method, matching this file's existing style and avoiding any
   `storage` ↔ `tts` import-cycle risk. `parse_tags` is idempotent, so this makes the existing
   `parse_tags` calls in `TagsWorker.run`/`_save_tags` redundant but harmless — leave them as-is
   to keep this diff minimal.

2. **`src/noveltrans/gui/workers.py`, `VideoWorker._write_metadata`** (~line 1197-1198) — cap
   right before the sidecar write, the actual point of use:
   ```python
   if self.tags.strip():
       from noveltrans.tts.tags import format_tags, parse_tags
       capped = format_tags(parse_tags(self.tags))
       if capped:
           sidecar(".tags.txt").write_text(capped + "\n", encoding="utf-8")
   ```
   Local import, consistent with how `workers.py` already imports `noveltrans.tts.tags` locally
   in `TagsWorker.run`.

   Do **not** additionally patch `_launch_video` in `tab_video.py` — capping at
   `_write_metadata` already closes the gap for the actual file write; a third redundant copy at
   the GUI layer adds no correctness.

**Do not touch:** `tags.py`'s `parse_tags`/`format_tags`/`YOUTUBE_TAG_CHAR_LIMIT` (already
correct, the single source of truth), `TagsWorker.run` and `_save_tags` (already correct).

## Part B — Suppress ffmpeg/ffprobe console-window flicker on Windows

**Root cause.** `packaging/NovelTrans-windows.spec` builds with `console=False`. Every
`ffmpeg.exe`/`ffprobe.exe` child (console-subsystem binaries) spawned via `subprocess` gets
Windows allocating it a fresh console window, since no spawn call anywhere in the codebase
passes a window-hiding flag (confirmed via repo-wide grep — zero hits for
`CREATE_NO_WINDOW`/`STARTUPINFO`/`windowsHide`). Most visible as rapid on/off flicker in tight
per-item loops (duration probing per segment, chapter-by-chapter decode).

Note: on CPython, `subprocess.CREATE_NO_WINDOW` is only imported from `_winapi` inside
`subprocess.py`'s `if _mswindows:` block — the attribute does not exist on macOS/Linux. The
helper must gate attribute access behind `sys.platform == "win32"`, not just gate whether it's
applied, or the module fails to import on non-Windows platforms.

**1. New shared helper in `src/noveltrans/runtime_env.py`** (append after `ensure_std_streams`,
matching its docstring style — this module already frames itself around "gaps only visible once
launched a way a terminal never would," which is exactly this bug):

```python
def no_console_kwargs() -> dict:
    """Extra subprocess.run/Popen kwargs to stop a spawned console app flashing a window.

    A Windows build is frozen with `console=False` — the app itself has no console, but every
    ffmpeg/ffprobe child is a console-subsystem exe, so Windows allocates it a brand-new
    console window on every spawn. In a tight per-chapter/per-segment loop this reads as rapid
    on/off flicker. CREATE_NO_WINDOW tells CreateProcess not to allocate one at all.

    No-op ({}) on macOS/Linux, where the flag doesn't exist on the subprocess module at all.
    """
    if sys.platform == "win32":
        return {"creationflags": subprocess.CREATE_NO_WINDOW}
    return {}
```

Add `import subprocess` to `runtime_env.py`'s imports. Update the module docstring's opening
("Two unrelated gaps...") to "Three unrelated gaps..." and add a short paragraph in the same
voice describing the console-flicker gap.

**2. Thread `**no_console_kwargs()` into every ffmpeg/ffprobe spawn** — 8 call sites, all in
`src/noveltrans/tts/`. Each needs `from noveltrans.runtime_env import no_console_kwargs` added
to imports and `**no_console_kwargs()` added as a kwarg, preserving every existing kwarg
(capture_output, text, encoding, errors, timeout, stdout/stderr redirection) exactly as-is —
only add a kwarg, never reorder or replace one. Re-locate each by function/symbol name (line
numbers below are approximate/stale):

- `src/noveltrans/tts/convert.py`: `ffmpeg_has_encoder()` (~21), `convert_to_mp3()` (~38),
  `apply_tempo()` (~92) — all `subprocess.run`
- `src/noveltrans/tts/subtitles.py`: `detect_silences()` (~220) — `subprocess.run`
- `src/noveltrans/tts/video.py`: `_probe_duration()` (~128, `subprocess.run`, ffprobe, called
  per segment — likely the most visible flicker source), `_run_ffmpeg()` (~484,
  `subprocess.Popen`), `_concat_audio()` encoder Popen (~531) and per-chapter decoder Popen
  spawned in the `for path in paths:` loop (~559, one new window per chapter today — likely the
  other most visible flicker source)
- `src/noveltrans/tts/merge.py`: `merge_chapters()` (~182) — `subprocess.Popen`

**Explicitly out of scope** (flag to the user, don't silently expand): `src/noveltrans/
translators/cli_agent.py:109` also does `subprocess.run(cmd, capture_output=True, ...)` to
invoke CLI translation agents (`claude`, `agy`, etc.) and shares the identical console-flicker
root cause on Windows. The prompt names only ffmpeg — leave `cli_agent.py` untouched, but it's a
natural follow-up using the same `no_console_kwargs()` helper. `src/noveltrans/gui/
keep_awake.py`'s `subprocess.Popen` is macOS-only (`caffeinate`) — not reachable on Windows, no
change needed.

**Part B:**

  video render (duration probing + concat), (c) chapter merge.

## Sequencing / risk

- Part A and Part B touch entirely disjoint files — implement/test/commit independently, in
  either order, as two commits on this branch.
- Part A risk: low. `parse_tags` is idempotent, so double-capping (both `save_tags` and
  `_write_metadata`) is safe, not a bug.
- Part B risk: low, behavior-preserving. `creationflags=subprocess.CREATE_NO_WINDOW` only
  affects window allocation — `Popen.terminate()` (used by `video.py`/`merge.py`'s
  cancel/deadline handling) still calls `TerminateProcess` regardless of creation flags, so
  cancellation/timeout behavior is unaffected. Verify during implementation (not just assume)
  that `subprocess.CREATE_NO_WINDOW` is only referenced inside the `win32` branch so
  `runtime_env.py` still imports cleanly on macOS/Linux.
