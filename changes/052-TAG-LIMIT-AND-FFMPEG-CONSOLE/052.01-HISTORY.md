## [IMPLEMENT] 2026-08-03 — follow-up bugs found while testing the above

User reported three more issues while trying out the build: generated tags still exceeded 500
chars in practice, YouTube's "We're still checking your content" gate had to be confirmed by
hand during Publish, and adding a video to a Playlist during upload appeared to freeze then
silently skip. Investigated and fixed all three.

**Tag budget bug — the 500-char model itself was wrong, not just unenforced.**
`parse_tags`'s running budget only charged a multi-word tag +2 (modelling YouTube's per-tag API
quoting), but never charged anything for the ", " separators `format_tags` inserts between
tags — the literal string this app writes to `.tags.txt` and types into YouTube's tag box.
Confirmed via web search that YouTube's tag field counts every typed character, separators
included, toward the 500 cap. Enough tags (the LLM prompt asks for 18–25) let the separator
overhead alone push the joined string past 500 even though the old per-tag cost sum stayed
under budget.
- `src/noveltrans/tts/tags.py`: reworked `parse_tags`'s cost model so the running total always
  equals `len(format_tags(kept))` — each tag after the first costs its own length plus 2 for
  its separator, not +2 for containing a space. Removed the now-unused `_tag_cost` helper and
  rewrote the module/constant docstrings to describe the real YouTube behavior.
- Updated `tests/test_tags.py` (removed the old space-cost test, added tests for the
  separator-cost model and single-oversized-tag skipping) and
  `tests/test_video_metadata.py::test_save_tags_caps_to_youtube_budget` (now asserts
  `len(...) <= 500` directly instead of the old per-tag cost sum).

**YouTube "still checking your content" gate — `_finish` didn't know about it.**
This dialog (title: "We're still checking your content", buttons "Publish anyway" / "Go back")
gates the publish click itself when YouTube's automatic copyright/policy scan hasn't cleared —
distinct from `_CONFIRM_DIALOG_SEL`'s post-publish share/processing dialog. Unhandled, the
upload dialog just sat there until `_finish`'s wait loop timed out, which is what read as
needing manual confirmation.
- `src/noveltrans/youtube_upload.py`: added `_STILL_CHECKING_PUBLISH_ANYWAY_SEL` (a combined
  `:text()` selector, English + best-effort Vietnamese labels) and made `_finish`'s wait loop
  check for and click through it before checking for real confirmation.
- Added `tests/test_youtube_upload.py::TestFinishConfirmation::
  test_still_checking_content_dialog_is_dismissed_then_confirms` (extended `_FakeStudioPage`
  with a `still_checking` flag and `.last`/`is_visible` support).

**Playlist picker "freeze" — best-effort steps were silently eating up to ~30s each with no
feedback.** Confirmed with the user that only the upload/publish run stalls (the rest of the
app UI stays responsive), consistent with a browser-automation step timing out rather than a
GUI-thread block. `_set_playlist`'s several sequential lookups (trigger, search box, new-
playlist button, title box) each defaulted to the full 30s `_STEP_WAIT_MS` and swallowed

- `src/noveltrans/youtube_upload.py`: added `_PLAYLIST_STEP_WAIT_MS` (10s, vs. the general 30s)

- Added `tests/test_youtube_upload.py::TestSetPlaylistReportsFailures` (missing-trigger case
  reports via `on_progress`, and stays silent/non-raising when no callback is given). Updated

## [FIX] 2026-08-03 — tag budget model was still wrong (real evidence: 516/500)

The separator-based model above turned out to still be insufficient: the user generated tags
with the fixed code and YouTube Studio's own counter showed **516/500** — over budget again,
despite the app's model computing ≤500. The web-search-derived "every character counts,
including separators" claim from the previous fix wasn't the whole story either.

Rather than keep guessing at YouTube's undocumented internal counting algorithm from
indirect evidence, changed `parse_tags`'s cost model to charge every plausible contributor
at once, deliberately double-counting for safety margin: each tag's cost is now `len(tag) +
(2 if it contains a space) + (2 for the ", " separator before every tag but the first)` —
combining the original quote-bonus model AND the separator model from the previous fix,
instead of picking one. This guarantees the kept list stays under YouTube's real cap
regardless of which contributor(s) actually apply, at the cost of keeping a few fewer tags
than a less conservative model would.

- `src/noveltrans/tts/tags.py`: `parse_tags`'s cost line now sums all three terms; rewrote
  the module docstring to document the 516/500 evidence and why the model deliberately
  over-charges rather than trying to nail the exact undocumented formula.
- `tests/test_tags.py`: added `test_first_multiword_tag_pays_quote_cost_but_not_separator`
  and `test_multiword_tag_pays_both_quote_and_separator_cost` covering the combined model;
  existing separator-only tests (using tags with no spaces) still hold unchanged.
- No change needed to `tests/test_video_metadata.py::test_save_tags_caps_to_youtube_budget`
  — its `len(...) <= 500` assertion holds more comfortably under the stricter model.

Verified: full test suite (`pytest -q`) — 1401 passed, 4 skipped, 5 deselected.

If tags still come back over budget in Studio after this, the remaining gap is either (a) a
Studio-side quirk this session's two rounds of guessing still haven't matched, or (b) tags
with unusual characters (CJK, emoji, etc.) costing more per character than assumed — would
need another real Studio counter reading to diagnose further.

## [FIX] 2026-08-03 — regenerated tags never reached already-rendered parts

User: tags now generate under 500 chars, but they don't show up in "phần chi tiết" (the part
detail dialog / an already-rendered part's info) for previously-rendered videos.

Root cause: each part's `.tags.txt` sidecar is written ONCE, at render time
(`VideoWorker._write_metadata`), and nothing ever touched it again. Both `_part_metadata`
(feeds the "Chi tiết phần" dialog — prefers the sidecar over the live tags box whenever the
sidecar file exists) and `_upload_request` (reads tags straight from the sidecar for the
actual YouTube upload) read from that frozen file. So regenerating or hand-editing tags after
a part was already rendered updated `project.meta.tags`/the tags box, but every existing
part's sidecar — and therefore both its detail view AND its next upload — kept the stale
tags from whenever it was rendered. Not a display bug alone: an unpublished-but-rendered part
would have uploaded with the old tags too.

Scope note: this fixes the LOCAL file staying in sync (detail dialog + future uploads of
not-yet-published parts). It does NOT push updated tags to a part that's already published
on YouTube — that would need new browser automation (open the video's edit page, set tags,
save) analogous to the existing "Cập nhật ảnh bìa" thumbnail-push feature, which doesn't have
a tags equivalent. Flagged to the user as a separate, larger ask if they need it.

- `src/noveltrans/gui/tab_video.py`: added `_resync_tags_sidecars(tags)` — for every window
  in `_windows_for_current_selection()` whose `.mp4` already exists, rewrites its
  `.tags.txt` with the given tags; returns how many were updated. Wired into both
  `_save_tags` (the "Lưu tags" button) and `_on_tags_ready` (after "Tạo tags" generates a
  fresh list), with the count surfaced in the status label
  ("✅ Đã lưu tags. (đã cập nhật N phần đã tạo)").
- Added to `tests/test_tab_video.py::TestYouTubeUploadUi` (reusing its existing rendered-part

## [FEATURE] 2026-08-03 — visibility mode now also per-novel (user's explicit choice)

User asked whether "chế độ hiển thị" (upload visibility) was auto-saved too. It wasn't — and
unlike the image/playlist bug above, that was a DELIBERATE prior design decision, documented
in `_build_upload_box`'s docstring: "the release plan for a novel is a decision the user makes
once at upload time, not a property of the project worth persisting," with visibility
defaulting to Riêng tư (private) specifically so an accidental click can't publish anything.

Asked the user explicitly since this overrides a documented safety-motivated default (a novel
remembering "Public" from last time reintroduces the exact accidental-publish risk the private
default existed to prevent) — they chose to persist it per-novel anyway.

- `src/noveltrans/models.py`: added `NovelMeta.upload_visibility` (`""` default = "never
  chosen for this novel").
- `src/noveltrans/storage/project.py`: added `save_upload_visibility`, same shape as the
  other per-novel savers.
- `src/noveltrans/gui/tab_video.py`:
  - `_on_project_selected` loads the saved key via `upload_visibility.findData(...)`,
    falling back to index 0 (private) — deliberately NO fallback to a global "last used"
    value here (unlike the image), since the whole point is a novel with nothing chosen
    must land on the safe default, never on some other novel's possibly-public choice.
  - `_on_visibility_changed` (already fired on every change, previously only toggling the
    schedule sub-controls) now also calls `project.save_upload_visibility(...)`.
  - Corrected `_build_upload_box`'s docstring, which had claimed the whole box was
    per-run — now explains playlist/visibility are per-novel while the actual schedule
    date/spacing genuinely stays per-run (reusing a stale date would be actively wrong).
- Tests: `tests/test_video_metadata.py::test_upload_visibility_persists` +
  updated `test_old_meta_without_new_fields_loads`;
  `tests/test_tab_video.py::TestVideoTab::test_loads_saved_visibility_on_project_select`,
  `test_unset_visibility_defaults_to_private_not_another_novels_choice` (the paranoid case:
  novel A set to Public, novel B never set — B must land on private, not leak A's public),
  `test_changing_visibility_persists_to_the_open_novel`.
