# 034 — VIDEO THUMBNAIL UPLOAD — history

## [DECISIONS] — 2026-07-28

Settled with the user before planning:

- **Flow**: a standalone post-upload action, *not* a change to 033's in-upload
  thumbnail step. Target is a part whose `<stem>.upload.json` already holds a `video_id`.
- **Image source**: the existing `<stem>.jpg` sidecar from the 026 cover editor.
  No file picker.
- **Trigger**: an explicit, visible button — one click, fully automated, no manual
  Studio steps in between. Not a context-menu item, not a side effect of another action.

## [PLAN] 034.01-INITIAL-PLAN — 2026-07-28

Generated plan: `034.01-INITIAL-PLAN.md`

Resolved the prompt's open questions:

- **Studio surface**: the video edit page (`studio.youtube.com/video/<id>/edit?hl=vi`),
  not the thumbnail dialog — it hosts the same `ytcp-thumbnails-compact-editor` and owns
  an explicit `#save` whose disabled → enabled → disabled swing is a language-independent
  proof that the change registered *and* committed.
- **Missing thumbnail input is fatal here**, unlike `_set_details()` where it is one
  optional field of an upload that must still finish. Here it is the whole job, so a
  silent skip would report success for nothing.
- **Eligibility**: any record with a `video_id` (drafts and scheduled parts included),
  not `is_published()` only — a thumbnail push cannot duplicate anything, so
  `is_uploadable()`'s conservatism has nothing to protect.
- **Buttons**: both a per-row "Cập nhật bìa" in the Thao tác column (appended fifth, so
  existing index-based tests keep passing) and a batch "🖼️ Cập nhật ảnh bìa" in the
  upload box. Interlocked with the render and upload runs — all three share the one
  `.youtube-profile` or rewrite the same files, so only one can be live, under one
  `Dừng`. Ineligible rows get a *disabled button with a tooltip naming the reason*,
  never a dead control.
  Batch is not a convenience: `Tạo lại tất cả ảnh bìa` and the 026 editor's
  *Áp dụng cho mọi phần* both rewrite every part's `.jpg` at once, so a cover change
  makes every published part stale simultaneously.
- **Write-back**: `thumbnail_updated_at` + `thumbnail_file` only, merge-only, never
  `status` — a thumbnail push cannot move the publication state machine.

**KNOWN GAP carried forward from 033**: every Studio selector in this plan is an
unverified guess, same as 033's were when it shipped (and 033's did drift). The design
compensates by failing loudly and naming the step rather than reporting a save it did
not observe. Expect one retune round after the first live run.

### Two things found while building

1. **`_send_thumbnail` discarded Studio's own error when the chooser fallback threw.**
   A test asserting "Ảnh quá lớn" reaches the user failed against the generic
   "giao diện có thể đã thay đổi" message. Now the toast is quoted on that path too —
   otherwise a rejected image sends the user hunting a selector bug that isn't there.

2. **The per-row button never worked as first written.** It looked its part up in
   `_thumbnail_update_rows()` by object identity, but that method re-plans the windows
   from scratch on every call, so the fresh `MergeWindow`s never matched the one the row
   had captured — every click would have reported "chưa có video trên YouTube". Now built
   straight from the row's own window, like `_upload_one`. Covered by
   `test_clicking_the_row_button_starts_a_run_for_that_part`.

Also moved the `live` count in `_regen_all_thumbnails` to *before* the render loop: the
loop's `processEvents()` can repopulate the voice combo mid-run, which empties the window
list. Counting the selection up front is both correct and what the message means.

### KNOWN GAP (carried forward from 033)

**Every selector added here is an unverified guess, never run against a live channel.**
That was true of 033's too, and three of those drifted in real use. The mitigations are
structural: narrow→wide fallback chains, a file-chooser second strategy for the one
irreplaceable step, `state="attached"` on every `ytcp-*` container, and errors that quote
what Studio actually showed. The specific assumption most likely to be wrong is that
`#save` is disabled-until-dirty; if it isn't, `_thumbnail_accepted` is always false and
every run fails **loudly and safely** — the inverse of the 033 transfer-gate bug, which
was always true and failed silently. The documented fallback in that case is watching the
thumbnail tile's `src`/`aria-label` instead.
