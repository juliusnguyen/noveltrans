# 034 — Cập nhật ảnh bìa cho video đã đăng — Implementation Plan

Builds directly on 033 (`src/noveltrans/youtube_upload.py`). Everything below assumes the 033 conventions: selectors in one retunable block at the top of the module, Vietnamese user strings, `YouTubeUploadError` / `UploadCancelled`, `on_progress` / `should_cancel` / `on_part_done` callback shapes, and a `QThread` worker mirroring `YouTubeUploadWorker`.

---

## Design decisions

| Decision | Rationale |
| --- | --- |
| **Both a per-row button and a batch button** — `Cập nhật bìa` in the "Thao tác" column, `🖼️ Cập nhật ảnh bìa` in the "Tải lên YouTube" box. | The two are different jobs. The row button is "I re-cut *this* cover" (the one-off the prompt describes). The batch button is the real workhorse: `Tạo lại tất cả ảnh bìa` and the 026 editor's *Áp dụng cho mọi phần* both rewrite **every** part's `.jpg` at once, so after any font/tagline/position/base-image change every published part is stale simultaneously. Making the user click 30 rows is exactly the chore that produced the "Đặt lại 'dở dang'" batch button in 033. |
| **Drive `studio.youtube.com/video/<id>/edit?hl=vi`, not the thumbnail dialog.** | The edit page has an explicit, language-independent save affordance (`#save`, disabled until something changes) and Studio's own "unsaved changes" guard. The upload dialog's thumbnail control has *no* save of its own — it only commits when the whole upload dialog does, which doesn't exist post-publish. |
| **Reuse `ytcp-thumbnails-compact-editor input[type='file']` as the first selector**, with a widening fallback chain ending at a `ytcp-video-metadata-editor`-scoped `input[type=file]`. | Same component Studio renders in the upload dialog (033's `_THUMBNAIL_INPUT_SEL`), and the same lesson from the 033 file-input bugfix: narrow `ytcp-*` forms first to avoid grabbing the wrong input, a wide form last because it can't be renamed away. |
| **A missing thumbnail input is a HARD error here**, unlike `_set_details()` which reports and continues. | In 033 the thumbnail is one field of a job that must still finish; here it *is* the job, so "skip silently" would report success while nothing changed on the channel. Stated in a comment at both sites so the asymmetry reads as deliberate. |
| **Studio must prove it took the file (save button becomes enabled) and prove it saved (save button goes back to disabled, or a "đã lưu" toast).** | Two independent gates modelled on `_file_accepted()` and `_finish()`. 033's most expensive bugs were both "a check that was always true": `_finish` waiting for a permanently-hidden dialog, and the transfer gate reading a never-disabled button. Neither gate here may be one-sided. |
| **Eligible = the record has a `video_id`, whatever its status** (`draft` / `committed` / `published`), plus an existing `.jpg`. | A scheduled or private video still has an editable thumbnail, and updating it is idempotent and non-destructive — it cannot duplicate anything, so the `is_uploadable`-style paranoia doesn't apply. `marked_by_hand` records have no id and are therefore correctly excluded: we have no idea which video they refer to. |
| **Confirm once per run, in both paths.** | It touches a video the public may already see. But it's *re-doable* (push the old jpg back), so the wording is informational, not the two-copies klaxon of `_reset_upload_state`. |
| **Write back `thumbnail_updated_at` (+ `thumbnail_file` basename) and never touch `status`.** | `write_upload_state` merges, so the publish record survives untouched. A visible timestamp is what makes a re-run — or a silent no-op — obvious in the "Đã tải lên" tooltip. |
| **Reuse `YouTubeUploadError` / `UploadCancelled` and the existing per-part continue-on-failure batch shape.** | The worker/tab layer already routes `needs_login`, per-part errors, and cancellation correctly. A parallel exception hierarchy would be a second thing to keep in sync for no gain. |
| **One "Dừng" button for the whole upload box; the two browser runs lock each other out.** | Both runs open the *same* persistent `.youtube-profile` — Chromium refuses a second instance on one user-data-dir — so only one can ever be live. A second cancel button would be a second control for one piece of state. Render also locks out both (it rewrites the `.mp4` **and** the `.jpg`). |

## Step 1 — `src/noveltrans/youtube_upload.py`: selectors and timings

Add a new block after the `step 4 — visibility` block, kept in the same house style (grouped by step, bilingual text fallbacks, comment explaining each choice).

```python
# -- video edit page (feature 034: replace the thumbnail of a published video) ---
#
# A different Studio surface from the upload dialog: the standalone edit page, chosen
# because it has an explicit save affordance. `#save` is disabled while there is
# nothing to save, which makes it a language-independent two-way signal — it going
# *enabled* proves Studio took the image, it going *disabled* proves the save landed.
_EDIT_URL = "https://studio.youtube.com/video/{video_id}/edit?hl=vi"
# The metadata editor mounting is how we know the id resolved to a real video on this
# channel (a deleted/foreign id lands on an error page instead).
_EDIT_PAGE_SEL = "ytcp-video-metadata-editor, #metadata-container, ytcp-uploads-details"
# Same component the upload dialog renders (see `_THUMBNAIL_INPUT_SEL`), widest net
# last — the 033 file-input stall was caused by only ever trying narrow `ytcp-*` forms.
_EDIT_THUMBNAIL_INPUT_SELS = (
    "ytcp-thumbnails-compact-editor input[type='file']",
    "ytcp-video-thumbnail-editor input[type='file']",
    "#file-loader",
    "ytcp-video-metadata-editor input[type='file']",
)
_EDIT_THUMBNAIL_BUTTON_SEL = (
    "#still-picker-upload-button, ytcp-thumbnails-compact-editor #upload-button"
)
_EDIT_THUMBNAIL_TEXTS = ("Tải file lên", "Tải tệp lên", "Upload file", "Upload thumbnail")
_SAVE_SEL = "#save, ytcp-button#save, ytcp-button#save-button"
_SAVE_TEXTS = ("Lưu", "Save")
# Studio's post-save toast. Secondary confirmation: the primary one is `#save` going
# back to disabled, which needs no text matching at all.
_TOAST_SEL = "ytcp-toast, tp-yt-paper-toast, ytcp-snackbar, #notification-text"
_SAVED_RE = re.compile(r"đã lưu|lưu thay đổi|saved|changes saved", re.IGNORECASE)
_SAVE_ERROR_RE = re.compile(
    r"không thể|thất bại|lỗi|quá lớn|không hợp lệ|error|failed|too large|invalid",
    re.IGNORECASE,
)
# Navigating away with an unsaved change puts up Studio's own confirmation. In a batch
# that lands between parts, so it must be cleared or every later part fails on a
# dialog nobody sees.
_DISCARD_DIALOG_SEL = "ytcp-confirmation-dialog, tp-yt-paper-dialog#dialog"
_DISCARD_TEXTS = ("Loại bỏ", "Bỏ thay đổi", "Discard", "Discard changes")

_EDIT_PAGE_WAIT_MS = 45_000   # the edit page to mount
_THUMB_ACCEPT_MS = 20_000     # Studio to register the new image (save becomes enabled)
_SAVE_CONFIRM_MS = 60_000     # the save to land (a 2 MB image + Studio round-trip)
_BETWEEN_THUMBNAILS_MS = 8_000  # human pacing; cheaper than an upload, so shorter
_MAX_THUMBNAIL_BYTES = 2 * 1024 * 1024  # YouTube's hard limit
```

## Step 2 — request/result types and the eligibility helper

Add beside `UploadRequest` / `UploadResult`:

```python
@dataclass
class ThumbnailRequest:
    """One part's thumbnail replacement: the already-uploaded video + the new image."""
    video: Path        # the .mp4 — identity key for `<stem>.upload.json`, need not exist
    thumbnail: Path    # the `<stem>.jpg` sidecar
    video_id: str = "" # "" → resolved from the record in `update_thumbnail_one`
    label: str = ""    # "Phần 3", for progress lines

    def validate(self) -> None: ...


@dataclass
class ThumbnailResult:
    video_id: str
    url: str
    updated_at: str


def uploaded_video_id(video: Path) -> str:
    """The YouTube video id recorded for this part, or "" if there isn't one.

    Deliberately status-blind: `draft`, `committed` and `published` all name a video
    that exists on the channel and whose thumbnail is editable. Only a record with no
    id at all (never sent, or `marked_by_hand`) is ineligible — we'd have nothing to
    navigate to.
    """
    return str(read_upload_state(video).get("video_id") or "")
```

`ThumbnailRequest.validate()` rules — all raise `YouTubeUploadError` before any browser opens, mirroring `UploadRequest.validate()`:

1. `self.thumbnail` missing → `f"Không tìm thấy ảnh bìa: {self.thumbnail}"`.
2. Zero-byte file → `"Ảnh bìa rỗng — hãy tạo lại ảnh bìa cho phần này."`
3. `> _MAX_THUMBNAIL_BYTES` → `"Ảnh bìa nặng {n:.1f} MB, YouTube chỉ nhận tối đa 2 MB."` (Pillow writes ~300 KB at q85, so this only bites a hand-swapped file — but finding out after the browser opens is worse.)
4. Suffix not in `{.jpg, .jpeg, .png, .gif, .bmp}` → say which formats YouTube takes.
5. **No** `.mp4`-exists check, unlike `UploadRequest` — the video is already on YouTube, and a user who cleaned up disk space should still be able to push a new cover. Comment this deviation.

`video_id` is resolved in `update_thumbnail_one` (not `validate`) so a request built on the GUI thread stays a pure value object, as `UploadRequest` is.

## Step 3 — the browser steps

Four small functions, each with exactly one failure story, all raising `YouTubeUploadError(..., video_id=...)`.

```python
def _open_edit_page(page, video_id: str, *, timeout_ms: int = _EDIT_PAGE_WAIT_MS):
    """Navigate to a video's edit page and confirm the metadata editor mounted.

    Same login check as `_open_upload_dialog`, and the same `state="attached"` lesson:
    Studio's `ytcp-*` wrappers read as hidden while filling the screen.
    """
    page.goto(_EDIT_URL.format(video_id=video_id), wait_until="domcontentloaded")
    try:
        page.wait_for_load_state("networkidle", timeout=5_000)
    except Exception:
        pass  # Studio keeps long-poll connections open; networkidle rarely fires
    if _LOGGED_OUT_URL_RE.search(page.url):
        raise YouTubeUploadError(
            "Profile YouTube chưa đăng nhập. Vào Settings → “Đăng nhập YouTube”.",
            needs_login=True, video_id=video_id,
        )
    editor = _first_present(page, _EDIT_PAGE_SEL, timeout_ms=timeout_ms, state="attached")
    if editor is None:
        raise YouTubeUploadError(
            f"Không mở được trang chỉnh sửa video {video_id} "
            f"(https://youtu.be/{video_id}). Video có thể đã bị xoá, thuộc kênh khác, "
            "hoặc giao diện Studio đã thay đổi.",
            video_id=video_id,
        )
    return editor


def _send_thumbnail(page, image: Path, *, video_id: str) -> None:
    """Hand the .jpg to the edit page's thumbnail editor, then prove Studio took it.

    Two strategies, same shape as `_send_file`: set the input directly, else click
    Studio's own "Tải file lên" inside `expect_file_chooser`.

    **Unlike `_set_details`, a missing input is fatal.** There it is one field of an
    upload that must still finish; here it is the entire job, so continuing would
    report success while the channel still shows the old cover. If the channel truly
    lacks custom-thumbnail privileges the message has to say that out loud, not shrug.
    """
    for selector in _EDIT_THUMBNAIL_INPUT_SELS:
        locator = page.locator(selector).first
        try:
            locator.wait_for(state="attached", timeout=5_000)
            locator.set_input_files(str(image))
        except Exception:
            continue
        if _thumbnail_accepted(page):
            return
    # fallback: Studio's own button + the intercepted file chooser
    ...
    if not _thumbnail_accepted(page):
        raise YouTubeUploadError(
            "Đã chọn ảnh bìa nhưng YouTube Studio không ghi nhận thay đổi "
            f"(nút “Lưu” vẫn tắt). {_toast_text(page) or ''} "
            "Hãy đổi ảnh bìa thủ công lần này và báo lỗi để cập nhật selector.",
            video_id=video_id,
        )


def _thumbnail_accepted(page, *, timeout_ms: int = _THUMB_ACCEPT_MS) -> bool:
    """True once `#save` is enabled — Studio's own "there is an unsaved change" bit.

    The 033 counterpart to this is `_file_accepted`, and the reason both exist is the
    same: `set_input_files` on a selector that matched the wrong element is a silent
    no-op that otherwise fails ten steps later with a misleading message.
    """


def _save_edits(page, *, video_id: str) -> None:
    """Click Lưu / Save and require Studio to confirm it.

    Confirmation is `#save` going back to disabled (no unsaved changes left) OR a toast
    matching `_SAVED_RE`. An error-shaped toast short-circuits into the raise so the
    real reason ("Ảnh quá lớn", "Kênh chưa được xác minh") reaches the user verbatim.

    Mirror of `_finish`, and of its bug: never confirm on a state that is true before
    the click. `#save` is *disabled* on arrival, so "disabled" alone means nothing —
    it only counts after `_thumbnail_accepted` saw it enabled.
    """
    if not _click_any(page, _SAVE_SEL, _SAVE_TEXTS):
        raise YouTubeUploadError("Không bấm được nút “Lưu”…", video_id=video_id)
    waited = 0
    while waited < _SAVE_CONFIRM_MS:
        text = _toast_text(page)
        if text and _SAVE_ERROR_RE.search(text):
            raise YouTubeUploadError(
                f"YouTube Studio báo lỗi khi lưu ảnh bìa: “{text}”.", video_id=video_id
            )
        if text and _SAVED_RE.search(text):
            return
        if _save_button_disabled(page):
            return
        page.wait_for_timeout(1_000)
        waited += 1_000
    raise YouTubeUploadError(
        "Đã bấm “Lưu” nhưng YouTube Studio không xác nhận đã lưu ảnh bìa. "
        f"Kiểm tra video trên kênh: https://youtu.be/{video_id}",
        video_id=video_id,
    )


def _dismiss_unsaved_changes(page) -> None:
    """Clear Studio's "bỏ thay đổi?" guard so the next part can navigate.

    Best-effort and silent: it only appears when a part FAILED mid-edit, and in a batch
    that dialog would otherwise block every remaining part behind a modal nobody sees.
    """
```

`_toast_text(page)` and `_save_button_disabled(page)` are two-line helpers wrapping `inner_text` / `get_attribute("disabled")` in `try/except → ""/False`, in the style of `_dialog_step`.

## Step 4 — public entry points

Signatures deliberately mirror `upload_one` / `upload_batch` so the tab and worker wiring is copy-shaped.

```python
def update_thumbnail_one(
    page,
    request: ThumbnailRequest,
    *,
    on_progress=None,
    should_cancel=None,
) -> ThumbnailResult:
    """Replace one already-uploaded video's thumbnail on an already-open page.

    Split from the batch for the same two reasons `upload_one` is: one browser per run,
    and a flow drivable from a test with a fake page.

    Nothing is written to the record until Studio confirms the save, so a failure
    leaves the sidecar exactly as it was — there is no half-state to reason about here,
    which is what makes this action so much cheaper than an upload.
    """
    request.validate()
    video = Path(request.video)
    video_id = request.video_id or uploaded_video_id(video)
    if not video_id:
        raise YouTubeUploadError(
            f"{request.label or video.stem}: chưa có video trên YouTube cho phần này "
            "(hoặc phần này chỉ được đánh dấu thủ công), nên không biết đổi ảnh bìa của "
            "video nào."
        )
    _check_cancel(should_cancel)
    _report(on_progress, "Mở trang chỉnh sửa video…")
    _open_edit_page(page, video_id)
    _report(on_progress, "Tải ảnh bìa mới…")
    _send_thumbnail(page, Path(request.thumbnail), video_id=video_id)
    _check_cancel(should_cancel, video_id=video_id)   # last safe cancel point
    _report(on_progress, "Lưu thay đổi…")
    _save_edits(page, video_id=video_id)
    updated_at = _now_iso()
    write_upload_state(
        video,
        thumbnail_updated_at=updated_at,
        thumbnail_file=Path(request.thumbnail).name,
    )   # merges: status / video_id / published_at are untouched
    return ThumbnailResult(video_id, f"https://youtu.be/{video_id}", updated_at)


def update_thumbnail_batch(
    requests,
    *,
    headless: bool = False,
    on_progress=None,
    on_part_done=None,
    should_cancel=None,
) -> list:
    """Update every request's thumbnail through ONE browser session. Returns results.

    Same contract as `upload_batch`: headed by default, `on_part_done(index, result,
    error)` per part, a failing part does NOT abort the run, `needs_login` does (every
    remaining part would fail identically). Between parts it dismisses any leftover
    "bỏ thay đổi?" guard and waits `_BETWEEN_THUMBNAILS_MS` — shorter than the upload
    pacing because the work per part is a page load, not a multi-GB transfer.
    """
```

Cancellation: `should_cancel` is polled before each part and once after the image is accepted but *before* the save click. After the click, cancellation is ignored until confirmation — same fence as `upload_one`'s, for the same reason (an unconfirmed save is precisely the state we refuse to be in). `UploadCancelled` is raised with **no** `video_id`, since nothing was created; the new worker's message says so.

## Step 5 — `src/noveltrans/gui/workers.py`: `YouTubeThumbnailWorker`

Directly after `YouTubeUploadWorker`; signal shapes identical so the tab's existing progress/cancel plumbing carries over unchanged.

```python
class YouTubeThumbnailWorker(QThread):
    """Replace the thumbnails of already-uploaded parts, in one browser session.

    Sibling of YouTubeUploadWorker — same signal shape, same cooperative cancel. The
    requests are built on the GUI thread (they only read sidecars) and handed over
    whole; this worker never touches a NovelProject.
    """

    progress = Signal(int, int, str)     # parts done, total, status line
    part_done = Signal(int, str, str)    # index, video url ("" on failure), error
    finished_ok = Signal(int, int)       # updated count, failed count
    failed = Signal(str)
    needs_login = Signal(str)

    def __init__(self, requests: list, parent=None):
        super().__init__(parent)
        self.requests = list(requests)
        self._cancelled = False

    def cancel(self) -> None:
        self._cancelled = True

    def run(self) -> None:
        from noveltrans.youtube_upload import (
            UploadCancelled, YouTubeUploadError, update_thumbnail_batch,
        )
        total, done, errors = len(self.requests), 0, 0

        def on_part_done(index, result, error):
            nonlocal done, errors
            done += 1
            if error:
                errors += 1
            self.part_done.emit(index, getattr(result, "url", "") or "", error)
            label = self.requests[index].label or f"phần {index + 1}"
            self.progress.emit(done, total, f"{label}: {'lỗi' if error else 'xong'}")

        try:
            update_thumbnail_batch(
                self.requests,
                on_progress=lambda msg: self.progress.emit(done, total, msg),
                on_part_done=on_part_done,
                should_cancel=lambda: self._cancelled,
            )
        except UploadCancelled:
            # Nothing half-done can exist here: a part is either saved or untouched.
            self.failed.emit(
                f"Đã huỷ cập nhật ảnh bìa. {done} phần đã đổi vẫn giữ ảnh mới."
            )
        except YouTubeUploadError as exc:
            (self.needs_login if exc.needs_login else self.failed).emit(str(exc))
        except Exception as exc:
            self.failed.emit(repr(exc))
        else:
            self.finished_ok.emit(done - errors, errors)
```

- `_cancel_upload` cancels whichever of `_upload_worker` / `_thumbnail_worker` is running.
- `__init__`: `self._thumbnail_worker: YouTubeThumbnailWorker | None = None`.
- `has_running_workers()`: include the thumbnail worker. (`_upload_worker` is missing from both `has_running_workers` and `shutdown` today — a pre-existing gap; note it, fix it only if the implementer wants a one-line drive-by.)
- `shutdown()`: `cancel()` + `wait(60_000)` on the thumbnail worker, like the video worker.

### 6e. Feedback in the "Đã tải lên" cell

In `_upload_item`, when `state.get("thumbnail_updated_at")`, append to the tooltip:
`f"\nẢnh bìa cập nhật: {state['thumbnail_updated_at'][:10]}"`. That is the only place a re-run is visible, and it's what turns "did that actually do anything?" into an answer.

### 6f. Cross-reference from the cover pipeline

In `_regen_all_thumbnails`, after the success line, when any part in the selection has a `video_id`:
`"⚠️ N phần đã có video trên YouTube — bấm “Cập nhật ảnh bìa” để đẩy bìa mới lên."`
Mirrors the 033 `_redo_all_videos` warning that re-rendering doesn't change what's on YouTube — same trap, same shape of answer.

## Risks / unknowns

1. **Every new selector is an unverified guess** — the 033 KNOWN GAP applies in full and this feature adds a *second* unverified Studio surface. Mitigation is structural, not hopeful: the block is grouped and commented for retuning, and both gates (`#save` enabling, then confirming) fail loudly with the toast text quoted, so the first live run produces a retunable report instead of a shrug. Expect one round of retuning.
2. **`#save` may not actually be disabled-until-dirty** on every Studio A/B variant. That would make `_thumbnail_accepted` always-false and every run fail — annoying, but it fails *safe* and visibly, unlike the 033 transfer-gate bug which failed always-true and silently. If it turns out to be wrong, the fallback signal is the thumbnail tile's `aria-label`/`src` changing, which is worth noting in a code comment now.
3. **Studio may not surface a toast at all** on some builds, leaving only the button signal. Both are accepted independently, so either alone suffices.
4. **Custom-thumbnail privileges.** An unverified channel has no upload input; the error will say so, but we cannot distinguish "unverified channel" from "selector drift" from the DOM. The message names both possibilities rather than guessing.
5. **Propagation delay.** YouTube can take minutes to serve a new thumbnail. A user who checks immediately will think it failed — hence the note in the confirm dialog and in the finish status line.
6. **Members-only / claimed / restricted videos** may refuse the edit outright with a Studio-side error; that path is only reachable through the error-toast branch, which is untested against reality.
7. **The `beforeunload` guard.** Playwright auto-dismisses native dialogs, but Studio's in-page Polymer confirmation is separate. `_dismiss_unsaved_changes` handles the latter best-effort; if its selector is also wrong, a batch could stall after its first failure. Bounded, because each part's `goto` has its own timeout and the error names the step.
8. **Scope creep to watch:** nothing here should touch title/description/tags on the edit page. The moment the edit-page plumbing exists, "while we're in there" is tempting and explicitly out of scope per the 034 prompt.
