## [IMPL] Item 1 — standard keyboard shortcuts — 2026-08-30

Implemented in full. 2868 tests pass (was 2846); ruff clean; no existing test needed editing.

### What was actually broken

The prompt asked for ⌘C/⌘V/⌘X/⌘A/⌘Z, and measurement (PySide6 6.11.1) showed **every text
widget already had them** — QLineEdit, QPlainTextEdit editable *and* read-only, even a
selectable QLabel — because they claim the keys via `QEvent::ShortcutOverride` before the
shortcut map sees them. The real gaps were narrower and sharper than the ask:

1. **Item views could not copy at all.** `QAbstractItemView` has `selectAll` and no copy.
2. **`enable_cell_copy` copied one cell, never the selection** (`_copy_index_text(currentIndex())`).
   Select twenty failed chapters, press ⌘C, get one cell.
3. **Five lists never called `enable_cell_copy`** and so had nothing: the video parts table,
   the cleanup table, both OneDrive dialogs, Find & Replace and the name glossary.

### Two traps, both measured before writing code

- **Ambiguity.** A `QShortcut(StandardKey.Copy, table)` and a menu `QAction` on the same key
  in one window make Qt log *"Ambiguous shortcut overload: ⌘C"* and fire **neither**. So the
  Edit menu could not simply be added — `widgets.py`'s QShortcut had to go in the same change.
- **A naive Edit menu breaks QLabel.** With a `QAction(StandardKey.Copy)` in a menu, a focused
  QLabel stops copying: the action wins, and `QLabel` has **no `copy()` slot**. `tab_scrape.py`
  deliberately makes the title/author/description labels selectable, so this was a live
  regression path with no crash to announce it. It has a named test.

### Source changes

- **`gui/shortcuts.py`** (new) — `selection_as_text`, six focus-widget dispatchers
  (`copy_from`/`cut_from`/`paste_into`/`select_all_in`/`undo_in`/`redo_in`),
  `EditShortcutFilter` and `build_edit_menu`. Everything matches on
  `QKeySequence.StandardKey`, never a literal `"Ctrl+C"`, so the macOS and Windows builds
  share one code path.
- **`gui/widgets.py`** — `enable_cell_copy` loses its `QShortcut` (the ambiguity fix) and its
  private `_copy_index_text`; the right-click "Sao chép" now copies the same *selection* ⌘C
  does, via `shortcuts.copy_from`.
- **`gui/main_window.py`** — a "&Sửa" menu after "&App", kept on `self.edit_menu`.
- **`app.py`** — `EditShortcutFilter` installed on the QApplication beside `DockActivateFilter`.

### Two design points worth keeping

- **Menu *and* application event filter, not one or the other.** A QAction on MainWindow —
  even `ShortcutContext.ApplicationShortcut` — does **not** fire for a focused table inside a
  modal QDialog; an app-level event filter does. Both measured. CleanupDialog,
  NameGlossaryDialog, FindReplaceDialog and the two OneDrive dialogs are all modal and all
  hold a list, so a menu alone would have left ⌘C broken exactly where a user most wants to
  copy an error message out.
- **The filter is deliberately narrow** (`_needs_help`): item views and QLabel only. A
  QLineEdit's KeyPress *does* reach the filter — claiming the ShortcutOverride means the key
  arrives as an ordinary KeyPress, which an application filter still sees — and handling it
  there would consume the event so the widget's own `keyPressEvent` never ran. That would
  swap Qt's implementation for ours with no gain. The menu's handlers still cover every
  widget, because clicking "Sao chép" with the mouse has to work everywhere.

### Verified on a real window, not just offscreen

Every claim above was measured with `QT_QPA_PLATFORM=offscreen`, so the result was re-checked
against a real `MainWindow` on the actual platform: the menu bar reads `['&App', '&Sửa']`,
`findChildren(QShortcut)` holds no Copy binding, and ⌘C on a table **inside an open modal
dialog** put `'dòng trong hộp thoại'` on the clipboard — the case the menu alone cannot reach.

### Tests

- `tests/test_shortcuts.py` (new, 17) — TSV selection, tooltip-over-display, the empty-cell
  rule, the **QLabel regression guard**, and the read-only paste/cut guards.
- `tests/test_shortcuts_filter.py` (new, 5) — the filter over synthetic `QKeyEvent`s, in the
  style of `TestDockActivate`.
- `tests/test_main_window.py::TestEditMenu` (new, 4) — the menu's actions, that every shortcut
  comes from a `StandardKey`, that **no QShortcut owns Copy** (the ambiguity guard, otherwise
  invisible except as a line on stderr), and that Copy follows focus.

### Not done here

No sort changes and no rename changes — items 2 and 3 of the plan. Also untouched: a ⌘F
binding for `FindReplaceDialog`, which the plan lists as out of scope.

## [IMPL] Item 2 — rename a novel — 2026-08-30

Implemented in full. 2927 tests pass (was 2884); ruff clean; **no existing test needed
rewriting** — including `test_the_slug_and_therefore_every_rendered_part_stays_put`, which
is the invariant this feature had to preserve.

### The keystone: the slug is now pinned, not derived

`NovelMeta.slug` + `slug_name()`. Empty for every existing project, and an empty `slug`
reproduces `slugify(translated_title or title)` byte for byte, so upgrading moves not one
file. The six sites that derived the stem now call `slug_name()`; landing that refactor
alone with a green suite is what made the rest safe.

The pin closes a hazard nobody asked about. While the stem was *derived*, anything that
touched `translated_title` moved it — a re-translation into another language silently
orphaned every rendered part and every `.upload.json`, with no error and no way back short
of renaming files by hand. `VideoWorker` and `MergeWorker` now `pin_slug()` before their
first write, so a rendered novel's filenames are anchored from that moment.

### What renaming does

The name is `display_title` — already what `display_name()` and `novel_label()` put on the
video, thumbnail, description, YouTube title, novel tab and picker. It is the novel's name
everywhere except filenames, so the whole feature is closing that last gap *safely*.

**Keeping the files is the default**, per the user's decision. It is not a compromise: the
pin is what makes a kept stem stay findable afterwards, which before this it would not
have. Moving them is one click away, previewed, and refused outright on a collision.

### Source changes

- **`slug.py`** (new) — `slugify` moved out of `storage/project.py` so `models` can use it
  without importing storage. Re-exported from `storage.project`; every existing import path
  still works and no test changed.
- **`models.py`** — `slug` field, `slug_name()`. `display_name`'s "Not for filenames"
  paragraph now points at it.
- **`storage/project.py`** — `rename_novel(title, *, pin_slug)` writes both fields in **one**
  `meta.json` write (two would leave a window where the name changed and the stem did not);
  `save_display_title` is re-based on it; `pin_slug()` is the workers' first-write anchor.
- **`rename.py`** (new, pure — no Qt, no sqlite) — `plan_rename` / `apply_rename` /
  `resync_title_sidecars`.
- **`gui/rename_novel.py`** (new) — the shared flow and its consequences dialog, with
  `rename_prompt` split out as a pure function so what the user is told can be asserted
  without a modal box.
- **`gui/tab_scrape.py`** — a ✏️ Đổi tên button on the "Tên truyện:" row, one form row from
  where *chapter* renaming already lives.
- **`gui/tab_video.py`** — `_save_display_title` routed through the shared flow;
  `_resync_title_sidecars` wrapper.
- **`gui/workers.py`, `gui/tab_video.py`, `gui/tab_export.py`** — the stem sites.

### Three things the plan got wrong, corrected here

1. **The Video tab's box must not ask.** The plan had it gaining the migration offer. It
   commits on `editingFinished`, so the question ambushes anyone who tabs past the field —
   and the first attempt **hung the whole test suite** on a modal `exec()` in
   `test_the_slug_and_therefore_every_rendered_part_stays_put`. It now passes
   `offer_migration=False`. The ✏️ button is the deliberate rename and the only one asking.
2. **`tab_export.default_export_name` is not a stem site.** The plan listed it as one; it
   actually honours the "dùng bản dịch" toggle for a `.docx`/`.epub` Save dialog. Pointing
   it at `slug_name()` would have broken that. It now prefers `display_title` when exporting
   the translation and stays on `title` otherwise — so a rename reaches it without the
   toggle losing its meaning.
3. **`apply_rename` moves files before their folder**, not folder-first as the plan said.
   Folder-first invalidates every `Move.src` the instant the folder moves. A renamed file
   inside a not-yet-renamed folder is a fine intermediate; a stale `src` is not.

Also moved: the title resync lives in the pure `rename.py`, not in the video tab, because a
rename can start from either tab and nothing about the job needs a widget.

### The `.title.txt` bug (flag 6) — a fix that predates this feature

`_resync_tags_sidecars` and `_resync_description_sidecars` both existed; `.title.txt` had no
equivalent, and `_upload_request` prefers the sidecar over recomputing. So the *existing*
display-title override already left a rendered, not-yet-uploaded part scheduled to
**publish to YouTube under the old name**. `resync_title_sidecars` closes it, from both
entry points and on project open (so a novel renamed by an older build is repaired the next
time its video tab is opened).

It reads the part number back out of the sidecar rather than recomputing it, so a later
batch-size change cannot renumber a part already on YouTube; it covers both editions, unlike
the description resync; and it rewrites only a name this novel has actually gone by, so a
hand-written "Bản đặc biệt - Phần 3" is left alone.

### What is deliberately NOT renamed

The project folder (sqlite handle open, workers hold absolute paths, `AppState` keyed on it
— and it is `sha1(url)[:8]`-identified, so the slug prefix is decoration); `title` and
`translated_title` (a re-scan overwrites the first, the second is the unpinned fallback);
already-exported `.docx`/`.epub`/`.md`; the published YouTube title; the OneDrive remote
tree (`_resolve_remote_root` already pins it) and its manifest keys (leaving them stale is
*correct* — `plan_uploads` iterates local items, so orphaned entries are inert, while
rewriting them would make `cleanup.py` reason from a lie); rendered `.jpg` covers, which are
pixels; per-chapter audio, which is chapter-keyed. All of it is said out loud in the dialog.

### Tests

- `tests/test_rename.py` (new, 24) — the plan/apply half and the title resync, pure. The
  highest-stakes one is `test_an_upload_record_travels_with_its_part`: losing a
  `.upload.json` re-publishes a live episode. Also: the source (`-nguon-`) edition moves
  (`iter_rendered_part_dirs` filters it out of a chapter scan; a rename must not), a novel
  sharing a slug prefix is not swept up, chapter-keyed audio never moves, a collision moves
  nothing, and a half-finished rename can be finished by re-planning.
- `tests/test_rename_novel_gui.py` (new, 16) — both branches, cancel, collision,
  `offer_migration=False`, and `rename_prompt` for what the user is actually told.
- `tests/test_storage.py` — `TestSlugName` (the **no-migration guarantee**, the pin
  surviving a re-translation) and `TestRenameNovel` (one write, scraped titles untouched,
  a re-scan not undoing a rename).
- `tests/test_tab_scrape.py::TestRenameNovel` (5) and
  `tests/test_tab_video.py::TestRenameFromTheVideoTab` (4).

### Verified end to end on a real project folder

Created a CJK-titled novel (folder `novel-5d45808b` — confirming the folder is not
name-derived), rendered a part, marked it published with video id `LIVE123`, then:
display-only rename → name changed, `.mp4` and its upload record untouched, `.title.txt`
updated to the new name; a following re-translation left the stem alone (the hazard the pin
removes); then the migrate branch → files moved, `LIVE123` followed its `.mp4`, old folder
gone, `title`/`translated_title` untouched throughout.

### Not done here

Item 3 (sorting). Also still out of scope, as planned: renaming the project folder, moving
an existing OneDrive mirror, re-rendering covers that carry the old name, and changing a
title already published on YouTube.

## [IMPL] Item 3 — sortable lists — 2026-08-30

Implemented in full. 2960 tests pass (was 2927); ruff clean.

Every list in the app that should sort now sorts by clicking a column header, the choice is
remembered per user, and the two lists that must *not* sort still do not.

### It started as a bug hunt, not a feature

Nothing sorted before this (`grep setSortingEnabled|sortItems|QSortFilterProxyModel` → zero
hits), and three lists mapped a view row to its data **by position**. Turning sorting on
without fixing them would have been actively dangerous:

- **`cleanup_dialog`** — `_ticked()` walked `enumerate(self._rows)` and read
  `table.item(index, 0)`. Sorted, ticking one file deletes **a different one**, in a dialog
  whose own header says deletion cannot be undone. `_on_verified` had the same walk — a
  **fourth** positional site the plan did not list — which would have unlocked the wrong row
  and written "có trên OneDrive" against a file nobody checked.
- **`onedrive_sync_dialog`** — identical shape; the failure is pushing the wrong novel.
- **`tab_video`'s parts table** — `windows[row]`, so "Tách phần", "Gộp 2 phần liền kề" and
  the bulk upload toggles would act on the wrong parts.

All three now key their rows on the row's own data (`UserRole`, or the window's `first_num`),
and each has a test that **fails against the old lookup** — verified by reverting each fix
and watching the new tests go red. Worth having regardless of sorting.

`_upload_rows` was already UserRole-keyed, so the upload column was safe as it stood.

### Two mechanisms, one interaction

Click a header, click again to reverse, and it is remembered. The implementation cannot be
one mechanism — four lists are `QTableView` + `QAbstractTableModel`, five are `QTableWidget`
— so:

- **`SORT_ROLE` + `sorting_proxy`** for the views. Every model gained a `SORT_ROLE` branch
  returning a *comparable* key, because the displayed strings do not sort: `#` reads 1, 10, 2
  as text; `format_duration` puts "3m05s" before "10s"; and the status words are alphabetical
  nonsense — "Lỗi" belongs beside "Chưa tải", not between "Đã tải" and "Đã dịch", so status
  sorts on a **pipeline rank**.
- **`SortableItem` + `setSortingEnabled`** for the item tables, with the standard
  off-while-filling bracket (rows arrive one at a time from a worker, so it brackets each
  insert rather than a batch).

### What the plan got wrong

1. **`setSortingEnabled(True)` alone opens every table BACKWARDS.** It leaves the header's
   indicator at its default, which is Descending. Measured, and caught only because the
   audio multi-select tests assert on real row numbers. `enable_table_sorting` exists to
   follow it with an explicit `sortByColumn` — and it also carries the persistence wiring,
   so no tab repeats it.
2. **A reset restores the user's saved sort, not `#` ascending.** The plan wanted
   `set_chapters()` to force chapter order back. Qt re-applies the proxy's sort on a model
   reset by itself, and forcing `#` would discard a choice made one action ago. `#`
   ascending stays the default for a table with nothing saved, which is the case the plan
   was really protecting.
3. **`_fold` needs the `đ` special case.** Diacritic folding via NFKD leaves `đ` alone — it
   is its own letter, not a d with a mark — so "Đấu La" sorted after "Z". `slugify` already
   carries the same special case for the same reason.

### The row-index audit

Every read of a row now goes through `source_index` / `source_rows`. `RowButtonDelegate.clicked`
carries a `QModelIndex` instead of a row number (the plan's preferred option): a row number
is a screen position, and the 🔊 / ↻ buttons would otherwise act on whatever chapter happened
to sit there.

`source_rows` returns **model** rows ascending — chapter order, not screen order — which is
what every caller wanted all along, since they feed indices to a worker that walks the novel
forwards.

The audio tab gets **two** proxies, because one view swaps between two models whose columns
mean different things; a shared proxy would carry the chapter view's sort column into the
release view, where that number is a different field.

### What sorts, and what deliberately does not

Sortable: the three chapter tables, the source-audio table, the video parts table, the
cleanup table, the OneDrive sync picker, the name glossary, the OneDrive folder list, and the
novel picker.

Not sortable, and the reasons are in the plan: the **sync log** (chronological *is* the
information) and the **Find & Replace** breakdown (its double-click handler is documented as
depending on row == match index; making it sortable changes a jump target feature 064 shipped
deliberately, so it belongs in its own turn). The **novel tab bar** keeps the user's own
drag order.

### Chapter order is data, not presentation

`plan_merge_windows`, `part_number`, the `{index+1:04d}` audio filenames and `add_chapters`'
MAX(idx)+1 rule all key on the chapter number. So: the default is always `#` ascending; every
action reads chapters, never rows; and the parts table stays part-ordered by default and is
never renumbered by a sort (`_part_number` is derived from the chapter range — its docstring
already warns that numbering by position once renamed a part the moment it was viewed).

### The picker was ordered by a key nobody could see

`Library.list_projects` sorts on the folder name, which is `slugify(meta.title)-<hash>` — the
**original** title — while every picker row shows the translation first. The dropdown looked
unsorted because the only key the user could read was never the key it was ordered by. It now
sorts on its own label, case- and diacritic-folded. This is flag 5 from the plan, and it is
probably the item-3 change the user notices first.

### Tests

- `tests/test_sorting.py` (new, 20) — the sort keys, the persistence contract (including a
  changed column count dropping a saved index, and corrupt settings reading as None), the
  Descending-default guard, and **`test_a_status_sort_still_acts_on_the_right_chapters`** —
  the promise of the whole item.
- `tests/test_cleanup_dialog.py::TestSorting` (4), `tests/test_onedrive_sync.py::TestPickerSorting`
  (3), `tests/test_tab_video.py::TestPartsTableSorting` (4) — each written to fail against the
  positional lookup it replaces, and each confirmed to do so.
- `tests/test_widgets.py::TestProjectPickerOrdering` (2).

Existing tests updated (only the row-index audit's callers, as the plan predicted): the audio
multi-select and download harnesses built selections and context-menu indices from the
**source** model, which a proxied view's selection model silently mis-resolves; and two
assertions on `table.model() is tab.model` now check what the proxy wraps.

### Verified on a real window

A 12-chapter novel in a real `Workspace`: the table opens 1, 2, 3, 4; sorting by "Trạng thái"
reorders it to 1, 6, 11, 4; selecting the top three rows returns model rows `[0, 5, 10]` in
chapter order — chapters 1, 6, 11, exactly the ones on screen; and a second Workspace built
afterwards came up with the remembered sort (column 3, ascending).
