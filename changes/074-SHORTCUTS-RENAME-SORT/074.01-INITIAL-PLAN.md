# 074.01 — Initial plan: standard shortcuts, novel rename, sortable lists

> Every Qt claim below was measured with `QT_QPA_PLATFORM=offscreen .venv/bin/python`
> against the repo's own PySide6 (**6.11.1**), not inferred from documentation. Where a
> behaviour is stated as fact, it was observed.

## Summary

Three unrelated asks, one shared theme: the app was built as a pipeline and never as a
*document* app, so the three places a desktop app is judged — the keyboard, the name of
the thing you are working on, and the order of a list — were never wired up.

1. **Shortcuts.** Text widgets already work everywhere (measured). The gaps are item
   views (no copy at all), a missing **Edit menu**, and one live bug: the per-table
   `QShortcut` in `widgets.py:726` cannot coexist with a menu `QAction` on the same key
   — Qt reports *"Ambiguous shortcut overload: ⌘C"* and **neither** fires. The fix is one
   `gui/shortcuts.py` with a focus-widget dispatcher, used by both an app-wide event
   filter (the only thing that reaches modal dialogs) and the Edit menu.
2. **Rename.** The blocker is that the video slug is *derived* from a mutable title
   (`slugify(meta.translated_title or meta.title)`, six sites). Pin it: a new
   `NovelMeta.slug` that is empty for every existing novel and only ever written by an
   explicit rename. Then renaming is `display_title` + an optional, previewed file
   migration — and, as a bonus, a pre-existing hazard goes away (a re-translation that
   changes `translated_title` today silently orphans every rendered part).
3. **Sorting.** No list in the app sorts today (`grep -rn "setSortingEnabled\|sortItems\|QSortFilterProxyModel" src tests` → **zero hits**). Two mechanisms, not ten: a
   `QSortFilterProxyModel` for the four `QTableView`s, `setSortingEnabled` for the
   `QTableWidget`s. **Three lists must be fixed before they can be sorted at all**,
   because they map view row → data by *position*; on one of them (`cleanup_dialog.py`)
   that would tick the wrong file for deletion.

---

## Flags: things the framing gets wrong or leaves out

1. **"Cmd+C to copy, Cmd+V, Cmd+X, Cmd+A, Cmd+Z" mostly already works.** Measured with
   the real widgets: a `QLineEdit`, a `QPlainTextEdit` (including `setReadOnly(True)`),
   and even a `QLabel` with `TextSelectableByMouse` all copy on ⌘C today, with no menu
   and no `QShortcut`. Text widgets claim these keys via `QEvent::ShortcutOverride`
   before the shortcut map sees them. **The prompt's literal ask is already satisfied for
   every text field.** What does not work is item views.
2. **Adding an Edit menu naively *breaks* something that works today.** Measured: with a
   `QAction(StandardKey.Copy)` in a menu, a focused `QLabel` no longer copies — the
   action fires instead, and `QLabel` has **no `copy()` slot** (`hasattr(lab, "copy")` is
   `False`; it only has `selectedText`/`setSelection`). `tab_scrape.py:125-132`
   deliberately makes the title/author/description labels selectable, so this is a live
   regression path. The dispatcher must special-case `QLabel`.
3. **`enable_cell_copy`'s ⌘C copies one cell, never the selection.**
   `_copy_index_text(table.currentIndex())` (`widgets.py:669-677, 715-716`). Select
   twenty error rows, press ⌘C, get one cell. That is the actual complaint behind "lists
   don't behave like a normal app", more than the missing menu.
4. **`ApplicationShortcut` does not save you in dialogs.** Measured: a
   `QAction` on `MainWindow` with `ShortcutContext.ApplicationShortcut` does **not** fire
   for a focused table inside a modal `QDialog` — Qt blocks shortcuts owned by a
   modally-blocked window. An `app.installEventFilter(...)` **does** see the KeyPress
   there (measured). The app already has exactly this pattern: `DockActivateFilter` in
   `app.py:22-49`, installed at `app.py:82`.
5. **The project folder is *partly* name-derived after all.**
   `NovelProject.create` builds `library_dir / f"{slugify(meta.title)}-{digest}"`
   (`project.py:223`). Identity is the `sha1(url)[:8]` digest, so the prefix is cosmetic —
   but `Library.list_projects()` sorts by `p.name` (`library.py:36-38`), so the *novel
   picker's order* is driven by the original title's slug while the picker *displays*
   `novel_label()` (translation first). Renaming does not break it; item 3 fixes it.
6. **The `.title.txt` sidecar is never resynced.** `_resync_description_sidecars`
   (`tab_video.py:2784`) and `_resync_tags_sidecars` (`:2758`) exist; there is no
   equivalent for `.title.txt`, and `_upload_request` prefers the sidecar over recomputing
   (`tab_video.py:3492-3493`). So today, renaming via the *existing* `display_title` box
   already leaves an already-rendered, not-yet-uploaded part scheduled to publish under
   the old name. That is a bug in feature 025 that item 2 must fix regardless of slugs.
7. **OneDrive is already rename-safe and says so.** `_resolve_remote_root`
   (`onedrive_upload.py:2355-2368`) pins `manifest.remote_root` on the first push
   precisely so "renaming a novel inside the app must not strand an already-uploaded
   tree". The remaining OneDrive risk is not the folder, it is the *manifest keys*
   (`relpath`), which a local file rename invalidates wholesale.
8. **`QTableWidget` cell widgets DO follow a sort in Qt 6.11.** Measured: after
   `sortItems(0)`, `cellWidget(row, 1)` is still the widget that was created for the item
   now at that row. So `video_list`'s per-row action buttons (`tab_video.py:1349`) are not
   the blocker they would have been in older Qt. The blocker there is the `windows[row]`
   mapping, which is a different problem.
9. **Chapter order is not "a sort", it is the data.** `plan_merge_windows`,
   `part_number`, `add_chapters`' `MAX(idx)+1` rule and every `{index+1:04d}` filename
   depend on chapter *number*. Sorting a chapter table by "Trạng thái" and then
   right-clicking "Tạo lại 30 chương" must still act on the right chapters — which it will
   only if the row→chapter mapping goes through the proxy. See §3.

## Ordering and dependencies

**1 → 2 → 3**, and the arrows are real:

- **1 before 3.** Item 3 puts a `QSortFilterProxyModel` between the three chapter tables
  and their models. Item 1 rewrites the one copy helper those tables share
  (`enable_cell_copy`). Doing 3 first means writing the multi-cell copy twice, once per
  index space. Doing 1 first means item 3 changes exactly one line of it
  (`view.model()` already returns the proxy).
- **1 before 2.** The rename confirmation dialog shows a table of files that are about
  to move. It should be copyable, and after step 1 it is, for free.
- **2 before 3** only weakly: the rename dialog adds one more list, and it is cheaper to
  make it sortable while writing §3's inventory than to come back.
- **3 last on purpose.** It is the only one of the three that can cause silent data loss
  (§3, `cleanup_dialog`), and it wants the other two settled so a bug report has one
  suspect.

# Item 1 — Standard keyboard shortcuts

## 1.1 What actually works today (measured, not assumed)

| Focus widget | ⌘C | ⌘V | ⌘X | ⌘A | ⌘Z | Why |
|---|---|---|---|---|---|---|
| `QLineEdit` | ✅ | ✅ | ✅ | ✅ | ✅ | claims `ShortcutOverride` |
| `QPlainTextEdit` (editable) | ✅ | ✅ | ✅ | ✅ | ✅ | same |
| `QPlainTextEdit` (**read-only**) | ✅ | n/a | n/a | ✅ | n/a | copy/select-all claimed; **paste/cut are *not* claimed** — a menu action would fire and must no-op |
| `QLabel` + `TextSelectableByMouse` | ✅ | — | — | ✅ | — | works today, **breaks if a menu Copy action is added** (flag 2) |
| `QTableView` / `QTableWidget` | ❌ | — | — | ✅ | — | `QAbstractItemView` has `selectAll` but **no copy** |
| `QListWidget` | ❌ | — | — | ✅ | — | same |
| `QComboBox` (non-editable) | ❌ | — | — | — | — | nothing to copy from |

So the honest problem statement is: **item views cannot copy, there is no Edit menu, and
the one place copy *was* bolted on (`enable_cell_copy`) copies a single cell and is
mutually exclusive with an Edit menu.**

## 1.2 The three traps, all measured

1. **Ambiguity.** `QShortcut(StandardKey.Copy, table)` (`widgets.py:726`) plus a menu
   `QAction(StandardKey.Copy)` in the same window ⇒
   `QAction::event: Ambiguous shortcut overload: ⌘C`, and **neither** handler runs.
   The `QShortcut` must go. It is the *only* `QShortcut` in `src/`
   (`grep -rn "QShortcut" src` → `widgets.py:30,726`), so this is a two-line removal.
2. **`ShortcutOverride` asymmetry.** Text widgets claim ⌘C/⌘V/⌘X/⌘A/⌘Z and the menu
   action never fires for them. Item views and `QLabel` claim nothing, so the menu action
   *does* fire and must do the work itself. One dispatcher, two behaviours, decided by
   `isinstance`.
3. **Modality.** `ApplicationShortcut` does not reach a modal `QDialog`; an app-level
   event filter does. `CleanupDialog`, `NameGlossaryDialog`, `FindReplaceDialog`,
   `OneDriveSyncPickerDialog`, `OneDriveFolderDialog`, `SettingsDialog` and
   `ThumbnailEditor` all hold lists or read-only text, so this is not academic.

## 1.3 Design — one module, two entry points

Rejected alternatives, briefly:

| Option | Verdict |
|---|---|
| A `QShortcut` per list (today's pattern, extended) | Rejected. Ten more shortcuts, all ambiguous with each other the moment two live in one window, and no menu. This is the "per-widget hack" the prompt rules out. |
| `QTableView` subclass with `keyPressEvent` | Rejected. Four `QTableView`s, five `QTableWidget`s, two `QListWidget`s, and `QTableWidget` cannot be swapped for a subclass without touching every `setItem` call site. |
| Menu-only (`QAction`s on `MainWindow`) | Rejected alone — dead in every dialog (trap 3). Kept as *one of two* entry points. |
| App-wide event filter only | Rejected alone — no menu means macOS users get no Edit menu and no discoverable ⌘ hints. Kept as the other entry point. |
| **Menu + app filter, both calling one dispatcher** | **Recommended.** The menu owns the key inside `MainWindow`; the filter picks it up in dialogs, where the menu is blocked. They cannot double-fire (the shortcut map consumes the key before it becomes a `KeyPress`), and even if they did, copy and select-all are idempotent. |

### New file: `src/noveltrans/gui/shortcuts.py`

Pure-Qt, no project imports, unit-testable under `qapp`. Contents:

```python
def selection_as_text(view: QAbstractItemView) -> str
```
Tab-separated, newline between rows, ordered by `(row, column)` of the *view*. Reuses the
existing rule from `_copy_index_text` (`widgets.py:669`): prefer `ToolTipRole` when it is
longer than `DisplayRole`, which is what makes a truncated error message copyable. Skips
columns whose `DisplayRole` is empty (the `RETRANSLATE_COLUMN` / `REGENERATE_COLUMN`
button slots, `widgets.py:512, 282`) so a copied block has no trailing tabs. Falls back to
`view.currentIndex()` when the selection is empty — preserving today's behaviour exactly.

```python
def copy_from(widget) -> bool
def cut_from(widget) -> bool
def paste_into(widget) -> bool
def select_all_in(widget) -> bool
def undo_in(widget) -> bool / redo_in(widget) -> bool
```
Each returns `True` if it handled the widget. Dispatch order and rationale:

- `QAbstractItemView` → `selection_as_text` / `view.selectAll()`; cut/paste/undo/redo are
  no-ops returning `True` (swallowing them is right: a table has no paste target and
  letting ⌘V fall through to a parent would be surprising).
- `QLabel` → `clipboard().setText(w.selectedText() or w.text())`;
  select-all is `w.setSelection(0, len(w.text()))`. **This branch exists solely to keep
  flag 2 from being a regression, and needs a named test.**
- anything with `copy`/`paste`/`cut`/`selectAll`/`undo`/`redo` **and**, for the writing
  ones, `not w.isReadOnly()` → call it. (Read-only `QPlainTextEdit` does not claim
  paste/cut, measured, so this guard is the thing that stops the menu item mutating a
  read-only preview pane.)
- otherwise → `False`, and the filter returns `False` so Qt's own handling proceeds.

```python
class EditShortcutFilter(QObject)
```
Shaped exactly like `DockActivateFilter` (`app.py:22-49`) — a free-standing filter, not a
`QApplication` subclass, "so the tests' shared QApplication keeps working and the filter
can be handed a synthetic event". Handles **only** `QEvent.Type.KeyPress`, matches
against `QKeySequence.StandardKey` (never hard-coded `Ctrl+C`, so Windows gets Ctrl and
macOS gets ⌘ from the same code — `packaging/` and `make.ps1` ship both), and delegates to
the dispatchers. Returns `True` only when a dispatcher handled it.

```python
def build_edit_menu(window) -> QMenu
```
Vietnamese labels matching the house style of `_build_menu` (`main_window.py:153-184`):
`Hoàn tác` / `Làm lại` / — / `Cắt` / `Sao chép` / `Dán` / — / `Chọn tất cả`, each with its
`StandardKey`, each `triggered` → the matching dispatcher against
`QApplication.focusWidget()`. `Hoàn tác`/`Làm lại` get `MenuRole.NoRole`; leave the roles
alone otherwise (macOS does not relocate Edit-menu items the way it does Preferences/Quit).

## 2.3 The keystone: pin the slug

Add to `NovelMeta` (`models.py`, beside `display_title`):

```python
slug: str = ""   # pinned filename slug; "" = still derived (see slug_name)
```

and

```python
def slug_name(self) -> str:
    """The slug every generated file of this novel is named after.

    Empty `slug` reproduces the pre-074 rule byte for byte, so no existing project
    moves a single file by upgrading. Only an explicit rename-with-migration ever
    writes it — and once written it is the ONLY thing consulted, which is what makes a
    later re-translation (or a second rename) safe.
    """
    return self.slug or slugify(self.translated_title or self.title)
```

`slugify` lives in `storage.project` and `models` must not import storage (it is imported
*by* it, `project.py:20-30`). Move `slugify` to `noveltrans/slug.py` and re-export it from
`storage.project` so `onedrive_upload.py:64` and the seven Group-B sites keep their import
paths. That is a pure move; `tests/test_storage.py` needs no change.

Then replace all seven Group-B derivations with `project.meta.slug_name()`, and delete the
four duplicated `# NOT display_name(): …` comments (`workers.py:1492, 1666, 2050`,
`tab_video.py:800, 822`) in favour of one on `slug_name`. `models.py:78-84`'s
`display_name` docstring paragraph — "Not for filenames" — becomes a pointer to
`slug_name`; it is the single most-cited comment in this codebase and must not be left
stating the old rule.

**Why a pin and not "recompute from the new name":** because recomputation is what breaks
things. With a pin, "what is this novel's slug" is answered by one field that only ever
changes when a migration has *already moved the files*. That also closes a hazard nobody
asked about: today, `save_meta_translation` (`project.py:835-851`) can change
`translated_title` on a re-translation into a different target language, silently moving
the slug and orphaning every rendered part and every `.upload.json`. See §2.7 step 7.

## 2.4 The rename operation

### `src/noveltrans/rename.py` (new, pure, no Qt, no sqlite)

```python
@dataclass(frozen=True)
class Move:      src: Path; dst: Path; kind: str   # "video-dir" | "video-file" | "audio"
@dataclass(frozen=True)
class RenamePlan:
    old_slug: str; new_slug: str
    moves: list[Move]; total_bytes: int
    collisions: list[Path]          # dst already exists — plan is REFUSED if non-empty
    published: int                  # moves whose .upload.json says "published"
```

- `plan_rename(project_path, old_slug, new_slug) -> RenamePlan` — walks
  `exports/video/` for directories named `old_slug` or `old_slug-*` (reusing the
  `iter_rendered_part_dirs` prefix logic, `tts/video.py:463-490`, and **including the
  `-nguon-` source edition**, which that helper deliberately filters out and a rename must
  not), plus `exports/audio/{old_slug}.*` and `{old_slug}-NNNN-NNNN.*`. For each part
  directory it emits one `video-dir` move plus one `video-file` move per file whose stem
  starts with the directory's stem.
- `apply_rename(plan) -> list[Move]` — directories first, then the files inside them, then
  audio. Returns what it actually moved so a partial failure is reportable.
- `refuses` by construction: any `dst` that already exists aborts the whole plan before
  touching anything. Two novels whose names slugify alike is not hypothetical —
  `slugify` truncates at 40 chars and strips every non-ASCII character (`project.py:90-96`),
  so `Trọng sinh: …` and `Trong sinh …` collide.

### `NovelProject.rename_novel(name, *, pin_slug) -> None` (`storage/project.py`)

Sits with the other nine `save_*` methods (`:835-987`) and follows their shape exactly
(mutate `self.meta`, re-read `meta.json`, `data.update(...)`, write back). Writes
`display_title` and `slug` in **one** `meta.json` write — two writes would leave a window
where the name has changed and the slug has not, and a crash there loses every rendered
part. `save_display_title` (`:911-921`) becomes `rename_novel(name, pin_slug=self.meta.slug_name())`
so the Video tab's existing box cannot diverge.

### `src/noveltrans/gui/rename_novel.py` (new)

One function, used by both entry points:

```python
def rename_novel(parent, project, new_name: str) -> bool
```

1. `new_name.strip()`; equal to `display_title` → return `False` (no-op, matching
   `_save_display_title`'s guard at `tab_video.py:2706`).
2. `wanted = slugify(new_name or project.meta.translated_title or project.meta.title)`.
   If `wanted == project.meta.slug_name()` → `rename_novel(name, pin_slug=wanted)`, done,

3. Otherwise `plan = plan_rename(...)`. If `plan.moves` is empty → pin `wanted`, done.

## 3.2 One approach, two mechanisms

The prompt asks for "one consistent sorting approach". The consistent thing is the
*interaction*: **click a column header to sort, click again to reverse, and the choice is
remembered.** The implementation cannot be literally one mechanism, because four of the
lists are `QTableView`+`QAbstractTableModel` and five are `QTableWidget`; forcing either
into the other's shape is a rewrite with no user-visible payoff.

Rejected: a "Sắp xếp theo…" combo box per tab (invents a control the platform already
has, and costs screen width in a tab that already scrolls — feature 037). Rejected:
sorting the *data source* (`project.chapters()` returns rows ordered by `idx`; re-ordering
there would desynchronise `row_for_index`, `widgets.py:541`, and every worker that
consumes `chapters()`).

### For the four `QTableView`s — `SortRole` + one proxy

Add to `widgets.py`:

```python
SORT_ROLE = Qt.ItemDataRole.UserRole + 1   # UserRole is taken by the row buttons
```
`UserRole` is already in use on `RETRANSLATE_COLUMN`/`REGENERATE_COLUMN` to mean "this row
is eligible for the button" (`widgets.py:246, 374, 623`), so the sort key must not share it.

Each of `ChapterTableModel`, `AudioChapterTableModel`, `AudioSourceTableModel` gains a
`SORT_ROLE` branch in `data()` returning a **comparable key**, because the display strings
do not sort:

| Column | Displayed | Sort key |
|---|---|---|
| `#` | `1`, `2`, `10` | `chapter.index` (int) — string sort gives 1, 10, 2 |
| Tên chương / Tên dịch | text | `str.casefold()` |
| Trạng thái | `Chưa tải`/`Đã tải`/`Đã dịch`/`Lỗi` | a **pipeline rank** (0..3), not alphabetical — "Lỗi" belongs next to "Chưa tải", not between "Đã tải" and "Đã dịch" |
| Âm thanh (audio) | `Chưa dịch`/`Chưa tạo`/`Đã tạo`/`Đã tải`/`Lỗi` | same idea, from `_audio_status` (`widgets.py:288-303`) |
| Ký tự | `1234` | int |
| Thời lượng / Thời gian | `3m05s` | the raw `float` seconds, **not** `format_duration`'s output |
| Dịch bằng / Giọng | text | `casefold()` |
| Lỗi | text | `bool(error)` then text — "which rows failed" is the question, and it is one click |
| button column | — | no key; header not clickable (`setSectionsClickable` off for that section) |

Then, in each tab's constructor, between model and view:

```python
self.proxy = sorting_proxy(self.model, self)          # implemented as a widgets.py helper
self.table.setModel(self.proxy)
enable_table_sorting(self.table, config=config, list_id="chapters.scrape")
```

**`setSortingEnabled(True)` is not enough on its own** — a fact the plan did not know.
It leaves the header's sort indicator at its default, which is **Descending**, so every
table opens *backwards*: chapter 12 above chapter 1. `enable_table_sorting` exists to
follow it with an explicit `sortByColumn`, and to carry the persistence wiring.

`setDynamicSortFilter(False)` is deliberate: these models emit `dataChanged` per chapter
during a run (`widgets.py:305-308, 536`), and with dynamic sorting on, a chapter that
finishes translating **jumps out from under the cursor** mid-run. Off, the order is stable
until the next header click or `set_chapters` reset.

**The row-index audit.** Every place that reads a row must map through the proxy. The
complete list (`grep -n "\.row()\|chapter_at\|item_at\|selectRow\|scrollTo\|self.model.index("` over the three tabs):

- `tab_scrape.py:407-408` (`selectRow` + `scrollTo` after a find), `:489` (`chapter_at(index.row())`), `:496` (`self.table.edit(self.model.index(...))`)
- `tab_translate.py:345` (`_on_row_selected`), `:511`, `:587-588`, `:797-799`
- `tab_audio.py:721-722, 758-759, 793, 917, 920, 956`
- `widgets.py:246-259` `RowButtonDelegate.editorEvent` → `self.clicked.emit(index.row())`, consumed by `tab_translate._retranslate_row` (`:511`) and `tab_audio._regenerate_row`/`_redownload_row` (`:817`)

Rather than sprinkle `proxy.mapToSource(...)` at 15 sites, add two helpers to `widgets.py`
and route every one of them through:

```python
def source_index(view, index) -> QModelIndex     # proxy-aware, identity when unproxied
def source_rows(view) -> list[int]               # the selection, in SOURCE row numbers
```

`source_rows` is also the fix for `_selected_rows` (`tab_audio.py:793`) and the
right-click "act on N chương" paths (`tab_translate.py:797`, `tab_audio.py:721`), whose
`sorted({i.row() …})` currently means "sorted view positions" and after this means "chapter
order" — which is what those callers actually want, since they feed `indices` to workers.
`RowButtonDelegate.clicked` should carry the **source** row: change it to emit
`index.row()` mapped via the delegate's `parent()` view, or — cleaner — emit the
`QModelIndex` and let the two slots call `source_index`. Prefer the latter; the signal has
exactly three connections.

### For the `QTableWidget`s — `setSortingEnabled` + a keyed item

Add to `widgets.py`:

```python
class SortableItem(QTableWidgetItem):
    """A cell that sorts by an explicit key instead of its own text.

    Measured: Python's __lt__ IS honoured by QTableWidget.sortItems, and "Phần 9" /
    "Phần 10" / "Phần 100" come back in that order rather than 10, 100, 9.
    """
```
storing the key under `SORT_ROLE` and falling back to `super().__lt__` when either side
has none.

And in every populate loop, the standard Qt dance — **`setSortingEnabled(False)` before
filling, `True` after**. Without it, each `setItem` re-sorts and the fill scrambles.
Affects `_rebuild_video_rows` (`tab_video.py:1321-1351`), `CleanupDialog._add_row`
(`:132-150`) and `OneDriveSyncPickerDialog._on_scanned` (`:113-136`) — the last two append
rows *as a worker discovers them*, so this must be a set/reset around each insert, not
around a batch.

## 3.5 Lists whose order is semantic — say it out loud

**Chapter order is data, not presentation.** A chapter's position drives
`plan_merge_windows`, `part_number`, `{index+1:04d}` audio filenames and
`add_chapters`' `MAX(idx)+1` rule (`project.py:270-296`). Three consequences the plan
commits to:

1. **The default sort is always `#` ascending.** ~~and it is restored by
   `set_chapters()`~~ **REVISED: the user's own saved sort is what a reset restores.** Qt
   re-applies the proxy's sort on a model reset by itself, and forcing `#` back would
   throw away a choice the user made one action ago. `#` ascending remains the default for
   a table with nothing saved — which is the case the plan was really protecting.
2. **Every action reads chapters, never rows.** After §3.2's audit, a right-click
   "Tạo lại 30 chương" on a status-sorted table sends 30 *chapter indices* to the worker,
   in chapter order, exactly as today. This is the single most important test in item 3.
3. **The video parts list stays part-ordered by default and is never re-numbered by a
   sort.** `_part_number` is derived from the chapter range (`tab_video.py:761-780`), and
   its docstring already warns "Never the row's index: … numbering by position renamed a
   part the moment it was viewed". Sorting must not create a second way to make that
   mistake — which is exactly why #5 gets a `first_num` key rather than a row map.
4. **Two lists are not sortable at all** and the plan says why rather than shipping a
   header that reorders them: the sync log (#8, chronological *is* the information) and
   the Find & Replace breakdown (#10, whose `itemDoubleClicked` handler is documented as
   depending on row == match index, `find_replace_dialog.py:188-199`). Making #10 sortable

   target that feature 064 shipped deliberately, so it belongs in its own turn.

## 3.6 Persistence

One `AppConfig` pair rather than ten properties (`config.py` is already 738 lines):

```python
def sort_state(self, list_id: str) -> tuple[int, Qt.SortOrder] | None
def set_sort_state(self, list_id: str, column: int, order) -> None   # QSettings key "sort/<list_id>"
```

`list_id` is a stable string per list (`"chapters.scrape"`, `"chapters.translate"`,
`"chapters.audio"`, `"audio.source"`, `"video.parts"`, `"cleanup"`, `"onedrive.sync"`,
`"names"`). Saved from `horizontalHeader().sortIndicatorChanged`, applied after the first
populate. Two rules:

- **Column *index* is persisted, not the column's meaning.** A future column insertion
  would silently re-point a saved sort. Guard with a stored `len(COLUMNS)`: if the count
  changed, drop the saved state and fall back to the default. Cheap insurance against a
  bug that would be invisible.
- **Per-user, not per-novel.** A sort preference is about how the user reads a table, not
  about the novel; putting it in `meta.json` would mean the video tab re-sorts itself when
  you switch novels. (Contrast `video_settings`, which is per-novel for the opposite
  reason — `models.py:60-69`.)

The picker (#12) is not persisted: it has one sensible order.

## Tests

Conventions taken from the existing suite: `tests/conftest.py` gives every test its own
`AppConfig` via an autouse monkeypatch of `AppConfig.__init__`, plus `sample_meta`,
`sample_refs`, `library_dir` and a session-scoped offscreen `qapp`. GUI tests are
class-grouped with sentence-shaped names; pure modules get their own `test_<module>.py`
with a round-trip test and a parametrised corrupt-input test
(`tests/test_video_windows.py`, `tests/test_name_glossary.py` are the models).

**`tests/test_shortcuts.py`** (new, `qapp`) — the pure half plus the dispatchers:
`selection_as_text` on a multi-row multi-column selection is TSV in view order;
it prefers a long tooltip over a truncated display (the reason `enable_cell_copy` exists);
it falls back to the current cell when nothing is selected;
**a `QLabel` with `TextSelectableByMouse` still copies through the dispatcher** (the
flag-2 regression guard, and the one test that would have caught the naive Edit menu);
a read-only `QPlainTextEdit` is not mutated by `paste_into`/`cut_from`;
an unrecognised widget returns `False` so Qt's own handling survives.

**`tests/test_main_window.py`** — new `class TestEditMenu`:
the Edit menu exists with six actions carrying `StandardKey` sequences (not literal
`"Ctrl+C"`, so Windows and macOS are one code path);
**`grep`-style structural assertion that no `QShortcut` for `StandardKey.Copy` exists
anywhere under the window** — the ambiguity regression, which is invisible except as a
Qt warning on stderr;
triggering `Sao chép` with a table focused puts the selection on the clipboard;
triggering it with a `QLineEdit` focused does not corrupt the clipboard.

**`tests/test_shortcuts_filter.py`** (new) — `EditShortcutFilter` handed synthetic
`QKeyEvent`s, in the style of `TestDockActivate` (`test_main_window.py:342-380`): it
handles Copy over an item view, declines over a `QLineEdit`, and declines for unrelated
keys.

**`tests/test_rename.py`** (new, pure, no Qt) — `plan_rename` finds part folders, their
sidecars, the source (`-nguon-`) edition and merged audio; it refuses a plan with a
collision and moves nothing; `apply_rename` moves directories before their contents;
a `.upload.json` ends up beside its renamed `.mp4` (the "no duplicate publish" guarantee);
a novel with no exports yields an empty plan.

**`tests/test_storage.py`** — `slug_name()` is byte-identical to
`slugify(translated_title or title)` when `slug` is empty (**the no-migration
guarantee**, over `sample_meta` and a CJK-only title that slugifies to `"novel"`);
a pinned slug wins over a later `save_meta_translation`;
`rename_novel` writes `display_title` and `slug` in one `meta.json`;
`refresh_meta` leaves both untouched (extend `tests/test_project_meta_refresh.py`, which
already asserts exactly this shape for `names.json`).

**`tests/test_tab_video.py`** — extend the existing `display_title` tests (`:2883-2891`):
after a rename with migration, `_part_output_path` resolves to the moved file and the part
still reads "đã tạo"; without migration, it resolves to the *old* name and still reads
"đã tạo"; `_resync_title_sidecars` rewrites a generated `.title.txt` and leaves a
hand-edited one alone.

**`tests/test_sorting.py`** (new, `qapp`) — the cross-cutting guarantees:
sorting a chapter table by "Trạng thái" and then reading `source_rows` returns **chapter
indices in chapter order** (the §3.5 promise, and the test that fails loudest if a `.row()`
was missed);
`RowButtonDelegate.clicked` on a sorted table retranslates the chapter under the button;
`format_duration`'s output sorts wrong and the `SORT_ROLE` seconds sort right
(`3m05s` < `10s` as text, `185` > `10` as key);
`#` sorts 1, 2, 10 and not 1, 10, 2;
`set_chapters()` restores `#` ascending.

**`tests/test_cleanup_dialog.py`** — the one that matters: build the dialog, sort by
"Dung lượng", tick one row, assert `_ticked()` returns the item **that row displays**.
Written to fail against today's positional lookup even before sorting ships.

**`tests/test_onedrive_sync.py`** — the same assertion for `_ticked()` / `accept()`.

**`tests/test_widgets.py`** — extend `TestProjectPickerLabel` (`:396`): the picker lists
novels ordered by their displayed label, not by folder name.

**No existing test should need rewriting** except the row-index audit's callers, none of
which assert on view rows today (`grep -n "\.row()" tests` is limited to model-level
assertions).

## Risks and open questions

**Decisions to confirm before implementation**

1. **Is `display_title` the name the user means?** The plan assumes yes: one editable
   name, already used for the video/thumbnail/description/YouTube title, now also driving
   filenames when the user asks. The alternative — editing `translated_title` — cannot be
   made safe against `refresh_meta` and re-translation. **ANSWERED: yes.**
2. **Default for the migration prompt.** ~~The plan defaults to "đổi tên cả file"~~
   **ANSWERED: "Chỉ đổi tên hiển thị" is the default button.** Migrating files stays on
   offer, one click away, but the safe branch is what Enter selects. This also means
   §2.3's slug pin does the heavy lifting: a display-only rename leaves every rendered
   file where it is, and the pin is what keeps them findable afterwards.
3. **How many parts and gigabytes does the user's real library hold?** **ANSWERED: the
   library is small**, so the OneDrive re-upload cost of a migration is not the deciding
   factor — but the default in (2) is the safe one regardless.
4. **Should the project folder be renamed?** The plan says no (§2.5). If the user does
   look at the library in Finder and cares, it is a separate turn requiring the novel to
   be closed first.
5. **Persist sort per user or per novel?** Plan says per user (§3.6).
6. **Should Find & Replace results (#10) sort?** Plan says not in this turn; it changes a
   jump target feature 064 shipped deliberately.

**Risks**

- **Ambiguity window.** Steps 1.2 (remove the `QShortcut`) and 1.3 (add the Edit menu)
  must land together. Between them, ⌘C on a table does nothing; if they land in the wrong
  order, ⌘C does nothing *and* prints a Qt warning nobody reads.
- **The `QLabel` regression is silent.** Nothing crashes; ⌘C on the "Thông tin truyện"
  header just stops working. Only the named test catches it.
- **A partial `apply_rename`.** A permission error or an antivirus lock (Windows) halfway
  through leaves some parts under the old slug and some under the new, with `meta.slug`
  written or not. Mitigation: pin the slug **after** the moves succeed, report the moves
  that did happen, and make `plan_rename` idempotent so re-running finishes the job. A
  fully transactional folder rename is not available on either platform.
- **Slug collisions between novels.** `slugify` strips non-ASCII and truncates at 40
  chars, so two Vietnamese titles can produce the same slug and their `exports/video/`
  trees are only separated by the project folder. Within one project this is refused by
  `plan_rename.collisions`; across projects it was already possible and is unchanged.
- **In-flight jobs.** A rename during a `VideoWorker`/`MergeWorker` run would move a
  folder the worker is writing into. Blocked by `has_running_workers()`, but the guard is
  per-`Workspace` — a novel open in one workspace and being uploaded from another is
  prevented by `MainWindow._claim_project` (`main_window.py:243-266`), which is what makes
  the single guard sufficient. Worth re-reading that guard during implementation.
- **`.upload.json` is the highest-stakes file in the repo.** Losing one re-publishes an
  episode to a live YouTube channel (`youtube_upload.py:723-745`). `apply_rename` must
  move it with the part, and the test asserting that must exist before the GUI does.
- **Sorting a table mid-run.** `setDynamicSortFilter(False)` stops rows jumping as a run
  progresses, but a manual header click during a run still reorders under the user's
  hands. Acceptable and normal; worth one look on a real run.
- **Offscreen ≠ on-screen.** Every measurement here is `QT_QPA_PLATFORM=offscreen`. The
  Edit menu's placement in the macOS native menu bar, and whether the app's dark QSS
  (`style.py:304-306` styles `QMenuBar` but nothing styles a sort indicator) renders the
  header's sort arrow legibly, both need one look on a real window.

**Out of scope**

Renaming the project folder; editing `title`/`translated_title`; renaming already-exported
`.docx`/`.epub`/`.md`; changing a published YouTube video's title; moving an existing
OneDrive mirror; re-rendering thumbnails that carry the old name; sorting the sync log,
the Find & Replace breakdown or the novel tab bar; a Find (⌘F) shortcut wired to
`FindReplaceDialog` (a genuinely good idea, and a different feature); filtering as opposed
to sorting.
