# 070 — Scraper adapter for timotxt.com

## Ask (user)

> support for this site: https://www.timotxt.com/2608569069/

## Site survey (done before writing this — all figures observed, not assumed)

Surveyed against the novel the user linked, id `2608569069` (376 chapters).

### Access

Plain HTTP, HTTP 200 from `curl` with an ordinary desktop UA. **No Cloudflare challenge, no
JS rendering, no cookie.** So the standard `HttpClient` is enough — neither `cf_browser.py`
nor `browser.py` should be needed. Worth re-confirming during implementation, since that is
the single biggest cost difference between adapters.

Served UTF-8 with a correct charset header. `<html lang="zh-cmn-Hant">` — **Traditional
Chinese**, like sto9. `source_lang` stays `"zh"`; no encoding fixup expected.

### URL shapes

| page | URL |
|---|---|
| landing / detail | `https://www.timotxt.com/<id>/` |
| **full chapter index** | `https://www.timotxt.com/<id>/dir` |
| chapter | `https://www.timotxt.com/<id>/<n>.html`, `n` = 1..376 |

`<id>` is a run of digits. The `www.` may or may not be present — `matches()` should accept
both, as the other adapters do.

### ⚠️ The landing page's chapter list is truncated — this is the trap

`https://www.timotxt.com/<id>/` carries only **13** chapter links: a "開始閱讀" link plus the
~12 most recent chapters, newest first. It does **not** say it is partial. For a 376-chapter
novel that is a 13-entry list that looks entirely normal.

**This is the same trap `sto9.py` documents at length**, and the consequence is identical:
`ChapterRef.index` is dense and positional, so saving a partial list files chapter 376's text
under row 2. `replace_toc` preserves content across re-scans, so a later good scan rewrites
titles and URLs while leaving the wrong bodies in place. Read `sto9.py`'s module docstring
before designing this — it decided to **raise rather than fall back** to a list the page has
already shown to be incomplete, and the same reasoning applies here.

The full list is at `/<id>/dir`.

### The `/dir` page has duplicates

388 `<a>` links matching `/<id>/<n>.html`, of which **376 are unique** — 12 are duplicated.
The page holds two lists:

- `ul.flex.one.two-700.three-900.all` — the real index, **376 links, ascending 1→376**
- `ul.flex.one.two-700.three-900` (no `all`) — a recent-chapters block, 12 links

The `all` class is what distinguishes them. Selecting on the container rather than
de-duplicating a flat link scrape is the cleaner fix, but either way **the adapter must not
emit 388 refs**. A count assertion in the tests is worth having.

### Chapter page

- `<title>` and the `<h1>`/`<h2>` heading both give the chapter title (e.g. `第1章`) — short,
  and notably *not* prefixed with the novel name.
- Body container: `div#chapterWarp.warp`.
- **Paragraphs are `<p>` elements, not `<br>`-separated** — 118 `<p>` in chapter 1, zero
  `<br>`. This differs from `sto9.py` / `shuba69.py`, whose `<br>` handling is *not* the
  right reference here. Check whether `#chapterWarp` also contains navigation or ad chrome
  that must be excluded from the body.
- Nav links present: 上一章 / 目錄 / 下一章. On chapter 1, 上一章 points at chapter 1 itself.

### Metadata

**No OpenGraph tags at all** (unlike sto9, whose adapter reads `og:novel:*`). Metadata has to
come from the markup:

- `<title>`: `《<novel title>》(<author>)小說在線閱讀` — both title and author are in there.
- Body text also carries `作者： <author>` and a `分類：` category link.
- A description paragraph is present on the landing page.
- Cover image: locate one during implementation; not confirmed by this survey.

Parsing the `<title>` is tempting but brittle. The plan should decide between that and the
in-body `作者：` label, and say why.

## Scope

Add `src/noveltrans/scrapers/timotxt.py` implementing `SiteAdapter`'s three abstract methods
(`fetch_metadata`, `fetch_chapter_list`, `fetch_chapter`) plus `matches()`, and register it in
`scrapers/__init__.py`'s `_import_adapters()`.

Follow the house pattern: a module docstring that documents the site's quirks and the
*reasoning* behind each decision — `sto9.py` is the model, and it is also the closest
relative (truncated list, Traditional Chinese, no Cloudflare).

## Test plan sketch

Every other adapter has a `tests/test_scrapers_<name>.py` built on saved HTML fixtures rather
than live requests — follow that exactly. Cover at minimum:

- `matches()` accepts the user's URL with and without `www.`, and rejects other sites.
- The chapter list comes from `/dir` and has **376 refs, not 388 and not 13** — the
  duplicate-block and truncation traps, pinned.
- Refs are in ascending chapter order with dense, positional `index` values.
- Body extraction joins `<p>` paragraphs and excludes any nav/ad chrome.
- Metadata yields the novel title and author separately.
- **A guard that the truncated landing page is never accepted as the chapter list** — the
  sto9 lesson, as an explicit test.
