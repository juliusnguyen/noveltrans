## [PLAN] 070.01-INITIAL-PLAN — 2026-08-29
Generated plan: `070.01-INITIAL-PLAN.md`

Four corrections to the survey in `070.00-PROMPT.md`, all measured live: the site DOES carry
OpenGraph tags (as `meta name=`, not `property=`, which is why the survey's probe missed
them); the cover is `og:image`; there are no `&emsp;` indents; and `#chapterWarp` has more
chrome than the survey recorded, including an **unclassed** notice `<div>` that no
class-based rule can name.

**The survey missed the feature's real risk surface entirely.** Chapter bodies are
character-obfuscated: ~2–5% of characters are replaced with visually-similar Hangul
syllables, server-side, with a different random subset on every request. Verified
independently before accepting the plan — two fetches of the same chapter returned 117
paragraphs each with identical paragraph lengths but different text (65 vs 64 Hangul chars),
and 26 mappings were recovered from that single pair with **zero conflicts**. No `@font-face`
on the page, so it is not a webfont trick; the corruption is in the delivered text and no
browser renders it correctly either. Titles and the description are clean — bodies only.

The plan's answer is a fixed substitution table applied to bodies only, chosen because its
worst case (an unmapped glyph) equals the do-nothing baseline, so it can under-correct but
never damage clean prose. Building it needs a one-off sampling script.

### The table, and why it is trustworthy

Built from 20 chapters of the reference novel plus 8 of a second novel, two fetches each:

- **122 mappings, zero conflicts** — a Hangul syllable never resolved to two different Han
  characters, which is the check that would have invalidated the whole "fixed table" premise.
- **Cross-novel: 80 shared keys, 80 agree — SITE-WIDE, not per-novel.** This was the
  assumption the design rests on, so it was tested rather than assumed.
- Convergence was visible in the run: the second novel's later chapters contributed +1 and
  +2 new mappings, against +19/+20 for the first novel's early ones.

The decoder can only under-correct: every key is a Hangul syllable, so no Chinese, Latin,
digit or punctuation character is reachable however incomplete the table is, and an unmapped
glyph survives verbatim. Its worst case is exactly the do-nothing baseline. That asymmetry is
what made a static table preferable to the alternatives — a runtime two-fetch merge would
have doubled the request budget (376 → 752 per novel) and *still* left residue, since a
character garbled in both draws stays garbled.

### Two traps encoded deliberately in the fixtures

1. **The landing page's 13-link list**, which is worse than sto9's because it runs
   newest-first — accepting it would file chapter 20 at index 1 and chapter 1 at index 0.
   The adapter never parses the landing page for chapters at all, not even as a fallback,
   because unlike sto9 there is no short-novel case where doing so would be safe.
2. **`/dir`'s recent block sits FIRST in document order**, so a flat anchor scrape returns
   the last 12 chapters reversed at the front. Fixing the count without fixing the order
   would not have saved it — hence container selection, with the fallback sorting by chapter
   number rather than trusting document order.

Safety rests on a self-contained invariant rather than a cross-check: chapter URLs embed the
reading position, so `chapter_numbers(refs) == [1 … N]` *proves* the list is a dense prefix
from chapter 1. The landing page's stated total is an upgrade from "prefix" to "complete",
never a requirement — so a dead landing page does not fail an otherwise perfect scan, which
is its own test.
