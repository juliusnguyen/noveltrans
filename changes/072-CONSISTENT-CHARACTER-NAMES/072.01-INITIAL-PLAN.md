# 072.01 — Initial plan: consistent character names (direction B)

## Summary

Two changes, one behavioural and one new:

1. **Ungate** the Hán-Việt substitution at `gui/workers.py:257` so it runs for every engine on
   a `zh → vi` run, not only Google.
2. **Persist** the glossary per novel as `names.json` beside `meta.json`, with a review dialog
   on the Dịch tab where the user corrects a reading, disables a false positive, or types in a
   name the detector missed. A re-detect merges into that file and **never overwrites a
   reading the user edited**.

The run stops building the glossary from scratch every time; it reads the sidecar. A novel
with no sidecar auto-builds one on its first run and writes it out, so existing Google users
lose nothing and LLM users gain consistency without visiting a dialog first.

## Additions to the prompt's findings

- **The problem is worse on simplified text than the prompt recorded.** `寧 → ninh`,
  `檸 → nịnh`, `柠 → nịnh` as stated — but also **`宁 → trữ`**. `宁` is the simplified form of
  `寧`, and the table gives it the reading of the *original, unrelated* `宁` it was merged
  with. So on a simplified novel the Google path today produces **`Hạ Trữ Thất`** from
  `夏宁七`: a fourth reachable output, from our own data rather than from the model, and a
  concrete regression case. (Spot-checked ~15 other simplified/traditional pairs — `后/後`,
  `发/發`, `云/雲`, `苏/蘇`, `会/會` all agree. `台/臺` differs too, but that is a genuine
  polyphone rather than a merge artefact. `宁` is an outlier, not a systemic table problem.)
- **`to_hanviet`'s all-or-nothing rule bites in practice.** Confirmed at `names.py:107`
  (`return None`), with a real example: `婳` (common in web-novel given names) has no entry, so
  `江婳` is dropped whole. The review list is where that gets fixed by hand.
- **`apply_glossary` also rewrites the novel title/description/author** (`workers.py:268-269`,
  `276`), gated on `project.meta.translated_lang != self.target_lang` (`workers.py:265`) — it
  runs **once per novel, ever**. So a later name correction never revisits the novel title.
  That belongs in the "what this does not promise" list.

## Design decisions

### 1. Storage — a `names.json` sidecar at the project root

The codebase has all three shapes and documents why each was chosen:

| Shape | Precedent | Why it was chosen there |
|---|---|---|
| Scalar on `NovelMeta` | `display_title`, `video_image_path` (`models.py:52-72`) | one small value that is part of the novel's identity and must survive a re-scan |
| Dict inside `meta.json` | `video_settings` (`project.py:942-962`) | a bag of keys written individually as the user touches them — hence `save_video_settings` merges |
| Standalone sidecar JSON | `video_manual_windows.json` (`video_windows.py:1-70`) | a user-override map with its own lifecycle, read from a worker thread and written from the GUI thread, pure and unit-testable without sqlite |

**Recommendation: the sidecar.** `src/noveltrans/name_glossary.py`, mirroring
`video_windows.py`, writing `<project>/names.json` with the same atomic temp-and-replace
(`video_windows.py:58-65`).

- **Size and churn.** Hundreds of entries. `meta.json` is read whole on every
  `NovelProject.open` and *rewritten whole* by nine `save_*` methods (`project.py:838-987`). A
  glossary there is re-serialised every time the user saves a YouTube tag list.
- **Two threads.** `TranslateWorker` opens its own `NovelProject` inside `run()` (a rule stated
  at `workers.py:1-6`) while the dialog writes on the GUI thread — exactly the split
  `video_manual_windows.json` already handles.
- **Testable without sqlite or Qt**, like `tests/test_video_windows.py`.
- **Backup is free.** `onedrive_upload.collect_payload` walks `rglob("*")`
  (`onedrive_upload.py:886`) and `_is_excluded` already drops `*.tmp`, so the sidecar is
  mirrored and the atomic write's temp file never is.

Rejected: a **SQLite table** needs a `_SCHEMA` plus `_migrate` entry (`project.py:44-84`,
`:149-170`) and buys nothing — the glossary is only ever read whole. A **`NovelMeta` field**
adds a fourth thing `refresh_meta` must remember to exclude; a sidecar is excluded by
construction.

**On re-scan:** `refresh_meta` (`project.py:853`) touches only the six scraped fields, and
`replace_toc` (`project.py:301-330`) only chapter rows — `names.json` is untouched by both.
Correct in each case, but the stored `count` goes stale as chapters arrive. The promise:
counts are "as of the last detection", shown with a date and chapter count, refreshed by
"Dò lại", which merges.

### 2. Data model — six fields, and one merge rule

```json
{"version": 1, "detected_at": "…", "chapters_scanned": 195,
 "names": [{"source": "夏檸七", "reading": "Hạ Ninh Thất", "auto": "Hạ Nịnh Thất",
            "edited": true, "enabled": true, "count": 812, "origin": "auto"}]}
```

A **list**, not a dict: the UI is a table sorted by count, and the report asked for a list to
review.

| Field | Why it is the minimum |
|---|---|
| `source` | the Chinese string; the key |
| `reading` | what actually gets substituted |
| `auto` | what the detector produced last time — the anchor the merge rule needs; `""` when `to_hanviet` could not convert |
| `edited` | true once the user changed `reading` away from `auto`; the one bit the merge rule turns on |
| `enabled` | switch off a false positive without deleting it (a delete would return on the next detect) |
| `count` | ordering, and the user's confidence signal |
| `origin` | `auto` / `manual` — a hand-typed entry must survive a detect that does not find it, which is not derivable from `count == 0` |

**The merge rule — `merge_detected(stored, detected)`:**

> **A detection never changes `reading` on an entry whose `edited` is true, and never removes
> an entry.**

- **In both** → keep the stored entry; refresh `count` and `auto`; update `reading` from `auto`
  **only if `edited` is False** (so an unedited entry still tracks a future table improvement).
  `enabled` always comes from storage.
- **Detection only** → append: `reading = auto`, `edited = False`, `enabled = True` (or `False`
  when `auto == ""`), `origin = "auto"`.
- **Storage only** → keep, set `count = 0`. This protects a manual entry the detector cannot
  see — the escape hatch for the prompt's finding 4.

Supporting rules: editing `reading` back to equal `auto` clears `edited`. And
`applied_glossary()` returns `{source: reading}` only for entries that are `enabled`, have a
non-empty `reading`, have a `source` containing CJK, and have a `reading` containing **no**
CJK — guards against `apply_glossary`'s blind `str.replace` (`names.py:196-200`), where an
empty replacement would *delete* every occurrence of the name and a CJK-bearing one would
confuse `cjk_count`'s retry scoring (`base.py:85-90`).

### 3. Ungating — safe for LLMs, with one prompt clause

`apply_glossary` (`names.py:194-200`) is a naive longest-first `text.replace`. On balance it is
**easier** for an LLM than for Google: the source becomes code-switched (`Hạ Ninh Thất皺眉`) and
the model copies the Latin run and translates around it. Neither Chinese nor Vietnamese
inflects around a proper noun. This repo already treats mixed script as a normal intermediate —
`base.py:87` cites exactly `"Phó Thanh Từ皺眉"` as a tolerated model output.

Three risks, none disqualifying: **retry scoring** improves (substitution lowers CJK on both
sides); **chunking** grows a few percent since a 3-character name becomes ~13, costing at most
one extra request; and **a false positive is now much worse**, because it corrupts the Chinese
before the model sees it. The last is what the review list and `enabled` exist for.

One LLM-specific hazard needs a defence: the prompts tell every engine to render names in
Hán-Việt and to "translate every word", so a model seeing `Hạ Ninh Thất` may "improve" the
spelling. **Add one clause to the `vi` entry of all three `_NAME_RULES`:**

> "Any name already written in Latin script is a Vietnamese Hán-Việt name: copy it EXACTLY,
> character for character — never re-spell it, never translate it, never convert it to pinyin."

This is **not** direction C: it is constant-size and does not list the glossary per chunk.

**Keep the `target_lang == "vi"` half** of the condition — the readings are Vietnamese and a
`zh → en` run must not get them. Drop only `engine_name == "google"`.

**Also change where the glossary comes from.** Today it is built inside `run()` from a
whole-novel corpus join plus jieba/opencc init (`workers.py:258-262`) — seconds to minutes, and
uninterruptible before the first `_checkpoint()`. With the sidecar the run reads a small JSON:
faster, deterministic, identical across engines. A novel with **no** sidecar auto-builds one and
persists it — chosen over "only apply what the user reviewed", because that would regress every
existing Google user and would fail this same user again ("names still inconsistent until you
find the dialog"). **The dialog is the correction path, not the activation path.**

### 4. UI — a modal dialog off the Dịch tab

A `👤 Tên nhân vật` button next to `Tìm & thay thế` (`tab_translate.py:169-190`): name
substitution is a translate-time concern, and the tab already holds the other per-novel text
tools plus the `_busy()` discipline that stops them writing rows a batch is writing.

Modal `QDialog` in `gui/name_glossary_dialog.py`, following `RewriteDialog`
(`rewrite_dialog.py:1-17`). `FindReplaceDialog` is modeless because double-clicking a row jumps
the tab to a chapter; there is no equivalent need here.

Header: `Đã dò 214 tên từ 195 chương — lần cuối 29/08/2026`, or `⚠️ Chưa dò lần nào`. Then a
`QTableWidget` (`cleanup_dialog.py:59, 136-149`):

| ✓ Dùng | Tên gốc | Cách viết (sửa được) | Máy đề xuất | Số lần |
|---|---|---|---|---|
| ☑ | 夏檸七 | `Hạ Ninh Thất` ✎ | Hạ Nịnh Thất | 812 |
| ☐ | 江婳 | *(trống)* | — không đọc được | 41 |

Checkbox via `Qt.ItemFlag.ItemIsUserCheckable` on column 0; only "Cách viết" editable; edited
rows marked so the user's own work is visible; sorted by count descending. Buttons:
`🔍 Dò lại từ bản gốc` · `+ Thêm tên` · `Xoá dòng` · `Lưu` · `Đóng`.

**`+ Thêm tên` is the escape hatch** for every gap in finding 4. It appends a blank row;
typing the Chinese auto-fills from `to_hanviet(source)` when it converts, and **shows a live
occurrence count over the novel's `content`**. That count is the important part — it catches
the two likeliest user errors (a typo, and pasting the traditional form into a simplified
novel) before the entry is saved as a substitution that never fires.

Detection needs a thread: **`NameScanWorker(QThread)`** shaped like `CliModelsWorker`
(`workers.py:489-517`) — takes a `project_path`, opens its own project, emits
`scanned = Signal(list)`, joined in `shutdown()` (`tab_translate.py:890`) but **not** counted
in `has_running_workers()`, matching the reasoning at `tab_translate.py:884-886`.

`names.py` needs one additive function so the dialog can show what `build_glossary` discards:

```python
def detect_names(corpus: str, min_count: int = 5) -> list[tuple[str, str, int]]:
    """(chinese, hanviet or "", count) for every recurring name — INCLUDING ones
    to_hanviet could not convert, which build_glossary drops on the floor."""
```

`build_glossary` gets re-based on it, so every existing test passes unchanged and
`to_hanviet`'s `None` contract is untouched. **No heuristic is loosened** — `min_count` stays 5
in both the auto-build and the dialog, or the user would see names the run did not use.

### 5. Apply time vs edit time — and the repair offer

**Promised:** the glossary is applied at translation time, so it governs every chapter
translated **after** the edit. A run snapshots it once at the top of `run()`.

**Not promised:** it does not retro-fix chapters already translated, and it does not revisit
the novel title/description/author — written once, gated at `workers.py:265`.

**But it offers the repair.** When `Lưu` changes a reading from `old` to `new`, scan existing
translations with `find_replace.scan(...)` (`find_replace.py:66`). On hits, a consequences
dialog in the style of `tab_scrape._repair_residue` (`tab_scrape.py:308-343`):

> Đã đổi "Hạ Nịnh Thất" → "Hạ Ninh Thất". Tìm thấy **812 chỗ** trong **190 chương** đã dịch.
> - **Sửa luôn trong bản dịch** — nhanh, không tốn AI *(mặc định)*
> - **Dịch lại 190 chương đó** — xoá bản dịch cũ, kể cả sửa tay và bản viết lại
> - **Để nguyên**

*Sửa luôn* → `project.apply_replacements(...)` (`project.py:696`, one transaction), then the
tab's existing `_on_replacements_applied` (`tab_translate.py:608`). *Dịch lại* →
`clear_translations(indices)` (`project.py:989`) + `_start_translate(indices=…)`
(`tab_translate.py:432`) — both already exist and both already take `indices`, courtesy of 071.

A literal replace is the right default: a proper noun does not inflect. The one hazard is a
short reading colliding with an ordinary Vietnamese word, so **only offer the repair when the
old reading is two or more syllables**, always case-sensitive, always with the count shown
first. This is not direction D — it repairs only the exact `old → new` pair we already know.

The dialog is gated on `_busy()` exactly like `_open_find_replace` (`tab_translate.py:509-512`).

   Update the docstring's opening line, which says "for the Google engine" (`names.py:1`).

   `names_path`; `read_names` (tolerant: missing file, bad JSON, wrong shape → `[]`, per
   `video_windows.py:36-56`); `write_names` (atomic); **`merge_detected`** — write and test this
   first; `applied_glossary`; `build_from_project`. Docstring: why a sidecar, and the merge rule.
3. **`gui/workers.py`** — `NameScanWorker(QThread)` after `LmStudioModelsWorker` (~`:533`).
   Opens its own project, calls `build_from_project`, emits, never writes.
4. **`gui/workers.py:255-262`** — replace the gated build with a sidecar read plus first-run
   auto-build, keeping `target_lang == "vi"`, followed by a `_cancelled` check. Rewrite the
   comment above it, which explains a Google-only rationale. Everything downstream unchanged.
5. **`translators/{claude,cli_agent,lmstudio}.py`** — append the "already in Latin script → copy
   exactly" clause to the `"vi"` entry of `_NAME_RULES`, identical in all three as today.
6. **`gui/name_glossary_dialog.py`** (new) — per decision 4. Signals `applied = Signal(set)` and
   `retranslate_requested = Signal(list)`.
7. **`gui/tab_translate.py`** — the button (`:169-190`), `_open_names()` mirroring `_open_rewrite`
   (`:621-641`) with the `_busy()` gate; wire the two signals; add `_names_worker` to
   `shutdown()` but **not** `has_running_workers()`.
8. *(Optional, off the critical path)* — the `宁 → trữ` outlier: a name-context override beside
   `_SURNAME_READING_OVERRIDES` (`names.py:34-41`). Fixes the class rather than one novel, but
   it is a data judgement and the review list already covers it, so it must not gate the feature.

Sequencing: 1 → 2 (fully tested standalone) → 4 (**the reported bug is fixed here**) → 3, 6, 7
→ 5 anywhere. Step 8 last or never.

## Risks / out of scope

**Risks**

- **False positives now corrupt LLM input too** — blast radius goes from one engine to four.
  Mitigated by `enabled`, the review dialog, and never loosening `min_count`. Worth eyeballing
  the top 30 detected names on a real novel before shipping.
- **First-run latency.** The auto-build joins the whole novel and initialises jieba (~100 MB).
  Once per novel now instead of every Google run, but it happens before the first
  `_checkpoint()`, so a cancel during it is not honoured until it finishes. The `progress.emit`
  and `_cancelled` check make it visible and bounded.
- **The user's actual novel is still unconfirmed.** The `檸`/`宁` analysis matches the symptom
  shape, but the plan does not depend on it: whatever the real characters are, the dialog is
  where the reading gets pinned. Worth asking for the Chinese name during implementation purely
  to add a real regression case.
- **`apply_glossary` is a blind `str.replace`** (`names.py:196-200`) — a two-character name that
  is a substring of an ordinary word fires everywhere. Pre-existing; `enabled` is the answer;
  making the replace boundary-aware is a separate change with its own risk profile.
- **Chunk growth** — Vietnamese readings are ~4× longer than the Chinese they replace, so a
  name-dense chapter may cross `max_chunk_chars` and cost one extra request.

**Out of scope** — direction C's per-request glossary listing (the step-5 clause is a
constant-size guard, not a glossary in the prompt); direction D's "find names spelled three
ways" detector (only the exact `old → new` repair that falls out of an edit); direction E
(`min_count` stays 5, the surname lists and `to_hanviet`'s all-or-nothing rule are untouched —
`+ Thêm tên` covers all three gaps and is strictly safer); a glossary shared across novels
(names are per-work, and a global list would leak one novel's `Ninh` into another's `Nịnh`);
place names, realm and technique terms (the detector is surname-anchored); `en` targets.
