# 072 — Character names translated inconsistently between chapters

## Report (user)

> khi dịch các chương, tên của các nhân vật không đồng nhất lẫn nhau. ví dụ như ở tiểu
> thuyết này, tên của nhân vật là Hạ Ninh Thất nhưng ở chapter 195 thì bị dịch thành
> `Hạ Chanh Thất`. Hãy tìm kiếm nguyên nhân và cho một vài hướng để giải quyết tên nhân vật
> dịch đồng nhất.

## Cause — investigated, with what is certain separated from what is inferred

### Certain: the name glossary never runs for LLM engines

`src/noveltrans/translators/names.py` builds a Hán-Việt glossary from the whole novel and
pre-substitutes recurring names into the source before it is sent to the engine. That is
exactly the machinery this problem calls for — **and it is hard-gated to Google**
(`gui/workers.py:257`):

```python
if self.engine_name == "google" and self.target_lang == "vi":
    corpus = "\n".join(...)
    glossary = build_glossary(corpus)
```

For **Claude API, CLI Agent and LM Studio**, `glossary` stays `{}` and every
`apply_glossary(...)` call downstream is a no-op. The module docstring says so in its first
line — "Hán-Việt name glossary **for the Google engine**" — so this is a deliberate original
scope, not an oversight. But the consequence is that on LLM engines nothing whatsoever
enforces name consistency across a novel.

### Certain: the prompt asks for consistency it has no power to deliver

All three engine prompts say "Translate character names consistently" (`claude.py:17`) and
"Render ALL Chinese person and place names in Sino-Vietnamese (Hán-Việt)" (`claude.py:29`).
Both are correct instructions — but their scope is **one request**. There is no cross-chapter
memory, no glossary in the prompt, and `Translator.translate_chapter` (`base.py:94`) splits a
long chapter into several chunks that are each translated independently. So the model
re-derives every name from scratch, potentially several times *within* one chapter, and
"consistently" can only mean "consistently within this chunk".

### Certain: the character itself is ambiguous, and the app's own table disagrees with the user

Checked against `data/hanviet.json` (16,308 entries):

| character | Hán-Việt reading in the table | also a common word |
|---|---|---|
| `寧` | `ninh` | — |
| `檸` | `nịnh` | `檸檬` = lemon → Vietnamese **chanh** |

So for a name built on `檸` there are **three** plausible outputs and the model may pick any:

- **Ninh** — what the user says is correct
- **Nịnh** — what this app's own Hán-Việt table would produce
- **Chanh** — the *meaning* rather than the reading, which is what chapter 195 got

That last one is a well-defined failure: the model treated a name character as a word. And
the middle row matters for the fix — **simply switching the glossary on would give
consistency but still not the spelling the user wants.** Consistency and correctness are
separate goals here, and any solution needs a way to pin the *chosen* reading.

### Inferred, and worth verifying first

The reported name is not in the timotxt novel used for features 070/071 (chapter 195 there
contains no `夏`, `檸`, `寧` or `柠`), so this is a different novel and the exact source
characters were not confirmed. The `檸` analysis above matches the symptom shape exactly —
`Ninh` and `Chanh` are the reading and the meaning of one character — but the plan should
confirm the real characters from the user's novel before building on it.

### Also relevant: the Google path has its own gaps

If the user *is* on Google, the glossary runs but can still miss a name:

- `build_glossary(corpus, min_count=5)` — a name appearing fewer than **5** times in the
  whole novel is never detected.
- `to_hanviet` returns `None` if **any** character has no reading, which drops the entire
  name rather than converting the rest.
- `extract_names` only matches surname + 1-2 characters, where the surname must be in the
  hardcoded `_SINGLE_SURNAMES` / `_DOUBLE_SURNAMES` lists (`names.py:21-32`).

### Nothing is persisted

The glossary is rebuilt in memory on every translate run and stored nowhere. There is no
per-novel name list the user can look at, correct, or carry across runs — so even when the
detection works, a wrong reading can only be fixed by find-and-replace after the fact.

## Directions — the user asked for several; these are not mutually exclusive

Ordered roughly by effort. **B is the one that addresses both consistency and correctness**;
the others are each partial.

### A. Ungate the existing glossary for every engine

Delete the `engine_name == "google"` condition. Smallest possible change, reuses code that
already exists and is tested.

*Gets:* consistency on LLM engines — the same Chinese name becomes the same Vietnamese string
every time, because the substitution happens before the model ever sees it.
*Does not get:* the user's preferred spelling. The table says `nịnh`; the user wants `Ninh`.
*Also:* pre-substituting into Chinese source text is a bigger behavioural change for an LLM
than for Google — worth checking it does not confuse the model's grammar around the name.

### B. A. plus a per-novel, editable name list

Persist the detected glossary per novel and give the user a screen to review and correct it —
"these are the names I found and how I will write them", with an editable reading per name.

*Gets:* consistency **and** the final say on spelling; fixes the `Nịnh`/`Ninh` mismatch
permanently and per novel; makes the invisible visible, which is the actual complaint.
*Costs:* storage (a `names.json` beside `meta.json`, or a table in the project DB), a small
dialog, and wiring into the translate flow.
*Note:* this also gives somewhere to fix the "5+ occurrences" and "unknown character" gaps by
hand, without changing the detection heuristics at all.

### C. Give the model the name list instead of substituting

Keep the source text untouched and append the glossary to the translation prompt.

*Gets:* the model handles Vietnamese grammar around names naturally, and the source is not
mutated.
*Does not get:* a guarantee — an LLM can still deviate, which is the whole reason the Google
path substitutes rather than instructs. Also costs prompt tokens on every chunk.
*Best as a complement to B, not a replacement for A/B.*

### D. Normalise a novel that is already translated

Detect names rendered several different ways across existing translations and offer to unify
them — a targeted, name-aware find-and-replace.

*Gets:* repairs work already done, which none of A-C do.
*Does not get:* prevention.
*Note:* `find_replace.py` already does literal replace across a novel with a preview, so this
is closer to a detector plus a pre-filled batch than new machinery.

### E. Loosen the detection thresholds

Lower `min_count`, convert partially-known names character by character instead of dropping
them, widen the surname lists.

*Gets:* catches more names.
*Risk:* every loosening also catches more non-names. `extract_names`' 80%-follower rule and
`_is_common_word` filter exist precisely to avoid that, so this should be measured against a
real novel rather than tuned by feel.

## Decision taken with the user

**Direction B.** Ungate the existing glossary so it runs for every engine, *and* persist it
per novel as a list the user can review and correct.

That combination is chosen because A alone cannot deliver what was actually reported: the
user's novel needs `Ninh` where the built-in table says `Nịnh`, so consistency without an
override would produce a name that is uniform and still wrong. The editable list is also
where the Google path's gaps (a 5-occurrence minimum, names dropped whole when one character
has no reading) become fixable by hand without touching the detection heuristics — so it
covers both engine paths even though they fail differently.

Not chosen, and out of scope unless they fall out naturally: C (prompt-injected glossary — no
guarantee, and B's substitution makes it redundant), D (normalising novels already
translated — repair rather than prevention, and `find_replace.py` already offers a manual
route), E (loosening detection thresholds — every loosening also catches more non-names, and
B lets the user add a missed name directly, which is strictly safer).

## Still to establish

The engine and the novel were not confirmed. The plan must therefore work for **both** paths
rather than assuming one: on Google the glossary already runs and the failure is inside
detection, while on the LLM engines it never runs at all. Verify the real source characters
of the reported name against the user's novel before relying on the `檸` hypothesis.

## Test plan sketch

`names.py` is pure and already has tests — extend rather than replace. Cover: the glossary is
built for a non-Google engine; a name with an ambiguous character resolves to the pinned
reading rather than the table default; an edited reading survives a re-run; and — the
regression for this report — the same name in two different chapters produces the same
Vietnamese string.
