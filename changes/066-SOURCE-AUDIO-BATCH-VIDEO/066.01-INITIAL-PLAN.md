# 066.01 — Initial plan: source-audio video fails in batch mode

## Summary

`VideoWorker.run()` picks its planner with an `if/elif` chain that tests
`self.mode == "batch"` **before** `self.source_audio`, so the default "Theo lô" mode
plans over `project.chapters()` filtered by `audio_voice == "__source_audio__"` — which
matches nothing — and the run dies with *"Chưa tải mục audio nào từ trang nguồn trong
phạm vi đã chọn."*. The fix is to hoist the `source_audio` branch above the batch branch
(mirroring `MergeWorker.run()`, which already gets the order right), because source audio
has no chapter grid to lock. `_redo_all_videos()` in the video tab has the same blind spot
for a different reason — it calls `plan_merge_windows` directly instead of going through
`_windows_for_current_selection()`. Route it through that helper with a new
`honor_committed=False` keyword, so its confirm dialog matches what the redo-all worker
actually renders (fresh grid + manual boundaries) rather than the incremental-run plan.

Two adjacent defects found while verifying: the video tab never clears its `_locked_*`
caches on the source-audio path, and `tab_audio._start_merge()` has the identical
"preview plans over chapters" bug that blocks merging the source edition.

## Root cause

### 1. `VideoWorker.run()` — `src/noveltrans/gui/workers.py:1635-1667`

```python
1635  locked_part_numbers: dict[int, int] = {}
1636  if self.explicit_windows is not None:
1637      windows = self.explicit_windows
1639  elif self.mode == "batch":          # ← wins for a source-audio batch run
1645      locked = plan_locked_video_windows(
1646          project.chapters(), self.voice, self.batch_size, {**committed, **manual},
1647      )
1651  elif self.source_audio:
1652      windows = plan_source_windows(project.source_audio(), self.mode, ...)
```

With `voice == SOURCE_AUDIO_KEY` and `mode == "batch"`, `plan_locked_video_windows`
(`src/noveltrans/tts/video.py:459-464`) filters `c.audio_path and c.audio_voice ==
"__source_audio__"` over chapter rows → `avail == []` → returns `[]` → `_nothing_message()`
(`workers.py:1574-1578`) → the dialog.

`video_mode` defaults to **batch** (`tab_video.py:227`), which is why this is the everyday
path.

**Correction to the report:** the failure is *batch-mode only*. `mode="all"` ("Toàn bộ")
with source audio already reaches the `source_audio` branch and works today. The working
paths are: per-row **Tạo / Tạo lại** → `_render_one` (`tab_video.py:3075`) passes
`mode="range"`; right-click multi-select → `explicit_windows` (`tab_video.py:3094`).

### 2. `_redo_all_videos()` — `src/noveltrans/gui/tab_video.py:3000-3073`

Lines 3029-3031 plan with `plan_merge_windows(self.project.chapters(), voice, mode, ...)`,
so for `SOURCE_AUDIO_KEY` it gets `[]` and stops at its own "Chưa có audio" dialog
(3032-3038) — the worker is never launched. `_windows_for_current_selection()`
(`tab_video.py:630-655`) *does* branch on `SOURCE_AUDIO_KEY` at line 643, before the
`mode == "batch"` check at 651 — the ordering the worker needs.

### 3. (New) Stale locked caches on the source-audio path — `tab_video.py:643-650`

`self._locked_part_numbers` / `_locked_committed` / `_locked_manual` are written **only**
inside `_locked_batch_windows` (`tab_video.py:688-690`) and initialised once at
`tab_video.py:130-132`. The source-audio branch returns early without touching them, so
values left over from an earlier chapter-voice batch plan (or another novel — nothing
resets them in `_on_project_selected`) leak into:

- `_part_number()` (`tab_video.py:706-709`): in batch mode it returns
  `self._locked_part_numbers.get(window.first_num)` if present. A source-audio window with
  `first_num == 1` would inherit a chapter part number → the table's "Phần N" and the
  worker's `part_number(first_num, batch)` fallback could disagree.
- `_chapter_range_item()` (`tab_video.py:985-988`): would paint a bogus "⚠️ bị khoá ở mức
  này vì đã tách/gộp thủ công" on source-audio rows.

### 4. (New) Same bug shape in the audio tab — `src/noveltrans/gui/tab_audio.py:1060-1070`

`_start_merge()` previews with `plan_merge_windows(self.project.chapters(), voice, ...)`
while the combo can be set to `SOURCE_AUDIO_KEY` (`tab_audio.py:473-477`) and the worker

So "Ghép audio" on the source edition dies at the tab's own "Chưa có audio" dialog in
*every* mode — `MergeWorker` itself (`workers.py:1416-1434`) is correct and simply never
runs. The report's note that "`MergeWorker.run()` … is correct" is right; its *caller* is
not.

## Design decisions

### D1 — `plan_source_windows` handles `mode="batch"` fine; no new planner needed

`plan_source_windows` (`src/noveltrans/tts/merge.py:62-86`) filters on `r.audio_path` only
and delegates to the shared `_group_windows` (`merge.py:88-124`), which supports
`"all" | "range" | "batch"` identically for both planners. Windows are keyed by
`r.index + 1` where `SourceAudio.index == ord - 1` (`src/noveltrans/models.py:188-190`),
i.e. release ordinals. `batch >= 1` is guaranteed by the spinbox range
(`tab_video.py:259`). The tab already previews exactly this (`tab_video.py:643-650`) and
`tests/test_video_downloaded_audio.py::TestPlanSourceWindows::test_each_release_can_be_its_own_part`
asserts `batch=1` numbering `[1, 2, 3]`. The worker only needs to call the planner the tab
already calls.

### D2 — Downstream of the source branch is already proven safe

Everything after the plan reads a narrow protocol that `SourceAudio` implements as
properties (`models.py:187-206`): `audio_path`, `audio_seconds`, `audio_source` (always
`AUDIO_SOURCE_DOWNLOADED`), `translated_title`, `index`. Concretely:

- `MergeSegment(...)` construction and `chapter_marker_title(c)` (`workers.py:1674-1682`,
  `merge.py:150-154`): `audio_source != "original"` → uses `translated_title` → the release
  title. Works.
- `locked_part_numbers` stays `{}` on the source branch → part numbers come from
  `part_number(window.first_num, self.batch_size)` (`workers.py:1712`), matching the tab's
  fallback (`tab_video.py:709`) — see D3.
- `video_part_name(slug, first, last)` (`video.py:370-378`) and the
  `whole_novel = total == 1 and self.mode == "all"` rule (`workers.py:1684`) match the
  tab's identical rule in `_rebuild_video_rows` (`tab_video.py:1196`).
- `skip_existing` / `effective_created(resolved)` (`workers.py:1694-1699`) are pure
  file/sidecar checks — no chapter concepts.
- `_write_metadata` (`workers.py:1745-1812`) uses only `segments` + `project.meta` +
  `project.counts()["total"]`.

This is all already exercised in production by the `mode="range"` per-row render the user
says works; the fix puts batch on the same code path.

### D3 — Part numbering stays release-ordinal grid arithmetic, and the tab caches must be cleared

The tab comment at `tab_video.py:646-648` and the `plan_source_windows` docstring
(`merge.py:70-75`) both state numbering counts **releases**. Tab and worker agree *only if*
`_locked_part_numbers` is empty: tab `_part_number` →
`part_number(window.first_num, self.video_batch_size.value())`; worker →
`part_number(window.first_num, self.batch_size)` — same function, same inputs.

**Decision:** clear `_locked_part_numbers`, `_locked_committed`, `_locked_manual` in the
source-audio branch of `_windows_for_current_selection`, so that agreement is guaranteed
rather than accidental. Cheap, and it also kills the bogus "bị khoá" warning.

### D4 — Manual split/merge and committed-window discovery must **not** apply to source audio

**Recommendation: skip both.** Reasons:

1. **Different number space, one shared file.** `video_manual_windows.json`
   (`src/noveltrans/video_windows.py:23-49`) is a per-novel `{first_num: last_num}` map.
   Chapter windows key it by chapter number; source windows would key it by release
   ordinal. Feeding either map into the other's plan silently corrupts both (a manual split
   of "chapters 1-10" would reshape "releases 1-10").
2. **`discover_committed_video_windows` scans by filename** (`video.py:395-417` via
   `iter_rendered_part_dirs`, `video.py:420-439`), matching any `{slug}-NNNN-MMMM` folder.
   Chapter parts and source parts share that namespace, so a rendered chapter part 1-5
   would freeze source-audio window 1-5.
3. **The semantics don't exist for releases.** Commit-locking solves "a part was rendered
   before translation caught up, don't retroactively grow it" (`video.py:444-457`). A
   release is atomic: it is either downloaded or not; a batch of releases never grows
   underneath a rendered part the way a batch of chapters does.
4. **The tab already made this call** at `tab_video.py:643-650` and the table is the
   contract the render must match.

Per-part skipping is unaffected: `skip_existing` still works window-by-window through
`effective_created(resolved)` in the render loop (`workers.py:1694-1699`), which needs no
plan-level locking.

**Corollary (optional step 7):** the split/merge context-menu entries at
`tab_video.py:800-814` are offered for source-audio rows in batch mode and would write
release ordinals into `video_manual_windows.json`, poisoning the chapter plan.

### D5 — `_redo_all_videos` should call `_windows_for_current_selection(honor_committed=False)`

The naive switch (plain `_windows_for_current_selection()`) fixes source audio but is
**not** behaviour-preserving for the chapter case, in a way that matters:

| path | windows the **confirm dialog** counts | windows the **worker** renders (`skip_existing=False` → `workers.py:1641-1648` passes `committed={}`) |
|---|---|---|
| today | `plan_merge_windows` — fresh grid, manual **ignored** | fresh grid + **manual honored** → already disagrees when a manual split exists |
| naive switch | `_locked_batch_windows` — committed **and** manual honored | fresh grid + manual honored → disagrees when anything is committed short |
| proposed | committed ignored, manual honored | identical |

`VideoWorker.run()`'s long comment (`workers.py:1618-1630`) states the rule explicitly:
redo-all honors manual boundaries but blows past auto-discovered commits.
`tests/test_video.py::TestVideoWorker::test_skip_existing_false_ignores_locked_windows_and_uses_the_fresh_grid`
(line 968) and `::test_redo_all_still_honors_a_manual_split_boundary` (line 1031) pin
exactly that. So the tab's redo-all preview should be "manual only" — which is what
`honor_committed=False` produces, and which is *more* correct than today for the
manual-split case.

**Guard note:** `_locked_batch_windows` writes the `_locked_*` caches that the table's
numbering/warnings read. Redo-all must **not** overwrite them with a committed-blind plan
(a subsequent per-row "Tạo lại" calls `_part_number` without first refreshing —
`tab_video.py:3075-3093`), so the cache writes are guarded by `honor_committed`.
`_redo_all_videos` itself never calls `_part_number` — it only needs counts,
`_part_output_path` and `_part_uploaded` — so nothing there regresses.

**Range validation:** `_redo_all_videos` currently validates `start > end` at
`tab_video.py:3013-3015` before planning, while `_windows_for_current_selection` just
returns `[]` for an inverted range (`tab_video.py:641-642`). **Keep the explicit
validation** so the user still gets "Phạm vi sai" rather than "Chưa có audio".

### 1. `src/noveltrans/gui/workers.py` — hoist the `source_audio` branch (the actual bug fix)

In the `SOURCE_AUDIO_KEY` branch (**643-650**), clear the caches before returning:

    # Nothing is locked for the source edition (see `_locked_batch_windows`), and

### 3. `src/noveltrans/gui/tab_video.py` — `_locked_batch_windows` honours the flag and guards its cache writes

At **line 657**:

```python
def _locked_batch_windows(self, voice: str, batch: int, *, honor_committed: bool = True) -> list:
    ...
    committed = (
        discover_committed_video_windows(self.project.video_dir, slug)
        if honor_committed else {}
    )
    manual = read_manual_windows(self.project.path)
    plan = plan_locked_video_windows(
        self.project.chapters(), voice, batch, {**committed, **manual}
    )
    # Only the table's own view (honor_committed=True) may refresh the caches: a
    # redo-all preview deliberately ignores commits, and writing that narrower plan
    # here would mis-number a per-row "Tạo lại" clicked before the next refresh.
    if honor_committed:
        self._locked_part_numbers = {w.first_num: part_num for part_num, w in plan}
        self._locked_committed = committed
        self._locked_manual = manual
    return [w for _, w in plan]
```

## Risks / out of scope

- **Filename namespace collision (pre-existing, not fixed here).** Source-audio parts and
  chapter parts both render to `{slug}-{first:04d}-{last:04d}.mp4` under the same
  `video_dir` (`tab_video.py::_part_output_path` / `video.py::video_part_name`). A novel
  rendered both ways will have part folders that overwrite each other and "đã tạo" ticks
  that read across editions. Fixing it means a distinct slug/subfolder for the source
  edition plus a migration for anything already rendered — a separate feature. It is the
  strongest argument for D4.
- **Manual split/merge on source-audio rows** writes release ordinals into the
  chapter-keyed `video_manual_windows.json`. Step 7 disables the menu entries; actually
  supporting per-edition manual boundaries is out of scope.
- **Redo-all preview vs. worker part numbers.** With a manual boundary present, the tab's
  cached `_locked_part_numbers` (committed-aware) can differ from the numbers `VideoWorker`
