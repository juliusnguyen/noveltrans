# 046 — Support `tieuthuyetmang.com` — history

## [RECON] — 2026-07-31

Measured against the live site before any planning, because feature 044 had just finished
paying for the opposite habit — four rounds of guessing a DOM that one diagnostic settled
in ten minutes.

- Plain `requests` reaches it: HTTP 200, ~130 KB, no Cloudflare challenge, no browser.
- **Next.js App Router.** No server-rendered chapter markup, but the landing page embeds
  React Server Component flight data in `self.__next_f.push([1,"…"])` — 9 pushes on the
  sample novel, a ~42 KB stream once concatenated.
- **The whole TOC is in that stream**, so `fetch_metadata` and `fetch_chapter_list` can
  share one request. Chapter objects carry `id` (ULID), `chapterNumber`, `title`, `isFree`,
  `hasAudio`, `isLocked`, `audioLocked`. 122 objects, numbered 1–122, unique, in order.
- **119 of the 122 chapters are `isLocked: true`.** Only 1–3 are free.
- Internal API routes referenced by the page chunk: `/api/stories/`, `/api/reading-history`,
  `/api/recommend`, `/api/favorites`, `/api/ratings`. Site routes seen as literals:
  `/truyen/`, `/doc/`, `/nghe/`, `/tac-gia/`, `/nhom-dich/`, `/hoi-vien`, `/dang-nhap`.

### The trap, found by falling into it

The stream also carries sidebar *recommended story* objects with identical field names. The
first `chapters_count` in the stream read 97 — a different novel's. Any parser that takes
the first match is wrong, and the plan encodes this as a deliberate fixture rather than
hoping a raw capture happens to contain it.

### Still unknown after recon: the chapter reader URL

Chapter objects have no slug and the client builds the hrefs, so nothing in the HTML gives
them away. Seven shapes were tried and all seven 404'd:
`/truyen/<slug>/chuong-1`, `/doc-truyen/<slug>/chuong-1`, `/truyen/<slug>/1`,
`/chuong/<slug>/1`, `/doc/<slug>/1`, `/doc/<slug>/chuong-1`, `/nghe/<slug>/1`.
`/doc/` is the lead. **An eighth guess is not the answer** — the plan opens with a
diagnostic script instead.

### robots.txt

`User-agent: *` gets `Allow: /`, and the file then names ClaudeBot, GPTBot, CCBot,
Google-Extended, Bytespider and others with `Disallow: /`, alongside
`Content-Signal: search=yes, ai-train=no, use=reference`. The user's own reader runs under a
browser UA and is covered by the `*` rule; Claude's own crawling is not, so reconnaissance
stopped at that point and the remaining observation moved into a script the **user** runs.

### The paywall decision

Asked, and answered: locked chapters are read with **the user's own session cookie**, the
mechanism `HttpClient.set_cookies` already provides and `medoctruyen` already uses. The
adapter fetches only what that account can already read and reports the rest. No
circumvention is planned or to be added.

## [IMPLEMENTATION] — 2026-07-31

1175 tests pass (1124 before, +51), ruff clean.

Everything in the plan that could be built without a live reader page is built. What
could not be observed is named, and the observation tool for it ships alongside.

### Q1 fell out of a file already on disk

The plan's §1 said the Next.js route chunks would probably reveal the reader URL. They
did — and the evidence had been sitting in `/tmp` since the recon pass, so no new request
to the site was needed. The route chunk builds the link in **three** places, every one of
them the same:

```js
"/truyen/".concat(s, "/doc/").concat(e.chapterNumber)   // the TOC list
"/truyen/".concat(s, "/doc/").concat(c)                 // "Đọc tiếp"
"/truyen/".concat(s, "/doc/1")                          // "Đọc truyện" empty state
```

So: `https://tieuthuyetmang.com/truyen/<slug>/doc/<chapterNumber>` — keyed off the plain
chapter number, **not** the ULID `id`. Every one of the seven guesses put `doc` in the
wrong place or used a `chuong-` prefix that does not exist here. Three independent call
sites agreeing is a stronger answer than any single probe would have been.

### The parser, and the trap encoded rather than hoped for

`flight_payload` reconstructs the RSC stream with `json.JSONDecoder().raw_decode` per push
rather than a regex — a Vietnamese title containing an escaped quote truncates
`push\(\[1,"(.*?)"\]\)` at the wrong place and silently drops the rest of the stream. The
fixture contains exactly such a title so that mistake cannot be made later.

The stream is **not** valid JSON (line-prefixed flight rows, `"$"` sentinels), so
`iter_objects` finds each key hit, walks left to the nearest `{`, and lets `raw_decode`
decide — an object that parses and carries the required keys is real; a nested one that
parses but lacks them is skipped for the next candidate outwards.

`find_story` anchors on the slug from the URL the user pasted. The landing page carries
sidebar recommendations with **identical field names**, and reading the first
`chapters_count` gives another novel's — measured during recon by getting it wrong. The
fixture puts a decoy *before* the real story and another after, so the test fails if the
anchoring is ever weakened.

### Fixtures are built, not captured

`medoctruyen`'s fixture is a raw 134 KB capture; webtruyendich's is trimmed. Trimming won
for three reasons, and the third is the interesting one: a raw capture would commit the
site's own chapter titles, 42 KB of flight stream is undiffable in review, and **a capture
contains the trap only by luck**. Every string in `tests/fixtures/tieuthuyetmang/` is
invented, and each one is there to break a specific mistake — a story split across two
pushes (so per-push parsing fails), chapters out of document order, a duplicated id, an
empty title, and two `latestChapter` stubs that carry a number but no lock flags.

### The cookie special case was deleted, not doubled

Both workers carried `if adapter.name == "medoctruyen": client.set_cookies(self.cookies)`.
A second gated site would have meant a second branch in two places, and a third would mean
a third. The decision moved to `AppConfig.cookies_for_url(url)` — where the cookies already
live — and both workers became unconditional, because `set_cookies` already ignores a blank
string. **Net deletion of a special case**, guarded by a test asserting the name check
never comes back.

### Locked chapters are listed, never filtered

`ChapterRef.index` is the project DB key. A TOC that shrank or grew with the cookie's state
would make `replace_toc` re-map existing chapters onto different content on the next scan —
corruption, not inconvenience. All 122 are listed; the count of locked ones goes out as a
status line through `SiteAdapter._status`, which `ScanWorker` already wires to the GUI.

### KNOWN GAP — `parse_chapter` is the one unverified seam

Where a chapter's *text* lives could not be observed: it needs a logged-in reader page.
Rather than guess a field name (`content` vs `body` vs `text` — a wrong guess fails
silently), the extractor is structural: server-rendered `<article>` paragraphs first, then
the longest non-URL string on the chapter object, which is right whatever the key is called.

The important half is the **lock gate, which runs before any extraction** — so a teaser can
never be returned as though it were the chapter. It reads the site's own `isLocked` /
`isPreview` flags rather than judging the body by length, which would call a genuinely
short chapter locked. `test_the_lock_gate_runs_before_extraction` uses a fixture that *has*
readable `<article>` text and still refuses.

`AuthRequiredError` is deliberately not a `RateLimitedError`: `_fetch_with_backoff` retries
that eight times a minute apart, and a 119-locked-chapter novel must not spend two hours
re-asking for chapters it cannot have.

If nothing extracts, the error names `scripts/diagnose_tieuthuyetmang.py` and the exact
command to run. That script answers Q2/Q3/Q4 in one pass, comparing a reader page fetched
with the cookie against the same page fetched anonymously.

### Not done

Q2–Q4 (chapter text location, the locked/unlocked discriminator, and whether "no cookie"
is distinguishable from "not unlocked") stay open until the diagnostic runs against a real
account. Metadata and the TOC need none of them and work today.

## [LIVE RUN 1] — 2026-07-31 — the reader page is reached, the text is not

> got this error:
> Không đọc được nội dung chương. Chạy scripts/diagnose_tieuthuyetmang.py --chapter
> https://tieuthuyetmang.com/truyen/<slug>/doc/1 …

Two things confirmed by that message alone, before any diagnostic runs:

* **Q1 holds.** The failure came from `parse_chapter`, which only runs after the fetch
  succeeded — so `/truyen/<slug>/doc/<n>` is a real page, as the route chunk claimed.
* **It is not the lock gate.** Chapter 1 is one of the three free ones, and the gate
  raises `AuthRequiredError`, not this. The page was readable and the text was simply not
  where either extraction strategy looked.

So Q2's answer is neither of the two shapes guessed at: not `<article>`/`<p>`, and not a
long string on the chapter object.

### The printed command did not run

`parse_chapter` printed `scripts/diagnose_tieuthuyetmang.py --chapter <url>`, but the
script required the novel URL as a positional — so the one command the error handed the
user would have died on `error: the following arguments are required: novel`. **A printed
command that fails is worse than no command**: it spends the user's attention and returns
nothing. `novel` is now `nargs="?"` and is derived from `--chapter` when omitted (a chapter
URL contains the slug), so the emitted command is complete on its own.
`test_the_failure_prints_a_command_that_actually_runs` pins both halves.

### One failure message was covering two different problems

"Không đọc được nội dung chương" was true for both *no chapter data on the page at all*
(usually not logged in) and *chapter data present but carrying no text* (the body is
fetched separately). Those have different fixes, so they now say different things — the
first points at the cookie in Cài đặt, the second says the text is loaded by JavaScript.
Only the second is a scraper limitation.

### The diagnostic now answers the question that was actually asked

Rather than guess a third extraction strategy, the script prints what IS on the reader
page: the five longest strings in the flight stream, the five text-densest elements as
`tag#id.class` with their text lengths, every `/api/` literal, and the reader route's own
chunk paths. If the body is server-rendered under some element other than `<article>`, it
appears as an obvious outlier and names its own selector; if it is fetched, the endpoint is
in the `/api/` list.

1177 tests pass (1175 before, +2), ruff clean.

## [LIVE RUN 2] — 2026-07-31 — the metadata was another novel's

> thông tin truyện parsing not right

It was returning a **different novel entirely** — title, author, cover and description all
belonging to a sidebar recommendation. Diagnosed against the landing page already saved
from the recon pass, so no further request to the site was needed.

### The trap sprung in the direction nobody planned for

Q5 assumed the page's own story object would be the *same shape* as the recommendations,
just harder to pick out. The truth is the reverse — the page's own is **poorer**:

| | page's own story | sidebar recommendation |
| --- | --- | --- |
| slug key | `storySlug` | `slug` |
| `title`, `coverUrl`, `status`, `categories` | yes | yes |
| `author` | **no** | yes |
| `excerpt` | **no** | yes |
| `chapters_count` | **no** | yes |

`find_story` anchored on `"slug":"<slug>"` and required `("title", "chapters_count")`.
Both halves were written to the sidebar's shape, so the real story matched neither: the
anchor missed, the required-keys filter excluded it, and the positional fallback then
picked the nearest object that *did* qualify — a recommendation. Every field came back
confidently wrong.

The author and description are not in the flight data **at all**; they are server-rendered
markup (an `/tac-gia/` link and the `div.prose` block under "Giới thiệu"). A parser reading
only the stream can never fill them.

### Fixes

- Anchor on `storySlug`, then `slug`. Require only `title`.
- **No cross-novel fallback, ever.** The old one is what made this silent. If nothing
  anchors, `parse_metadata` falls back to *this page's own DOM* — the `<h1>`, the author
  link, the description block, the cover `<img>` — which cannot be another novel's by
  construction. Anything less certain raises.
- `parse_metadata` and `parse_chapter_list` now take **markup**, not a pre-extracted
  stream, because half the fields only exist in the markup. The adapter caches the markup
  for the same reason, so a scan is still one request.
- The chapter list anchors on the component whose props name the novel
  (`{"storyId", "storySlug", "chapters": […]}`), with the page-wide census as fallback.

Verified against the real saved landing page: correct title, correct author, correct cover,
a 1111-character description, 122 chapters in order.

### The fixture was the actual failure

Every test passed the whole time. `landing.html` had been built from what the sidebar
objects looked like during recon, and the page's own story was given those same fields —
so the fixture described a page that **does not exist**, and the tests confirmed the parser
worked on it. This is the third fixture in three features to be wrong in the direction of
"everything works" (042's constant-amplitude audio, 044's over-agreeable `is_visible`, now
this).

The rebuilt fixture mirrors the measured asymmetry: the page's own story deliberately
carries *fewer* fields than the decoys around it, and
`test_a_story_without_chapters_count_or_author_is_still_found` states that as a property so
the filter cannot drift back.

**The lesson, sharper than "build the observation tool":** the tool was built, and it was
pointed at the wrong question. It reported what the *chapter* pages do and took the landing
page for solved, because the landing parser already "worked". A fixture written from a
guess is worth exactly as much as the guess — running the parser once against the real
saved page would have caught this before it shipped, and that check now belongs in the
diagnostic.

1180 tests pass (1177 before, +3), ruff clean.

## [LIVE RUN 3] — 2026-07-31 — the fix was correct and the user still saw the old data

> still wrong when parsing … the thông tin truyện should be: [the Giới thiệu block]

The parser had already been fixed and was producing exactly that block. What had **not**
been fixed is that a re-scan never writes metadata back to disk.

### `ScanWorker` updated the chapter list and nothing else

```python
if existing is not None:
    project = NovelProject.open(existing)
    project.replace_toc(refs)      # …and `meta`, freshly fetched, was dropped on the floor
```

So a project created while an adapter was buggy keeps the wrong title, author and
description **for ever**. Re-scanning looks like it does nothing, and the only cure is
deleting the project and starting again — losing every downloaded and translated chapter
with it. This predates 046 and would have hit any adapter fix on any site; it only surfaced
now because 046 shipped a wrong parse and then corrected it.

`NovelProject.refresh_meta(meta)` writes back the **scraped** fields only —
`site`, `title`, `author`, `description`, `cover_url`, `source_lang`. The translated
title/description/author, the generated tag list and the thumbnail prompt are this app's
own output, cost real time and money to produce, and a scan knows nothing about them; a
fresh `NovelMeta`'s blank defaults landing on top of them would be silent destruction.
`test_work_this_app_produced_is_never_overwritten` holds that line.

### The description is returned verbatim now

The "Giới thiệu truyện :" opener reads like a UI label and was being stripped. It is inside
the block, written by whoever posted the novel, and the user's own statement of what the
field should contain includes it — so nothing is trimmed but blank lines.

Worth noting for later: the real block runs to **17 lines**, and the user's paste ends at
line 7. The remaining lines are more synopsis, an author's note and a cast list, with no
structural marker separating them — the site collapses the block behind a "read more", so
what was pasted is what was on screen, not what the page holds. Keeping all of it is the
safer default; trimming would need a rule the markup does not supply.

### Chapter text: confirmed fetched separately

The download error came back as the *second* branch of the split message added in LIVE RUN
1 — "trang có dữ liệu chương nhưng không kèm nội dung". So the reader page carries the
chapter's metadata and not its body: the text is fetched by JavaScript, and the endpoint is
what `scripts/diagnose_tieuthuyetmang.py --chapter <url>` prints. That command has not been
run yet; it is the one remaining blocker, and guessing an eighth URL shape instead is the
mistake this feature has already paid for twice.

## [LIVE RUN 4] — 2026-07-31 — the text was in the HTML all along

The user sent the reader page's request/response headers and reported that **the browser's
Preview of that plain `GET` shows the novel text**. So the earlier conclusion — "fetched
separately by JavaScript" — was wrong. It is a normal server-rendered page; the extractor
was looking in two places that page does not have.

(The paste included a live `__Secure-next-auth.session-token`. It was flagged to the user
as a credential to rotate and is deliberately recorded nowhere in this repo.)

### Why it read as empty

`parse_chapter` tried exactly two things: `<article><p>` — which the reader page has no
`<article>` for — and the longest string **on the chapter object**, when the body is a
different flight row entirely. Two narrow guesses, both missing, reported as "no content".

The evidence for what to try instead was already in hand: the landing page renders its
synopsis in a Tailwind `prose … whitespace-pre-wrap` wrapper. A site tends to render long
prose the same way twice.

### The ladder now

1. `<article>` — kept, some builds use it;
2. `div.prose` / `.prose` / `[class*=whitespace-pre-wrap]` — **this site's own convention**,
   measured on the landing page;
3. the longest text block on the page, ignoring anything inside `nav`/`header`/`footer`/
   `aside` — needs no class name at all, because a chapter dwarfs every label around it.
   The **deepest** element holding ≈all of that text wins, otherwise the answer is
   whichever `<div>` wraps the document;
4. the chapter object's own longest string;
5. any long string anywhere in the flight stream.

The lock gate still runs before all five, so a teaser can never be returned as a chapter.

### Fixtures for each rung, and one that had been lying

`chapter_free.html` held a three-line body — under `_MIN_BODY_CHARS`, so the new extractor
correctly refused it and the test failed. The fixture was wrong, not the code: a real
chapter is not 60 characters. All the chapter fixtures now carry a believable body, and
each rung of the ladder has one of its own — `chapter_prose.html` (the shape the real site
uses), `chapter_plaindiv.html` (no article, no known class), `chapter_flight.html` (body as
a sibling flight row, not a field of the chapter object).

Nav and footer chrome is in every one of them, and two tests assert none of it reaches the
chapter text — a "longest block" rule that quietly swallows the site header would be a
silent corruption of every chapter, and TTS would read it aloud.

1186 tests pass (1184 before, +2), ruff clean. Still unverified against a live reader page;
the difference from the last three attempts is that the ladder now covers every shape the
page could plausibly take rather than the one shape that was guessed.
